# 评分标准详解 (Scoring Criteria)

六维度评分体系的详细量化标准。

## 评分总览

```
┌─────────────────────────────────────────────────────┐
│ 维度                 权重    满分    加权分          │
├─────────────────────────────────────────────────────┤
│ Schema 合规性        20%     100     20.0           │
│ Frontmatter 质量     25%     100     25.0           │
│ Body 内容质量        30%     100     30.0           │
│ 方法论审计           15%     100     15.0           │
│ 质量门槛达标         10%     100     10.0           │
│ 目录结构              5%     100      5.0           │
├─────────────────────────────────────────────────────┤
│ 总计                100%             100.0          │
└─────────────────────────────────────────────────────┘
```

## 维度 1: Schema 合规性 (20%)

### 评分细则

| 检查项 | 权重 | 100分标准 | 80分 | 60分 | 40分 |
|--------|------|-----------|------|------|------|
| name 格式 | 5% | kebab-case，无下划/大写/空格 | 1处不规范 | 2处不规范 | 3处+不规范 |
| description 结构 | 5% | 功能+触发条件+触发词完整 | 缺1项 | 缺2项 | 缺3项+ |
| description 格式 | 4% | 无XML标签，第三人称 | 1处问题 | 2处问题 | 多处问题 |
| complexity 声明 | 3% | 已声明且有效 | - | 无效值 | 未声明 |
| compatibility 声明 | 3% | 声明1+核心联盟 | - | 格式错误 | 未声明 |

### 评分示例

#### name 格式
```yaml
# 100分: pdf-processor
# 80分: pdf_processor  (下划线)
# 60分: PDF-Processor  (大写+连字符)
# 40分: pdf processor  (空格)
```

#### description 结构
```yaml
# 100分示例
service-function: "处理PDF文档"
trigger-condition: "当用户...时使用"
trigger-keywords: ["PDF转Word", "提取PDF", "合并PDF"]

# 80分: 缺少触发词列表
# 60分: 缺少触发条件和触发词
# 40分: 只有简单功能描述
```

## 维度 2: Frontmatter 质量 (25%)

### 评分细则

| 检查项 | 权重 | 100分标准 | 80分 | 60分 | 40分 |
|--------|------|-----------|------|------|------|
| 长度 | 5% | 200-1024字符 | 150-200 | 100-150 | <100 或 >1024 |
| 触发短语具体性 | 8% | 3+种表达方式，都很具体 | 3种但不够具体 | 2种具体 | <2种 |
| 触发词覆盖度 | 7% | 覆盖同义词+变体+隐含 | 覆盖同义词+变体 | 仅覆盖同义词 | 触发词模糊 |
| 防过度触发 | 5% | 明确说明不适用场景 | 暗示边界 | 边界模糊 | 无边界说明 |

### 触发词覆盖度评分

```yaml
# 100分: 覆盖同义词+变体+隐含需求
triggers:
  synonyms: ["PDF转Word", "Word导出PDF"]
  variants: ["合并PDF", "把PDF合到一起", "PDF合并工具"]
  implicit: ["老板发了个PDF要改", "需要处理这个文件"]

# 80分: 覆盖同义词+变体
triggers:
  synonyms: ["PDF转Word", "Word导出PDF"]
  variants: ["合并PDF", "把PDF合到一起"]

# 60分: 仅覆盖同义词
triggers:
  synonyms: ["PDF转Word", "PDF转Excel"]

# 40分: 触发词模糊
triggers: ["处理文档"]
```

### 防过度触发评分

```yaml
# 100分: 明确适用和不适用
适用: 文字提取、格式转换
不适用: 图片处理、扫描件OCR

# 80分: 暗示边界
适合简单PDF处理任务

# 60分: 边界模糊
处理各种文档

# 40分: 无边界说明
帮助用户处理PDF
```

## 维度 3: Body 内容质量 (30%)

### 评分细则

| 检查项 | 权重 | 100分标准 | 80分 | 60分 | 40分 |
|--------|------|-----------|------|------|------|
| 写作语态 | 6% | 全篇祈使语态 | 1-2处第二人称 | 3-5处 | 大面积第二人称 |
| 核心工作流 | 8% | 步骤清晰，每步可操作 | 步骤略简 | 步骤模糊 | 无明确步骤 |
| 适用性说明 | 6% | When to Use + When Not to Use 完整 | 缺1个 | 都很简略 | 都缺 |
| 错误处理 | 5% | 有Error Handling章节，内容完整 | 有但不完整 | 只有简单提及 | 无 |
| 长度合规 | 5% | 符合complexity限制 | 超限10% | 超限30% | 超限50%+ |

### 写作语态评分

```markdown
<!-- 100分: 全篇祈使语态 -->
运行脚本验证输入格式。
查阅 references/api-guide.md。
检查结果并输出报告。

<!-- 80分: 1-2处第二人称 -->
运行脚本验证输入格式。
你应该查阅 references/api-guide.md。  <!-- 这里 -->
检查结果并输出报告。

<!-- 60分: 多处第二人称 -->
你可以运行脚本验证输入格式。
你应该查阅 references/api-guide.md。
你可以检查结果并输出报告。

<!-- 40分: 大面积第二人称 -->
你需要先运行脚本，然后你应该查看文档，最后你可以检查结果。
```

### 核心工作流评分

```markdown
<!-- 100分: 步骤清晰，可操作 -->
## Core Workflow

1. **理解需求**
   - 确认任务类型
   - 识别约束条件

2. **执行处理**
   - 加载输入文件
   - 应用处理逻辑
   - 验证输出

3. **输出结果**
   - 生成报告
   - 保存文件

<!-- 80分: 步骤略简 -->
## Core Workflow

1. 理解需求
2. 执行处理
3. 输出结果

<!-- 60分: 步骤模糊 -->
## Core Workflow

处理输入并生成输出。

<!-- 40分: 无明确步骤 -->
（无 Core Workflow 章节）
```

## 维度 4: 方法论审计 (15%)

### 同质化检测 (7.5%)

| 命中问题数 | 分数 | 说明 |
|------------|------|------|
| 0 | 100 | 低风险，有独特方法 |
| 1 | 85 | 较低风险 |
| 2 | 70 | 中风险，需改进 |
| 3 | 60 | 高风险，建议重构 |
| 4 | 50 | 极高风险，通用流程堆砌 |

**4个问题**:
1. 方法是否是公开教科书式流程？
2. 几乎任何 AI 都会给出类似步骤？
3. 主要靠模板填空，而非判断？
4. 没有任何行业语境或私有视角？

### 竞争壁垒评估 (7.5%)

| 壁垒命中 | 分数 | 说明 |
|----------|------|------|
| 2+ 项 | 100 | 强壁垒，高价值 |
| 1 项 | 85 | 有壁垒，有价值 |
| 0 项但非通用 | 70 | 一般，有优化空间 |
| 0 项且通用 | 55 | 无壁垒，同质化风险 |

**4类壁垒**:
- 私有数据: +4分
- 行业洞察: +4分
- 失败案例: +3分
- 反共识框架: +4分

## 维度 5: 质量门槛达标 (10%)

### DoD 检查清单评分

每项 2%，通过得满分，不通过得 0 分。

| 检查项 | 通过标准 |
|--------|----------|
| 单一职责明确 | 能用一句话说清做什么和不做什么 |
| 差异化价值 | 通过方法论审计或有竞争壁垒 |
| 触发准确 | 有明确触发词和 When to Use |
| 可测试 | 有验证方法或测试用例说明 |
| 可打包 | 目录结构完整，无无效文件 |

## 维度 6: 目录结构 (5%)

### 评分细则

| 检查项 | 权重 | 状态 |
|--------|------|------|
| SKILL.md 存在 | 2% | 存在 2分，不存在 0分 |
| references/ 存在 | 1% | 存在 1分，不存在 0分 |
| examples/ 存在 | 1% | 存在 1分，不存在 0分 |
| scripts/ 存在 | 1% | 存在 1分，不存在 0分 |

**注意**: 目录结构仅为存在性检查，不检查内容。内容质量在其他维度评估。

## 总分计算示例

### 示例 1: 优秀 Skill

```yaml
scores:
  schema_compliance: 100    # 20% = 20.0
  frontmatter_quality: 95   # 25% = 23.75
  body_quality: 95          # 30% = 28.5
  methodology_audit: 90     # 15% = 13.5
  quality_gate: 100         # 10% = 10.0
  directory_structure: 100  #  5% =  5.0
  
total: 100.75 → 100 (cap at 100)
status: excellent
```

## 状态判定标准

| 总分范围 | 状态 | 发布建议 |
|----------|------|----------|
| 95-100 | excellent | 可以发布，可选小幅优化 |
| 85-94 | good | 可以发布，推荐修复 warning |
| 70-84 | needs_optimization | 必须优化后再发布 |
| < 70 | needs_refactor | 建议重新设计 |

### 特殊规则

1. **有 error 级别问题**: 最高只能评 needs_optimization
2. **schema_compliance < 60**: 最高只能评 needs_optimization
3. **body_quality < 60**: 最高只能评 good
