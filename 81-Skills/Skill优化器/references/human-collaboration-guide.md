# 人机协作指南

> lute-skills-opt 的协作模式设计和最佳实践

---

## 为什么需要人机协作？

### 全自动优化的局限性

| 问题 | 说明 | 案例 |
|------|------|------|
| 上下文丢失 | AI 无法理解 Skill 的业务逻辑 | 删除了关键的领域特定术语 |
| 过度泛化 | 强行套用标准模式 | 将独特的创新点替换为通用模板 |
| 幻觉风险 | 生成看似合理但不正确的内容 | 虚构不存在的工具引用 |
| 用户意图 | 无法完全理解用户的设计意图 | 删除了用户特意保留的表述 |

### 人机协作的优势

| 优势 | 说明 |
|------|------|
| 用户决策 | 关键修改由用户确认 |
| 上下文保留 | 用户了解 Skill 的业务背景 |
| 意图对齐 | 用户可以调整优化方向 |
| 风险控制 | 发现问题及时干预 |

## 协作模式设计

### 模式 1: 完全引导模式（新手友好）

**适用场景**: 用户对 Skill 优化不熟悉

**流程**:
```
系统: 发现 4 个高优先级问题：
      1. 缺少 version 字段（影响 +2 分）
      2. 缺少 complexity 字段（影响 +2 分）
      3. 缺少方法论审计（影响 +5 分）
      4. description 可优化（影响 +3 分）
      
      建议按顺序修复？
      
用户: [确认]

系统: 开始修复 #1：添加 version 字段
      将添加: version: "1.0.0"
      
用户: [确认] / [跳过] / [修改]

系统: #1 完成，评分提升 +2
      开始修复 #2：添加 complexity 字段
      根据内容长度判断应为: complexity: "standard"
      
用户: [确认] / [修改]

...
```

**优点**: 引导清晰，适合学习
**缺点**: 交互频繁，耗时较长

```
      ║ ┌──────────────────────────────────┐ ║
      ║ │ [✓] F001 添加 version            │ ║
      ║ │     添加: version: "1.0.0"       │ ║
      ║ │     影响: +2 分                  │ ║
      ║ │                                  │ ║
      ║ │ [✓] F002 添加 complexity         │ ║
      ║ │     添加: complexity: "standard" │ ║
      ║ │     影响: +2 分                  │ ║
      ║ │                                  │ ║
      ║ │ [✓] U001 添加方法论审计          │ ║
      ║ │     添加: Methodology Audit 章节 │ ║
      ║ │     影响: +5 分                  │ ║
      ║ └──────────────────────────────────┘ ║
      ║                                      ║
      ║ 中优先级（推荐）                      ║
      ║ ┌──────────────────────────────────┐ ║

      ║ │                                  │ ║

      ╚════════════════════════════════════════╝

用户: [选择性执行]
      → 取消勾选 F004
      → 确认

系统: 执行 3 项优化...
      F001 ✓
      F002 ✓
      U001 ✓
      
      验证结果: 89 → 96 (+7) ✅
      
      未执行的优化:
      - F004 description 优化（用户跳过）
      - B004 DoD 增强（用户跳过）
      
      是否继续执行跳过的项？

用户: [否]

系统: 优化完成！
      最终评分: 96/100
      查看详细报告: optimization-report.md
```

**优点**: 平衡效率和确认

### 模式 3: 预览优先模式（谨慎用户）

**适用场景**: 对关键 Skill 的谨慎优化

**流程**:
```
系统: 展示优化计划（同模式 2）

用户: [预览 F001]

系统: 【修改预览: F001 添加 version】
      
      --- 修改前 ---
      ---
      name: my-skill
      description: xxx
      ---
      
      --- 修改后 ---
      ---
      name: my-skill
      description: xxx
      version: "1.0.0"
      ---
      
      [确认此修改] [跳过] [修改内容]

用户: [确认此修改]

系统: 【修改预览: U001 添加方法论审计】
      
      --- 修改前 ---
      （无此章节）
      
      --- 修改后（新增）---
      ## Methodology Audit / 方法论审计
      
      创建本 Skill 前，执行同质化检测：
      ...
      
      [确认此修改] [跳过] [预览下一项]

用户: [预览下一项]
...
```

**优点**: 完全透明，风险最低
**缺点**: 耗时最长

## 用户决策点设计

### 决策点 1: 优化计划确认

**系统提供**:
- 当前评分 vs 预期评分
- 优化项列表（带影响评估）
- 优先级分类

**用户选择**:
- ✅ 确认全部
- ☑️ 选择性执行（勾选/取消）
- 👁️ 预览修改
- ❌ 取消

### 决策点 2: 单项修改确认

**系统提供**:
- 修改位置
- 修改内容（或 diff）
- 影响评估

**用户选择**:
- ✅ 确认
- ✏️ 修改（用户提供修改方案）
- ⏭️ 跳过
- 🔍 查看更多上下文

### 决策点 3: 批次执行后确认

**系统提供**:
- 批次执行结果
- 评分变化
- 是否继续

**用户选择**:
- ✅ 继续下一批
- ↩️ 回滚本批
- 🛑 停止优化

## 协作界面设计原则

### 原则 1: 信息分层

**第一层（概览）**:
- 总分变化
- 优化项数量
- 主要影响

**第二层（详情）**:
- 每项的具体修改
- 评分影响
- 参考依据

**第三层（完整）**:
- 修改前后对比
- 完整上下文
- 技术细节

### 原则 2: 默认安全

**安全默认值**:
- 高优先级默认选中
- 中优先级默认选中
- 低优先级默认不选中
- 高风险修改需额外确认

### 原则 3: 可逆操作

**必须提供**:
- 取消当前操作
- 回滚已执行批次
- 恢复原文件

### 原则 4: 清晰反馈

**状态反馈**:
```
执行中...    → 进度条
执行成功     → ✅ + 评分变化
执行失败     → ❌ + 错误信息 + 建议
已回滚      → ↩️ + 原因
```

## 典型用户场景

### 场景 1: 快速优化

**用户**: 时间紧迫，希望快速优化

**推荐模式**: 批量确认模式

**流程**:
```
1. 系统展示优化计划（高优先级全部选中）
2. 用户快速浏览后确认
3. 系统自动执行并验证
4. 输出结果
```

**预计耗时**: 2-3 分钟

---

### 场景 2: 精细优化

**用户**: 对 Skill 质量要求高，愿意花时间

**推荐模式**: 预览优先模式

**流程**:
```
1. 系统展示优化计划
2. 用户逐项预览修改
3. 用户确认/跳过/修改每项
4. 分批执行并验证
5. 最终确认
```

**预计耗时**: 10-15 分钟

---

### 场景 3: 学习优化

**用户**: 希望学习如何优化 Skill

**推荐模式**: 完全引导模式

**流程**:
```
1. 系统介绍发现的问题
2. 逐个解释修复方案
3. 用户确认学习每项
4. 解释修复后的改进
```

**预计耗时**: 15-20 分钟

---

### 场景 4: 批量处理

**用户**: 有多个 Skill 需要优化

**推荐模式**: 批量确认模式 + 批量执行

**流程**:
```
1. 系统批量评估所有 Skill
2. 按评分排序展示
3. 用户选择要优化的 Skill
4. 系统按优先级批量优化
```

**预计耗时**: 取决于 Skill 数量

## 错误处理与用户引导

### 错误 1: 用户不理解优化项

**系统响应**:
```
用户: [这是什么意思？]

系统: 【解释 F001: 添加 version 字段】
      
      作用: 声明 Skill 的版本号
      为什么重要:
      - 便于版本管理
      - 用户知道使用哪个版本
      - 符合 Universal Skill Schema 规范
      
      示例:
      version: "1.0.0"  # 初始版本
      version: "1.2.3"  # 语义化版本
      
      是否继续？
```

### 错误 2: 用户想自定义修改

**系统响应**:
```
用户: [我想自己改 description]

系统: 【自定义修改 F004】
      
      当前 description:
      "Use when processing data"
      
      建议优化:
      "Use when processing CSV, JSON files. 触发词: CSV处理, JSON解析"
      
      请输入您的版本（或输入 "skip" 跳过）:

用户: "Use when processing data files for analysis"

系统: 确认使用您的版本？
      
用户: [确认]
```

### 错误 3: 优化后评分下降

**系统响应**:
```
系统: ⚠️ 批次 2 执行后评分下降
      
      批次 2 执行前: 95 分
      批次 2 执行后: 93 分
      
      可能原因:
      - B004 DoD 增强引入了冗余内容
      
      自动回滚批次 2...
      
      回滚完成，评分恢复: 95 分
      
      建议:
      - 跳过 B004 修改
      - 或手动调整 DoD 内容
      
      是否继续执行剩余优化？
```

## 最佳实践

### 对用户

1. **首次使用**: 选择完全引导模式，理解优化逻辑
2. **日常使用**: 选择批量确认模式，平衡效率和质量
3. **关键 Skill**: 选择预览优先模式，确保不出错
4. **批量处理**: 先评估所有 Skill，优先处理评分低的

### 对系统

1. **智能默认**: 根据用户历史选择推荐模式
2. **渐进披露**: 不一次性展示所有信息
3. **及时反馈**: 每个操作后立即反馈结果
4. **容错设计**: 允许用户随时回滚或取消
