# Iron Law Testing - 严格测试法

**核心原则**: NO SKILL WITHOUT A FAILING TEST FIRST

在编写或修改 Skill 前，必须先验证"没有该 Skill 时 agent 会失败"。

## 测试流程: RED → GREEN → REFACTOR

### Phase 1: RED (基线失败)

**目标**: 证明 Skill 是必要的

**步骤**:
1. 不加载目标 Skill，给 subagent 真实任务
2. 记录错误行为与原话（verbatim rationalizations）
3. 提炼失败模式：
   - 漏步骤
   - 乱用工具
   - 格式不一致
   - 理解偏差

**输出**: RED 报告（失败场景 + 错误模式）

---

### Phase 2: GREEN (最小修复)

**目标**: 仅针对 RED 暴露的问题写最小内容

**原则**:
- 避免"想当然的全量堆砌"
- 只解决已验证的问题
- 保持最小可用

**输出**: 初版 SKILL.md

---

### Phase 3: REFACTOR (加固闭环)

**目标**: 应对压力场景，消除漏洞

**施压场景**:
- 时间压力（"尽快"、"简单处理"）
- 模糊需求（"帮我弄一下"）
- 并行任务（"顺便把 X 也做了"）
- 异常输入（空值、超大输入、格式错误）

**步骤**:
1. 收集新借口/失败模式
2. 加入反例/约束到 Skill
3. 重测直到稳定通过

**输出**: 强化版 SKILL.md

---

### Phase 4: PUBLISH (通过后发布)

**必须满足**:
- [ ] RED 基线已记录
- [ ] GREEN 修复已验证
- [ ] REFACTOR 压力测试通过
- [ ] 安装路径验证成功

---

## 按 Skill 类型的测试策略

| Skill 类型 | 测试输入 | 通过标准 |
|------------|----------|----------|
| **Technique** | 新场景执行题 | 步骤完整且可复现 |
| **Pattern** | 选择题/归因题 | 能识别何时用、何时不用 |
| **Reference** | 检索+应用题 | 能找到正确信息并用对 |

### Technique 类型测试示例

**测试输入**: "用我给你的 csv 生成柱状图"

**检查点**:
- [ ] 先检查数据格式（而非直接画图）
- [ ] 询问关键字段含义
- [ ] 选择合适的图表类型
- [ ] 输出包含数据洞察

### Pattern 类型测试示例

**测试输入**: "这个 bug 是什么原因？"

**检查点**:
- [ ] 使用 Skill 定义的归因框架
- [ ] 区分表面原因和根本原因
- [ ] 提供可验证的假设

### Reference 类型测试示例

**测试输入**: "API 的 rate limit 是多少？"

**检查点**:
- [ ] 在 reference 中定位正确信息
- [ ] 区分不同 plan 的限制
- [ ] 提供相关上下文（重试策略等）

```markdown
- [修复2]: 针对 [失败模式2]

### 验证结果
- [x] 修复后通过测试

## REFACTOR 压力测试

| 压力场景 | 输入 | 通过 |
|----------|------|------|
| 时间压力 | "尽快生成" | ☐ |

```

## 常见问题

**Q: 修改已有 Skill 需要 RED 吗？**
A: 需要。先建立 RED 基线（当前版本的失败场景），再修改。

**Q: 小改动也需要完整流程吗？**
A: 改动影响的工作流需要测试。如果改动是局部且不影响核心流程，可以简化。

**Q: 如何判断 REFACTOR 足够？**
A: 当常见压力场景都能稳定处理，且连续 3 次测试无新问题时。
