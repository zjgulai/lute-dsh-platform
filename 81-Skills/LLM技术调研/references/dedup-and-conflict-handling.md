# Dedup And Conflict Handling

研究型 skill 的一个常见问题，是把同一件事从多个平台重复写进报告，或者在存在冲突信息时直接给出武断结论。这份规则用来处理重复、互补、冲突和传闻。

## 关系类型

### 1. Duplicate / 重复

特征：

- 多个来源讨论的是同一事件
- 核心事实一致
- 只是表述方式不同

处理：

- 合并为一条结论
- 保留最强的一手来源作为主来源
- 其他来源放进 `Source Log` 或作为补充佐证

### 2. Complement / 互补

特征：

- 多个来源指向同一主题
- 但分别提供不同细节
- 合并后能更完整

处理：

- 合并进同一节
- 明确哪条来源提供了哪个细节
- 不把互补细节误写成同一来源都确认过

### 3. Conflict / 冲突

特征：

- 来源对同一主题给出不同说法
- 时间、适用条件、是否正式发布等信息不一致

处理：

- 不强行拍板
- 保留分支表达
- 优先以时间更近、来源更强的一方为主
- 把另一方写入 `Risks / Caveats` 或 `Signals Worth Watching`

冲突写法示例：

```markdown
目前官方页面更接近“已可用”的表述，但社区仍有用户报告该功能在部分环境中不可见，因此将其视为“已发布但可能分批开放”更稳妥。
```

### 4. Rumor / 传闻

特征：

- 只有单一低信源
- 无原始链接或无法追溯
- 只有截图、转述或猜测

处理：

- 默认不进入主结论
- 如确有观察价值，只能放入 `Signals Worth Watching`
- 必须明确标记 `待验证`

## 去重步骤

1. 先按主题聚类
2. 再判断是否是同一事件的不同转述
3. 为每个聚类挑一个主来源
4. 把重复来源折叠进补充来源列表
5. 最终每个主题只保留一条主结论

## 冲突处理步骤

1. 先分清是“事实冲突”还是“适用条件不同”
2. 优先检查时间差，避免把旧说法和新变化硬碰硬
3. 优先检查官方定义是否更新
4. 如果仍不明确，写成条件化结论
5. 无法验证时，降级为观察信号

## 条件化写法模板

### 模板 1：版本或人群差异

```markdown
该能力看起来已经在官方渠道出现，但社区反馈显示它可能仍在逐步放量。对于大多数用户，更稳妥的判断是：可以开始关注和试验，但不要假设所有环境都已一致可用。
```

### 模板 2：说法不一致

```markdown
目前存在两种说法。官方资料支持 A，但部分社区反馈更接近 B。现阶段更适合把 A 视为正式方向，把 B 视为落地层面的兼容性问题或灰度差异。
```

## 哪些内容应该直接舍弃

- 纯情绪评价，没有事实支撑
- 与核心主题关系很弱的闲聊
- 只为博眼球的标题党内容
- 旧信息重新转发，但没有新价值

## 输出纪律

- 一个主题只写一个主结论
- 不重复统计同一条更新
- 有冲突就显式说明，不装作没有冲突
- 有传闻就降权，不把猜测写成事实
