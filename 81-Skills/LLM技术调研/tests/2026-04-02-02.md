# 今日 LLM 开发工具情报简报

> 时间窗口说明：严格按最近 `24h` 检索时，没有发现足够多的官方高置信更新可支撑一份高质量简报。按本 skill 的 fallback 规则，本报告回退为“最近一段时间最值得学习、今天就能实践的官方变化总结”。

## Executive Summary

- 如果你在 `Cursor` 里已经反复做同类任务，现在最值得学的不是“再换一个 prompt”，而是把任务升级成 `automations`。
- 如果你担心代码、构建产物和密钥离开内网，`Cursor` 的 `self-hosted cloud agents` 是近期最值得关注的企业级变化。
- `Claude Code` 这段时间最值得学的不是单个新命令，而是整套使用方式：`先探索 -> 再计划 -> 再实现 -> 给验证方式`。
- `Claude Code Skills` 现在最关键的能力不是“能不能写 SKILL.md”，而是：`description 要前置触发意图`、`正文保持精简`、`把细节拆进 supporting files`。
- 在权限控制上，`Claude Code auto mode` 比 `--dangerously-skip-permissions` 更值得学习，因为它更接近日常可长期使用的平衡点。

## High-Confidence Updates

### Cursor Automations：把重复任务从“手动聊天”升级成“持续运行的 agent”

- **What changed**: Cursor 已支持 `automations`，可以基于 schedule、Slack、Linear、GitHub、PagerDuty、webhook 触发持续运行的 agent。
- **Why it matters**: 很多开发者还在把 Agent 当成一次性对话工具，但这个更新意味着你可以把“定时检查、重复分析、固定格式输出”固化成自动流程。
- **How to use it**: 如果你有“每天查 changelog、定时巡检 issue、重复生成报告、周期性做代码检查”这类任务，优先考虑把它写成 automation，而不是每天手动重开一次会话。
- **Confidence**: High
- **Sources**: [Cursor Automations changelog](https://www.cursor.com/changelog/03-05-26)

### Cursor Self-hosted Cloud Agents：对内网代码和敏感环境更友好

- **What changed**: Cursor 支持 `self-hosted cloud agents`，让代码、工具调用、构建产物和密钥都留在你自己的网络环境里。
- **Why it matters**: 如果你之前因为代码安全、内网访问、密钥合规问题而不敢把 agent 深度接入流程，这个更新会直接改变可用性判断。
- **How to use it**: 只要你的团队已经开始认真使用 agent，而且代码与秘钥不能离开私有环境，就应该优先评估这条能力，而不是只盯模型强弱。
- **Confidence**: High
- **Sources**: [Cursor Self-hosted Cloud Agents](https://www.cursor.com/changelog/03-25-26)

### Cursor Composer 2：更适合高难度任务，但要把“质量”与“成本”一起看

- **What changed**: `Composer 2` 已正式可用，并且 Cursor 公开了标准与 fast 模式的价格。
- **Why it matters**: 这不是单纯的“更强模型”新闻，而是提醒你：以后在 Cursor 里做复杂任务，应该显式区分“探索阶段”“实现阶段”“高难任务阶段”。
- **How to use it**: 把贵的高性能能力留给真正高价值的复杂编码任务，不要把它浪费在信息搜集或简单改字面量这种低杠杆工作上。
- **Confidence**: High
- **Sources**: [Cursor Composer 2 changelog](https://www.cursor.com/changelog/composer-2)

### Claude Code：真正高杠杆的用法是“验证优先”，不是“提示词更花哨”

- **What changed**: Anthropic 官方最佳实践持续强调一套明确 workflow：`Explore -> Plan -> Code -> Commit`，并把“给 Claude 一个验证方式”视为最高杠杆动作之一。
- **Why it matters**: 很多低质量使用方式的问题，不是模型不够强，而是没有给它测试、截图、预期输出或成功标准，导致它只能猜。
- **How to use it**: 以后你让 Claude Code 做任何稍复杂的任务，都尽量补一条“怎么自证做对了”。例如：测试命令、截图对比、预期文件变化、输出结构。
- **Confidence**: High
- **Sources**: [Claude Code best practices summary](https://docs.anthropic.com/en/docs/claude-code/best-practices)

### Claude Code Skills：真正值得学的是触发设计和渐进式披露

- **What changed**: 官方 skills 文档已经非常明确地把 skill 的价值中心放在三件事上：`description` 决定何时触发、`SKILL.md` 负责主流程、supporting files 负责延迟加载的细节。
- **Why it matters**: 如果 description 太长、关键触发意图不在前面，skill 就可能该触发时不触发；如果所有细节都塞在 `SKILL.md`，上下文效率会越来越差。
- **How to use it**: 写 skill 时优先保证：
  - description 前 1-2 句就写清“做什么 + 何时用”
  - 主 `SKILL.md` 保持短而强
  - 把长说明拆进 `references/`、`examples/`、`scripts/`
- **Confidence**: High
- **Sources**: [Claude Code skills docs](https://docs.anthropic.com/en/docs/claude-code/skills)

### Claude Code Auto Mode：比“跳过权限”更适合作为长期默认工作模式

- **What changed**: Anthropic 推出 `auto mode`，试图在“频繁人工确认”和“完全跳过权限”之间找到一个更实用的中间带。
- **Why it matters**: 官方明确指出，用户会批准绝大多数权限请求，但 `--dangerously-skip-permissions` 在很多场景下又太危险。auto mode 的价值不在于绝对安全，而在于长期工作流更稳。
- **How to use it**: 如果你已经被大量 permission prompts 打断节奏，不要第一反应就是全局跳过权限。先评估 auto mode，尤其是在低到中等风险、但高频重复的开发任务里。
- **Confidence**: High
- **Sources**: [Claude Code auto mode engineering writeup](https://www.anthropic.com/engineering/claude-code-auto-mode)

## New Tactics You Can Use Today

### Tactic 1：把“每天都在重复做”的事情从 prompt 升级成 automation

- **Action**: 盘点你最近 7 天重复超过 3 次的 agent 任务。
- **When to use**: 例如每日简报、定时巡检、固定模板汇总、PR 周期检查。
- **Expected benefit**: 从“反复手动发起”切换到“持续运行”。
- **Caveat**: 如果任务本质上仍然高度依赖人工判断，不要过早自动化。

### Tactic 2：给 Claude Code 每个复杂任务都补一个“自证方式”

- **Action**: 以后在任务描述末尾追加一段“验证方式”，例如测试命令、截图要求、预期文件、预期结构。
- **When to use**: 代码实现、重构、前端修改、数据转换、文档生成。
- **Expected benefit**: 明显减少来回返工。
- **Caveat**: 验证方式要具体，不能只写“自己检查一下”。

### Tactic 3：重写你最常用 skill 的 description

- **Action**: 检查现有 skill 的 description，确保前半句就包含“做什么 + 何时用”。
- **When to use**: 任何自动触发不稳定、需要你手动提醒 agent 的 skill。
- **Expected benefit**: 提高触发命中率，减少 undertrigger。
- **Caveat**: 不要把 workflow 细节全塞进 description。

### Tactic 4：把 `SKILL.md` 从“大全”改成“导航页”

- **Action**: 保留主流程在 `SKILL.md`，把评分规则、模板、示例、脚本说明拆进 `references/` 和 `examples/`。
- **When to use**: 任何超过 300-500 行、或你已经感觉“每次加载都太重”的 skill。
- **Expected benefit**: 上下文更省，结构更稳，也更容易持续迭代。
- **Caveat**: 拆出去的文件必须在主 skill 里明确引用。

### Tactic 5：把权限管理从“烦人的阻塞”转成“明确的工作模式选择”

- **Action**: 以后在 Claude Code 里区分三类任务：低风险日常任务、中风险自动化任务、高风险操作。
- **When to use**: 你已经开始深度使用 shell、web、MCP、subagent 时。
- **Expected benefit**: 更容易决定什么时候用 manual，什么时候试 auto mode，什么时候必须保持人工审查。
- **Caveat**: auto mode 不是高风险基础设施操作的免思考通行证。

## Signals Worth Watching

- 社区越来越强调“不是 prompt engineering，而是 workflow engineering”，这和官方 best practices 的方向高度一致。
- 对 `Claude Code Skills` 的讨论正在从“能不能写”转向“如何提高触发率、如何降低上下文成本、如何设计 supporting files”。
- 对 `Cursor` 的使用方式正在从“智能编辑器”过渡到“带云端 agent、automation 和生态插件的 workflow 平台”。

## Risks / Caveats

- 很多社区文章会把“某功能存在”误写成“已经适合所有人默认启用”。
- `24h` 维度下并不总有足够的高置信新增，日报如果不设置 fallback，很容易变成凑数。
- 中文社区文章适合发现线索和实操口径，但不适合作为唯一主证据。

## Suggested Experiments

1. 在你的日常工作里挑 1 个重复任务，判断它更适合做成 `skill` 还是 `automation`。
2. 找一个你常用但触发不稳定的 skill，重写 description，压缩到前两句就说清用途。
3. 下次让 Claude Code 改代码前，额外补一个“验证方式”段落，观察返工次数是否下降。
4. 把一个过重的 `SKILL.md` 拆成主 skill + `references/` + `examples/`，比较前后使用体验。
5. 选一个中低风险任务，评估 auto mode 是否比你当前的权限模式更顺手。
