# Problem Statement

要把「岗位 Preset」从**组织清单**变成**交付物**：一个 Preset 下挂多个 Agent 产品，一个产品由多个功能组成工作流；每个功能是「页面引导输入 → 确定性拼提示词 → 触发模型/工具 → 结果按预置 UI 模板填充 → 作为下一功能的输入」。

今天这台机器上，这件事缺的不是机制，是**声明**：

1. **产品没有家。** `/Users/lute/project/` 下没有任何一份文件说明「这个目录是一个 Agent 产品、它有哪些功能、入口在哪」。新应用抽屉今天能列出的两类东西都不是产品：50 个岗位是材料里的组织拓扑（`/api/dsh-role-matrix/list`），11 个容器是「有会话的目录」的（`/api/worktable/workspaces`）。
2. **产品没有判据。** 于是抽屉只能二选一：列岗位（你明确不要），或列容器（那是会话分组，不是产品）。二者都会让卡片说假话——卡片必须做到「点开必能用」。
3. **提示词没有可审形态。** 拼接逻辑尚不存在；一旦散进 TSX，它就是整个产品里唯一**无法回放、无法审计**的部分，而它恰恰决定模型看到什么。
4. **结果没有契约。** 模板填充若交给模型自由发挥，「预置 UI 模板」就不再是预置，字段与版式会随模型漂移。

本规格定**形态**（声明 / 功能 / 工作流 / 提示词 / 模板 / 入口 / 审计）。v2 的差异全部来自 M1 试点压出来的偏差，见 [§11](#11-m1-试点压出来的读数实测非推测)。

# 1. 词汇（四个层，一套说法）

| 层 | 是什么 | 这份事实的家 | 谁写 |
| --- | --- | --- | --- |
| **Preset**（岗位） | 垂直基座：`agent.cordis.yml` 装配清单 + 人格 + 技能子集。决定「哪个会话挂了什么」 | `~/.dsh/.agent-presets/<id>/`（官方 roster 拥有） | 由材料装配（本平台已有 50 个 `agt-*`） |
| **Product**（Agent 产品） | 一份声明 + 一个实现包：能在本机被**发现、点开、跑通、审计**的交付物 | **项目目录里的 `product.json`** | 你或 agent 写进产品自己的项目 |
| **Feature**（功能） | 工作流的一个节点：页面引导字段 → **多条技能组合**成提示词 → 触发工具/模型 → 模板填充 → 产出物 | `product.json` 的 `features[]`；骨架是 `features[].skills[]` 指向的**多条**技能 | 同上 |
| **Workflow**（工作流） | 功能之间的有向边，边上的数据 = 上游产出物。**一条工作流 = 多个技能被自动执行的串联 + 人在预设 UI 上填写/筛选后再组合进提示词** | `product.json` 的 `workflow` 段（或每条 `features[].next`） | 同上 |

**一处必须改词**：产品是**代码**，preset 是**装配**。把流程写进 preset，会让一次 preset 改动静默改掉产品行为——本平台吃过同类亏（`file:` 依赖是安装时刻的硬链接快照，安装后新增的文件不会自动进去，症状是「功能静默不生效 + 日志一句 warn」，见 `docs/architecture.md` §1 同步语义）。正确的依赖方向是：**preset 挂载产品，产品自己声明功能与工作流**。

# 2. 一个产品长什么样

```
<项目目录>/
├─ product.json              # 声明：身份 + 功能 + 工作流（唯一入口，机读）
├─ skills/                   # ★ L2 产品局部技能（打包进产品，随产品走）
│  └─ <kebab>/SKILL.md
├─ data/                     # 产品自己的事实表（如候选人池、亲和表）
├─ schemas/                  # 模型只许产出这个结构
├─ templates/                # 结果落点模板（确定性渲染）
├─ pipeline/                 # 拼装 / 打分 / 渲染（纯函数优先）
├─ prompts/__snapshots__/    # 提示词快照（可审证据，不手改）
├─ artifacts/                # 每次运行的产出物（下一功能的输入）
├─ runs/<runId>/             # 四件证据（§7）
├─ run.mjs                   # ★ 一条命令：跑通 / 自检
└─ （实现包可在本目录，也可独立成包后装进 desktop profile）
```

**产品代码放哪（本规格的立场）**：本仓库（Magpie-Horch）只出**规格 + 校验器 + 启动器**，不吞并产品代码——产品是各自项目的事。这与「一份事实只有一个家」一致：`product.json` 与它的实现、模板、产物都在同一个目录里，改产品不用改第二个地方。**M1 证实这条可行**：整个 `select-candidates` 功能（声明 + 2 条技能 + 打分 + 拼装 + 渲染 + 自检）全部落在产品目录内，本仓库一行代码未动。

# 3. `product.json` v1 契约

```jsonc
{
  "schemaVersion": 1,
  "products": [
    {
      "id": "kol-hunter",                    // kebab；= 卡片主键的一半
      "name": "深链星探 KOL Hunter",
      "summary": "一句话说清这个产品替谁做什么",
      "version": "0.1.0",
      "status": "draft" | "ready",
      "statusReason": "为什么是这个 status（机读，卡片直接展示）",
      "preset": "agt-033",                    // 归属岗位：50 个 preset 之一（必填）
      "skills": "skills/",                    // 产品局部技能根（产品技能必须在这里）
      "icon": "data:image/svg+xml;base64,…",  // 与岗位头像同约定（官方 icon 字段，ADR-0022）
      "entry": { "kind": "panel", "service": "…-workbench", "action": "open" },
      "features": [ /* §4 */ ],
      "workflow": { "entry": "select-candidates", "edges": [] }
    }
  ]
}
```

约定与理由：

- **只有一种形状**：顶层恒为 `{ schemaVersion, products: [...] }`，即使只有一个产品。**不做单对象/数组双形状**——双形状解析器是漂移的温床，本仓库已修过一次同类问题（`sources.ts` 的解析器一律 total，见 ADR-0028）。
- **`id` 唯一且 kebab**：它同时进路径与 DOM 属性，是容纳边界（与 preset id、技能名的既有约定一致）。
- **`icon` 走官方 `icon` 字段的同一形态**（ADR-0022：图标库是唯一事实之家），不新造一套。
- **`status` 只有两档**：`draft`（功能未跑通）/ `ready`（至少一条工作流端到端跑通过并留下产物证据）。卡片按它区分呈现，不隐藏 draft。**v2 新增 `statusReason`**：M1 压出的教训——只有两档枚举时，卡片无法回答「draft 到底卡在哪」，于是人只能去翻仓库。理由必须是机读字段，不是文档里的散文。
- **`preset` 必填，语义是「归属」**：产品归属 50 个岗位之一，岗位是它的垂直基座与默认装配。归属不是装饰——卡片、技能解析顺序、未来部署都以它为准；一个产品不属于任何岗位，说明它还没想清替谁干活。

# 4. 功能（节点）声明

```jsonc
{
  "id": "select-candidates",
  "label": "选人条件 → 推荐名单",
  "kind": "model",                       // 本功能是否含模型调用
  "skills": [                            // ★ 骨架是「多条技能」，不是一条（v2 修订，见 §11.1）
    { "id": "p2s-kol-creator-matching",     "layer": "L1", "role": "method",   "resolveFrom": "global-skills"  },
    { "id": "kol-hunter-candidate-screen",  "layer": "L2", "role": "contract", "resolveFrom": "product-skills" }
  ],
  "steps": [                             // ★ 功能内部的分工（v2 新增，见 §11.2）
    { "id": "score",  "kind": "deterministic", "tool": "score_candidates", "implementedAt": "pipeline/score.mjs",
      "does": "归一化 → 加权 → 总分 → 硬约束 → 排序。不得调模型。" },
    { "id": "advise", "kind": "model", "outputSchema": "schemas/candidate-list.json",
      "does": "读工具算出的数字与事实，产出理由、下一步动作、结论。" }
  ],
  "inputs": [
    { "key": "product", "label": "产品",          "type": "text",   "required": true },
    { "key": "market",  "label": "目标市场",       "type": "select", "required": true, "options": ["美国","英国","澳大利亚"] },
    { "key": "budget",  "label": "单达人预算（USD）","type": "number", "required": true, "min": 100 }
  ],
  "output": {
    "schema": "schemas/candidate-list.json",
    "template": "templates/candidate-list.md",
    "artifact": "artifacts/select-candidates/<runId>.json",
    "rendered": "artifacts/select-candidates/<runId>.md"
  },
  "next": []
}
```

硬约定：

1. **功能必须声明，不得只活在 TSX 里。** 一个功能 = 一条声明 + N 条技能 + 若干步骤 + 一个模板。理由：同一份声明要同时喂三处——抽屉列出工作流、自检做校验、将来换模板不用改 TSX。
2. **`inputs` 是页面引导的唯一来源。** 面板按它生成表单；表单字段与声明不一致 = 自检红。
3. **`deterministic` 步骤不许调模型。** 纯计算走工具即可，混进模型会让「同一输入两次不同结果」变得无法解释。**v2 把这条从「功能级」下沉到「步骤级」**——M1 里同一个功能既有算数的部分也有判断的部分，功能级的二选一表达不了（§11.2）。
4. **每个功能必须留下四件证据**（§7）。

# 5. 提示词与模板

## 5.1 骨架 = **多条**技能的组合，技能分三层

一个功能的提示词骨架是**若干条技能的组装**，各有其职，而不是 `product.json` 里的内联字符串，也不是一条技能孤军奋战：

| 角色 | 层 | 管什么 | M1 实例 |
| --- | --- | --- | --- |
| `method` | L1 岗位专属技能 | **怎么想**：方法论、算法口径、业务约束 | `p2s-kol-creator-matching`（六维匹配框架） |
| `contract` | L2 产品局部技能 | **产出什么形状**：本产品的字段、权重取值、分级阈值、边界 | `kol-hunter-candidate-screen` |

分工的理由很实际：**方法归岗位，形状归产品**。同一套达人方法论换个产品就换一套字段；把两者写进同一条技能，会让「改产品」必须动岗位技能（或反之），而这两件事的评审人是不同的。

技能按**可见范围**分三层，越靠近产品越优先：

| 层 | 内容 | 物理位置 | 谁装载 | 可见范围 |
| --- | --- | --- | --- | --- |
| **L0 全局技能** | 平台通用技能、1338 张 p2s 卡、各处 importer 产物 | `~/.dsh/skills/<kebab>/` | 技能装载器（全局） | 所有会话 |
| **L1 岗位专属技能** | 该岗位的本职方法论 | 与 L0 同目录，由 preset 的 `dsh-skill-subset` 子集声明 | preset composition 的 `config.skills` | 挂载该 preset 的会话 |
| **L2 产品局部技能** | 该产品自己的功能提示词骨架 | **产品目录内 `<产品>/skills/<kebab>/`**（产品根 == 包根，`skills/` 只有一份） | 产品插件注册；**落入哪一层由包挂在哪一层决定**（v2 修订，见 §11.8） | 挂载该产品所属 preset 的会话 |

**同名遮蔽**：近层胜远层（L2 > L1 > L0）。这与既有机制一致——`dsh-skill-subset` 正是用「运行时重注册同名技能」遮蔽全局副本（`packages/contract/dsh-skill-subset/lib/index.js`）。

- **产品技能不落全局目录**：产品技能是产品的一部分，随产品打包、随产品挂载、随产品卸载消失。散进 `~/.dsh/skills/` 会让「这个技能属于哪个产品」变成只能靠名字猜的事实。**M1 已把这条做成机检**：自检项「L2 产品技能没有落进全局技能目录」。
- **局部性由挂载层决定，且要防误挂**（v2 修订，见 §11.8）：技能注册表是「宿主 + 按 scope 分层」——宿主行落全局层，**agent preset 常驻组合挂载的行落该 preset 层**，最近层赢得重名。因此产品包**必须由岗位 preset 的行挂载**，且**故意不声明 `dsh.bundle`、不提供 `cordis.patch.yml`**：缺这两样会让「把它加进 profile bundles」在启动期硬失败，而声明了则会静默把局部技能变成全局技能。**M2a 已做成机检**：自检项「产品包被挂在该岗位的组合里」+「产品包没有被写进 profile 的 `dsh.profile.bundles`」。
- **产品引用的 L1 必须真的是那个岗位的技能**：不能只在 `product.json` 里写个 id 就算数。**M1 已把这条做成机检**：自检项「L1 技能确实属于该岗位」，读 preset composition 的 `skills: [...]` 逐个比对。
- **命名仍带产品前缀**（如 `kol-hunter-candidate-screen`）：此时前缀的作用不再是防撞名（层级已经隔离），而是**标明来源**与让日志/自检能一眼归属。
- **变量**：技能正文里用 `{{key}}` 占位，`key` 必须能在 `inputs[]` 里找到；找不到 = 自检红。

## 5.2 拼接是纯函数，且有快照

```
composePrompt({ skills, inputs, facts }) -> string
```

- **`skills` 是有序数组**（v2 修订）：L1 在前、L2 在后，缺任一层直接抛。
- **`facts` 是工具读数**（v2 修订）：确定性步骤算出的数和候选池事实进提示词，**模型不得重算**。
- **纯函数**：无 IO、无时间、无随机。输入相同，输出逐字节相同。**M1 已实测**：同一输入连跑两次，提示词 SHA-256 逐字节相同。
- **缺变量必须抛**，不得静默留下 `{{topic}}` 这种半成品提示词。
- **快照**：`prompts/__snapshots__/<feature>.md` + 旁证 `<feature>.snapshot.json`。输入或技能正文改了，必须**显式**改快照——这让「模型到底看到了什么」成为可回放的证据。**M1 已实测**：换输入后提示词哈希变化且快照被标 `stale`；`--update-snapshot` 才落盘。
- **快照必须能分辨「谁动的」**（v2 新增，见 §11.7）：旁证记下 `{promptHash, inputs, skills[{id,layer,hash}]}`。快照 stale 时比对旁证，结论只有两种之一——**本次输入变化**（作者自己改的）或**技能正文被外部改写**（平台管线批量重刷），后者要指名是哪条技能、从哪个哈希到哪个哈希。只报「stale」而不说原因，等于把诊断成本推给人。
- **反例（自检拒）**：提示词字符串字面量散在面板代码里；用模板字符串直接拼用户输入而不经过 `composePrompt`。

## 5.3 模型只出结构化字段，模板由确定性渲染

模型产出 `output.schema` 描述的结构化字段（JSON），模板渲染是确定性的（Markdown / HTML）。**不允许模型自由生成 UI**：那会让「预置模板」失去意义，字段与版式随模型漂移，且无法审计。

**v2 新增两条由 M1 压出来的机检契约**（§11.3）：

- **数字归工具，判断归模型**——模型回写的六维分 / 总分 / 预估 ROI / 预算契合必须与工具读数**逐字相等**，否则违约。
- **分级只能降不能升**——阈值判出的分级是算术结果；模型可以降级并写明理由，不得升级。

# 6. 运行缝（每条都有已在本机跑通的先例）

| 需求 | 基座机制 | 先例（本机可查） |
| --- | --- | --- |
| 功能按钮与页面引导输入 | client 插件面板：`<dialog>` + `showModal()` 进 top layer，或官方 slot（`conversation.input.*` / `sidebar.footer.action` / `shell.overlay` / `settings.section`） | 本仓库 6 个 surfaces 包；ADR-0027 |
| 触发模型 / 工具 | `ctx.tools.register(defineTool(...))`，工具名 ≤64 且 `[A-Za-z0-9_-]` | `packages/capabilities/*` |
| 面向会话开工 | `sessions.create({cwd\|workspaceId})` → `agentPresets.select({sessionId, agentPreset})` → `sessions.open(sessionId)` | 工作台客户端（`vendor/dsh-worktable/01_content/lib/client.js`，本机在跑） |

# 7. 每次运行必须留下的证据

一个功能跑完，落盘四件（缺任何一件 = 该功能不算跑通）：

1. **输入**：`runs/<runId>/01-inputs.json`——`inputs` 的实际取值，以及它由哪条声明采集。
2. **提示词**：`runs/<runId>/02-prompt.md` + `prompts/__snapshots__/<feature>.md`——拼接后的全文与哈希。
3. **回执**：`runs/<runId>/03-receipt.json`——每个步骤的实现、口径来源、读数、以及模型步是否执行（含失败与拒绝；失败不许静默）。**v2 修订：回执必须自洽**——M1 首版只摘了总分与分级，导致「模型回写的数是否等于工具读数」无法核验；现改为写入完整读数行。
4. **产出物**：`artifacts/<feature>/<runId>.json` + 渲染后的 `.md`。
5. **模型产出原文**：`runs/<runId>/03-model-output.json`（v2 新增，见 §11.4）。
6. **清单**：`runs/<runId>/manifest.json`——把上面五件的路径、哈希、技能组合与快照状态串起来。

这四件同时是「下一步功能的输入」与「审计的凭据」。**没有它们，「AI 可视化工作流」就只是好看的按钮。**

# 11. M1 试点压出来的读数（实测，非推测）

试点：`/Users/lute/project/KOL-Hunter`，功能 `select-candidates`，归属 `agt-033`。运行命令 `node run.mjs`，验收命令 `node run.mjs --check`。

## 11.1 骨架不是一条技能——v1 写错了

v1 的 `features[].skill` 是**单数**。真做下去立刻发现它表达不了实际情况：达人方法论在岗位技能里（`p2s-kol-creator-matching`），但「本产品输出哪些字段、六维权重取多少、分级阈值是多少」是产品自己的事，写进岗位技能就等于让产品改口径必须动岗位。v2 改为 `skills[]`（L1 `method` + L2 `contract`）。

**配套的口径纪律**：权重与阈值写在 **L2 技能正文的表格里**，打分工具**从技能正文读**（`readWeightsFromSkill` / `readGradesFromSkill`），并有自检项断言「工具实现的维度集合 == 技能权重表的维度集合」。这样改口径只改一处；若只改一处而另一处没跟上，自检红。

## 11.2 功能内部要再切一层 `steps[]`

v1 的 `kind: "model" | "deterministic"` 是**功能级**的。但 `select-candidates` 天然是两段：一段是纯算术（归一化 → 六维加权 → 预算硬约束 → 排序 → 折减 ROI），一段是判断题（写理由、下结论、指出池子缺什么）。把它标成 `model` 会让「deterministic 不得调模型」这条约束失效；标成 `deterministic` 则等于说谎。v2 把它下沉成 `steps[]`。

**这条下沉还带来一个可机检的好处**：分工一旦写死在声明里，「数字归工具、判断归模型」就从倡议变成了契约（§11.3）。

## 11.3 两条新的机检契约（都来自真实失败模式）

| 契约 | 为什么需要 | 负例探针实测 |
| --- | --- | --- |
| 模型回写的数字必须与工具读数逐字相等 | 提示词里写了「不得重算」，但写进提示词的是**建议**；模型完全可能顺手「优化」一下分数，而人看不出 | 把 k03 的 `totalScore` 从工具值 70.24 改成 88.88 → **exit 1**，报 `k03.totalScore: 工具 70.24，模型写了 88.88` |
| 分级只能降不能升 | 分级是算术结果。允许升级，等于允许模型绕过预算硬约束把超预算的头部捞回名单 | 把 k10 从工具判的 `exclude` 升到 `test` → **exit 1**，报 `只许降不许升` |

## 11.4 回执必须自洽（v1 漏了）

v1 的 §7 只说「留下回执」。M1 首版按最省的方式只摘了总分与分级——直到要核验「模型回写的数是否等于工具读数」时才发现**回执里的信息不够做这个核验**。改为写入完整读数行。**教训**：证据的字段集是由「将来要拿它做什么判定」倒推的，不是由「现在有什么」正推的。

M1 落地时的真实状态是：功能已端到端跑通并留下产物，但入口面板的客户端服务还没打包安装，所以卡片点开走不了第 1 级。`draft` 与 `ready` 都说不准。v2 加 `statusReason` 让卡片能说实话。这属于「等 M2 把入口装起来后可能自然消失」的临时缺口，但**在不消失之前，卡片不该靠人翻仓库才知道原因**。

## 11.7 岗位技能会被平台自己重刷——提示词会「无故」变化

M1 收尾时撞上一件事：同一份输入、同一份产品代码，提示词哈希从 `b738e62723be` 变成 `4b22687e11ce`，体积 +443 字节。

追下去的真实读数：

| 探针 | 读数 |
| --- | --- |
| `~/.dsh/skills` 下 10:55–11:01 之间被改写的 `SKILL.md` | **1338 个**（几乎整个技能库） |
| `p2s-kol-creator-matching/SKILL.md` | 8859 → 9302 字节；正文多出「参数移植纪律」段与「技能关联」段 |
| 同期本仓库 `packages/capabilities/dsh-paper2skills/` 的写入 | `generated/assemble-report.json` + `staging/**/SKILL.md` 批量重建 |

即：**p2s 技能装配管线在跑，它把全局技能库整体重刷了一遍**，而产品的提示词是从 L1 技能正文拼出来的。

**这条对产品形态是可操作的，不是轶事**：

1. 产品的提示词哈希会因为**平台侧**的动作而变化，产品一行未动。若快照只报「stale」，运维会以为是自己改的，于是去翻产品仓库，白费一轮。
2. 所以快照必须有**旁证**：`{promptHash, inputs, skills[{id,layer,hash}]}`。stale 时比对旁证，把结论收敛成两种之一——**本次输入变化** 或 **技能正文被外部改写**，后者指名技能与哈希迁移。
3. **M1 已实现并实测**：真改一个字节的 L1 技能正文 → `--check` exit 1，报 `技能正文被外部改写（非本次输入变化）：L1:p2s-kol-creator-matching b39e777889eb→2d34c44f5ac3 → 复核后再 --update-snapshot`；还原后 14/14 复位。
4. **顺带的纪律**：产品**不得**依赖 L1 正文的稳定性来做缓存或幂等判定。要稳定，就得把该条技能的哈希写进运行证据（manifest 已记 `skills[].hash`），而不是假设它不变。

**这条同时说明 M1 证据里的 L1 哈希为什么值得记**：它是「这一轮到底用了哪一版岗位方法」的唯一凭据。没有它，两次运行的差异无法归因。

## 11.8 产品包与挂载层：局部技能是挂出来的，不是写出来的（M2a）

用户的要求是「产品技能要**单独打包**到对应的产品中作为**局部技能**」。M1 只做到「产品目录里一个 `skills/` 文件夹 + 产品自己的加载器」——把那个文件夹拷到 `~/.dsh/skills/`，行为一模一样，**当时没有任何东西在阻止它变成全局技能**。M2a 把它做实。

**权威契约**（`@deepseek-ai/dsh-skill`）：注册表是「宿主 + 按 scope 分层」——宿主行与 repository 插件落**全局层**，**由 agent preset 常驻组合挂载的插件落该 preset 层**；读取时合并，**最近层直接赢得重名**。

**先例 `dsh-skill-subset` 同时挂两层**：profile 的 bundles 里一行（全局层，无 config → `hideOthers` 把全部技能注册为不可见）+ 50 个 preset 各一行（preset 层，重注册本岗位子集）。净效果是「全局隐藏、preset 内可见」——它同时示范了误用形态：**只想做局部的包若也进 bundles，patch 会在宿主层插一行，技能进全局层，全程零报错。**

落地的四条形态：

| 决定 | 理由 |
| --- | --- |
| **产品根 == 包根**（`product.json`/`skills/`/`pipeline/`/`lib/` 同住产品目录） | `skills/` 只有一份，管线与插件两个消费者读同一个文件，不存在「两份技能」的漂移面 |
| **挂载点写进生成器**（`generate.mjs` 的 `PRODUCT_MOUNTS`） | 50 个 `agent.cordis.yml` 全是生成物，手改会被下一次生成冲掉 |
| **故意不声明 `dsh.bundle`、不提供 `cordis.patch.yml`** | 误进 bundles 会**硬失败**（`profile bundle "…" declares no dsh.bundle`），响而不哑；反例见上一段 |
| **`link:` 安装，不用 `file:`** | `file:` 是安装时刻的硬链接快照（`docs/architecture.md` §1），`link:` 是活软链 |

**归属与装配是两个事实，各自有家**：`product.json` 的 `preset` = 产品说它属于谁；`PRODUCT_MOUNTS` = 岗位说它挂谁。产品自检读生成的 `agent.cordis.yml` 断言两者一致——不一致即红，因为挂错层不报错。

**解析器只有一份**：插件复用 `pipeline/skills.mjs` 的 `parseFrontmatter`，只把失败策略由「抛」换成「warn 后跳过」（构建期要严格，运行期缺一条技能不该拖垮整个组合）。自检项「插件注册的正文与管线读到的逐字节相同」钉死这条。

## 11.9 M2 压出来的读数（实测，非推测）

M2 做「抽屉读 `product.json`、出卡、点开」。压出三件事，前两件是规格没写清的，第三件与产品形态无关但**在真探针下才现形**。

### 11.9.1 卡片要的和入口要的，不是同一份东西

宿主半边返回的 `DeclaredProduct` 是**归一化视图**：`features[]` 只有 `{id, label, kind, steps}`。
而入口面板的表单来自 `features[].inputs[]`——**它不在里面**。于是第一版能出卡、点开是空壳。

修法：`DeclaredProduct` 增加 `declaration`（`product.json` 里那个对象的**逐字副本**），
与归一化字段并存。**归一化服务卡片，逐字服务入口**：`inputs[]` 是**产品自己的 schema**，
本插件不拥有也不该重塑——重塑它正是它被丢掉的原因。两者同源于一次读取，谁也不落盘。

**可复用的一条**：**「卡片要什么」不等于「点开要什么」**。只要一个声明有两个消费者，
要么让其中一个读原件，要么迟早会漏字段——而漏字段的症状是「按钮能按、面板是空的」。

### 11.9.2 允许根是读取边界：读不到必须报，不能像「没有」

扫描根默认为空 = 不扫（§8）。实测三类**非空但读不到**的情况必须各自进报告，否则
「读不到」与「没有产品」在界面上不可区分：

| 情形 | 落点 | 实测读数 |
| --- | --- | --- |
| 根不存在 | `skipped[].root` + reason | `ENOENT: no such file or directory, stat '…'` |
| 根是文件 | `skipped[].reason` | `不是一个目录` |
| 声明不是合法 JSON | `unreadable[].dir` + reason | `Expected property name or '}' in JSON at position 1` |
| 目录没有声明 | **照样成卡** | `declared:false` + `尚未产品化：没有 product.json` |

### 11.9.3 共享栅栏在生产里是「抛异常」而不是「拒绝」——真 curl 探针才看得见

M2 的实况探针对第 30 条栅栏负例全部期望 403，实测 **400 空 body**。根因不在本产品形态里：
`shared/host/pair-access.ts`（三张插件共用）读 `ctx.remoteWebUiPairing`，而 cordis 对**未 inject
的服务**的属性读**是抛异常的**——该模块故意不 inject（没有 remote-web-ui 也要能用），
于是每个非回环请求都在栅栏里抛，被 webserver 兜成 400。判决没出自栅栏，`403` 那条分支
在生产里不可达。决策见 [ADR-0038](../../docs/adr/ADR-0038.md) 与其 Note。

**它对本规格的意义**：§8 写的「按 ADR-0030 逐插件打栅栏」不只是「要打」，还得**证伪到
真 cordis 上下文 + 真 HTTP 事务那一层**——合成 req 对象与普通对象 ctx 替身测的是纯函数分支，
测不出「判决会不会在到达 handler 之前抛掉」。M2 的探针因此把仪器自检（不存在的路由必须 404、
死端口必须失败、正控必须 200）放在任何结论之前。

# Alternatives considered

- **集中一份产品登记表（启动器自己拥有一份清单）**：放弃。它是第二份事实，产品一改就漂移；且与 ADR-0028「启动器只拥有连接，不拥有事实」冲突。
- **点开 = 新建会话**（工作台三连）：放弃作为默认动作。你要的是「进产品」，不是「开聊天」；三连保留为第 2 级回退。
- **提示词内联在 `product.json`**：放弃。长 Markdown 塞进 JSON 不可读、不可复用，而技能库已经是这一层的家（还有加载契约、分发、装配三样现成能力）。
- **一条功能的骨架只挂一条技能**（v1）：放弃，见 §11.1。
- **模板由模型生成**：放弃。见 §5.3。
- **产品代码收进本 monorepo**：放弃。产品是各自项目的事；本仓库只出规格、校验器和启动器（M1 实测：整个功能落在产品目录内，本仓库零改动）。
- **把流程写进 preset 的 composition**：放弃。见 §1 末的硬链接教训。
- **口径写在代码里、技能只写散文**：放弃。M1 选了「技能正文写权重与阈值表，代码读它」——理由同「一份事实只有一个家」；代价是技能正文格式被约束成可解析的表格，这个代价值得。

# Consequences

**正面**：一个文件说清一个目录是什么；卡片可以做到「点开必能用」；提示词与模板第一次成为可回放、可门禁的证据；产品可以在不改基座的前提下增删；方法（岗位）与形状（产品）可以各自演进。

**负面**：多了一次约定的写入（每个产品要有人写 `product.json`）；技能命名要靠前缀自律，否则会静默遮蔽；扫描根是新的安全面，必须与第一期同等对待（栅栏 + 允许根 + 负例探针）；**多技能骨架要求产品明确声明它依赖哪条 L1**，声明错了自检会红，但「该不该依赖这条」仍是人的判断。

**后续动作**：M2 做发现与开入口（含栅栏负例探针），M3 做两节点工作流，M4 把 14 项自检搬进门禁。**M1 已把 v1 的四处偏差压回本文件**（§11.1–11.4），后续每期照此办理：偏差回写规格，而不是让规格与实现各说各话。
