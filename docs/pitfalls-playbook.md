# 复发故障总账（Pitfalls Playbook）

> **本页是「复发故障」的唯一 home**，按**根因类**组织——不按日期、不按事件。
> 事实（哪一次、什么读数、怎么修的）一律留在 ADR / Note / SOP 里；本页只写
> 「模式 + 拦它的机制名 + 指向事实的链接」（[ADR-0009](adr/ADR-0009.md)：一份事实只有一个家）。
>
> **结构由门禁 `pitfalls-playbook` 守着**：条目四段必须齐全、编号自 `P-01` 起连续、
> 「已落地机制」点名的每个 `gate:<名字>` 必须真实出现在 `node scripts/gate.mjs --list`，
> 每个 `script:<路径>` 必须真实存在，正文相对链接必须可达（**逐字引用的坏链写进行内代码
> 或代码块即可**——引缺陷原文是本账的正当写法，校验跳过这两处，规则与 `docs-link-integrity`
> 共用同一份实现）。
> 这条门禁本身就是 **P-03** 的应用——一张靠自觉维护的总账，三个月后就是一堆谎。
>
> **新增一条的门槛**：同一根因**复发过两次**，或第一次的代价大到不允许发生第二次。
> 落笔前问三句：症状能不能被机器判出？拦住它的机制**叫什么名字**？下一个人该先做什么？
>
> **写作约定（无强制）**：不复述 ADR/Note 里的数字、读数与版本号——复述等于给同一条事实
> 再造一个家，改一处漏一处就是 P-07 本身。这条只靠评审，门禁管不了
> （P-03 的诚实读法：哪些是**拦住**的，哪些只是**约定**，必须分开说）。

## 贯穿做法（三条）

1. **判据化**：凡「出货前必须成立」的命题，都做成带退出码的判据，而不是人工复测清单。
   人工复测过一个月就不再是证据（[ADR-0063](adr/ADR-0063.md) 的判据①~⑤ 即此形态）。
2. **证伪式读法**：证明「没有退化」不要看「读数还在」——读数可能是假的「已开启」；
   要看**字节变了而读数没变**。用变化的对照证明解耦，比用不变证明存在强得多。
3. **反向自测进门禁**：每条判据都要配一支「恒真桩突变下必须变红」的自测，并挂进门禁。
   判据自己也要被证伪——`tcc-*-selftest`、`setup-app-locator`、`release-verify-selftest`
   与 `pitfalls-playbook-selftest` 都是这个形状。

## P-01 · 未验证的事实被钉进出货面

- **症状**：出货面（安装手册、README、安装器提示、门禁）写着一条没人实测过的「事实」，
  用户照着做，能力静默失败。更坏的一种：门禁把它变成了**强制校验**，于是「改对」反而判红。
- **根因类**：把「看起来合理」当成「已验证」。这条事实的家只有一句转述，没有可复现的读数，
  而它一旦进了出货面就会被复制、被断言、被当成前提。
- **已落地机制**：`gate:tcc-pane-guidance`、`gate:dmg-readme-tcc-panes`
  （否定式校验：只允许「辅助功能 / 屏幕录制」两项，把「输入监控」「自动化」写成待授项即红灯）
- **下一版默认动作**：任何要写进出货面的「事实」，先拿到一条**可复现的读数**（命令 + 原始输出）
  再落笔；拿不到就写成「未验证」，并且**只留在内部文档里**，不出货。
- **详见**：[ADR-0069](adr/ADR-0069.md)、[ADR-0063](adr/ADR-0063.md)

## P-02 · 仪器假绿

- **症状**：仪器、面板、门禁全绿，而能力已经死了。报告里看不出任何异常。
- **根因类**：两件事被当成同一件——「没有读数」与「读数为好」；以及只读了状态的一半
  （读了值，没读这个值绑在谁身上）。假绿比红灯贵得多：红灯会被处理，绿灯会被相信。
- **已落地机制**：`gate:tcc-dead-grant`（同时读开关值与绑定对象）、
  `gate:tcc-grant-status-selftest`（恒真桩突变下必须失效）、`gate:tcc-persistence-selftest`、
  `gate:dead-instrument`（**开出去给人敲的判据**——发布前清单项、围栏代码块、脚本代码行——
  不得出现读数已知为空的仪器；登记簿每条都带可复现读数与替代物，射程为空/登记簿为空一律判红）、
  `gate:brand-icons`（品牌的两个家里，被 `setIcon()` 覆盖的那一套此前从未被核对；
  核对表 ↔ 资产目录两向对照，且**资产的像素尺寸必须等于声明**——原来只核了目标那一侧，
  等于量错了对象）、
  `gate:patch-anchors`（**射程为空报 `skip`**，与「通过」在读数上分开——「没量到东西」被读成
  「都合格」是本条最便宜的复发路径）、
  `gate:gate-result-selftest`（所有门禁统一记 `expected/discovered/checked/skipped/failed`，空射程 pass、
  非守恒、checker throw 与 strict skip 都有负例）、`gate:live-presets` 与 `gate:live-presets-selftest`
  （每条 preset row 有稳定身份与 checked/disabled/failed 结论，inventory 让“删一条、分母也缩一条”判红），
  `gate:profile-metadata-sync`（**「比了 0 个包」必须与「都比过且一致」不同形**：归组重构后
  vendor 路径写成了扁平的 `vendor/<包名>`，实际是 `vendor/packages/<组>/<包>`，25 个受管包
  一个都没命中，于是该项与它自己开出的 remediation（`sync-profile.mjs --apply --only-metadata`，
  同样的路径错法）**双双恒绿、从未比过任何字节**；现在两侧都断言「真的比过」，
  阳性对照下必须变红。同类教训：护栏只挂在一条分支上时，它保护的只是自己那条）、
  `gate:profile-bundle-sync`（**断言面留了个洞等于没断言**：`loadPointFiles` 把
  `package.json` 整个排除在外，理由是「pnpm 在装载点重写它（剥 scripts/devDependencies）」——
  实测该前提在本机**不成立**，于是清单漂移在装载点一侧**一台仪器都没有**；
  现按装载字段子集 `main`/`exports`/`dsh` 对账，既补上洞又不会因 pnpm 真去剥那两个字段而误红）、
  `gate:changed-packages` + `gate:changed-packages-selftest`、`gate:plugin-entry-contract` +
  `gate:plugin-entry-contract-selftest`、`gate:profile-metadata-sync` / `gate:profile-files-sync` /
  `gate:profile-bundle-sync` 三面共用的 `gate:profile-coverage-selftest`
  （**分母 = 被检查对象的完整集合**：三处判据统一成 `expected = checked + skipped + failed`，
  射程收缩一律判红，见下条同族前科）
- **下一版默认动作**：写任何仪器先定「读不到时输出什么」——必须是**失败**或**显式的跳过**，
  不是通过；凡读状态一律「值 + 绑定身份」两项一起读；交付前做一次恒真桩突变，红不了就是没测。
  **清单里的命令也是仪器**：它会被人照着跑，所以一条返回空输出的命令比没有命令更坏——
  复核者会拿那个「空」当成结论（2026-09-13 实测：一条 `pgrep -f` 检查项在主进程确实在跑时
  返回 0 条，于是「没有实例在跑」成立，接着就是运行中替换 app bundle 与整屏白屏）。
  判据「读不出」与「读出来是零」必须是两个不同的退出码，且调用方对前者**中止**。
  **另一面同样贵：仪器假红。** 判据在**已验收的产物**上报红时，那不是发现，是仪器坏了 ——
  而它的长相与产品缺陷一模一样。2026-09-16 做品牌头像判据时实测四次同形：结构判据第一版把
  **全部 324 枚已验收图标**判红（颜色白名单漏了渐变的一个 `rgba(255,255,255,0)` 停）；
  改完范围仍用「组内全部数字」，把 `stroke-width="2"`、`r="2.9"` 当坐标，于是又全红；
  栅格判据把 qlmanage 的不透明背景当成内容、又拿色板去卡线性渐变本就存在的插值色，
  三枚图标给出**一模一样**的外溢数字。**「三枚数字完全一样」本身就是仪器坏了的读数** ——
  真实缺陷不会这么整齐。所以改判据前的第一件事固定为：**先拿已验收的一批跑一遍，它必须静默**；
  判红时先问「是不是我在量错了对象」，再问「产物是不是真坏了」。
  **同族前科（2026-09-16，SEC-RT-006/007）**：同一形态一天里出现两次，而且两次都出在**新写的判据**上。
  ① 一条断言的名字写着「旧实现会读成 `enabled:true`」，而它实际量的是**另一个字段**——
  拿旧实现重放时它照样通过：判据与它宣称要拦的缺陷不是同一件事，**改名永远不会让它变红**，
  只有 RED 重放（把工作树换成缺陷版本真跑一遍）才会。② 一条「预建 0644 → 写后 0600」的断言，
  在**去掉那一步 `chmod` 之后仍然全绿**——把权限位带上新 inode 的其实是 `open(…, mode)`，
  那条 `chmod` 只在受限 umask 下承重，默认 umask 下它看起来就是装饰。两条都不是「没写测试」，
  而是**测试了别的东西**。所以「红不了就是没测」只能按**变异**判，不能按「这条断言看起来在测它」判。
  **同族前科（2026-09-17，QG-003 / QG-004 / QG-005）**：一天里三张卡各有一个 Red，
  形状不同、根因同一个——**射程变小与「没有问题」在读数上同形**。
  ① `changedPackages` 的三条来源里有 `git diff --name-only main...HEAD`：在 `main` 上
  它就是 `main...main`，**自比较**，恒为空。临时仓库实测：本地超前 `origin/main` 两个提交、
  两个包被改，三条来源合起来是空集；真实仓库里 31 个 untracked 文件一个都不在集内，
  新包在 `git add` 之前对门槛完全隐形。② `plugin-entry-contract` 硬编码 `<dir>/lib/index.js`，
  读不到就 `continue`、不导出 `apply` 也 `continue`，于是 23 个候选里有 2 个从分母里消失、
  门禁报「核对 21 个」并退出 0——而这两个**本来就是插件**（默认导出是 Cordis `Service` 子类），
  且这个模块当时**从未被任何东西 import**（P-04 的形态叠在 P-02 上）。
  ③ `installedProfileDependencies()` 的失败路径是 `catch { return {} }`，
  把 profile 的 `package.json` 写成截断 JSON 之后，三个 profile 门禁**全部绿**，
  `profile-bundle-sync` 的读数还写着「对比 0/0 个 file: 依赖」——它的守卫
  `fileDeps > 0` 防的是「声明了却一个都没对上」，防不住「声明本身就没了」。
  **共同的错法**：守卫挂在「已经读到的东西」上，而不是挂在「应该被读到的完整集合」上。
  所以现在三处的第一句都是先算分母（`expected`），再要求每个对象落在且只落在一个桶里。
  **同一天还有一条更便宜的复发路径**：`changed-packages` 在射程为空时返回老式
  `{passed: true}`，被规范化器换算成 `checked=1`——「没看」被记成「看过且没问题」。
  空射程只能是 `skip`，且必须带类型化的跳过理由。
- **详见**：[ADR-0068](adr/ADR-0068.md)、[ADR-0063](adr/ADR-0063.md)、[ADR-0075](adr/ADR-0075.md)、
  [ADR-0080](adr/ADR-0080.md)、[ADR-0081](adr/ADR-0081.md)、[ADR-0094](adr/ADR-0094.md)、
  [ADR-0099](adr/ADR-0099.md)、[ADR-0102](adr/ADR-0102.md)

## P-03 · 「知道」没有变成「拦住」

- **症状**：这条教训早就写在某处了，下一个人照样再犯，而且犯在更贵的位置上。
- **根因类**：「知道」与「拦住」是两件事。写在注释里、写在 Note 里、写在 SOP 里，
  都只是知道——没有任何东西会因此停下来。
- **已落地机制**：`gate:pitfalls-playbook`（本账自身：每条教训必须点名一个**真实存在**的机制，
  写一个不存在的门禁名字即红灯）、`gate:shell-var-multibyte`（实例）
- **下一版默认动作**：写完一句「我们知道了」，立刻问「它**叫什么名字**、在 `gate --list` 里吗」。
  不在，就当场补一条判据；补不了，就在原处**明写**「这只是约定，无强制」——
  不要让它看起来像受保护的红线。
- **详见**：[ADR-0064](adr/ADR-0064.md)、[ADR-0057](adr/ADR-0057.md)

## P-04 · 写了但从没跑到

- **症状**：判据、分支、错误报告路径都写好了，却从来没有真正执行过；出问题时它什么也不说。
- **根因类**：没有读数的分支等于不存在，而「不存在」在报告里长得和「正常」一样。
  错误报告路径尤其危险——它自身一炸，反而把真实错误盖住。
- **已落地机制**：`gate:setup-app-locator`、`script:packaging/scripts/setup-app-locate-test.sh`、
  `script:scripts/acceptance/settings-shell-live.mjs`（**错误报告路径本身也要被跑过一次**：
  python 段里那几处 `raise SystemExit` 逃出 `try` 之后哨兵行**从未打印**，调用方只看得见空
  stdout，于是「AX 树只剩 AXApplication 一个节点」被误报成「harness 未回传报告」——
  诊断指向了错误的仪器，而真正坏掉的是 AX 子树（CG 层窗口还在、renderer 还活）。
  现由 `except SystemExit: pass` / `except Exception` 兜底，并把 AX 节点数写进报告）
- **下一版默认动作**：交付前把每条分支都跑出一次真实输出（**含失败分支**）；
  `set -e` 下的条件分支用 `if` 写，不要用 `[ ... ] && cmd`——条件为假时它就是一次非零返回；
  验收时优先验**错误报告路径**，而不是主路径。
- **详见**：[ADR-0066](adr/ADR-0066.md)

## P-05 · 隔着一层解释器写「字面量」

- **症状**：我写的字符，到了用户手里变成别的东西——被解释、被展开、或被吞并。
- **根因类**：中间隔着**会解释字面量**的一层（shell heredoc、bash 词法、模板），
  而我把它当成了透明的。危险在于两端的证据都正常：源文件看着对，用户只是拿到了别的东西。
- **已落地机制**：`gate:readme-heredoc-literal`、`gate:shell-var-multibyte`
- **下一版默认动作**：凡「生成一段给别人看的文本」，写完先 grep 一遍会被解释的字符
  （反引号、`$(`、`${`）；shell 里变量紧邻非 ASCII 一律写 `${VAR}`；
  heredoc 里要字面量就给分隔符加引号。
- **详见**：[ADR-0064](adr/ADR-0064.md)

## P-06 · 把平台行为当常量

- **症状**：代码在本机是对的，到用户机器上、到挂载盘里、到下一版就不成立。
- **根因类**：把**平台行为**当成「大概如此」。系统怎么定位被双击的 app、签名身份的要求
  长什么样、系统库会不会原样保存它——都不是可以推定的，是必须实测的，而且必须按最坏情况设计。
- **已落地机制**：`gate:setup-app-locator`（多候选搜索 + 载荷指纹 + 版本消歧）、
  `script:packaging/scripts/verify-tcc-persistence.sh`
- **下一版默认动作**：涉及外部平台行为的假设，先在最坏环境里实测一次
  （挂载盘里双击、换机、重启后、升级后）；实测不了就写「未验证」，并按最坏情况加兜底——
  兜底失败的方向必须是「不出货」，不是「照常出货但少个权限」。
- **详见**：[ADR-0066](adr/ADR-0066.md)、[ADR-0063](adr/ADR-0063.md)

## P-07 · 一条事实多个家，只改了其中一处

- **症状**：事实改对了，但改正只落在它所有出现位置中的一个；剩下的那些继续骗人。
- **根因类**：同一条事实被复制到多处，而**没有一处是清单**。于是「改一处」在感觉上
  已经完成了任务，实际上只是修正了 N 分之一。
- **已落地机制**：`gate:tcc-pane-guidance`（出货面**清单本身即判据**：新增一处指引
  而没登记进清单，等于新增一处「写错了也没人说」的地方）、`gate:sidebar-row-axis`
  （注入式侧边栏导航行：**同列必须同行轴**，且期望轴是**显式声明**的而非「拿第一行当基准」
  ——后者在第一行本身就错时恒绿；未登记的注入行、登记项指向不存在入口、`position` 与清单不符
  三者都判红，所以清单不会腐烂）、`gate:dead-instrument`
  （「在不在跑」这类**会被人照着跑**的判据收成一家：`script:packaging/scripts/dsh-running.sh`
  由安装器 / 首启验收 / 品牌重放 / 发布前清单四处消费，谁都不许重写；同一形态的判据面
  ——清单行、围栏代码块、脚本代码行——由门禁按登记簿逐行核对）、`gate:brand-icons`
  （**品牌有两个家**：Finder 图标与 Dock/托盘图标；表 ↔ 资产目录两向逐名对照，
  资产的实际像素必须等于声明像素——`--apply` 量的是目标那一侧，资产自己错了没人管）、
  `script:scripts/gates/checks.mjs`（**「哪段文字算链接」这条规则收成一家**：
  `gate:docs-link-integrity` 与 `gate:pitfalls-playbook` 都从 `collectDocLinks` 取，
  不再各写一份——两份实现的第一次分叉就让本账里逐字引用的坏链被判红，见下文第四例）、
  `gate:adr-note-links`
- **下一版默认动作**：改一条事实前先 `grep -rn` 它的全部出现位置；
  把这份「全部出现位置」写成**清单**并交给门禁托管，而不是靠记性。
  复制一条事实时，顺便问「它的清单在哪」。
  **改对了一半也要当成没改**：写下的注释能准确说出根因，不等于有一处机制在对照（P-08）。
  同一个判据出现在两个以上文件里时，正确动作不是「都改对」，而是**收成一家**——
  两份实现迟早分叉，而分叉时没有任何东西会说话。
- **同族前科**：2026-09-13 侧边栏两行（技能中心 / 岗位矩阵）——当天先修「文字居中」时，
  注释已准确写出根因并引用本条，几何那半（行框 68…316 vs 64…320）却原样留着，

## P-08 · 用纪律守只有机制能守住的东西

- **症状**：靠「不应该」守住的资产没守住，事后查不出是谁动的，也回不到出事前。
- **根因类**：把「不应该发生」当成「不会发生」。以及只守住了资产、没守住**账目**——
  字节找回来了、清单没回来，于是「完整」这件事本身没了判据。
- **已落地机制**：`gate:release-artifacts-intact`、`gate:release-verify-selftest`、
  `gate:changelog-release-sections`（**账目也要有判据**：已发布版本必须在 `CHANGELOG.md` 里有
  它自己的一行 `## [<版本>]`。此前「发了版就把 Unreleased 改成版本号」**只靠人记得**——
  SOP 里 grep 不到 CHANGELOG，没有任何门禁读它，于是实测两份账都停在 `[Unreleased]`，
  2.3.3 与 2.4.0 两个已发布版本在文档里不存在）
- **下一版默认动作**：凡是「绝不允许发生」的事，先问它有没有**机制**（锁、仓库外归档、
  门禁核对）；没有就先建机制再往下走。找回资产时连**账目一起**找回，
  并且让「只剩半截」也是一个红灯，而不是一个没人看的状态。
- **详见**：[ADR-0067](adr/ADR-0067.md)、[ADR-0057](adr/ADR-0057.md)、[ADR-0058](adr/ADR-0058.md)

## P-09 · 死指针：文档指向不存在的东西

- **症状**：文档里写着「对应 ADR：[ADR-00XX]」「详见 xxx.md」，读者以为背后有决策事实，
  实际上那条路通向空地址。
- **根因类**：**指路也算事实，而它除了读者之外从来没有谁验证过**。最典型的形态是层级写错——
  相对链接以**所在文件所在目录**为基准，而写的人按记忆里的深度写。它的危害不是「点不开」，
  而是把「这里没有依据」伪装成「这里有依据，只是我没点」。
- **已落地机制**：`gate:docs-link-integrity`、`gate:docs-link-integrity-selftest`
  （跳过代码块与行内代码里的示例，避免误报把校验变成噪声）、
  `gate:dmg-layout-doc`（**随包语境**下的同一条：手册正文里的相对链接必须在**卷上**可达——
  链接在**仓库里**可达不等于**随包**可达。2026-09-14 实测：手册开头的「一页速查」指向
  `INSTALL-CARD.md`，而该文件自 2.2.0 起从未进过任何一版载荷，所有门禁却都是绿的——
  因为那两个文件在仓库里确实同处 `packaging/` 目录下，只有把它当**卷内**相对路径量才会红）
- **下一版默认动作**：写链接时把**目录层级数**数一遍，不要按感觉；链接是「事实的家」的地址，
  对方文件挪了位置，就要搜一遍谁在指向它。
- **详见**：[ADR-0071](adr/ADR-0071.md)

## P-10 · 出货边界由构建机的状态决定，而守卫看不见打包后的载荷

- **症状**：客户拿到的产物里有构建机上「碰巧存在」的东西——私有预设、私有目录结构、
  只在那一台机器上成立的绝对路径——而所有守卫都是绿的。**反过来也发生**：产品该有的能力
  只因打包那台机器当时没引用它，就静默地少发了，而全部读数是绿的。
- **根因类**：把「开发机的状态」当成出货源，**且只检查了未打包的树**。这里的「状态」有两种形态：
  ① 一个目录列表（本机有什么就发什么）；② **一张引用图**（谁引用了就发谁）。两类都答不了
  「产品要不要发它」——引用图能证明的只有「有人用」。叠加的第三层是仪器：打包后的二进制载荷
  （tarball）既不在扫描面里，也天生被文本扫描跳过（`grep` 把它当二进制）。
- **已落地机制**：`gate:shipped-presets-scope-selftest`、`gate:shipped-skills-scope-selftest`、
  `gate:build-path-rewrite-selftest`、`gate:machine-path-tarball-selftest`、
  `script:packaging/scripts/select-presets.mjs`、`script:packaging/scripts/select-skills.mjs`、
  `script:packaging/scripts/rewrite-build-paths.mjs`、`script:packaging/shipped-presets.json`、
  `script:packaging/shipped-skills.json`
- **下一版默认动作**：往 payload 里加任何「从本机状态推出来的东西」之前先问三句——
  ① 出货面是不是**白名单**（没登记就该中止，而不是默默带上）？
  ② 这项内容是**算出来的**吗？若是，产品自己要发的部分有没有一次**显式表态**，
     以及这份表态**缺文件时是否响亮失败**（而不是退化成空名单）？
  ③ 这项内容**打成包之后**还有哪个判据看得见它？看不见就先给守卫开一个能看进去的口，
  再用真实坏输入证明它会说「不」。同族前科：P-02（仪器假绿）、P-08（用纪律守边界）。
- **详见**：[ADR-0073](adr/ADR-0073.md)、[ADR-0074](adr/ADR-0074.md)、[ADR-0056](adr/ADR-0056.md)

## P-11 · 判据的射程没有定义：拿今天的尺子量历史产物

- **症状**：门禁长期挂一条红，谁都不觉得自己该管；把红读完之后发现它说的**是真的**，
  但它本要拦的缺陷一次都没发生过。想让门禁变绿的唯一手段是**删掉历史产物**——
  而删除恰恰是门禁看不见的动作。反过来也发生：扫描集里那些**绿**的对象，其中一部分
  根本不是出厂的字节（被就地改过的暂存树），绿得毫无证据价值。
- **根因类**：判据写成了「对**环境里碰巧存在**的一切成立」，而不是「对**待发布的那个**成立」。
  射程由环境决定 ⇒ 判据的真值由打扫卫生决定。再叠加一层不对称：判据随时间**单调增长**
  （锚点越加越多），对象随时间**单调累积**（历史产物越留越多），两条各自正确的规则相乘，
  必然导出一条**永久红**；而这条红与真缺陷在输出上不可区分，于是它只能被忽略。
  同族前科：P-02（空射程被读成通过）、P-07（「当前版本」同时住在脚本默认值、门禁扫描集
  和人的记忆里）、P-10（射程由本机状态决定）。
- **已落地机制**：`gate:patch-anchors-scope-selftest`（射程判据的反向自测：已打 tag 的退出、
  未打 tag 的（含同号重制的新树）纳入、射程为空必须报空——两个方向各钉一条恒真桩突变）、
  `gate:patch-anchors`（射程为空报 `skip` 而非 `ok`）、
  `script:scripts/gates/patch-anchor-scope.mjs`（射程 = 本机 app ∪ 未打 tag 的树）、
  `script:scripts/lib/run-script.mjs`（**超时读数**：对机器负载敏感的判据报红时，把当时的
  load 均值、核数与占 CPU 最高的几个进程一起打出来——「环境假红」与「代码真红」在输出上不再同形；
  `ps` 读不到时明写「取不到 ≠ 机器空闲」，并附 `script:scripts/lib/run-script.test.mjs`
  的三条用例，其中一条**真起一个烧 CPU 的进程**、要求它的名字出现在读数里——写死的读数混不过去）
- **下一版默认动作**：写判据之前先写下**「它对谁成立」**，并检查三件事——
  ① 对象集合是不是从一个**在 git 里的家**推导的（tag / 入库清单 / 登记的哈希），
     而不是从 `readdir` 本机产物推出来的？判据跟着 git 走，不跟着磁盘走。
  ② 射程为空时输出什么？必须是**显式的跳过**，不是通过；并且这个状态要**渲染在读数里**
     （模型里有区分、输出里没有 = 没有）。
  ③ 默认的错误方向选**多量**还是**放行**？选「读不到就照量」——放行是这条判据最贵的失效方向。
  ④ 判据**对机器状态敏感**吗（超时、并发、网络、磁盘）？若是，报红时必须带上**当时的机器读数**
     （load、占 CPU 的进程），否则「环境假红」与「真红」在输出上同形，读的人只能二选一地猜——
     而猜错的代价是**把真缺陷当成噪声关掉**。放宽阈值是错的方向：那会把真缺陷一起放过去。
  另：**别用清理去修仪器**。历史产物该不该留是取证问题，不是让门禁变绿的手段。
- **详见**：[ADR-0075](adr/ADR-0075.md)、[ADR-0058](adr/ADR-0058.md)、[ADR-0067](adr/ADR-0067.md)

## P-12 · 豁免不会过期：为某个原因开的绿灯，原因消失后没人关灯

- **症状**：一条「已知且已处理」的豁免长期挂在读数里，每次门禁都把它念一遍，看起来像负责；
  而被它罩住的那个对象**早已恢复正常**、或者**再次坏掉**，都不会有人说话——因为豁免做的第一件
  事，就是让判据不再看它。同类形态：`.lost` 台账、白名单与基线、`exemptions.json`、
  `*.replaced-*` / `*.superseded-*` 留档目录。
- **根因类**：豁免是**为某个原因**开的，但只登记了「豁免谁」，没登记「凭什么叫它成立、
  什么条件下失效」。判据于是从「核对该对象」退化成「复述一条旧结论」，而旧结论一旦是错的，
  就会被永久复述下去。本例的错因还叠了一层**阴性读数的误用**：宣告「不可找回」的取证是
  「Spotlight 全盘查不到」——**搜索工具的沉默不是缺席的证据**，查不到只说明没搜到。
  一句全称否定（「本机无任何副本」）需要的是一次**遍历**，而不是一次查询。
  同族前科：P-01（未验证的事实被钉进出货面）、P-02（豁免本身就是一种「跳过即通过」）、
  P-08（用纪律守只有机制能守住的东西）。
- **已落地机制**：`script:packaging/scripts/release-verify.sh`（对「字节已在位却还留着 `.lost`」
  判红——豁免只在字节确实缺席时才成立）、`gate:release-verify-selftest`（V7 过期豁免→红 /
  V8 如实宣告的缺席→绿：两条一起才说明判据是「分得清」，而不是一律判红）、
  `gate:release-artifacts-intact`、`script:packaging/scripts/release-restore.sh`（找回是命令、
  不是手工，哈希与入库清单对不上即拒收）
- **下一版默认动作**：开任何豁免时，在**同一处**写下它的失效条件，并让某个判据去**读那个条件**；
  典型形式是「对象已恢复即判红，直到豁免被撤下」。另外，凡取证里出现「查不到 / 不存在 / 没有」
  这类**全称否定**，先问一句：这是遍历的结论，还是一次查询的沉默？
- **详见**：[ADR-0067](adr/ADR-0067.md)、[release/2.3.1.recovered](../release/2.3.1.recovered)

## P-13 · 流程的最后一环没有产出物：前面每一步都有脚本，最后一步只有一个动词

- **症状**：逐环检查时每一环的产物都在，读起来像「链是通的」；而某一环**从来没有任何产物**
  ——没有脚本、没有命令、没有检查项，只有一句散文。它的缺席在每一步的读数里都不可见，
  因为**每一步都只报自己的产出**。本例：产物（`packaging/release/` + 仓库外归档 + `uchg`）、
  入库清单（`release/<版本>.sha256`）、tag（`v<版本>`）、代码推送（origin + codeup）四环齐备，
  第五环「送到客户拿得到的地方」从来没有过——`gh release list` 最新是 v2.0.0，而仓库根
  `README.md` 正写着「从 Releases 下载」，**客户按文档操作拿到的是早三个版本的包**；
  同一批的四个版本（2.0.1 / 2.2.0 / 2.3.0 / 2.3.1）从未在任何公开分发面出现过，实际渠道是 IM。
- **根因类**：判据是按**环节**写的，而缺口在**环节之间**。有产物的环节会把自己报绿，
  于是「绿 × 绿 × 绿 × 绿」被读成「链是通的」——四个绿各自只覆盖自己那一段，
  没有一个覆盖「上一环的产物有没有被交出去」。判据还天然只看得见仓库**内部**的状态，
  而这一环的失败发生在仓库**之外**（客户拿不拿得到），所以它既不在门禁射程里，
  也不在任何一篇 Note 的「后果」里。同族：P-04（那条是**代码**写了没被跑到，这条是
  这个环节**从来没有代码**）、P-08（用纪律守只有机制能守住的东西）、P-02（假绿）。
- **已落地机制**：`gate:release-published`（射程 = **既有** `release/<版本>.sha256`、**又有**
  `v<版本>` tag 的版本，逐个核对 GitHub Releases 上是否存在且**非 draft**；`gh` 不可用或未认证时报
  `skip` 而不是 `ok`）、`gate:release-published-scope-selftest`（9 条反向自测：修复前的真实形状
  必须报四个 missing、draft 不算已发布、只有清单没有 tag（2.3.2）与只有 tag 没有清单（2.0.1）
  都必须出局且不得变成永久红、射程为空必须报空）、`script:scripts/gates/release-publish-scope.mjs`
  （纯函数判据），以及 `docs/sop/dmg-release.md` §6 把「发布到 GitHub Releases」从一句散文
  变成带命令与 `--latest=false` 规则的编号步骤。
- **下一版默认动作**：给流水线的每一环都问一句「这一环的**产物**是什么、**谁能读它**」。
  凡只能用散文描述的环节（「上传」「登记」「通知某人」），就是缺口所在——把它变成
  **一条命令 + 一个能读它的判据**。特别地：判据要能看见**仓库之外**的那一半
  （客户拿不拿得到），而不是只核对仓库内部的自洽。
- **详见**：[ADR-0076](adr/ADR-0076.md)

## P-14 · 描述「产物形态」的文档断言没有与产物绑定

- **症状**：文档写着「挂载后应看到 X 与 Y」，而产物里是 Z。**复核者读出来的结论是「产物坏了」，
  不是「文档旧了」**——失败方向是反的：一条过期的断言会让人去修一个没坏的东西，
  或者让客户去找一个不存在的东西。2026-09-13 实测：SOP §5「终验」三处同时如此——
  §5.1 让 `codesign` 去签一个不存在的路径（那个目录下只有 DMG 与三件清单），
  §5.2 断言卷根有 `DSH Desktop.app` 与 `Applications` 快捷方式（实物是
  `DSH Desktop.app.tar.gz` + `install.sh` + `LUTE Setup.app` + 四个 tarball），
  §5.4 教用户「把 DMG 里的 app 拖到 `/Applications`」。
- **根因类**：形态是**产物**的属性，却被按**文档**的属性维护。这类句子有两个特征让它特别难自查：

## P-15 · 把「写进磁盘」当成「已经生效」：运行中的实例有自己的字节

- **症状**：源码改了、构建产物核对了、装载点推了、逐字节比对一致——**屏幕上毫无变化**，
  而所有仪器都是绿的。2026-09-13 实测：修完侧边栏两处缺陷后刷新页面，AX 几何读数与刷新前
  **逐位相同**（技能中心标签 x=163 仍居中、两个注入行 y 仍是 233/271）。三个问题叠在一起：
  ①**刷新在原理上就不是生效路径**——`@deepseek-ai/dsh-client-modules` 在激活时把每个包的
  `client.js` 读成**不可变字节**，`compose()` 预先算好 `URL -> body` 的 Map 供 HTTP 直吐，
  改写内存的唯一入口是 `rebuilt(id)`；而 `dsh-client-hmr` 的 production guard
  （`process.defaultApp !== true && process.env.DSH_DEV !== "1"`）在打包应用里**只推进 mtime/size
  基线然后 return**，源码注释即「下一次完整重启才会从新字节重新组合」——**它连变更信号都吞掉了**，
  这个文件此后再改也不会被注意到。②`sync-profile.mjs --check --loadpoint` 与
  ③门禁 `profile-bundle-sync` 有同一个 bug：把 `file:` spec 里的相对路径拿去对 **cwd** 做
  `existsSync`，而 `file:` 的基准是**声明它的 package.json 所在目录**（profile）。
  实测 23 个 `file:` 依赖**全部**在此被 `continue`，门禁实际对比 **0** 个、恒绿；
  从 profile 目录跑则退化为比「profile 的 vendor 副本 <-> node_modules」，两份都旧也互相相等。
  **而这条门禁的 remediation 原文就是「否则应用重启后仍跑旧字节」——它存在的唯一理由
  正是拦住此刻这件事。**
- **根因类**：**「产物被写进磁盘」与「运行中的实例在用这份产物」是两个事实**，
  而默认把前者当成了后者的证据。这类故障的形状特别难自查：**磁盘侧的证据链是完整且真实的**
  （字节确实一致、mtime 确实是新的），错的只是「所以它已经生效了」这一步推论；
  更坏的是**负责拦住它的那条仪器自己也空射程**——它用了一个基准错误的路径去枚举对象，
  枚举为空时既不报错也不出声，于是「一个都没比」与「逐字节全一致」在读数上完全同形（P-02）。
  与 P-02 相邻但不同：P-02 说的是仪器说谎，本条说的是**「生效」这个概念本身没有判据**——
  即使仪器全修好，它量到的也只是磁盘 <-> 磁盘，**没有任何静态判据能回答「跑着的那个进程读的是不是它」**。
  与 P-06（把平台行为当常量）相邻：这条不是假设错了，而是**假设从来没被当成需要验证的东西**。
- **已落地机制**：`gate:profile-bundle-sync`（射程 0/23 -> **23/23**，读数常显分母

  `ok` 行常显 `（对比 N 个包）`，空射程报 `warn` 并以退出码 1 结束）
- **下一版默认动作**：改**客户端 bundle** 之后，生效路径只有一条，照它走完再验收——
  **改 -> 构建 -> `node scripts/sync-profile.mjs --apply --loadpoint` -> 重启应用 -> 看几何读数**；
  **不要**把「刷新页面」当验收动作（在打包应用里它连原理上都不是）。
  验收要挑**可见的**读数（AX 几何、截图），因为那是唯一能区分「磁盘对了」与「真的生效了」的证据。
  写完任何「已经同步 / 已经生效」的结论前，先问一句：**这条仪器这次到底量了几个对象？**
  读数为 0 的仪器必须自己喊出来——空射程在读数上不能长得像全绿。

## P-16 · 格式层的不变量没有读者：值往返正常，只有字节比对看得见

- **症状**：一个「点两下开关 = 磁盘上什么都没变」的承诺，在一部分文件上**每一张都失效**，
  而系统里没有任何一处报错。用户点开再点回去，文件里两个键**被挪到了别的位置**——
  值一个没错、键一个没少，页面读回来状态完全正确。发现它的唯一途径是一次**全量字节比对**，
  而那次比对的读数是 `expected [ Array(145) ] to deeply equal []`，看起来更像「测试写死了
  一个过期数量」，于是最省事的读法是把它归给「语料漂移」——**而它说的是真的**。
- **根因类**：**不变量住在格式层，而格式层没有读者**。键序、行序、引号风格、行尾这类东西
  不进任何解析结果（解析出来的是一张 `Map`），所以「值正确往返」与「字节没被动过」是
  **两个事实**，而前者被当成了后者的证据。第二层：侵入性的重写逻辑总是**照着写它时看得见的
  那种形状**写的——「已有的键替换掉、再追加到末尾」在「键本来就在末尾」的文件上完全正确，
  而那正是同一个仓库里的组装器产出的形状；第二种形状由**另一个写入者**（上游追加的字段）
  造成，它出现得晚，且出现的只是位置不同。第三层：唯一能看见它的那条判据是**按语料**验证的，
  而在没有语料的机器上它会**跳过**，于是 CI 与全新检出上这道守卫等于不存在。
  同族前科：P-02（假绿）、P-11（判据的射程没有定义——那条是**对象**射程，本条是**输入形状**射程）、
  P-14（描述产物形态的断言没有与产物绑定）。
- **已落地机制**：`script:packages/surfaces/dsh-algo-skills-local/tests/frontmatter.spec.ts`
  （三条**纯函数**用例钉住输入形状：键在块中间、重复键收敛到最后一次出现的那个槽位、
  只缺一个键——不依赖本机语料，因此 CI 与全新检出上同样有效）、
  `script:packages/surfaces/dsh-algo-skills-local/tests/corpus-write.spec.ts`
  （全量已装卡的字节比对，射程动态枚举 `p2s-*` 目录并**常显它实际量了几张**）
- **下一版默认动作**：写任何「重写文件但其余字节不动」的东西时，先问三句——
  ① **这个不变量谁在读？**如果答案是没有读者（键序、行序、引号、行尾），那它唯一的判据
     就是**字节比对**，别指望别的环节替你发现。
  ② **我照的是哪一种形状？**手上的样本只是语料的一**种**方言；去数一遍**全部**方言
     （本例实测：开关在中间 145 张／在末尾 0 张／无该字段 1245 张——现实只有一种，
     而它**不是**代码假设的那一种）。计数本身就是判据，`grep` 一次比读十个文件强。
  ③ **守它的那条判据在别人的机器上跑不跑？**按语料/按本机状态验证的判据，要在同一份提交里
     配一条**不依赖环境**的最小输入用例，否则它只在作者这一台机器上存在。
  另：读数形如 `expected [ Array(N) ] to deeply equal []` 时，先确认 N **是不是断言射程全长**——
  是的话它说的是「射程内每一条都中」，那就不是数量写错，是真缺陷。

## P-17 · 三态读数在聚合处被压回两态：退出码分不清「都核对了」与「有一项没核对」

- **症状**：同一次门禁运行的终态里有**两个互相矛盾的事实**，而汇报层只剩一个。实测：
  发布 2.4.0 的那次 `pnpm run gate:full` 打印 `ok 54/55 项通过（mode=full，跳过 1）`、
  退出码 0，而同一份输出里 `release-published` 那一行写的是「gh release list 读不到……
  本项**未核对任何版本**（不是「都发了」）」。逐项是诚实的，汇总在说谎——而项目常驻规则
  写着的正是「退出码即契约」，于是**规则本身在教人读那个有损投影**：只看退出码的人会把
  「发布面从未被核对」读成「发布面合格」，接着把这条读数写进发布结论。
- **根因类**：`skip` 这个第三态在**单项层**已经存在，却没有在**聚合层**存在。
  单项仪器是诚实的（ADR-0075 要求 `skip` 与 `ok` 在读数上分开、`note` 必须渲染、
  跳过不计入通过数），但退出码与汇总行是**另一处**读数，它对逐项状态做**有损投影**：
  `skipped` 既不在分子里、也不改变退出码，于是「射程为空 / 环境读不到」与「逐项全过」
  在契约面同形。第二层：聚合处丢掉的还有 skip 的**含义**——「本项在这一版不适用」（设计）
  与「本该核对而没核对」（缺口）在读数上不可区分，而二者的正确处置相反。第三层：
  这次 skip 的直接成因是**作业环境没导出代理**，即缺口的成因住在**调用方**，而判据住在
  被测对象里——判据无法把它自己「没跑成」与「跑了且合格」分开报给调用方。同族前科：
  P-02（仪器假绿——那条修在**单项**层，本条是同一根因在**聚合**层复发，而 P-02 的
  「下一版默认动作」已经写明「读不到时必须是失败或显式的跳过」——显式跳过已落地，
  剩下的那半句「不是通过」在聚合层从未成立）、P-11（判据的射程没有定义）。
- **已落地机制**：`gate:release-published`（**单项侧已诚实**：读不到 `gh` 时报 skip 而非 ok、
  `note` 明写「未核对任何版本」、且不计入通过数）、`gate:release-published-scope-selftest`、
  `gate:pitfalls-playbook`（本账自身）。**诚实划界：拦住聚合层的那一步尚未落地**——
  只有 skip 时退出码仍为 0，`scripts/gate.mjs` 里没有 `--strict` 或「跳过即失败」之类开关；
  本次的处置是**先记账、不改门禁**，所以这一条目前只被本账记着，**没有任何机器拦着它**。
- **下一版默认动作**：在这个环境跑发布链门禁**之前**先证实代理真的通
  （`curl -s -o /dev/null -w '%{http_code}' https://api.github.com/rate_limit` 必须返回 200；
  不是 200 就是**未核对**，不是「都合格」），跑完**读单项行、不读退出码**，
  写「已核对」结论时引用逐项输出而不是 `RC=0`。要把这条机器化，最小改动是两处：
  ① 汇总行在 `skipped > 0` 时显式写成「N 项未核对」——现在的 `跳过 N` 混在
     「通过」那句话里，读起来仍像通过；
  ② 给 `gate.mjs` 一个能让 skip 判非 0 的开关，供发布前那一次运行使用（日常开发保留
     skip 的宽容语义，否则断网环境下门禁不可用）。
  两处**尚未落地**，下次同族复发前做掉。

## P-18 · 判据的输入事实住在被判对象之外，且那份事实会消失

- **症状**：产物里有一条**在本机成立、在客户机不成立**的引用（预设行、依赖、路径），

  它如实报告「没有发现外部产品」，因为它要的那个事实已经不存在了。
- **根因类**：判据写成**反向特征**（先在**本机**找出「什么属于本机装配」，再拿这份名单去产物里删），
  而不是**正向闭合**（产物里的每一条引用，能不能在**产物自己的**解析面里解析出来）。

  第三层：出货源就是开发机的运行时目录，本机装配与出货面共用一份文件，

- **下一版默认动作**：写任何「出货前必须成立」的判据时，先问它的**输入住在哪里**：

  下一次清理、换一台机器之后**悄悄失明**，判据会继续报绿。把它换成产物自己的性质

## P-19 · 判据量的是「过程有没有报错」，而坏的是产物

- **症状**：脚本退出码 0、stderr 干净、文件也生成了，**产物本身是坏的**。所有仪器全绿。

## P-21 · 判据把「环境事实」与「数据缺陷」报成同一句话

- **症状**：一条判据恒红，红了很久没人管——因为它报的原因是错的，人无法从读数决定该修谁。
  实测（2026-09-15）：`verify-fullstack.mjs` 断言
  `~/.dsh/.agent-presets/ai-product-developer/skills/{tdd,to-spec,grill-me}` 存在，
  报的是「**预设副本丢失**」；真相是那个 preset 组在 v3 重组时已从本机移出
  （现存只有 `agt-001..050` + `bobo-cto` + `lute-cordis`）。
  「预设不在本机」是**环境事实**，「副本被动了」是**数据缺陷**——同一句话把两者说成一样，
  于是这条红既不能驱动「重新安装 preset」，也不能驱动「去查谁改了数据」。
  它还有一处同族毛病：期望条数硬编码为 3，于是「少了一条」与「改过清单」也分不出来。
- **同族第二例（同一天，出在 P-21 的修法自己身上）**：`manifest/generic-skills.json` 派生自
  `staging/intake-localize.json`，而 `staging/` 按 `.gitignore:44` **不入库**——干净 clone 上
  没有派生源。两个 verifier 都把派生器 `--check` 的**任何**非零报成「清单与派生源不一致」：
  前者的修法是「本项无射程」，后者是「重建清单」，又一次共用一句话。
  修法把非零**分成了两态**：派生器 `--check` 遇「源不在本机」退出码 **2**（并打印跳过了什么），
  「与磁盘不一致」仍是 **1**；两个 verifier 各认一个 `status === 2` 分支。
- **根因类**：判据的输出是**给人做决定用的**，而「红」本身不带信息。当一条判据的失败在
  两种完全不同的前提下都会出现，它的红就退化成一个没有指向的信号。恒红的判据与恒绿的判据
  一样没有信息量——**人只会学会绕过它**，而绕过之后连它原本能守的那点东西也一起没了。
  这是 P-11（射程没有定义）的近亲：P-11 说的是时间射程，这里说的是**前提射程**。
- **已落地机制**：`gate:skill-lines`（三个验证器的射程前提统一为「本机有没有
  `~/.dsh/skills` 与 `~/.dsh/.agent-presets`」；两者都不在 → **跳过并写明跳过了什么**，
  不假绿也不假红，与 `patch-anchors` / `theme-tokens` 同一语义）、
  `script:packages/capabilities/dsh-overseas-skills/scripts/verify-fullstack.mjs`
  （目录不在 → 跳过并说明；目录在 → 逐条核对，且期望条数改从 `presets/preset-skills.json` 读）、
  `spec:packages/capabilities/dsh-overseas-skills/test/generic-manifest-skip.spec.mjs`
  （G1–G4 把「退出码 2 = 源不在本机」这条契约钉住：源不在 → 2 且打印跳过；源在而不一致/坏掉
  → 必须是 1，**不许退化成跳过**；G4 反向盯着两个 consumer 的 `=== 2` 分支还在不在。
  已做突变自测：把 `exit(2)` 改成 `exit(1)`，G1 立刻红）。
- **下一版默认动作**：写判据时先问一句「**它红了以后，人能不能只看输出就知道该改哪边？**」
  不能，就说明这条判据把两种前提说成了一句话，必须先把前提分开：
  ① 环境前提不在（目录没装、应用没装、平台版本不对）→ **跳过**，并在读数里写清跳过了什么；
  ② 环境在而数据不对 → 红。
  另外，任何**硬编码的期望条数**都要改从事实源读：硬编码让「少了一条」与「改过清单」
  无法区分，而这两种情况要修的地方完全不同。
- **详见**：`packages/capabilities/dsh-overseas-skills/docs/maintenance-sop.md` §12.12

## P-33 · try 里 return promise 不 await：拒绝逃出 catch，变成「永远没有响应」

- **症状**：请求进了处理器、日志里能看到它开始执行，**却永远没有响应**——客户端挂到超时、
  连接不关，同时冒出一个未处理拒绝。而错误处理代码整段都在、读起来完全正常。
  2026-09-16 实测：`dsh-team-hub` 的 admin 控制台、RPC、代理三条主通路全部如此，
  任何异常都退化成「静默悬挂」而不是 500；做 SEC-RT-005 时被自己的测试逼出来
  （代理面超限用例拿不到任何响应，插桩显示请求已进入处理器、`readBoundedBody` 也已正确拒绝，
  于是问题不在新代码而在错误传播路径）。
- **根因类**：`async` 函数 `try` 块里 `return f()` 与 `return await f()` 语义不同——
  前者把 promise **交出去**，此时 `catch` 已经退出，拒绝不再经过它；后者在 `try` 内结算。
  这是**看起来对、读起来也对**的写法缺陷，静态眼检几乎不可能发现；而它的表现（悬挂）
  与「网络慢」「客户端问题」同形，很容易被归因到别处。与本账 P-04 的合体形态：
  错误处理**写了**，却在真实路径上从没跑到。
- **已落地机制**：`script:packages/infra/dsh-team-hub/test/bounded-body.test.mjs`
  （三条真实用例分别守三条通路：代理面异常必须回 500、admin 面异常必须回 500、
  代理面超限必须回 413；**变异自测 3/3 判红**——把三处 `return await` 分别改回 `return`，
  对应用例全部失败，证明它们不是恒真的）、
  同一脚本内的失败模式硬化（`request()` 自带 5s 超时、`server.closeAllConnections()`）：
  缺这两条时「少一个 await」的失败表现是整个测试文件**挂住**而不是判红，
  仪器本身会假绿——同一根因在测试侧再犯一次。
- **下一版默认动作**：`try` 块里返回 promise 一律写 `return await`。写错误处理路径的用例时，
  先注入变异确认它会响，再相信它——**没响过的判据等于没有判据**。
  断言「有响应」的用例必须自带超时，否则被测缺陷会让测试挂住而非判红，把它伪装成「环境慢」。
  另外，一处修复配一条判据：本批三处修复最初只写了「代理面超限」一条，而那条走的是
  `handleApiPost`，**根本没在守 `proxyRequest`**——判据数与修复数相等不代表覆盖面相等，
  要靠逐条变异来验。

  `TMPDIR`，两天内累积 **2,066** 个残留根、**35 MB**——而没有任何一份报告提过它们。三个来源各自
  「看起来没问题」：一个每用例 `mkdtempSync` 且从不清理，一个同样只建不清，一个有 `test.after(() =>
  rmSync(...))`——而 `test.after` 只在正常跑完时执行。
- **根因类**：「回收代码存在」被当成「回收真的发生」。`finally` 与 `test.after` 的覆盖面止于
  **进程正常走到那里**；信号、超时、kill 三条路径上它们一次都不跑，而这三条恰好是 CI 里最常见的
  结束方式。与本账 P-31 同族（把「最终看起来恢复了」当成 ownership），但更隐蔽：P-31 至少还有一个
  写回动作，这里连动作都没执行，因此**执行痕迹只留在文件系统上**，而门禁看的全是它自己的读数。
  叠加一层 P-02：门禁跑前跑后都是同一份脏工作树，「没看」与「看过且干净」在读数上同形。
- **已落地机制**：`gate:mutation-fixture-selftest`（真子进程 SIGTERM/SIGINT 用例：自有根必须被回收，
  且退出方式必须仍是**信号死亡**而不是被改写成正常退出）、
  `script:scripts/lib/mutation-fixture.mjs`（live 根注册表 + `process.on('exit')` + `SIGINT`/`SIGTERM`/`SIGHUP`
  先回收再以默认处置重发；`mutationRoot()` 是给「只想要一个不会泄漏的临时根」的窄接口）、
  `script:scripts/lib/repo-snapshot.mjs`（before/after 快照：tracked/untracked 内容哈希、声明根名录、
  未声明 ignored 区域、HEAD/refs/index 字节；空射程与目录折叠一律判红）、
  `gate:repo-attest-selftest` 与 `script:scripts/lib/repo-attest.test.mjs`（六条结束路径逐条见证）、
  `gate:gate-concurrency-selftest`（10 轮 × 2 条完整 gate 并发，仓库零差异 + lane 读数不得分裂）。
- **下一版默认动作**：给临时资源写回收时，先问「进程被 kill 时谁收」——只写 `finally` 等于没写。
  凡「某某没被改动」这类断言，先立一份可复算的 before/after 快照契约再断言，不要用「跑两遍 `git status`
  看起来一样」代替。数的对象要**真的去数**（`ls -d $TMPDIR/prefix-* | wc -l`），不要凭印象说「应该没有残留」。
- **详见**：[ADR-0103](adr/ADR-0103.md)、
  [Note](notes/implemented/contract/2026-09-17-self-attestation-and-process-reaping.md)

## P-35 · 管道把退出码换成了末端命令的：判红被写成判绿

- **症状**：CI 上 workflow 显示**全绿**，而同一份 artifact 里的门禁 JSON 写着
  `"status": "fail", "failed": 6`。2026-09-17 实测：`gate (quick)` 与 `gate (full)` 两个 job 都是
  success，`pnpm`/下载 artifact 全部正常，只有人去看 JSON 才会发现六个检查失败。
- **根因类**：`cmd | tee out.json` 的退出码来自 `tee`（永远 0），被测命令的退出码**在管道里被丢掉**。
  这与 P-02（仪器假绿）同族但形状不同：P-02 是判据**没看**，这里是判据**看了、判红了，
  而它的返回值在进程组合的某一层被替换掉**。危险在于它比 `|| true` 隐蔽得多——`|| true` 一眼可疑，
  而 `| tee` 是"为了留下证据"这个**正确动机**带来的副作用。本仓库的整个门禁哲学（退出码即契约）
  因此在这条管道上失效。
- **已落地机制**：`gate:ci-workflow-contract`（判据 `MASKED_PIPE_PATTERN`：管道末端是
  `tee`/`cat`/`head`/`tail`/`grep`/`sort`/`uniq` 且该步骤的 `run` 里没有 `set -o pipefail` 即判红；
  变异 22 与一条「基线里每个含管道的步骤都必须真有 pipefail」的反向断言守着它）、
  `script:.github/workflows/gate.yml`（四个含管道的步骤都先 `set -o pipefail`）、
  `gate:ci-workflow-contract-selftest`（29 条反向自测）。
- **下一版默认动作**：写 CI 步骤时，只要命令进管道，先写 `set -o pipefail`；能不用管道就不用
  （`> file` 重定向不会丢退出码）。审别人的 workflow 时，**不要看 GitHub 的绿勾判断门禁是否通过**——
  打开 artifact 读 JSON 里的 `status`，绿勾只说明"步骤没非零退出"，那正是本条要说的事。
- **详见**：[ADR-0105](adr/ADR-0105.md)、
  [Note](notes/implemented/contract/2026-09-17-ci-workflow-contract-and-clean-runner-simulation.md)

## P-36 · 判据读错端点，把「保护在」判成「保护不在」

- **症状**：保护面审计报「API 里没有任何 ruleset 覆盖 `refs/heads/main`」，
  而此刻**保护已经生效**——同一次会话里 `DELETE /git/refs/tags/v2.4.1` 正被服务端 422 拒绝。
  2026-09-17 实测：`GET /repos/{r}/rulesets`（列表端点）**刻意只返回摘要**
  （`_links/created_at/enforcement/id/name/node_id/source/source_type/target/updated_at`），
  **不带 `conditions` 也不带 `rules`**；拿列表去逐条比对规则，每一条都必然「不存在」。
- **根因类**：判据的输入端与它以为的输入端不是同一个东西。这是 P-02 的**镜像**——P-02 是假绿，
  本条是假红；而假红有自己的危害：它让人去"修"一个不存在的问题，或更糟，让人开始不信判据
  （一旦某条判据被证明会假红，它下一次真红也会被当成噪声）。根子在于**读一个 API 之前没有确认
  它返回的字段集**：端点名对了、HTTP 200 了、JSON 也能解析，唯独少读了两个字段，而缺字段与
  「字段为空」在比对逻辑里长得一样。
- **已落地机制**：`gate:ruleset-audit`（先 `GET /rulesets` 列 id，再逐条 `GET /rulesets/{id}` 取详情；
  退出码 0/1/2 = 全等 / 不符 / **拿不到读数**，第三种必须与前两种分开）、
  `gate:ruleset-declaration-selftest` 与 `script:scripts/gates/ruleset-audit.test.mjs`
  （15 条反向自测，其中一条专门用**真实摘要形状**做负例：判据必须判红，而不是判成「保护不在」）、
  `script:scripts/gates/fixtures/rulesets-live.json`（基线取自真实 API 读数而非手写样本）。
- **下一版默认动作**：读一个 API 之前，先把它**实际返回的字段集**打出来对一遍（`gh api … --jq 'keys'`），
  不要凭 schema 记忆。凡是"某东西不存在"的结论，先问一句：**找不到，是因为它真的没有，
  还是因为我查的地方本来就不放它？** 拿到「不存在」时，用法一次**已知存在**的同类对象做对照实验。
- **详见**：[ADR-0106](adr/ADR-0106.md)、
  [Note](notes/implemented/contract/2026-09-17-branch-and-tag-protection.md)

## P-37 · 射程里的一个特殊对象让整批判据停下来：悬空软链与 `git hash-object`

- **症状**：门禁的并发见证项整条抛错退出——`RepoSnapshotError: git hash-object 失败`，
  栈里没有路径、没有哪个文件、没有说为什么。2026-09-17 实测：checkout 里有一个悬空软链
  `packaging/backup/pre-2.0.10-migration/DSH Desktop.app/…/Electron Framework.framework/Helpers
  -> Versions/Current/Helpers`，git 对它的回答是
  `fatal: could not open '…/Helpers' for reading: No such file or directory`，
  而 `<stdin-paths>` 模式**在第一个坏路径上就停**，于是整批 256 个路径一起丢。
- **根因类**：把「射程里的每一个对象都是普通文件」当成了前提。软链是一种**不同类型**的对象，
  而判据按「内容哈希」这一个维度处理它：`lstatSync` 对悬空软链**是成功的**（链接本身存在），
  所以它顺着存在性检查一路走到了 `git hash-object` 才炸——失败点与缺陷点隔了两层，
  错误信息里除了 git 的原文什么都没有。叠加一层 P-13（隔着解释器写字面量）的变体：
  真正的判据（`git`）在另一个进程里，它的失败被包成一句自己的错误，现场就丢了。
  更隐蔽的是它**依赖机器状态**：干净检出上没有软链，所有自测全绿；一旦有人在 checkout 里
  放了个软链（哪怕是打包备份），门禁才开始红。
- **已落地机制**：`script:scripts/lib/repo-snapshot.mjs`（untracked 射程先分拣：符号链接走
  `readlinkSync` 记目标字符串、普通文件才交给 `git hash-object`；悬空与有效软链都能读，
  且「目标 A → 目标 B」与「有效 → 悬空」都是可见变化）、
  `script:scripts/lib/repo-snapshot.test.mjs`（新增回归用例：仓库里同时放悬空软链与有效软链，
  必须各自成条目、digest 互不相同、连拍两次逐字相同、目标一变必须点名判红）、
  `gate:repo-snapshot-selftest`。
- **下一版默认动作**：给一批对象做内容哈希（或任何批量外部命令）时，先问一句：**这批东西里
  有没有不是普通文件的对象？**（软链、FIFO、socket、设备节点）。批量命令在第一个坏输入上
  停下来的行为很常见，所以「一个坏输入」要按**整批失败**来设计错误信息——把路径与原因带出来，
  不要只留一句"命令失败"。写完记得用**含该特殊对象的真实形状**跑一遍，不要只用干净夹具。
- **详见**：[ADR-0102](adr/ADR-0102.md)、
  [Note](notes/implemented/contract/2026-09-17-self-attestation-and-process-reaping.md)
