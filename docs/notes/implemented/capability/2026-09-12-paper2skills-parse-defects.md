# p2s `parses=False` 的 20 张：拆成「源码写坏 5」与「判据未定终点 15」

- 日期：2026-09-12
- 类别：capability / dsh-paper2skills
- ADR：[ADR-0051](../../../adr/ADR-0051.md)
- 上一入口：[ADR-0050](../../../adr/ADR-0050.md) 收尾提的「那 20 张源码本身写坏的卡」

## Problem

ADR-0049 / ADR-0050 两轮收尾都停在同一句：**1,317 张已恢复，其中 20 张 `ast.parse` 不过**，
并把它归成「源码本身写坏（全角 `（`、`：`）」，据此提了下一入口：
「失败集中在全角标点，很像一次批量的中文化替换误伤了代码」。

这个归因把三件事混成了一件事：

1. `parses` 只回答「这段能不能跑」，**不回答「这段是不是实现」**；
2. 20 张里有多少是抽取判据的问题、多少是语料的问题，从没分开量过；
3. 「全角标点」是从报错信息里读出来的，从没在全语料上验过。

于是每次收尾都重新数一遍 20，数完还是不知道要不要修、修哪边。

## Decision

### 一、用一把与 oracle 无关的结构尺子分类

尺子是：**被选中的那个围栏之后，还剩几个围栏边界**（`after`）。

- `after <= 1`（只剩收栏）→ 正文终点**唯一确定**，取到多少就是全部；解析失败只能来自源码本身。
- `after > 1` → 终点不唯一，恢复区可能一路吃到卡正文。

实测 20 张：`after <= 1` 的**恰好是 5 张 oracle**，`after > 1` 的**恰好是 15 张 unverified**，
零例外。补一把独立尺子（恢复区末行是不是散文行）：18/20 末行是散文
（`## ④ 技能关联`、`**组合效果**：`、`<CAMEL_TASK_DONE>`…），全部在 `after > 1` 侧。

| 分类 | 张数 | 含义 | 取到的正文 |
| --- | ---: | --- | --- |
| `UNLABELED` | 5 | 卡里源码写坏，终点唯一 | 是实现，但跑不起来 |
| `WINDOW_TRUNCATED` | 15 | 无 oracle 时终点不唯一，吞了卡正文 | **不是实现** |

### 二、5 张源码缺陷逐卡定位到行

| 卡 | 行 | 病 | 复现要点 |
| --- | ---: | --- | --- |
| `Skill-CodeXEmbed-Code-Semantic-Embedding` | 208 | 嵌套三引号 | 第 204 行 `"code": """` 开串，串体 docstring 又写三引号；Python 的串**不嵌套**，外层落在内层**开引号**上，剩下的裸标识符触发 `SyntaxError` |
| `Skill-Model-Performance-Monitor` | 62 | 控制字符 | `health_` 后跟 `U+0001` |
| `Skill-RFM-Segment-Campaign-Dispatcher` | 170 | 括号种类不匹配 | 第 168 行开 `(`，第 170 行 `}` 收 |
| `Skill-Real-Time-Competitive-Repricing` | 58 | 三引号未收尾 | 开串到文件末尾 |
| `Skill-TimeCMA-LLM-Forecasting` | 1 | 模块名非法 | `from paper2skills-code.03-时间序列…`，连字符不在标识符字符集里 |

五种形态、五种成因。**没有一条来自「批量替换标点」。**

### 三、把「全角标点误伤代码」这条假设证伪

| 事实 | 读数 |
| --- | --- |
| 全角 `（` 出现在恢复区 | **1,110 张** / 9,768 次 |
| 其中正常 `ast.parse` | **1,091 张**（都在字符串与注释里，合法） |
| 全角 `：` | 1,037 张中出现，1,018 张能过 |
| `U+0001` | 全语料 2 处，另一处 `Skill-New-Product-Opportunity-Mining` **能 parse** |
| 含连字符模块名的 import | 全语料 **5,355 条 import 里 1 条** |

所以既没有批量污染，也没有批量可修。

### 四、卡里实现 ≠ 仓里实现文件（顺手钉死）

拿 vault 仓 git 历史的 `paper2skills-code/**/*.py`（**1,288 个**，工作区只剩 199 个）
当外部真值逐卡做行签名覆盖率：

- 20 张里 **1 张**（`Skill-Model-Performance-Monitor`，0.989）确实来自真源文件；
- 其余 **19 张**卡内实现不在真源码树里（最高 ≤0.10）。
- 全语料 1,317 张里覆盖率 >0.25 的只有 **18 张**。

「坏的是卡里那段，仓里那份是好的」由此有了独立参照；同时「去仓里取完整实现」这条路也断了。

## Alternatives considered

- **按语法把 15 张的正文截到最后一个完整语句当实现交付。**
  编造边界。反证本身就是那 5 张 oracle：`longest_parseable` 给出的「最长可 parse 前缀」
  是 199 / 61 / 164 / 56 / 0 行，与残缺位置无关（199 行是测试块起点，不是缺陷点）。
- **给 `unverified` 的降级路径加 `ast.parse` 门槛，让它自己认输。**
  ADR-0050 已实测否掉：`## ④ 技能关联`、`### 前置技能` 都是合法 Python **注释**，
  15 张因此把整段正文当成了实现。无 oracle 时语法尺子不够用。
- **只写文档不改索引字段。** 那就还是每轮重新数 20。文档会漂、字段不会：
  `--check` 与单测都盯着它。
- **就地修好这 5 张。** 修的是**语料**不是本包；本包只读 vault 的 git 历史，
  改工作区既不入交付，也会与 `sha256` 口径打架。

## Consequences

- `data/code-recovery.json`：`parses=false` 的卡多三个字段
  `defect` / `defect_line` / `defect_detail`；`stats` 多一项 `defects`。
  其余一切**逐卡不变**：落盘 1,317 张、259,365 行、可解析 1,297、`sha256` 全部未动，
  也没有任何卡改变分层（那 15 张本来就是 `unverified`）。
- `--check` 把四个新字段纳入对账；单测 77 → **81**；`--selftest` 5 组 → **36 条断言**。
- README 的归因就地订正，并把 5 张缺陷逐张列成表。
- 5 张缺陷**留在语料侧**，属语料自身的债；本包对 vault 仍只读。

## 取证

可信度三档，逐条落在 `.scratch/p2s-parse-audit/`：

1. **可复算**：`recon1.py`（1,338 张围栏落单/散文命中）、`recon2.py`（四把尺子）、
   `recon3.py` + `canonical.pkl`（1,288 个真源文件）、`probe-defects.py`（逐卡缺陷定位）。
   全部只读，产物 `recon*.json` / `probe-defects.json`。
2. **可复现的红测**：把 `defect_of()` 里的嵌套三引号分支拆掉 → `--selftest` 以
   **2 条断言失败、exit 1**（干净报错，非崩溃）；单测里 4 条新断言里 2 条**逐张点名**
   锁定 5 张的行号与原因文案。
3. **只能人工确认的**：⑪ 里 `longest_parseable` 在 5 张 oracle 上的输出（199/61/164/56/0）
   是「不能用前缀法」这条结论的**唯一**依据，已把数字写进 ADR 备查。
