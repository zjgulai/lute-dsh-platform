# 把 1338 张论文技能卡装成岗位技能库：分类维度必须与岗位矩阵同构（ADR-0031）

> 决策记录（ADR-0015 的 Note 侧）。决定本身见 [ADR-0031](../../../adr/ADR-0031.md)。

## Problem

用户要求：把 paper2skills 语料的技能卡「全部安装」，并且**技能分类要严格匹配岗位矩阵的 4 面 /
8 责任域**，后续还要按这个三级结构做技能的分类管理；同时给了三个前提——权威源是本地
`/Users/lute/project/paper_to_skills/`（不再访问 iCloud）、L3 用岗位的「材料业务技能」名、全量 1338 张。

三个前提里，第一个当场就不成立，第二个引出一条判据错误，第三个引出两个必须实测才能定的问题。
这篇 Note 记录的是**取证过程与两次判据纠错**，因为这两次纠错才是这次工作真正的产出。

### 取证一：所谓「已下载完成」的语料只有 11.5%

先数，不猜：

| 位置 | `Skill-*.md` | 文件总数 |
| --- | ---: | ---: |
| 本地 `/Users/lute/project/paper_to_skills/`（用户说已完成） | **156**（130 唯一） | 2,008 |
| iCloud 同名项目工作树 | 1,356 | 78,253 |

本地缺 10 个整域（`17-价格优化` … `25-搜索流量工程`），也没有 `playbook/`。逐域对比更刺眼：
`04-供应链` 本地 5 张 / iCloud 130 张，`08-知识图谱` 本地 9 张 / iCloud 114 张。

再查 iCloud 侧能不能补：工作树里 1,356 个 `.md` **全部是加密态**（共享魔数 `887d1c8bcd0aa302`），
`head -c 32` 出来是二进制；git HEAD 只跟踪 185 个 vault `.md`（其中 149 张卡），覆盖不到
`17-价格优化` 之后的域。**两条路都断了。**

但 iCloud 的 `playbook/`（构建于 2026-07-20 的静态站）是干净的：1,339 个卡页 HTML、抽样 400 个
零加密、`build-report.json` 写着 `skill_pages: 1338, domains: 25, edges: 16371`。而且卡页结构比
`.md` 更完整——八段正文（①问题 ②算法 ③场景 ④输入 ⑤输出 ⑥ROI ⑦代码 ⑧论文来源）+ `Skill Relations`。

于是按用户的裁决把 `playbook/`（70 MB）一次性物化到本地，**此后 iCloud 再不触碰**，本地从此自足。

### 取证二：判据「不允许跨面多挂」被真实数据推翻

原判据写的是「L1/L2 由 L3 唯一导出，不允许跨面多挂」——理由是两套账要对得上。

25 个源域分类回来后跑门禁：**266 项失败**。逐条看，266 项全是同一条判据，没有一条是别的错误。
再看数据：1296 张卡里 264 张（20%）天然跨面。抽查一张合规监控卡，它确实同时服务
`独立控制/产品准入核对`（法规影响侧）与 `业务运营/规则监测`（平台规则侧）——这不是脏数据，
这是业务实况。

**判据错、数据对。** 改判据：树的主归属由**首个 L3** 唯一决定（保证目录树、preset 装配、卡面分组
都有唯一归属），其余 L3 照常记录并参与供给覆盖统计，另标 `cross_plane` 供抽检。

### 取证三：缺口认领 41% 是虚报

9 个平台缺口**本身就是 151 条 L3 里的名字**（`数据管道` = AGT-046 清源的一个细分业务）。
所以「这张卡补上某缺口」必须与「这张卡被分到了哪些 L3」对得上——否则就会出现：

- 工厂**产能**卡认领 `容量管理`，而矩阵里的 `容量管理` 指 **AI 运行容量**（并发/配额/推理成本）；
- 供应链**单点依赖**卡认领 `依赖协调`，而该缺口指 **AGT-002 的跨角色/跨能力依赖定序**；
- 平台账号关联风控卡认领 `利益冲突检查`，而该缺口指 **关联交易审查**。

实测 262 次认领中：130 次由本卡 L3 支撑、24 次同责任域邻接、**108 次（41%）跨域虚报**。
补 `auditGapClaims` 三档判据（strong / adjacent / dropped）后：**strong 178 · adjacent 32 ·
dropped 124**。虚报不再进入装配，但**保留在 `fills_gap_dropped` 里供审计**——不静默抹掉。

这个修正直接影响用户能看到的东西：`agt-002` 的 persona 原本写着「依赖协调 / 异常冻结与恢复 →
**平台无供给**」，接线后变成 5 个真实技能。

### 取证四：红线——全库有 1 处明文 API Key

装配前对 8 类密钥特征做全库扫描，1338 张卡命中 27 处。逐条看上下文：**26 处是误报**——
`Task-Decomposition` 里含 `sk-` 子串被朴素正则误伤；**1 处是真的**：

```
Skill-FActScore-Claim-Verification-Pipeline / 第 7 段代码模板
  api_key="sk-<32 位十六进制>", base_url="https://api.deepseek.com"
```

装配器会把第 7 段原样拼进 SKILL.md，也就是会随技能包进仓库。已在装配器加 `redactSecrets` 闸门
（赋值式 key / `sk-` / AKIA / ghp / AIza / xox / Bearer / PEM 八类），装配时拦下 3 处，装后复扫 0 命中。

## Decision

见 [ADR-0031](../../../adr/ADR-0031.md)。一句话：**分类骨架原样取自岗位矩阵（4/8/151），
树的主归属取首个 L3、跨面多挂合法；缺口认领必须与卡的 L3 落点自洽，分 strong/adjacent/dropped 三档。**

## Alternatives considered

| 备选 | 为什么没选 |
| --- | --- |
| 坚持「不允许跨面多挂」，把跨面卡的次位 L3 删掉 | 等于人为丢掉 20% 的真实供给，覆盖统计会低估；而且删哪个是武断的 |
| 允许一张卡有 2 个主归属 | 目录树、preset 装配、卡面分组都要唯一归属；多主会让「这个技能属于谁」每次都需解释 |
| 缺口认领沿用子任务的语义判断，只做人工抽查 | 抽查挡不住 41% 的虚报；而且虚报的后果是 persona 对不具备的能力宣称"我能"，正是 ADR-0021 要防的 |
| 全库 `sk-` 全局替换脱敏 | 会误伤 26 处技能名引用（`Task-Decomposition` 等）；只脱敏赋值形式的 key |
| 只装 T1 强相关的 331 张 | 用户明确要全量；而且分类维度的价值恰恰在于把「不相关」也标出来 |

## Consequences

**做到了什么**

- 1338 张全量安装：技能库 `272 → 1610`；能力、分类、可见性三层判据全绿。
- **151 个 L3 中 134 有供给、17 零供给**。17 条空白集中在硬件研发/工业设计（9）、B2B 商务（3）、
  人事与内控（2）、生产现场（1）、术语治理（1）——**论文语料结构上不产出这些能力**，这份清单
  本身就是要走公司 SOP 或另造卡的部分。
- **9 个缺口关闭 8 个**；`利益冲突检查` 保持空白（8 个源域独立扫描零候选，如实保留）。
- 50 个 preset 的 `skill-subset` 与「技能供给实况」段重写：全库只剩 1 处「平台无供给」字样。
- `verify-lossless.mjs` **4821 条断言全绿**（基线 4060，增量来自新增的 subset 引用），
  岗位卡 142,085 字节逐个 7 小节无损；`pnpm run gate` 14/14。
- 密钥脱敏 3 处；56 KB 以下的 `staging/backup/` 快照 + 一条命令回滚。

**没做到 / 需要用户决定**

- **17 条零供给 L3 + 11 张无家可归的卡，指向矩阵本身的两处欠缺**（硬件/工程类、AI 治理/ESG 类
  细分业务）。是否给矩阵补 L3 属材料侧决策（D-021），不在技能库范围。11 张卡已照常安装但放在
  `未归类（矩阵空白）`，不进任何 preset。
- **L6 路由实测与 L7 SkillOpt 未运行**（需为 1338 张卡构造三类任务跑真实 subagent），需授权。
- 源站 `playbook` 的 ④⑤ 段 98.7% 是占位串，SKILL.md 正文跳过 4520 处占位段落，
  输入输出规格由合成字段承载——这一层是模型写的，不是卡页原文。
- 28 张卡（2%）源站缺标题，`title` 退化为卡 id。
