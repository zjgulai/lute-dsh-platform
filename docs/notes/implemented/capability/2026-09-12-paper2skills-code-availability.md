# p2s 卡的代码节选口径

对应 [ADR-0048](../../../adr/ADR-0048.md)。本文只记**怎么发现的、怎么验的**，
判据与取舍在 ADR，不在此复述。

## Problem

上一轮（[ADR-0047](../../../adr/ADR-0047.md)）留的下一入口是「**787 条悬空代码路径 +
461 张截断代码**」，并断言两者「都需要 `paper2skills-code/` 源树」。用户同意按此优先级开工。

本轮第一件事是复核这两个数，结果**两个前提都不成立**：

1. **「787 悬空」量错了基准。** 上一轮拿本地 `project/paper_to_skills/paper2skills-code/`
   （199 个 `.py`）当基准。全量树在 iCloud（15,694 个 `.py`，0 个未下载占位符），
   本地那棵是它的严格子集（本地独有目录 0 个）。换基准后：本地 22/838 解析（悬空 816）、
   iCloud **838/838 解析（悬空 0）**。两个基准下都复现不出 787，这条断言整个作废。
2. **「拿到源树就能补全代码」方向错了。** 源树取到了，但**里面不是这份代码**。

## Decision

见 ADR-0048。要点：⑦ 段改名「代码节选」并**按实测口径渲染**（不转发源站自述）、
判据入 `data/code-availability.json`、上限加双向守卫、`verify-install.mjs` 守卡面。

## 怎么查出来的

### 一、树是两代并存的

iCloud 那棵树里同时有：

| 代 | skill 目录数 | `.py` 行数中位 | 脚手架命中 |
| --- | --- | --- | --- |
| 带编号（`01-因果推断`/`04-供应链`…） | 41 | 373 | **0/41** |
| 无编号（`logistics`/`supply_chain`…） | 1,017 | 70 | 772/1017（76%） |

抽样看 `04-供应链/multilevel_flp_2024/model.py` 是 **627 行真领域代码**（抬头写
`论文: Multilevel Facility Location Optimization … (arXiv: 2406.07382)`、`业务场景:`
—— 那是旧富代码代）。而卡的 `code_path` **838/838 全指向无编号那一代**。

### 二、同名不同物：卡的节选 vs 树里的脚手架

把卡里预览的 `def`/`class` 名拿到整棵树里找：**召回 25.0%**（962/3,854），
**746 张卡（64%）零命中**。

逐个看最直白 —— `Skill-3D-Bin-Packing-Optimization`：

- 卡里 60 行：FFD 装箱算法，`@dataclass class Item`、`get_rotations()`、`used_volume`。
- 树里 `logistics/3d_bin_packing_optimization/model.py`（72 行）：通用脚手架，
  `generate_logistics_data()` / `run_analysis()`，**只为这个技能换了个抬头**。

结论：**同一个技能名下放着另一份代码，比悬空指针更危险** —— 悬空会响亮报错，同名会静默给错。

### 三、那代代码被覆盖了，预览是唯一存世的地方

- 卡里节选的抬头写 `Author: paper2skills / Date: 2026-06-06`；树里 `model.py` 是 **6 月 20 日**。
- `git log -S'def run_analysis(data)' -- paper2skills-code/` → **只有一条提交** `75344064`
  （`2026-06-22 build: rebuild playbook — 917 Skills`），且该提交**新增**了 771 个 code 路径。
- `git log -S'class OWLClass' -- '*.py'` → **全历史为空**（那 6 条 `-S` 命中全部来自
  playbook 产物，它内嵌了预览文本，不是 `.py`）。
- `grep -rl 'First Fit Decreasing'` 在整个 iCloud 项目里只命中 playbook 的 HTML/JSON。

即：6 月 6 日那一代富领域实现已被 6 月 22 日的脚手架批量生成**覆盖**，
生成器本身不在任何一棵树里（`grep -rl 'code_preview'` 在 `paper_to_skills/` 下零命中）。

### 四、上限是真的，而且卡页自己写着

- 源站 `<span class=code-meta>60 行 · 可运行</span>` 的自述行数**最大 60**，
  **1,150/1,338 张正是 60**，无一超过。
- 上限判据用**自述行数**而非内容行数：内容行数会因尾部换行在 58–60 间浮动，
  而「N 行」是源站自己的口径。换用自述行数后，1,150 这个数与源站 HTML 逐张对上。

### 五、卡面的三处声明逐条证伪

| 卡面声明 | 实测 |
| --- | --- |
| 段名「⑦ 代码模板」 | 节选：1,150 张顶在 60 行上限 |
| 「N 行 · **可运行复制**」 | 457/1,279 张 Python 节选 `ast.parse` 失败 |
| 「代码块数量：N · 路径：…」 | 806 张在承诺一个代码位置；树不在本包内，且同名不同物 |

## 怎么验的

- **红测（真跑）**：把 5 条新判据喂给上一轮的实现（`fenceCodeIfNeeded`，原样重建），
  **旧实现 5/5 红、新实现 5/5 绿**（`.scratch/p2s-code-recovery/red-old-impl.mjs`）。
  脚本还把旧卡面打了出来 —— `Python60 行 · 可运行复制` 下面直接跟一段截断代码，没有任何口径。
- **校验器验伪**：往一张已装卡注入「可运行复制」并抹掉口径，`verify-install.mjs` **报出 2 项问题**；
  从备份恢复后 **0 问题**。否则无法排除它是个永远绿的空壳。
- **双向守卫**：有卡自述超 60 行 → `exit 1`；**没有任何卡顶到上限** → `exit 1`（判据失效，
  不是「真没截断」）。后者是这次特意加的：一个「全都不满足」的判据最容易假装通过。
- **交叉对账**：可得性表的四个数与独立测量逐一对上 —— 顶上限 **1,150** = 源站自述 60 行的张数；
  声明路径 **838** = `code_path` 的条数；`未检测到` **500** = 1,338 − 838；
  不可解析 **457** ≈ 逐卡语法检查的 456/457。
- **端到端保真分类**（已装 1,338 张）：**1,082 逐字节相同** ·
  **188 仅末尾一行纯空白差** · **3 处刻意脱敏** · 65 无代码可比。
  那 3 处与 `assemble-report.json` 的 `redactions` 名单**逐一对上**，非空白非脱敏差异 **0**。

## 一处自己算错又改回来的

初次量「源站预览行数」用 `len(preview.split('\n'))`，得到 1,150 张 ==60；
再用 `rstrip` 得到 1,006 张 ==60。两个数打架，一度以为**我方抽取又丢了一次行**。
逐张 `rstrip` 对账后：**1,283 张行数差为 0**，差的全是尾部换行（`split` 把结尾空串也数成一行）。
抽取是逐字忠实的，那 1,006/1,150 的差只是两种数法。**这条差点被误记成一个新缺陷。**

末尾那 188 张的纯空白差则是另一回事，且**确实归我方**：`cards.json` 保住了尾部
`\n        `（被截断的第 61 行残留缩进，63 行），丢在装配器对每个段落做的 `.trim()`。
无语义内容，本轮未改，但 ADR-0047 那句「逐字节相同 1,283/1,283」不够准，已在 ADR-0048 拆成三类。

## Consequences

- 卡面三处假声明清零：「可运行复制」**1,283 → 0**（已装库实测 0 处）。
- **代码一行没多**：源站只发布了 60 行。ADR-0047 说对了「截断是源站的责任」，
  说错了理由（不是「源树没拿到」，是「源树里不是这份代码」）。
- 回滚：`staging/backup/skills-p2s-pre-rebuild.tar.gz`（上一轮的 1,338 张）。
- 本包仍 untracked，改动未提交。
