# 2026-09-12 · 大模型调用成本看板：从「账单超预算」到「钱花在哪、哪笔能省」

- 事实之家：[`packages/platform/dsh-cost-guard-local/README.md`](../../../../packages/platform/dsh-cost-guard-local/README.md)（口径与工具契约）、
  `packages/platform/dsh-cost-guard-local/lib/rates.js`（价率）、
  `packages/platform/dsh-cost-guard-local/scripts/e2e-live.mjs`（实况判据）。
  本文只记**为什么这么定**。

## Problem

需求是「每月账单超预算一大截，看不出钱花在哪、哪笔能省，想压一半又不弄差业务效果」。
平台里其实**已经有**全部原始数据：每笔调用都留了 `request/header`（provider / model /
reasoningEffort）与 `assistant/chunk` 的 `usage`，但没有一层把它折算成钱。
没有账本，压缩阈值、降档路由、预算闸门这些动作就没有依据，只能凭感觉调。
所以这件事不是「缺一个省钱技巧」，而是**缺一层把事件流变成金额的结算层**。

### 取证：事实与直觉相反的三处

在 1129 份真实会话、24364 次调用上逐笔核算，三条关键事实都不是凭直觉能猜到的：

1. **`totalTokens` 含输出，不是 prompt 长度。**
   99.8% 的调用满足 `totalTokens = inputTokens + cacheReadTokens + outputTokens`。
   最初把它当 prompt 用，账单直接虚高（实测 $604 被算成 $281 的一半区间之外）。
2. **命中率会骗人。** 全局命中率 96.5% 看着很健康，但命中价只有未命中价的 1/31
   （flash 谷时 0.007 vs 0.22），剩下 3.5% 的未命中按 31 倍价计费、再乘 25 万 token 的 prompt，
   才是账单的真正构成。**决定账单的是「未命中 token × 调用次数」，不是命中率。**
3. **账单极度集中于单条会话。** 最贵的一条会话（1 个 UIUX 对抗审计任务，2461 次调用）
   一家占全量账单 53%。它不是"做得最多"，而是**跑在 Gemini 3.1 Pro 上做工具迭代**：
   单次输出仅 260 token、工具调用占比 96.7%——这类活本不需要贵档。

### 取证：杠杆相加会得到 109% 的假降幅

四个杠杆（贵档改道 / pro→flash / 上下文压缩 / 谷时排程）单独算出的收益**不能相加**：
同一批 token 既会被降档改价、又会被压缩改价、还会被谷时再打一次折。
第一版把它们相加，得到「降本 109.1%」——比总账单还多。这是本轮最有价值的失败。

## Decision

**建 host 插件 `dsh-cost-guard-local`，把结算层做进平台，而不是写一份省钱建议。**

1. **价率与口径独立成纯函数**（`lib/rates.js`），只读事件流，不改任何会话；
   收益口径一律保守，宁少算不多算。
2. **两种收益口径并列输出，互不冒充**：
   - `combined` = 天花板（每笔贵档调用都当可降档），按固定顺序逐级施加、每步只在上一步剩余账单上取收益；
   - `portfolio` = 落地口径（只把满足形态判据的会话按 90% 分流，其余 30%）。
3. **「能不能降档」用离线可观测、可复核的形态判据**，不猜语义：
   调用 ≥200 次 + 单次输出 ≤1K token + 工具调用占比 ≥50% + 命中率 ≥70% 判为迭代型/机械活。
   命中率只作反向排除项、不作必要条件——否则「调用多但没吃上缓存」的最大一笔会被判成判断型活，
   实测正是如此，白白放过 53% 的账单。
4. **预算闸门用与任务长度无关的形态指标**（调用数、命中率），不用绝对金额：
   长任务天然花得多，用金额判会把正常的大任务全部误标（实测 1193 条会话里误标 779 条）。

## Alternatives considered

- **写成一份「省钱建议」文档交付。** 否决：没有账本，建议无法验收；且每条建议的金额都成了拍脑袋。
  现在的每条建议都带金额、占比与会话级证据，可复核、可回填。
- **按绝对金额判定"跑飞"会话。** 否决：见上，误标率 65%。
- **把四个杠杆的收益直接相加。** 否决：重复计数，得到 109% 的假降幅。
- **逐条猜测 usage 口径，而不是按会话判定。** 否决：会在同一会话里给出两种口径的混合账本。
  改为按恒等式在会话级判定，并用单测钉死。
- **为省钱直接全局换便宜模型。** 否决：这正是「把业务效果弄差」的做法。
  本插件只做归因与闸门，降档决策按任务类型分流，并保留 `keptPremiumUsd` 给判断型活。

## Consequences

- 平台的成本可见性从「月底看账单」变成「随时看会话」；`cg_scan` 每次追加一行账本快照，
  可做改造前后的对照曲线。
- 收益数字有两档口径，汇报时必须说明用的是哪一档，否则会把天花板当天花板。
- 形态判据是启发式：只能识别「像机械活」，不能确认「这一步确实是机械活」。
  因此分流比例刻意留了 10%/70% 的余量，最终仍需业务方按任务类型确认一次。
- 非 DeepSeek 线路单价随供应商合同变动，默认价标 `estimated`；
  要让金额可对账，必须用 `config.overrides` 换成实际结算价。
- 本插件只读，但会写 `$DSH_HOME/cost-guard/ledger.jsonl`；账本文件是唯一副作用。
