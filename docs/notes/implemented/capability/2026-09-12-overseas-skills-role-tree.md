# 让技能说出它服务于谁：出海技能页的四层下钻与 329 条可复核的归位判定（ADR-0044）

> 决策记录（ADR-0015 的 Note 侧）。决定本身见 [ADR-0044](../../../adr/ADR-0044.md)；
> 页面契约与数据来源见
> [`packages/capabilities/dsh-overseas-skills/README.md`](../../../../packages/capabilities/dsh-overseas-skills/README.md)。

## Problem

「出海技能」页此前按 **8 大场景 / 28 细分场景**摆目录（222 项），能回答「这技能属于哪类业务」，
答不了「它服务于组织里的谁」。而《AI组织变革》的骨架——4 面 / 8 责任域 / 50 岗位——就在本机
（50 个 preset 的 manifest 里），页面上一个字都看不到。用户的要求因此很具体：**照算法技能页的
分类标准重构，但换入口**，下钻关系是 L1 场景 → 4 面 → 责任域 → 岗位。

动手前先量了既有事实。`scripts/role-presets/skill-map.json` 是 151 条中文责任名 → 技能供给的
人工映射，它的本职是**接线**（喂 50 个 preset 的 skill-subset）。把它反查成「技能 → 岗位」：

```
222 个出海技能：有岗 135　无岗 87　跨多岗 61　岗位有供给 48/50（AGT-005、AGT-049 零供给）
```

**87 个（39%）没有岗位可站**。这不是页面渲染问题——是这份表本来就没打算回答归位问题。
用户据此在两个选项里选了重的那条：**先把 222 个技能的岗位判定补全，再重构页面**。
（另一条是「复用现有映射、无岗的如实进未归岗」，交付更快但缺口更大。）

## Decision

### 1. 判定是新增事实，它必须有自己的家

落在 `packages/capabilities/dsh-overseas-skills/manifest/role-assignments.json`，
`lib/role-map.js` 由 `scripts/build_role_map.py` 从它编译（与 `lib/catalog.js` 同样的
「manifest 是事实、lib 是产物」分工）。每条带：

| 字段 | 含义 |
| --- | --- |
| `roles[].source` | `skill-map`（继承既有接线表的人工先验）或 `assigned`（本轮判定新增） |
| `roles[].confidence` | high / medium / low |
| `roles[].evidence` | `from_skill` + `from_role` 两条逐字引文 |
| `roles[].note` | 跨岗理由、同一岗位多条责任的合并说明 |
| `dropped[]` | 被显式删除的既有先验 + 理由 |

**没有**写进 222 个已安装技能的 frontmatter（它们是 Accio 导入的他人资产，上游重导会覆盖），
**也没有**扩写 `skill-map.json`（那会连带改动 50 个 preset 的接线，把归类与接线绑死）。

### 2. 判定可被机器复核，不靠「模型说是就是」

10 个批次各领 22–29 条技能，`PROTOCOL.md` 是唯一规则来源。每条挂载必须给两条**逐字引文**：
`from_skill` 必须是该技能文本里的连续子串，`from_role` 必须是该岗位 mission / 标准产物 /
责任名里的连续子串。校验器（`validate-assignments.py`）逐条断言：

1. 覆盖：输出与输入**同序同集**（不增不删不重名）；
2. 词表：岗位 id 在 50 个之内，责任名逐字属于该岗三条之一；
3. **防伪造**：两条引文都是原文连续子串（改写、拼接、跨行一律判错）；
4. 一致性：≥3 岗不得标 high；`roles: []` 必须写 `no_role_kind` + 理由；
5. 不留暗账：既有先验被删除却没写 `drop_reasons` → 直接判错。

校验器先做了**红测**（塞入未知岗位、伪造引文、静默删除、无岗不写理由），56 条错误全部报出；
10 个批次随后**一次全绿**。

结果（251 条 = 222 出海 + 29 AI全栈）：

| 事实 | 数字 |
| --- | --- |
| 有岗 / 无岗 | 217 / 34（TOOL_ONLY 13、GENERIC_METHOD 20、OUT_OF_SCOPE 1） |
| 挂载条数 | 329（继承既有 197 + 本轮新增 132） |
| 显式删除的既有先验 | 24 条（涉及 20 个技能，均带理由） |
| 跨岗（≥2 岗） | 82 条，最多的一条挂 6 个岗位 |
| 置信度 | high 101 / medium 180 / low 48 |
| 岗位有供给 | 49/50（仅 AGT-005 内控审计与独立复核仍零供给） |

页面树只承载 222 条出海技能：209 归位 / 13 未归岗 / **319 行**（卡片只有 222 张）/
47 个岗位有卡（零卡：AGT-013、AGT-005、AGT-049）。

### 3. 页面上三件事必须与用户对得上

- **一卡多岗 → 卡片数 ≠ 行数**：222 张卡渲染成 319 行，因为一张卡在每个归位岗位下都出现
  （岗位视图 = 工具箱）。页脚两个数都写：把行数说成技能数就是假读数。
- **归位 ≠ 接线**：卡挂在本岗下是归位；本岗 preset 的 `skill-subset` 是否真挂载它是接线。
  卡片上三态徽标，另有「preset 挂了但未归本岗」的独立账（50 个岗位都有这类卡，共 553 条）。
- **没有位置的东西必须有位置**：13 张未归岗卡按场景进「未归岗」分组（带分型计数）；
  零卡岗位在诊断条里逐个点名。

路由注册是这次唯一一处**只有重启才验证得了**的东西，所以它被挪进了单测：
`test/host-routes.spec.mjs` 直接 `apply()` 一遍插件、把 `webServer.register` 的 handler 截下来真的调用，
断言路由表六条齐全、围栏（非回环 401 / 错方法 405）成立、`/org` 负载的每个数字都与 manifest 和 catalog 对得上。
这条测试在**不重启进程**的前提下覆盖了「代码写完但路由不存在」这一类事故。

### 4. 「取不到骨架」也是一种可验收的状态

四层下钻的负载走宿主新路由 `/org`，而平台的生效契约是硬的——**宿主变更 = 重启，客户端变更 = 刷新**
（`docs/architecture.md` 第 1 节）。三条「不重启也能生效」的路子实测都不成立：profile 的
`patchReload: "live"` 只监视 patch 文件、profile 里没有 hmr 行、`touch lib/index.js` 后 20 秒内
`/org` 一直 401。也就是说，**刷新页面会先于重启发生**。

第一版把这种情况渲染成一句「四层骨架加载中…」，下面什么都没有——页面上除了一行提示全是空的。
按 [ADR-0043](../../../adr/ADR-0043.md) 的读法，这是把「增强项拿不到」折算成了「整页空白」。
改成本轮契约的一部分：`/org` 失败 → **退化为原场景分组**（可展开，和改造前一模一样）
＋ 一行说明原因。探针为此加了场景 B（8 条断言，其中 5 条在修复前的 bundle 上会红）。

### 5. 12 枚层头像：两个包各烘一份 + 跨包断言

4 面 + 8 责任域的头像从 lute-brand-icons 的同一份品牌清单烘焙而来，本包与算法技能页各存一份
（两个页面分属不同插件，必须能独立渲染）。防漂移靠测试：本包断言 12 条 data URI 与隔壁包
**逐字节相等**，缺了隔壁包就**跳过并说明**、不静默通过。红测：手改一枚字节 → 该用例红，重跑
生成脚本 → 绿。

## Alternatives considered

| 备选 | 为什么否掉 |
| --- | --- |
| 页面直接用既有接线表反查 | 省一轮判定，但 87 个技能无处可站；用户已明确否掉 |
| 判定写进技能 frontmatter | 上游重导会覆盖，且等于把页面侧的分类塞进他人资产 |
| 扩写 `skill-map.json` | 连带改动 50 个 preset 的接线，归类与接线再也没法分开看 |
| 责任域只做面内的分组标题（三层） | 用户明确选了四级下钻 |
| AI全栈 29 条也进场景树 | 它们没有场景轴（分类是 `fs-*`）；判定已入库备用，挂法待定 |
| 把 12 枚头像放一个共享包 | 两页分属不同插件、各自要能独立渲染；共享包会把两个 surface 绑在一起 |

## Consequences

**正面**：251 条技能第一次有可复核的岗位归属；「归位 vs 接线」的落差第一次在页面上可见；
AGT-025（零售渠道与B2B拓展）从零卡变有卡，零卡岗位从 2 个缩到 1 个；
判定过程、证据、删除理由全部入库，任何一条都能回溯到原文。

**负面**：48 条 `low` + 180 条 `medium` 仍需人工复核（跨岗或只链到使命而非责任名）；
319 行 > 222 张卡这件事必须一直解释，否则会被读成 319 个技能；
12 枚头像存在两份字节，防漂移完全依赖那条跨包测试。

## 顺带修掉的一个 CSS 幻觉

搭目视验收链时，`compose-page.mjs` 的 token 覆盖自检抓出一处：本包 client bundle 的
`.ovpGrid` 引用了 `--dsw-alias-scrollbar-thumb`，而**这个 token 在官方主题里根本不存在**
（官方是 `--dsw-alias-scrollbar-bg-l1` / `-hover-l1`，经 `--dsh-scrollbar-thumb` 间接层使用，
见官方 `scrollbar.css`）。后果是两个引擎都退化：自行声明的 `scrollbar-width: thin` 会让
Chromium **丢弃该元素全部 `::-webkit-scrollbar*` 规则**，而 `scrollbar-color` 因 var() 失效
在计算值阶段被判无效、回落到 `auto`——深色主题下这一格滚出浅色原生滚动条，正是官方
`scrollbar.css` 开头点名要避免的现象。

修法是**删掉而不是改对**：官方样式表已经对 `body, body *` 与 `::-webkit-scrollbar*` 两条路径
上好了滚动条皮肤，本包不该有第二份。
