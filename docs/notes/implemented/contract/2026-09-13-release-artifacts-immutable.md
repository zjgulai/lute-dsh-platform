# 发布产物不许被删：从「查是谁删的」转向「让它删不掉、丢了看得见、找得回来」

- 日期：2026-09-13
- 状态：implemented
- 对应 ADR：[ADR-0067](../../adr/ADR-0067.md)
- 相关：ADR-0057（产物要么缺席要么完整）、ADR-0058（入库清单是「承诺过什么」的家）、ADR-0043（失败必须给出为它负责的读数）、ADR-0014（门禁硬门槛 / 豁免只减不增）

## Problem

用户报：**发布版本的 dmg 经常被删除**，并要求「不允许删除发布的版本和历史发布的版本」。
现状核对（`pnpm run gate` 现在会自己说话）：

```
[2.2.0] 产物在；哈希=ok；无归档副本；未锁定
[2.3.0] 产物在；哈希=ok；无归档副本；未锁定
[2.3.1] ✗ 清单在、字节没了 → 找回：bash packaging/scripts/release-restore.sh 2.3.1
[2.3.2] 产物在；哈希=ok；无归档副本；未锁定
```

这次没有再重复「查是谁删的」，而是先把**能不能查出来**这件事本身取证完：

1. **本机无法回滚**：`tmutil listlocalsnapshots /` 为空（没有 APFS 本地快照），所以 2.3.1 的字节
   既不在仓库、也不在任何可回滚的位置——`mdfind -name DSH-Desktop-LUTE` 全盘查不到它。
2. **仓库里没有删除者**：`grep -rn "git clean|rm -rf.*release|rm -f.*\.dmg"` 只命中发布守卫自测删它
   自己的沙箱（`release-publish-guard-test.sh:141`，路径是 `$SANDBOX`）。
3. **没有定时清理**：cron 只有两个品牌数据任务；`~/Library/LaunchAgents` 里的 LUTE 代理是做备份、
   起 vite、设环境变量的，没有清理动作；`~/.zsh_history` 里没有相关命令。
4. 上次（2026-09-12）的结论是「不是 `sign-and-dmg.sh` 所为」——依据是三个伴随文件保留了原始 mtime，
   可证 `rm -rf` 未执行。这个结论今天依然成立，而且**至今没有第二个嫌疑人**。

换句话说：**凶手查不出来，而这件事已经发生两次**。于是真正要修的不是「谁」，而是下面两条：

- **删得掉**：产物只有一份（`packaging/release/<版本>/`），在构建树里，任何清理动作都能带走它；
- **丢了没人说话**：`release/<版本>.sha256` 已进 git，等于我们书面承诺过那串字节，而承诺与字节分家后
  系统里没有任何一处会报错——直到客户拿着清单来核对。

## Decision

1. **仓库外归档**：`sign-and-dmg.sh` 发布成功后把版本目录复制到
   `$HOME/Library/Application Support/LUTE/releases/<版本>/`，并**回读校验**哈希与已发布那份一致
   （不一致即判本次发布失败）。归档在构建树之外：`git clean -xdf`、`rm -rf packaging/release`、
   重新克隆都碰不到。
2. **两处副本 `uchg` 锁定**：`rm` / `mv` 一律 `Operation not permitted`；唯一合法解锁点是重制同名版本
   时 `sign-and-dmg.sh` §5 的归档改名。锁不上即发布失败（不允许「以为锁了其实没锁」）。
3. **判据唯一实现 + 进门禁**：`release-verify.sh`（对照 git 清单核存在/哈希/归档/锁）由
   `scripts/gate.mjs` 的 `release-artifacts-intact` 每次 `pnpm run gate` 调用。
   「版本目录在、dmg 不在」= 红灯，正是 2.3.1 的形态；「版本目录整体不存在」= SKIP（新克隆不假红）。
4. **找回是命令**：`release-restore.sh <版本> [--from <路径>]`，先与清单对哈希、对不上即拒收，
   恢复后自动加锁。`--from` 同时是「客户手上那串字节是不是我们发的」的判定器。
5. **丢失要宣告**：`release/<版本>.lost` 记录不可找回的事实。它不是豁免——除它之外任何缺失都红灯，
   且每次门禁都会把宣告念出来。

## Alternatives considered

| 备选 | 为什么不选 |
| --- | --- |
| 在 SOP 里再补一句「请注意不要删」 | 已经写过两次，两次都没拦住；把纪律寄托在记忆上是本仓库反复否决的做法 |
| 把 dmg 纳入 git | 每版 600 MB，仓库会被撑爆；LFS 又引入「谁有权删远端对象」的新问题 |
| 只归档、不在仓库里留副本 | 构建侧看不到产物、门禁无从对照，等于把核对推回给人 |
| 只上锁、不做归档 | `chflags` 挡得住 `rm`，挡不住「先解锁再删」「磁盘清理工具」「整个目录被搬走」 |
| 归档放云端（GitHub Releases / 对象存储） | 需要网络与凭据，且把「谁有权删」搬到远端；列为后续项，不替代本地不可变性 |

## Consequences

**机制实证（本机，逐条跑过）**：

- 锁定后 `rm -f` → `Operation not permitted`，文件仍在；
- 锁定后 `mv` → `Operation not permitted`，文件仍在；
- 显式 `chflags -R nouchg` 后把 2.3.2 的 dmg 搬走（模拟又一次丢失）→
  `release-verify.sh` 立刻报 `[2.3.2] ✗ 清单在、字节没了 → 找回：…`，退出码 1，
  `pnpm run gate` 变红在 `release-artifacts-intact`；
- `release-restore.sh 2.3.2`（从归档找回）→ 落位后哈希与搬走的那份**逐字节相同**
  （`7756564e834f9748…`），自动重新锁定，门禁恢复 22/22。

**其它后果**：

- 磁盘占用翻倍（每版本 ~600 MB）。历史版本已补：2.0.1（早于清单机制，无哈希可核，归档时留下
  `ARCHIVED-SHA256`）、2.2.0、2.3.0、2.3.2。
- **2.3.1 已宣告丢失**（`release/2.3.1.lost`）：本机无副本、无快照，不能重建（同号不同字节，ADR-0057）。
  任何外部副本可经 `release-restore.sh 2.3.1 --from <路径>` 核验收回——**已发给客户的那份是唯一存世副本**。
- 门禁增加约 4 秒（全量哈希三份 610 MB 产物）；版本变多后需评估是否把哈希挪进 `--mode full`。
- 顺带修掉一个自测脚本的假红：`release-verify.sh` 的「未登记目录」扫描最初会把找回时的改名留档
  （`<版本>.replaced-<时间戳>`）当成「缺产物」——一次 `release-restore` 就能让门禁变红。已限定只认
  裸版本号目录名。
- 覆盖范围仅本机：产物离开本机后（飞书直传、Releases 附件）的存续取决于远端保留策略。
