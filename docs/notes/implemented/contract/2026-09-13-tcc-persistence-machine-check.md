# 判据⑤ 从「人工复测一次」变成「每版出货前可判定的命题」

- 日期：2026-09-13
- 状态：implemented
- 决策记录：ADR-0063
- 相关：[2026-09-13-signing-identity-tcc-stability.md](../architecture/2026-09-13-signing-identity-tcc-stability.md)（ADR-0063；本 Note 是它第 6 条验收里「判据⑤」的落地）、[2026-09-13-shell-var-multibyte-guard.md](2026-09-13-shell-var-multibyte-guard.md)（ADR-0064；同一轮里另一件「知道 ≠ 拦住」）

## Problem

ADR-0063 的四条机读判据里，前三条（无 cdhash、Authority 为证书名、跨重建不变）都能对**产物本身**判定；只有判据⑤「升级后 TCC 授权不再重置」看起来必须靠人：装一版、点一次授权、再装一版、再看一次。它因此成了一条**每版都要消耗一次真实授权、且只能事后发现失败**的验收——而它恰恰是这次换签的**全部目的**。

更深一层的问题：进程里跑着旧 app 时 `macos-harness doctor` 读到的是旧 app 的授权状态，所以判据④⑤都只能在「重启之后」读，而重启会结束发起验收的那个会话。验收链条的最后一环落在了一个**无法从内部观测**的时刻上。

## Decision

把判据⑤ 还原成一个可判定的命题，并钉成机读脚本（`packaging/scripts/verify-tcc-persistence.sh`）。

关键在于 TCC 的存储语义：**TCC 为一次授权保存的 csreq 取自该 app 的指定要求**（本机实测：TCC 里两条授权的 csreq 解码后与旧 app 的 `codesign -d -r-` 逐字节相同）。于是

    新 app 满足旧 app 的指定要求  ⟺  已存授权在升级后仍然有效

这条等价关系不需要人工、不需要重启、不需要消耗真实授权，因此每一版都能在出货前跑。

三条实现上的硬要求（都由本轮实际踩到的假绿倒推出来）：

1. **判据必须附带反向对照。** 脚本内置一条**必须不满足**的虚构身份要求；只有对照为假时，正向读数才被采信。理由见 Consequences 的三次假绿——它们共同点是「判据没有能力给出否」。
2. **「不满足」与「写错」必须分开。** `codesign --verify -R=` 会先验封条再判要求，两者共用一个退出码；判定输出分 SAT / UNSAT / MALFORMED 三类，MALFORMED 算失败而不是算「要求不匹配」。
3. **封条破损时输出 INCONCLUSIVE，而不是硬判失败。** 输入坏了与结论是坏的必须分开报。

同时把反向自测做成 `packaging/scripts/verify-tcc-persistence-test.sh`（G1 同身份重建须放行 / G2 adhoc 旧支须判红 / G3 签名后追加一字节须拒绝认证 + 未篡改对照须放行 / G4 探测器须能说不）。

## Alternatives considered

- **维持人工复测。** 每版一次真实授权 + 一次重启即可，不需要新代码。否决理由：它把「验收」放在发布**之后**，且失败时用户已经经历了权限丢失——正是 ADR-0063 要消除的那类代价。而且重启会结束观测会话，链条最后一环无法从内部闭合。
- **只用逻辑论证（③ ⇒ ⑤），不写脚本。** 判据③ 已证明两次指定要求逐字节相同，把它与「TCC 存的是指定要求」两句连起来，⑤ 就成立了。这个论证是对的，本轮也把它写进了证据档。但论证本身不可执行：日后任何一次改动（换证书、改 bundle id、DR 生成方式变化）都会让它静默失效，而没有人会重读那段文字。**可执行的判据才会在失效当天报错。**
- **把判定写成 `csreq` 的一次调用。** 这是最初选的路，直接踩空——见下。

## Consequences

### 判据⑤ 现在可在出货前判定（本机实测）

| 情形 | 输入 | 结果 |
|---|---|---|
| 一 · 真实命题 | 已装 2.3.0 → 待升级 2.3.1 | **9 通过 / 0 失败，退出码 0**（命题成立） |
| 二 · 负向 | 换签前 adhoc app → 2.3.1 | 5 通过 / 3 失败，退出码 1（cdhash + 要求不一致 + 封条破损） |
| 三 · 负向 | 2.3.1 → 签名后追加一字节 | 6 通过 / 2 失败，退出码 1（拒绝认证，未硬判） |

自测 G1~G4：**8 通过 / 0 失败**。

### 得到一条可证伪的预测（当日 13:13 已验证）

`auth_value=2`（TCC 记着「允许」）**不等于**「新 app 已授权」——那行记录绑定的是旧字节。因此预期：重启后 `macos-harness doctor` 三项为 **false**，直到人工重授。若重启后直接为 true，说明推断有误，须重新查因，不得当作好消息收下。

同日 13:13 直读系统库（`/Library/Application Support/com.apple.TCC/TCC.db`，需完全磁盘访问）把这个预期变成了读数，三项逐一落定：

| service | auth_value | 库里存的 `csreq` |
|---|---|---|
| `kTCCServiceAccessibility` | 2 | `cdhash H"595283898d…" or cdhash H"3d09f5a3…"` |
| `kTCCServiceScreenCapture` | 2 | 同上（逐字节相同） |
| `kTCCServiceListenEvent` | 2 | 同上（逐字节相同） |

三项正是 doctor 的 `accessibility` / `screen_recording` / `post_events`。用库里这条要求判已装 2.3.0（CDHash `3833cbbc…`）得 `codesign rc=3`（不满足）；而旧支（回滚副本）的 CDHash 实测**就是** `595283898d…`。于是「TCC 仍写着允许」与「新支不满足该授权」在同一屏上同时成立——预测成立，且失败模式被完整复现。

### 第四次假绿：读数没错，但测的不是你以为的那个对象

上面第 3 条假绿的探针（读数互相矛盾）同日在 `verify-tcc.sh` 上又触发了一次，形态是新的：

13:13 系统 TCC 库明写「已装 app 不满足这三条要求」，而 `macos-harness doctor` 同时报 `true/true/true`。两个读数都对，却指向**不同对象**：doctor 归因于**进程**，而授权要求约束的是**路径上的字节**。`lsof` 给出判决——承载会话的进程实际执行的是

```
…/LUTE/rollback/DSH Desktop-2.0.5-lute.2.0.0-20260913-125713.app/Contents/MacOS/DSH Desktop
```

即换签前的旧支仍在内存里运行（它已被 `mv` 到回滚位，`ps` 显示的却是 `/Applications/...` 这个已不存在的路径）。**「doctor 为 true」与「已装 app 有权」是两个命题。**

这条已修进 `verify-tcc-runtime.sh`：先比对进程实际执行的文件与 `/Applications/DSH Desktop.app/Contents/MacOS/DSH Desktop`，不一致就**拒绝**给出判据④ 结论并说明原因。四条假绿的共同点仍是那一条——**判据没有能力指出「我测的不是这个」**；区别只在于，第 4 条的对象错误连读数本身都是真的，只有跨读数交叉才能发现。

### 判据⑤ 的运行时读法也必须防空测试

把④⑤ 做成 `--diff`（基线快照 vs 升级后快照）时，同一个族又出现一次，形态是「**PASS 但什么也没证明**」：两次快照若来自**同一支**，「三项未变」是必然的——app 根本没换。第一版 `--diff` 照直打了三个 `[PASS]`，只在末尾附一行 `（字节确实变了: 3833cbbc5958 → 3833cbbc5958）`——**值相同却写着「变了」**，自相矛盾。

判据⑤ 要的是「换了字节、授权仍在」，所以 CDHash 必须不同，否则是空测试。现在 CDHash 相同即输出 `[空测试]` 并声明「判据⑤ 本次未判定」，不同才给 `⇒ 判据⑤ 成立`。这与判据③ 用「CDHash 不同 + 要求相同」成对断言排除空测试是同一条纪律，只是换到了运行时。

**一条自我适用**：本 Note 记录的三次假绿都出在「判据」上，而第四次之后新增的两处（快照 JSON、空测试）出在**我自己新写的仪器**上。仪器也是判据，同样要能被证伪；`verify-tcc-runtime.sh` 因此对快照做了 `JSON.parse` 断言、对 `--diff` 做了 CDHash 配对断言——两条都是「产出必须当场证明自己能解析、能区分」。

### 用户照着做的那句话本身是错的

判据做对了，指引却是错的：出货 README 让用户授权「屏幕录制/辅助功能/**自动化**」，而实测三项是
`kTCCServiceAccessibility` / `kTCCServiceScreenCapture` / **`kTCCServiceListenEvent`**——第三项在
**输入监控**下，系统 TCC 库里**根本没有 `PostEvent` 行**（`post_events` 由「输入监控」承载）。
用户按 README 授了「自动化」，`mac.key` / `mac.click` 仍会静默失败：**一份写错的指引，与一条不会
判否的判据，产生同一种后果**——能力死了而没人收到通知。

修法与守住它的方式：

- 改正 `packaging/assemble.sh` 生成的 README 段（三项 + 说明第三项为什么不在「自动化」下）；
- 新增门禁 `dmg-readme-tcc-panes`（`scripts/gates/checks.mjs: checkDmgReadmeTccPanes`），要求该段
  三项齐备，并配 5 条单测——其中一条**特意用机器上真实发生过的错法（写「自动化」）做输入**，
  它必须判红。判据只要求齐备、不禁止正文解释「不要授权自动化」，因为那正是需要讲清楚的地方。

**这类「指引」和判据一样属于契约面**：它不会被编译器检查，错了也没有报错，唯一能拦住它的是把它
也做成机读判据。

### 三次假绿，同一族（本 Note 的方法论来源）

| # | 形态 | 表面读数 | 真相 |
|---|---|---|---|
| 1 | `codesign -d -r- <相对路径>` | 空串 + 退出码 0 | 读数为空 → `[ "" = "" ]` 判「一致」 |
| 2 | `csreq -t` | 恒 rc=0 | `-t` 是 **text output** 不是 test-file，它从不读目标 |
| 3 | 用自己的 DR 判自己 | 恒「满足」 | 被测对象与判据同源 |

第 3 条是**本轮新写脚本时自己引入的**：`verify-tcc.sh` 第一版把 TCC 里存的要求解码打印，却用 app 自己的 DR 去判，标签写着「满足 TCC 的要求」而实际测的是「app 满足它自己」。之所以没被收下：那一句与同屏的另一个读数自相矛盾——已装 2.3.0 的 CDHash 是 `3833cbbc…`，而 TCC 存的要求写的是 `595283898d… or 3d09f5a3…`，两者都不匹配。**读数之间的互相矛盾是最便宜的探针。**

### 已知边界

- 脚本判定的是「**已存授权对新支是否仍然有效**」。若新支改了 bundle id 或换了证书，命题为假且**必须**为假——那是身份变了，不是判据失效。
- 首次授权（从无到有）不在本判据范围内，仍需人工一次；本判据管的是**此后每一版**。
- G1~G3 依赖本机存在发布身份「LUTE Code Signing」；缺失时自测**显式打印 [SKIP]** 并以 0 退出，不伪装成通过。

### 判据④ 的漏洞：doctor 全 true 推不出判据⑤（本轮补上）

ADR-0063 把判据④ 定成「装机后 `macos-harness doctor` 三项为 true」。本轮把本机 TCC 库**全部 27 条**
带 `csreq` 的条目解码后，发现这个判据**可以在我方路线失效时照样通过**。

形态只有两类：Apple 锚定系（`anchor apple`，以及
`identifier + anchor apple generic + certificate leaf[subject.OU] = "<TeamID>"`）与 cdhash 系。
**唯一不含 `anchor apple` 的就是我方那四条**（`ai.deepseek.dsh.desktop` 的 accessibility /
screen capture / listen event / all files），且四条全是 cdhash 型。也就是说，「tccd 会接受并原样
保存一条**自签**的 `identifier + certificate leaf = H"…"` 要求」在本机数据库里**没有先例可援**。

于是存在一个此前没人写下来的分支：若 tccd 因该要求不锚定到受信证书而**退回存 cdhash**，那么——

1. 用户重授后，doctor 三项**照样全 true**；
2. 判据④ **照常通过**；
3. 而授权绑定在当前字节上，下一版一换字节即全部重置：判据⑤ 失败。

失败出现在**下一版**，而验收记录上写着「④ 已通过」。这与 ADR-0057 点名的「靠人记得不是工程解」
同源，只是搬进了验收环节内部。

**决定**：判据④ 增加一条附加断言——看**要求形态**本身，而不只看 doctor 的布尔值。
`verify-tcc-runtime.sh` 第 2 节本就把 `csreq` 解码打印，现增加 `judge_req_form()`：

| 形态 | 退出码 | 结论 |
|---|---|---|
| 含 `cdhash` | 3 | ④ 成立但 ⑤ **必然失败**，明写「不得把本次读数当作证据」 |
| 含 `certificate leaf = H"` | 0 | 授权绑身份而非字节，⑤ 具备成立条件 |
| 都不是 | 4 | 形态未知，要求人工判读 |

实现唯一：主流程与自测走**同一段代码**（`--judge-form` 从 stdin 读同一份 TSV），不复制逻辑。
反向自测 `packaging/scripts/verify-tcc-form-test.sh`：F1 用库里那两行 **cdhash 真实坏输入**必须
退 3，F2 用真实产物 DR 退 0，F3 未知形态退 4，F4 空输入不得通过。已实测把实现换成恒真桩后
F1/F3/F4 全红——它不是空转。

**边界（重要）**：这条断言把「⑤ 会不会成立」从「下一版才知道」提前到「重授当场就知道」，但
**不能**让 ⑤ 无条件成立。若重授后形态仍是 cdhash，那是 ADR-0063 的路线在自签前提下失效，须回到
该 ADR 的备选（Developer ID + 公证）决策，**不得**继续调判据来让它变绿。

### 未接线：这两个自测本身没有门禁在看

`test:gate` 只跑 `scripts/gates/*.test.mjs`，全仓**没有任何门禁会运行 `packaging/scripts/*-test.sh`**；
两个 TCC 自测目前只在 SOP 第 5.5 节以「请运行」的形式登记。即「这条判据会不会说不」**仍靠人记得**，
与 ADR-0057 相抵。**未做**——原因是要留痕的取舍（glob 还是显式白名单、`first-launch-test.sh` 一类
需入参的自测如何排除、`verify-tcc-persistence-test.sh` 依赖发布身份故只能声明跳过），不夹带在本次
验收里；已登记为 ADR-0063 后续动作 ⑦。

### 同一句话的另外五个家：判据守了一个文件，另外五处仍在说错话

上一节把「用户照着做的那句话」改对了——但只改了 `assemble.sh` 生成的那一段 README。
本节按 ADR-0009 追这句话的**全部家**，发现它散在六处，其中**五处当时仍是错的**：

| # | 位置 | 出货? | 当时的写法 |
|---|---|---|---|
| 1 | `packaging/assemble.sh` 生成的 README | 是 | 已改正（上一节） |
| 2 | `packaging/installer/install.sh` 收尾提示 | **是** | `录屏/辅助功能/自动化` |
| 3 | `packaging/installer/pkg-postinstall.sh` 提示 | **是** | `录屏/辅助功能/自动化` |
| 4 | `packaging/INSTALL-CARD.md` | 是 | `屏幕录制 / 辅助功能 / 自动化` |
| 5 | `packaging/README.md` | 是 | `录屏/辅助功能/自动化` |
| 6 | 仓库根 `README.md` | 是 | `录屏/辅助功能/自动化` |

第 2 条尤其难看：用户装完机器，**最后看到的那一行提示**就是错的——他按 README 授对了三项，
再核对安装器末行，反而会以为自己漏授了「自动化」。

而 `dmg-readme-tcc-panes` 只读 `assemble.sh` 一个文件，对着另外五处的错法会说「全部通过」。
**一条只守一个家的判据，会对同一条事实的其余五个家视而不见**——这正是 ADR-0009 要防的漂移，
只是这次漂的不是内容新旧，而是「同一事实有六个家，只改了一个」。

**决定**：

1. ~~六处统一改成「辅助功能 / 屏幕录制 / 输入监控」~~ —— **于 2026-09-13 15:44 更正为两项
   「辅助功能 / 屏幕录制」**，见本 Note 末尾的「更正」。下文三条决断作为历史记录保留：
   `install.sh` 另加一句「第三项在『输入监控』下，不在『自动化』下」——那正是会踩的坑。
2. 新增门禁 `tcc-pane-guidance`，扫描**已登记的出货指引面清单**（上述六个文件），凡同时提到
   「授权 / 隐私与安全」与授权项名的行，必须含「输入监控」。→ **该判法已反转**（见末尾更正）。
3. **清单本身也受判**：登记了却读不到内容的文件判红，防止文件改名后清单静默失效。

两处刻意的判法取舍，都配了测试：

- **不禁止正文解释「不要授权自动化」**：权威 README 正是要讲清这一点的地方，一律禁会把它逼成错话。
- **shell 脚本里 `#` 开头的行跳过**：那是给人看的注释，不发到用户面前。`assemble.sh:316` 正有一段
  注释在解释本缺陷的机制（「TCC 授权（辅助功能 / 屏幕录制 / 事件投递）」），它写得对，只是没在
  同一行点出第三项。markdown 里的 `#` 是标题不是注释，**照查**——这条单独配了测试钉住。

**验收**：门禁 20/20、`test:gate` 139/139；并做了负向实测——把 `install.sh` 末行改回
`录屏/辅助功能/自动化`，`tcc-pane-guidance` 当场判红并给出 `install.sh:302` 与处置办法；
恢复后复绿。

**留下的一个事实**：已产出的 2.3.1 DMG（`source_commit=2534451`）**早于**上述任何修复，
其 `payload/README.md:23` 与 `install.sh` 仍写着「自动化」。它只可用作判据⑤ 的升级用产物，
**不得分发**。
