# 判据⑤ 从「人工复测一次」变成「每版出货前可判定的命题」

- 日期：2026-09-13
- 状态：implemented
- 决策记录：ADR-0063
- 相关：[2026-09-13-signing-identity-tcc-stability.md](../architecture/2026-09-13-signing-identity-tcc-stability.md)（ADR-0063；本 Note 是它第 6 条验收里「判据⑤」的落地）、[2026-09-13-shell-var-multibyte-guard.md](2026-09-13-shell-var-multibyte-guard.md)（ADR-0064；同一轮里另一件「知道 ≠ 拦住」）

## Problem

ADR-0063 的四条机读判据里，前三条（无 cdhash、Authority 为证书名、跨重建不变）都能对**产物本身**判定；只有判据⑤「升级后 TCC 授权不再重置」看起来必须靠人：装一版、点一次授权、再装一版、再看一次。它因此成了一条**每版都要消耗一次真实授权、且只能事后发现失败**的验收——而它恰恰是这次换签的**全部目的**。

更深一层的问题：进程里跑着旧 app 时 `macos-harness doctor` 读到的是旧 app 的授权状态，所以判据④⑤都只能在「重启之后」读，而重启会结束发起验收的那个会话。验收链条的最后一环落在了一个**无法从内部观测**的时刻上。

## Decision

把判据⑤ 还原成一个可判定的命题，并钉成机读脚本（`packaging/scripts/verify-tcc-persistence.sh`）。

关键在于 TCC 的存储语义：**TCC 为一次授权保存的 csreq 取自该 app 的指定要求**（本机实测：TCC 里两条授权的 csreq 解码后与旧 app 的 `codesign -d -r-` 逐字节相同）。于是

    新 app 满足旧 app 的指定要求  ⟺  已存授权在升级后仍然有效

这条等价关系不需要人工、不需要重启、不需要消耗真实授权，因此每一版都能在出货前跑。

三条实现上的硬要求（都由本轮实际踩到的假绿倒推出来）：

1. **判据必须附带反向对照。** 脚本内置一条**必须不满足**的虚构身份要求；只有对照为假时，正向读数才被采信。理由见 Consequences 的三次假绿——它们共同点是「判据没有能力给出否」。
2. **「不满足」与「写错」必须分开。** `codesign --verify -R=` 会先验封条再判要求，两者共用一个退出码；判定输出分 SAT / UNSAT / MALFORMED 三类，MALFORMED 算失败而不是算「要求不匹配」。
3. **封条破损时输出 INCONCLUSIVE，而不是硬判失败。** 输入坏了与结论是坏的必须分开报。

同时把反向自测做成 `packaging/scripts/verify-tcc-persistence-test.sh`（G1 同身份重建须放行 / G2 adhoc 旧支须判红 / G3 签名后追加一字节须拒绝认证 + 未篡改对照须放行 / G4 探测器须能说不）。

## Alternatives considered

- **维持人工复测。** 每版一次真实授权 + 一次重启即可，不需要新代码。否决理由：它把「验收」放在发布**之后**，且失败时用户已经经历了权限丢失——正是 ADR-0063 要消除的那类代价。而且重启会结束观测会话，链条最后一环无法从内部闭合。
- **只用逻辑论证（③ ⇒ ⑤），不写脚本。** 判据③ 已证明两次指定要求逐字节相同，把它与「TCC 存的是指定要求」两句连起来，⑤ 就成立了。这个论证是对的，本轮也把它写进了证据档。但论证本身不可执行：日后任何一次改动（换证书、改 bundle id、DR 生成方式变化）都会让它静默失效，而没有人会重读那段文字。**可执行的判据才会在失效当天报错。**
- **把判定写成 `csreq` 的一次调用。** 这是最初选的路，直接踩空——见下。

## Consequences

### 判据⑤ 现在可在出货前判定（本机实测）

| 情形 | 输入 | 结果 |
|---|---|---|
| 一 · 真实命题 | 已装 2.3.0 → 待升级 2.3.1 | **9 通过 / 0 失败，退出码 0**（命题成立） |
| 二 · 负向 | 换签前 adhoc app → 2.3.1 | 5 通过 / 3 失败，退出码 1（cdhash + 要求不一致 + 封条破损） |
| 三 · 负向 | 2.3.1 → 签名后追加一字节 | 6 通过 / 2 失败，退出码 1（拒绝认证，未硬判） |

自测 G1~G4：**8 通过 / 0 失败**。

### 得到一条可证伪的预测

`auth_value=2`（TCC 记着「允许」）**不等于**「新 app 已授权」——那行记录绑定的是旧字节。因此预期：重启后 `macos-harness doctor` 三项为 **false**，直到人工重授。若重启后直接为 true，说明推断有误，须重新查因，不得当作好消息收下。

### 三次假绿，同一族（本 Note 的方法论来源）

| # | 形态 | 表面读数 | 真相 |
|---|---|---|---|
| 1 | `codesign -d -r- <相对路径>` | 空串 + 退出码 0 | 读数为空 → `[ "" = "" ]` 判「一致」 |
| 2 | `csreq -t` | 恒 rc=0 | `-t` 是 **text output** 不是 test-file，它从不读目标 |
| 3 | 用自己的 DR 判自己 | 恒「满足」 | 被测对象与判据同源 |

第 3 条是**本轮新写脚本时自己引入的**：`verify-tcc.sh` 第一版把 TCC 里存的要求解码打印，却用 app 自己的 DR 去判，标签写着「满足 TCC 的要求」而实际测的是「app 满足它自己」。之所以没被收下：那一句与同屏的另一个读数自相矛盾——已装 2.3.0 的 CDHash 是 `3833cbbc…`，而 TCC 存的要求写的是 `595283898d… or 3d09f5a3…`，两者都不匹配。**读数之间的互相矛盾是最便宜的探针。**

### 已知边界

- 脚本判定的是「**已存授权对新支是否仍然有效**」。若新支改了 bundle id 或换了证书，命题为假且**必须**为假——那是身份变了，不是判据失效。
- 首次授权（从无到有）不在本判据范围内，仍需人工一次；本判据管的是**此后每一版**。
- G1~G3 依赖本机存在发布身份「LUTE Code Signing」；缺失时自测**显式打印 [SKIP]** 并以 0 退出，不伪装成通过。
