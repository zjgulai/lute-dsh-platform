# 发布前门禁的射程与三态读数：让「没量到东西」不再长得像「都合格」

> 决策：[ADR-0075](../../../adr/ADR-0075.md) · 分类：contract · 生命周期：implemented

## Problem

### 一条红，两种读法，而且都说得通

`pnpm run gate:full` 收尾是 `fail 40/41 项通过（mode=full）`，唯一红项 `patch-anchors`，
四条违规全指向 `packaging/staging/2.2.0/app` 与 `staging/2.3.0/app` 缺 G1「HMR 生产守卫」
与 G2「console 转发」。

第一反应是「陈旧构建产物，清了就好」。这个读法**部分正确**：那两棵树确实不该被当成可发布物。
但它解释不了三件事，而这三件事合起来把结论翻了过来。

### 一、红的与要拦的，在输出上不可区分

锚点清单**单调增长**（36 → 38 → …，每加一条运行时守卫就多一条）；`packaging/staging/` 是
**累积的历史堆积**。两条各自正确的规则相乘，结果是：任何一棵在「某条锚」出现之前装配的树
**永久**判红，而这条红与「本次装配把补丁弄丢了」长得一模一样。

这正是 `packaging/verify-patches-v2.sh` 头部写下过的教训：

> 把历史版本号（曾为 2.0.0）硬编码在默认值里，会随目录裁剪变成结构性红灯：
> 表现为 35 条 MISSING，与「补丁真的漂移」在输出上不可区分。

当时修的是**脚本默认值**，同一根因随后从**门禁扫描集**长回来。**同一根因，第二次。**

### 二、那棵「绿」的树也不可信

| 版本 | `staging/<v>/app` 里守卫文件 mtime | 该版入库清单记的 build | 结论 |
| --- | --- | --- | --- |
| 2.2.0 | 09-12 22:20:42 | （早于 ADR-0058 清单机制） | DMG 23:14 → 产物确实无守卫 |
| 2.3.0 | 09-13 12:34:07 | 12:39:45 | DMG 12:45 → 产物确实无守卫 |
| 2.3.1 | **09-13 14:07:15** | **12:53:55** | 树在**发布之后**被就地改过 |

2.3.1 那棵树当时是最新的树，守卫开发中顺手 patch 了它。于是 `patch-anchors` 对它的绿
**不证明任何出厂字节**——扫描集里同时住着两种不可信：永久红的历史树，和被改过的假绿暂存树。

### 三、射程为空时，本项静默报绿

```js
// 旧代码（gate.mjs）
if (targets.length === 0) return { passed: true, violations: [] }
```

更早一步，`main()` **根本不渲染 `note`**：`passed: true` 一律打成 `ok contract <名字>`。
于是三处 check 注释里写的「环境不存在时跳过，不假绿也不假红」，在**读数上完全同形**。
模型里有这个区分、读数里没有——等于没有（P-02 的第二种形态）。

**空射程恰恰是「清理过之后」的必然状态**：删掉那两棵树不会有任何东西说话，门禁看起来被修好了，
实际是被弄哑了。清理于是成了一条能修仪器的捷径。

### 四、同源镜像：搜索工具的沉默不是缺席的证据

同日并发会话实测：2.3.1 曾在「Spotlight 全盘查不到 dmg」的取证下被宣告永久丢失，
18:06 却从飞书落地目录找回了**哈希逐位相同**的副本。那份副本在宣告之前就已经在。

本 Note 修的是它的对偶：**射程为空的沉默不是合格的证据**。两处的错法都是把
「我没看到」当成「不存在」。

## Decision

1. **射程判据落到 `scripts/gates/patch-anchor-scope.mjs`**（纯函数，可反向自测）：
   射程 = 本机 `/Applications` ∪ `packaging/staging/` 下**未打 tag** 的 app 树。
   判「已发布」的权威家是 **git tag**——ADR-0058 的口径（清单入库 → 打 tag，tag 才担保得住字节）。
   已有 tag 的版本由产物负责：`packaging/release/<版本>/` + 仓库外归档 + `uchg` 锁（ADR-0067）。

2. **读数分三态 `ok` / `skip` / `fail`，`note` 必须渲染。** `skip` = 「本项没量到任何东西」，
   不计入通过数。`theme-tokens` 与 `worktable-fence` 的「环境不存在」路径接到同一状态上：
   它们早就声称会跳过，只是读数里看不出来。

3. **不删除任何 staging 树。** 射程判据让历史树**自动退出**扫描，不需要谁记得清理。
   删目录是这条路的**结果**，不是**手段**——2.3.1 找回之前，`staging/2.3.1/payload` 曾是
   本机唯一残存的字节痕迹，而「清掉陈旧 staging」这条压力正好指向它。

4. **判据的默认错误方向选「多量」。** 取 tag 而非「有无入库清单」：同号重制时旧清单仍在
   `release/` 里，按清单判会把**重制出来的新树**静默排除（门禁对一棵从未量过的树说 ok）。
   读不到 tag 时全部纳入。

## Alternatives considered

- **删掉 `staging/2.2.0`、`staging/2.3.0`**：红会消失，但仓库里再没有任何地方记录
  「v2.2.0 / v2.3.0 出货时不含 G1/G2」；而且它清空的正是门禁的输入，而空射程当时报绿。
  **否决：用打扫卫生修仪器。**
- **把已发布版本登记进 `exemptions.json`**：豁免是「存量未达标」的家（只减不增）。这里的问题是
  **判据射程错了**，不是对象劣于标准；登记进去等于承认「已发布版本应当通过今天的锚点集」。
- **让空射程继续静默绿**：即现状，也是最需要说话的时点。
- **按「有无 `release/<版本>.sha256`」判已发布**：会把同号重制的新树静默放行。
- **只改注释与文档**：已经写过一次，第二次从门禁长回来。

## Consequences

- `patch-anchors` 转绿，且把射程写进读数：

  ```
  ok   contract patch-anchors（扫描 本机 /Applications；待发布 staging：2.3.2 2.3.3；
       已发布（有 tag，由 ADR-0067 归档负责）不参与：2.2.0 2.3.0 2.3.1）
  ok   contract patch-anchors-scope-selftest
  ```

- 门禁项 41 → 42；新自测 7 个用例，钉住两个方向的退化：把过滤换成「无条件纳入」、
  把空射程恒置 `false`——两种恒真桩突变下用例必须变红。
- 顺带纠出一条**出货事实**（此前无家）：随包出货的锚点尺子是逐版不同的——
  2.2.0 / 2.3.0 / 2.3.1 载荷内是 **36 锚点、无 G1**；2.3.2 / 2.3.3 是 **38 锚点、有 G1**。
  即 **G1/G2 首见于 2.3.2**。这条已补进 [CHANGELOG](../../../../packaging/CHANGELOG.md)。
- **遗留一**：`verify-patches-v2.sh` 的默认 `STAGE_VERSION=2.3.1` 仍陈旧（裸跑验的是**已发布**的树）。
  今日**故意不修**：它在出货载荷里，改动会与已装配的 2.3.3 载荷不同源
  （`gate:staging-freshness` 会判红），须随下一版一起改。
- **遗留二**：v2.3.2 有入库清单、有已归档锁定的产物，却**没有 tag**，故仍留在射程内。
  这不是缺陷，是口径如实（ADR-0058：tag 才担保得住字节）。
- **遗留三**：无 tag 的环境会全量纳入；那里没有 staging 树，实际无影响。
