# 一张卡到底开没开：技能调用状态的真值归属，与「看不懂的词」（ADR-0070）

> 决策记录（ADR-0015 的 Note 侧）。决定本身见 [ADR-0070](../../../adr/ADR-0070.md)；
> 页面契约与数字口径见
> [`packages/surfaces/dsh-algo-skills-local/README.md`](../../../../packages/surfaces/dsh-algo-skills-local/README.md)。
> 本轮**只改了显示与真值归属**，没有改任何 preset 的装配语义——那一条是下面「已知未决」的第 1 项。

## Problem

使用方对「设置 → 算法技能」提了两条反馈，看起来是文案问题和一个偶发 bug，实际是三个独立缺陷：

1. **四个统计词读不懂**：已归位 / 未归类 / 本岗已接线 / 空白岗位。
2. **「有些卡片打不开，技能卡片右上角的开关被冻结关闭了」**。

第 2 条在诊断中被拆成三个互不相同的事实，其中只有一个是「开关坏了」：

### 缺陷 A：技能中心面板的开关是真的会弹回去（真 bug，已修）

线上 `GET /api/dsh-skill-explorer/list` 的读数：1623 条里 **1613 条 `modelInvocable: false`**，
而磁盘上只有 197 个非 `p2s-` 技能写了 `disable-model-invocation: true`。逐条对照文件真值后，
**77 个技能是「文件说开、面板说关」**——全部是 `~/.dsh/skills` 下手写的那批
（`code-review`、`codebase-design`、`loopx-*`、`pb-001`..`pb-008`、`understand-*` …）。

决定性实验（对象 `code-review`，此刻零净变更）：

| 步骤 | 读数 |
| --- | --- |
| 文件真值 | `disable-model-invocation: false`（模型可调用） |
| list 视图 | `modelInvocable: false` / `provider: "runtime"` |
| `POST set-enabled {enabled:true}` | `{"enabled":true,"modelInvocable":true}` |
| 写后文件 | sha256 与写前**逐字节相同**（`87680ee5…2fdd2`）→ 本来就开着 |
| 再看 list | **仍然是 `false`** |

写盘是对的、接口回的是 `true`、文件没动，**面板照样显示关**——所以用户点一下、亮一下、重渲染又灭回去。
这正好解释了「有些」：只是那 77 张（其余 1535 张文件本来就是关的，两个来源恰好一致，看不出来）。

成因不在注册表「说谎」，而在**我们自己的合并规则**（`dsh-skill-center-local/src/collect.ts`）：
文件扫描早已给出 `provider: 'filesystem'` 与文件里的调用开关，合并时却被同名注册表条目
**无条件反向覆盖**。而那个条目是**预设作用域的遮蔽**，不是同一张卡：

- `dsh-skill-subset` 挂在 **51/52** 个 `agt-*` 预设里（`agent.cordis.yml`），名单 5–8 个，
  `respectFileFlags: true`，**没有一处写 `hideOthers: false`** → 默认 `true`；
- `hideOthers` 会把 `~/.dsh/skills` 里**名单之外的每一张卡**注册成
  `{modelInvocable:false, userInvocable:false}`，`provider` 记为 `runtime`；
- 这个注册在宿主级 `skills.snapshot()` 里可见，于是覆盖了扫描结果。

**它是遮蔽而不是「文件真值缺失」的证明**：诊断中新建一张探针技能，它报
`provider: "filesystem"` / `modelInvocable: true` ——遮蔽名单是**启动时的目录快照**，
启动之后新建的卡不在名单里，所以不被遮蔽。旧卡被遮蔽、新卡不被遮蔽，这就是指纹。

修法只有一处：文件扫描赢得优先级，且它自己回答过的字段（provider + 两个调用开关）
**不再被注册表覆盖**；注册表只补 `whenToUse` / `title`，并照旧贡献 bundle/runtime 独有条目。

### 缺陷 B：算法技能页的开关没坏，但全库默认关、页面从不解释

算法技能页走**文件真值**，与注册表无关。1338 张卡**全部**写着
`disable-model-invocation: "true"`，所以 1338 个开关全是关的。这是 [ADR-0031](../../../adr/ADR-0031.md)
的有意设计（全局模型目录已占约 7.2 万字符，可见性只经 preset 白名单开放），
不是冻结。实测开关本身可用：`p2s-business-scale-kpi-growth-achievement` 由 `"true"`→`"false"`，
tree 回读 `modelEnabled=true`，反向写回后 sha256 与改前一致（`300900cb…b99c99`）。

也没有「点不动的卡」这一类：1338/1338 目录名与 frontmatter `name` 完全一致，
全部通过写入路由的 `P2S_NAME` 闸门，没有一张会 404。

**但页面从不解释这件事**，而且它自己就印着一句会误导的话：`chip.off`（「模型不可自动调用」）
在 `locales.ts` 里定义了却**从未渲染**（全仓 grep 零引用）。于是「本岗已接线 + 开关关着」
这个矛盾状态在界面上没有任何解释——用户只能理解为「坏了」。

### 缺陷 C（本轮未修，见「已知未决」）：白名单被文件开关反向否决

`dsh-skill-subset` 的正向注册是 `modelInvocable: respectFileFlags ? !parsed.disableModel : true`。
预设写的是 `respectFileFlags: true`，而语料全库 `disable-model-invocation: "true"`
→ **白名单挂了它，它仍然不可调用**。实测全量：

- 50 个有白名单的预设、439 个白名单位，**275 个（62.6%）实际不可被模型调用**；
- **没有任何一个预设是全部生效的**；
- agt-001（衡远）8 个白名单里 6 个失效，只有 `pb-002` / `pb-008`（没写该键）真的能用。

这就是「打不开」在**效果层**的真身：用户进岗位会话，以为本岗技能可用，实际 62.6% 不可达。
页面上的「本岗已接线（会带上）」在 preset 层是真的，在模型层是假的——两个事实混在一个词里。

## Decision

见 [ADR-0070](../../../adr/ADR-0070.md) 的三条：

1. **技能调用状态的真值只有一个家：技能文件。** 注册表可以提供元数据（whenToUse / title）
   与它独有的条目，但**不得覆盖**文件对 provider 与两个调用开关的回答。
2. **面向使用方的词必须自解释**：统计口径改成业务白话，并在**页面上**（不是只在 tooltip 里）
   给出一段口径说明；定义了的文案必须被渲染（`chip.off` 的教训），且这条由测试守着。
3. **矛盾状态必须明说**：卡被本岗装配、但模型不会自动调用时，卡上直接标出并指向开关。

## Alternatives considered

- **改注册表用法：调用 `registry.snapshot({cwd})` 时带作用域参数，避开预设遮蔽。**
  被否：遮蔽是**宿主级快照里已经可见**的事实（读数是 `provider: runtime`），
  不是查询姿势问题；而且「带哪个作用域」需要面板知道自己是哪个预设——技能中心是全局管理器，
  它没有、也不该有预设身份。改合并规则是不依赖调用方的修法。
- **把 51 个预设逐个加 `hideOthers: false`。** 被否：`hideOthers` 默认开是该插件的**既有设计**
  （「该 preset 的模型目录与 `/` 菜单只显示子集」），关掉它会让 50 个岗位会话各暴露 1600+ 张卡，
  与 [ADR-0031](../../../adr/ADR-0031.md) 的意图正相反。预设作用域内的遮蔽是**对的**，
  错的是它泄漏进了全局管理器的显示。
- **在面板上按「注册表说了算」显示，但把开关改成写注册表。** 不可能：注册是插件的运行时行为，
  面板写不进去；而且那样开关就不再是「这张卡开不开」，而变成「这次会话开不开」，语义被换掉了。
- **算法技能页把开关全部默认打开（批量翻转 1338 个文件）。** 被否：那是产品决策，不是 bug 修复。
  全库默认关是 ADR-0031 写下的取舍（模型目录体积），改它要连白名单语义一起重新设计
  （缺陷 C）。本轮不动数据。
- **只改 tooltip，不加常显说明。** 被否：使用方的反馈就是「看不懂」，而没有人会去悬停一个
  自己还没打算在意的数字。解释必须在页面上。
- **只在算法技能页修文案，不碰技能中心。** 被否：缺陷 A 是真 bug，且它让开关的承诺
  （「点一下就能打开」）变成假的；留着一个会弹回去的开关，文案改得再好也只是把问题说圆。

## Consequences

- **正面**：
  - 技能中心的开关不再弹回：面板显示的是文件的回答，而写盘写的也是文件——两个方向现在一致
    （也修掉了反向的错：注册表曾能把**文件已关**的技能显示成开着）。
  - 算法技能页每个数字自带一句短解释，页面上另有一段口径说明；「本岗会带上 + 模型不会自动调用」
    的矛盾状态有专门的提示与指向。
  - 合并规则的两条测试**先红后绿**地钉死了两个方向（遮蔽说关 → 仍开；注册表说开 → 仍关），
    外加「注册表独有条目保留自己的开关」的反向保护。
  - `chip.off` 这一类缺陷拿到了**机制**而不是约定：新增
    `tests/copy-wiring.spec.ts` —— locales 里每个键要么被渲染、要么登记在只减不增的清单里
    （照 `exemptions.json` 的规矩）。它落地时当场抓到了一条我自己写错的清单条目
    （`nav` 其实是接线的），即「清单只能减」这条判据在第一次运行就生效了。
- **负面 / 边界**：
  - **修复原落在仓库 fork 里，本机装配已完成**：线上技能中心本来跑的是 npm
    `@linxin666/dsh-client-ui-skill-explorer@0.3.6`（`/api/dsh-skill-explorer/health` 回
    `{"plugin":"skill-explorer"}`），其 `lib/index.js:407-409` 是与 fork 同一处的缺陷。
    已按 ADR-0061 把 fork `dsh-skill-center-local` 装进本机 profile（vendor 与装载点两份
    与仓库产物逐字节一致），并在 profile patch 里停用 npm 那一行——两者会注册同一组
    `/api/dsh-skill-explorer/*` 路由与同一个侧边栏入口。`dsh plugin --profile desktop` 被
    CLI 拒绝（「managed exclusively by the Electron application」），故为手工装配。
    **生效需重启应用**（插件花名册在加载期读取），重启后 health 的 `plugin` 字段应从
    `skill-explorer` 变为 `skill-center-local`。
  - 遮蔽在预设作用域内**依然存在且是对的**；面板只保证「这张卡在文件层面开不开」，
    不承诺「在某个岗位会话里一定可达」。这两个问题现在是分开的两个问题——这正是缺陷 C。
  - 算法技能页的 1338 个开关仍然默认关着（数据未动）。
- **后续动作**：
  - **缺陷 C 待决策**：275 个失效白名单位怎么办——翻转这些卡的文件开关（模型目录会变大）、
    还是把正向注册改回不尊重文件开关（设置页开关在预设会话内失效）、还是别的组合。
    三条路的代价见上文实测数字。
  - **技能中心的投递路径待决策**：把 fork 装进 profile（[ADR-0061](../../../adr/ADR-0061.md)
    的本地装配路线）还是让 npm 包发一版。
  - 反馈里若仍能指认「具体哪张卡、在哪个页面点、期望它做什么」，可用来判定是否还有第四类缺陷；
    本机扫描 1338/1338 与 1612 张的文件真值已全量对照，没有第四类的证据。
