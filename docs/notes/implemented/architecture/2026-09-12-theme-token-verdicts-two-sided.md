# 主题 Token 的判据要两侧共同证伪：真实 CSS 引擎 + 真实供给函数（ADR-0029）

## Problem

上一轮把「无硬色值（只走 `--dsw-alias-*`）」从**口头验收**变成了门禁项 `theme-tokens`。
它的「已定义」是**静态文本提取**：对应用目录 grep 出 `--dsw-x:`，对本仓库 `src/` 正则
找 `"--dsw-x":` 字面量。这次去查它的判据本身，实测到两件事。

### 取证 1：命名空间只覆盖了一个前缀

对 `packages/*/src` 里所有 `var()` 引用按前缀统计（2026-09-12 实测）：

| 前缀 | 引用数 | 性质 |
| --- | --- | --- |
| `--dsw-*` | 719 | 平台命名空间 |
| `--appearance-*` | 30 | **组件局部变量**：`studio.css` 里 `--appearance-accent: var(--dsw-alias-state-business-primary)` 自己定义自己用 |
| `--card-*` | 4 | **组件局部变量**：`views.module.css` 的 `.projectCard { --card-tint: #5b8def }` |
| `--ds-*` | 3 | 平台命名空间：`--ds-font-family-code`，官方 CSS 有声明，本仓库在 `theme-tokens.ts` 里真的用它 |

旧口径只扫 `--dsw-`，于是**一整类错别字两边都扫不到**——门禁看不见，页面照走字面兜底。
这正是 `theme-tokens` 这一项当初要根除的静默失败，只是换了个前缀。

局部变量那两族**不该**收进来：它们不是平台供给的名字，收进来只会造出一批假阳性。

### 取证 2：「门禁说已定义」有两种理由，失效方式不同

- **官方 CSS 声明**：源码里有、级联里可能永远不生效（被后写规则覆盖、落在未生效的
  媒体查询里、写在匹配不到的选择器下）。
- **本仓库主题插件的 JS 供给**：门禁的判据是「`"--dsw-x":` 这个字面量在 src 里出现过」。
  但真正决定发不发它的是 `buildThemeTokenOverrides(settings)` 的返回值。写在**永不进入
  的分支**里，正则照样命中、门禁照样判已定义，页面里却依旧走字面兜底。

两条路径要用两种方法证伪，混成一条会把自家供给全判成门禁假阳性——那正是假阳性：
它训练人忽略输出，真正的违规就藏进噪音里。

## Decision

1. **门禁命名空间扩到平台自身的三个前缀**：`--dsw-` / `--ds-` / `--dsh-`（`NAMESPACE`），
   引用侧与定义侧同步扩。
2. **新增按需验收探针** `scripts/acceptance/theme-tokens-live.mjs`：真实 Chrome + 逐字取自
   产物的主题样式表 + 逐字调用 `buildThemeTokenOverrides`，与门禁判据逐条对照，分歧按
   「官方声明」与「自家供给」两路分别点名。
3. **探针必须带仪器自检**：正控（必须解析成功）、负控（必须解析为空）、切主题确实生效
   （浅深两态必须解析出不同值）。任一条不成立即 **exit 2**，绝不在仪器坏掉时产出一片绿色。
4. **把「解析成功」与「在这一态里真的产生了一个面」分开**：与抽屉底色同色的 token 单独标注，
   让这一类同族静默失败出现在报告里，而不是靠肉眼。

## Alternatives considered

- **只扩命名空间，不做探针**：最便宜，但治不了取证 2 的假阳性——门禁在结构上看不见它。
- **把探针做成门禁项**：它需要 Chrome 与已安装的应用。做成门禁项后，在没有这些的机器上
  只能要么失败（不可用）要么静默跳过（把「已验收」变成「没验」）。与 `patch-anchors`
  同一性质的问题，选择保持为按需验收产物。
- **直接打开实况 GUI 验（`http://127.0.0.1:43120`）**：实测 `/` 与 `/api/...` 均返回 **401**
  （浏览器信任栅栏要求已配对设备的凭证）。要打开就得先在用户**正在运行**的实例上完成一次
  配对，那是对用户环境的侵入，且会把「验 token」和「验实况页面」两件事混在一起。
- **在探针里重写一份 token 清单**：违反 ADR-0009，且清单从建好那一刻就开始漂移。

## Consequences

### 正面

- 扩命名空间后（实测）：引用 90 → **91**、官方已定义 358 → **393**、自家已定义 66 → **67**。
  **自家字面量扫描与真实供给函数的输出首次完全一致（67 = 67）**——此前差的正是
  `--ds-font-family-code`。
- `pnpm run gate --mode full` **17/17 退出码 0**：扩命名空间没有产生新违规。
- 探针实测：91 个引用 token 在两条供给路径上**零分歧**；本包 15 个 token 全部解析成功、
  13 个跟随主题。
- **变异测试（证明探针非空转）**：在 `buildThemeTokenOverrides` 上方注入一个只出现在
  永不进入的分支里的字面量键 `--dsw-alias-zzz-mutation-probe`，并让本包引用它 →
  **门禁仍然通过**（结构上看不见），探针 **exit 1** 且逐字点名该 token 与两个文件；
  还原后门禁 17/17、探针 exit 0。

### 负面 / 未决

- 探针不进 `pnpm test`（需要 Chrome 与已安装应用），是**按需验收产物**，与
  `scripts/acceptance/root-brand-live-anchors.mjs` 同一性质：它**不会自动阻止回归**，
  只在有人主动跑它时说话。
- 探针测的是「**产物里的样式表在真实 CSS 引擎下如何解析**」，不是「实况页面此刻长什么样」。
  后者仍挂在重启后的实况验收（C4）。

### 由它暴露出来的一条产品事实（**未改动**）

官方浅色主题里 `--dsw-alias-bg-base` / `-layer-1` / `-layer-2` / `-layer-3` **全部解析成同一个白**
（静态色阶 `bluish-00` 如此）——浅色主题靠**边框与阴影**表达立面，深色主题才靠**底色**。
于是本包 `.total` / `.chipMuted` 两个**只靠底色定义、没有边框**的药丸，在浅色下与抽屉底色同色。

上一轮把幻觉 token 换成 `--dsw-alias-bg-layer-2`，修好了深色，代价是浅色失去原有的
`rgba(0,0,0,0.05)` 字面兜底。**这次没有改**：官方自己的 `.pill`
（`dsh-web-frontend/dist/assets/index-b24khbeK.css`）用的就是 `bg-layer-2` 且无边框，与平台一致；
单方面改动会在两态都改视觉，而实况验收（C4）还没跑。该事实现在出现在探针报告的
`newappFlatWithSurface` 里，不再依赖肉眼。
