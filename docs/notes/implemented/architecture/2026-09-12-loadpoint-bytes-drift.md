# 改动生效的判据是装载点的字节：用户屏幕说「胶囊还在」，门禁说「全绿」

- 日期：2026-09-12
- 状态：implemented
- 决策记录：ADR-0054
- 相关设计稿：[.scratch/newapp-midcol-design/plan.md](../../../../.scratch/newapp-midcol-design/plan.md)（R1–R8 寄存器；本轮改的是 R3 的默认值与 R1 的交付判定）
- 上一轮：[2026-09-12-composer-role-capabilities.md](2026-09-12-composer-role-capabilities.md)（ADR-0053）

## Problem

上一轮交付（ADR-0053：输入框下方新增「分身能力导引」）被用户验收退回两条：

1. **「出海技能」和「AI全栈技能」并没有从对话框上方消除。**
2. **「对话框下方要求默认是收起来，目前是展开状态，特别长。」**

第 2 条是设计决定被推翻（R3 当时写的是「默认全开」），第 1 条则是一次没有任何迹象的失效——R1 的代码改动在仓库里、测试全绿、门禁全绿。

第 1 条的诊断：**仓库里改对了，应用跑的是旧字节。**

`packages/capabilities/dsh-overseas-skills/lib/client.js` 在仓库里已经不再注册 `conversation.input.dock`（`OverseasPaletteStack` 整段已删），但 DSH 的真实装载点

```
~/.dsh/profiles/desktop/node_modules/dsh-overseas-skills/lib/client.js
```

仍是带该组件的旧版——66,796B / mtime 14:23，而仓库是 52,671B / mtime 18:01。应用于 18:34 启动，读的是装载点那份。

三个原因叠加才让这件事无声发生，**缺任何一个都会被当场发现**：

| # | 环节 | 为什么没拦住 |
| --- | --- | --- |
| 1 | profile 里的 `file:` 依赖是**硬链接实体副本**，不是符号链接 | 编辑工具 tmp+mv 落盘换掉 inode，硬链接当场断开；此后每次构建都只写进仓库那一份 |
| 2 | 该包的契约测试读**仓库**文件 | 断言的是「源码里没有两枚胶囊」，因此全绿 |
| 3 | 门禁 `profile-files-sync` 只断言**文件在不在** | 副本旧、但它**在**，因此也全绿 |

于是「门禁全绿 + 功能没生效」可以同时成立，唯一的证据在用户的屏幕上。

诊断时顺带查出两处同族缺陷：

- 门禁 `profile-metadata-sync` 盯的是 `<profile>/vendor/`，而 `vendor/` **不是装载点**——它只是「内嵌 profile 拷贝物化」的判别标记（harness 全仓仅一处引用：`existsSync(join(profileDir, 'vendor'))`）。真正的解析锚点是 profile 根 `package.json`（`resolveOverlayPackage` 的 `profilePackageUrl`）。这条校验一直在看一份没人执行的东西，却在报文里自称「live profile 副本」。
- `scripts/sync-profile.mjs` 同样只写 `vendor/`。所以当晚「同步一下就好」这句话本身是错的：照它做，用户屏幕不会有任何变化。

## Decision

**一、把「改动生效」的判据钉在装载点的字节上，且只钉可执行的产物面。**

- 新增门禁项 `profile-bundle-sync`：对仓库受管、且已在装载点安装的每个 `file:` 依赖，逐文件比较字节，不一致即失败，报文里带可执行的修复命令。
- 断言面 `loadPointFiles` 规则**一处定义、门禁与同步脚本共用**，避免校验面与修复面各写一份然后悄悄分叉：
  1. `lib/` 顶层的 `*.js|mjs|cjs`——**直接读源码目录**，不读 `files` 清单（有的包用 `lib/**` 通配声明，按清单取会一个都取不到，恰好漏掉最该盯的文件）；
  2. `files` 清单里声明的**文件**条目（`manifest/*.json`、`cordis.patch.yml`…）。
- 排除面同样写进代码注释：`lib/types/**`（类型产物）、`*.d.ts`/`*.map`/`*.tsbuildinfo`、`.md`、通配条目、声明的**目录**条目、以及 `package.json`（pnpm 在装载点**重写**它：剥掉 `devDependencies`/`scripts`，拿它比必然不等）。
- `scripts/sync-profile.mjs` 增加 `--loadpoint`，把修复落到真实装载点（tmp+mv 原子替换）。
- 作用域限定为**本仓库受管的包**：别的项目自己的 `file:` 依赖漂移不在本门禁里判。

**二、输入框下方那一面改为默认收起（推翻 R3 的「默认全开」）。**

- 收起粒度＝**每一列的列体**，列头仍在：三列组头并排（名称 + 覆盖等级徽标 + 供给数）仍然一眼回答「这个岗位有哪些能力」，变短的只有列体。这与用户此前对卡片墙的「默认收起」是同一个形状（一行头部带计数，正文在开关之后）。
- 语义依据是用户自己给的目标：能力要「清楚」且「有层级」。整体收成一行摘要会把这个目标一起收掉，所以不采用。
- 场景手册一条不折——它是一行 chip，不是长度来源。

## Alternatives considered

**门禁口径**

- **断言整个包目录逐字节一致**：更彻底，实测在本机立刻多出 3 条与运行时无关的红（deepresearch 的 `lib/types/**` 类型产物、KOL-Hunter 的 `client.template.js`）。门禁为噪声变红的下场是被整体忽略——那正是本次要修的病，不能在这里复发。
- **只断言 `files` 清单声明的条目**：漏掉用通配声明的 `lib/client.js`；而且清单是「交付形态」的声明，不是「装载点执行什么」的事实。
- **保留 `vendor/` 校验，只加一句注释说明它不是装载点**：不解决任何问题——用户的症状就是「照门禁做了，屏幕没变」。
- **不建门禁，把这两个文件手工同步过去**：下一次任何人用编辑工具改 `lib/*.js`，坑原样复现。2026-09-11 `dsh-preset-lint-local/lib/lint-preset.mjs` 丢失是第一次，本次是第二次。

**收起粒度**

- **整体收成一行摘要**（如「能力导引 · AGT-027 守店 · 3 组 / 12 项 ▸」）：最短，但把能力组名一起藏了，违背「一眼看到它有什么能力」的初衷。
- **保持默认全开，只把列数从 3 降到 2**：长度问题只缓解不解决；且 R8 的三列是用户明确要的。
- **默认收起 + 场景手册也折**：再省一行，但手册是 chip 行、不是长度来源，折掉只是让要点两次。

## Consequences

- **正面**：失效模式有了结构性哨兵；修复方向变成一条与门禁共用判据的命令；本机当场抓到第二条真实漂移——同一包的 `manifest/role-assignments.json` 停在 172,674B（仓库 197,708B），它是 `lib/role-map.js` 的构建输入，装载点旧一份意味着任何直接读它的消费者会拿到过期的归位表。
- **反直觉的好消息**：`tsdown` 是**就地写** `lib/client.js`，硬链接在构建后仍存活（实测构建前后 inode 相同、sha256 相同）。真正打断硬链接的是**编辑工具**。所以常规构建路径不需要手动同步，门禁的告警面因此收窄——这也解释了为什么这个坑只在手改文件时出现。
- **负面**：这条门禁守的是**开发机的真相**，不是 CI 的真相（profile 未安装时按「未安装即跳过」，与同族两项同语义）。这是刻意的：失效只发生在开发机。
- **负面**：默认收起之后，供给卡需要一次点击才可见。代价被两处断言守住：`tests/hero-entry.spec.tsx` 断言「默认收起 + 点开/再点收起」的契约（变异测试：把默认改回全开 → 6 条转红），真 Chrome 探针断言收起态的几何（`N1` 三列仍在、`N2` 列体不在 DOM 且列高 = 组头高 + 边框、`N3` 行高 200.5px → 50.0px）。
- **未覆盖（如实登记）**：`dsh-kol-hunter-local` 的源码在另一个项目 `/Users/lute/project/KOL-Hunter`，其 `lib/client.template.js` 同样漂移（仓库 11,714B vs 装载点 10,383B）。按本次作用域不在本仓库门禁内，应由那个项目自己的流程处理。
- **仍未运行**：真实 GUI 的浅/深 × hero/active 四态目视回归。装载点字节与客户端 bundle 均需**重启 DSH Desktop** 才被读取，本轮未重启。
