# 「新应用」抽屉改成产品卡：声明原样中转，判据落在「点开必能用」

> 分类：architecture · 生命周期：implemented · 关联决策：[ADR-0033](../../../adr/ADR-0033.md)（发现与开入口的边界）、
> [ADR-0038](../../../adr/ADR-0038.md)（本轮同批压出的栅栏缺陷）、产品规格 `.scratch/native-agent-product/spec.md` §9 M2

## Problem

抽屉的第一版把「连接」的两半（岗位名册 + 工作台容器）各列一个区块。两半都是诚实的读，
但**都不是人能启动的东西**：名册是一张组织拓扑（50 个岗位来自材料），容器是会话分组。
用户的原话是「不要放岗位，只放已经通过 dsh 完成的 Agent 的产品矩阵卡片，点开可以直接用」。

要在 M2 落地，路上压出两个必须回答的问题，都不是 UI 问题：

1. **卡片要点开，就必须拿到「面板渲染表单所需要的那份东西」。** 入口面板的表单来自
   `product.json` 的 `features[].inputs[]`，而宿主半边返回的 `DeclaredProduct`
   是**归一化过的视图**——它有 `{id, label, kind, steps}`，**没有 `inputs`**。
   于是卡片能列出产品，点开却是一个没有字段的空壳。这不是疏忽，是**第一版把
   「卡片要什么」当成了「入口要什么」**。
2. **点开必须真的能开。** 三级回退里任何一级判错，表现都是「按钮看着能按、按了什么也没发生」——
   抽屉无法自证这件事，所以判据必须是可单测的纯函数。

## Decision

### 1. 声明原样中转，归一化只服务卡片

`DeclaredProduct` 增加 `declaration`（`product.json` 里那个对象的**逐字副本**），
与既有的归一化字段**并存**，理由是两者消费者不同、容忍度不同：

| 消费者 | 要什么 | 为什么不能共用 |
| --- | --- | --- |
| 卡片 | 一个不必再校验就能渲染的形状（id 非空、status 收敛、preset 有保证——ADR-0033） | 归一化字段就是这个 |
| 入口面板 | **声明本身**：`inputs[]` 渲染表单、`skills[]` 解析依赖、以及产品作者以后往里放的东西 | 那是**本插件不拥有、也不该重塑**的 schema；重塑它正是 `inputs` 被丢掉的原因 |

两者来自**同一次读取的同一时刻**，谁也不落盘，所以不存在第二份事实会漂移——只有一个中转。

### 2. 卡片列表 = 扫描出来的工作目录；岗位名册退成「一个问题的答案」

- 主区块 = **产品卡**（主键 = 工作目录，产品是卡上的选项，规格 §0 第 4 条）。
- 没有 `product.json` 的目录**照样列出**并标「尚未产品化」——丢掉它会让一个用户知道存在的项目
  看起来像被删了（ADR-0028 的 degrade-don't-disappear）。
- 名册**不再渲染**，只回答一个问题：*这个产品声明的岗位在本机存在吗？* 它是第 2 级回退
  （新建会话并选中岗位）能不能成立的前提。名册读不到时**按「不知道」处理并放行第 2 级**——
  因为另一个插件没装，不该把这张卡变成禁用。
- 工作台项目区保留在下方，标题写明「另一份事实，只读」，不再当第二块头条。

### 3. 点开的三级判据写成纯函数（`planOpen`）

| 级 | 条件 | 动作 | 按钮文案 |
| --- | --- | --- | --- |
| 1 | `entry.service` 已注册 | 把 `declaration` + 工作目录交给该服务的 `open()` | 「打开」 |
| 2 | 未注册，但声明的岗位在本机名册里 | 工作台那条已验证的三连：`sessions.create({cwd})` → `agentPresets.select` → `sessions.open` | 「开会话」 |
| 3 | 其余 | **禁用并写明原因**（没有声明 / 声明读不出 / 没写 preset / 岗位不在本机） | 「不可用」+ 原因 |

第 2 级按钮文案**刻意不同**：它不打开产品面板，说「打开」就是另一类假话。
第 3 级把原因**写成按钮旁的文字**而不是 tooltip——tooltip 恰好对需要它的那个人不可见。

## Read 实况

**真实 curl 探针**（`pnpm run accept:newapp-products`，19 条硬判分 + 1 条待重启复核）：

```
阶段 B · 信任栅栏          products-ok 200 → cross-site / foreign-origin / foreign-host 各 403，POST 405
阶段 C · 允许根与扫描语义    roots 原样回显；坏声明进 unreadable；不存在的根进 skipped（不是静默空）
                          → 声明原样中转读数：inputs=["a","b"] skills=1
                          → 未产品化目录照样列出（declared=false + note）
                          → 空配置冷进程：scannedRoots=[] cards=[]（安全默认）
阶段 D · 运行中的实例        health 200；worktable 同实例正控 403；products 401（宿主半边早于路由加载）
```

**单元测试**：newapp 116（新增 product-cards 14 条 + launcher 14 条 + 栅栏回归 2 条），
role-matrix 56，skill-center 74，全绿；`pnpm run gate` 14/14。

**一个刻意的诚实**：阶段 D 的两条要重启才能改变，探针**如实记为待复核**（`restartRequired`），
不由绿色假装已经改变。

## Alternatives considered

- **把 `inputs[]` 加进归一化字段**：否决。那等于把「产品声明 schema」复制一份到本插件里，
  以后入口要用 `skills[]` 或别的字段就得再改一次宿主——正是这次踩到的坑本身。
- **入口面板自己读 `product.json`**：否决。浏览器半边没有文件系统；让它去 fetch 启动器的路由，
  等于把「谁是声明的读者」变成两个，且面板必须自己解析一边。
- **卡片列表改为「扫描根 ∪ 工作台容器」的并集**：否决。工作台的容器记录只有 `{title, sessionIds}`，
  **没有路径**（实测 payload），并集只能靠标题与目录名猜——猜错的卡片就是「点开不能用」。
  宁可两个区块各自说自己是谁的事实。
- **把岗位名册整段删掉（不再读）**：否决但不反对。今天它还在为第 2 级回退与「声明的岗位是否存在」
  提供判据；等产品入口全部装齐、第 2 级真的没人走时再删，那时删的是**没有消费者的读**。
- **第 3 级按钮点下去弹提示说明为何不可用**：否决。能点但只弹解释的按钮，与不能点的按钮相比，
  只多了一次无效交互。

## Consequences

- 「点开必能用」第一次成为**可单测的判据**，而不是一句设计意图：三级各自的输入都是可观测事实
  （服务注册表、名册内容、声明字段），所以「按钮为什么不可用」能在没有浏览器的情况下被断言。
- 抽屉的读少了一半（不再渲染名册），但多了两条路由读：本插件自己的 `products` + 仍读名册做判据。
- `DeclaredProduct` 里出现「同一份数据的两种表示」，代价是响应体略大；换来的是
  **产品 schema 的演进不再需要改启动器**。
- 仍未运行：浏览器里的实际渲染与点击（需页面刷新 + 重启宿主半边）。**本记录不宣称已验证。**
