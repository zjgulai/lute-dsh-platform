# 三记忆系统的写入策略与来源域（Loop 4.1）

> 本文件是「谁写哪个记忆库」的**唯一事实源**（ADR-0009）。
> 实测时间：2026-09-11。证据为配置文件与数据库文件本身，逐条标注来源。

## 0. 结论先说：不存在三库并写

任务板把本 Loop 描述为「三记忆库」，实测**实为两个存储 + 一个桥接**：

| 名字 | 实际是什么 | 存储 | 实测状态 |
| --- | --- | --- | --- |
| **Noema** | 独立的持久记忆系统 | `~/.dsh/profiles/desktop/...`（tenant `personal`） | 活跃，写入策略 `review` |
| **LingShu（灵枢）** | 知识图谱 + 组合联想召回 | `~/.dsh/profiles/desktop/data/lingshu.db`（212 KB） | 活跃，最近写入 **2026-09-11** |
| `dsh-memory` | **灵枢的桥接插件，不是第三个库** | 同上（它自己不存数据） | 暴露 `lingshu_*` 工具 |

`dsh-memory` 的定位有代码级证据：它的默认 dbPath 哨兵落在 lingshu.db
（`src/index.ts:30-34`），且它向模型暴露的工具名前缀是 `lingshu_`
（如 `lingshu_remember`）——**包装的是灵枢，不是另有其库**。

## 1. 写入策略：已在配置里收敛，并写明理由

`~/.dsh/profiles/desktop/cordis.patch.yml:13-20` 原文：

```yaml
- id: dsh-memory
  config:
    python: /Users/lute/.dsh/aeis-venv/bin/python
    dbPath: /Users/lute/.dsh/profiles/desktop/data/lingshu.db
    # P2 记忆收敛：Noema 为主持久记忆；LingShu 降载（brain→core 12 工具）
    # 并关闭自动记忆（消除双写与上下文税），显式 lingshu_* 调用仍可用。
    tools: core
    memory:
      userMessage: false
```

即**双写问题已被处置**：

- **Noema = 主持久记忆**。状态端点实测 `write_policy: "review"` —— 写入先进复核队列，
  不直接落库。
- **LingShu 自动记忆已关闭**（`memory.userMessage: false`），并降载到 `core` 工具面
  （原 `brain` 12 工具）。**消除双写与上下文税**是配置里写明的动机。
- 显式 `lingshu_*` 调用**仍然可用**——降载不等于废弃。

## 2. 来源域标注：靠写入路径区分，靠 namespace 隔离

| 维度 | Noema | LingShu |
| --- | --- | --- |
| 租户/命名空间 | `tenant: personal`（状态端点） | 单一 SQLite，按 `tags` 分域 |
| 写入触发 | 显式 `noema_remember`（`review` 策略） | 自动写入已关；仅显式 `lingshu_*` |
| 典型标签 | 由调用方给（如 `lute` / `架构事实`） | `session` / `dsh` / `user` 等 |

**两者不共享命名空间，也不互相同步。** 因此「同一事实被两处写入」在当前配置下
**不会自动发生**——它的唯一来源是人或模型显式调用了两边的写入工具。

## 3. 已处置：陈旧残留（2026-09-11 删除）

| 路径 | 大小 | 最近修改 | 判定 |
| --- | --- | --- | --- |
| `~/.dsh/profiles/desktop/data/lingshu.db` | 212 KB | **2026-09-11** | ✅ 活跃库（配置指向它） |
| ~~`~/data/lingshu.db`~~ | 630 KB | 2026-08-31 | 🗑 **已删除** |

**删除前的三项确认**（避免误删）：
1. 无进程持有该文件（`lsof` 无输出）；
2. 无配置或环境变量指向它（`cordis.patch.yml` 指向 profiles 下的活跃库，
   `AEIS_DB` 未设置）；
3. 活跃库仍可读（13 张表）。

**一个容易漏掉的细节**：该残留**不止一个文件**，还有
`lingshu.db-shm`（32 KB）与 `lingshu.db-wal`（**4.1 MB 未检查点的 WAL**）。
WAL 里可能含尚未并回主库的写入，因此三件必须一起处理——只删 `.db`
会留下一个孤儿 WAL，既不完整也不再可用。备份因此打包了全部三个文件。

**处置方式**：先打包备份到 `_attic/lingshu-db-stale-20260831/lingshu-db-20260831.tar.gz`
（738 KB），再删除原件。恢复方式：`tar -xzf <备份> -C ~/data`。

`_attic/` 是仓库既有的归档位（既有 17 个退休条目），且**未被 git 跟踪**——
备份因此不入版本管理，符合该目录惯例（归档物留在本机，不进仓库）。

**为什么值得删**：一份体量更大（含 WAL 共约 4.9 MB）、名字更「正统」的旧库
留在 `~/data/` 下，任何按默认路径、或按「找最大的那个」选库的工具/人都可能
读到**过期数据**——而它看起来才像主库。

## 5. V2→V3 迁移评估结论（2026-09-11）

### 外部依赖已解除

任务板此前记「外部依赖：上游 0.1.5 发布」。**实测该依赖已满足**：

```
npm view @deepseek-ai/dsh-tools versions
→ …, 0.1.3-alpha.2, 0.1.5-alpha.1, 0.1.5-alpha.2, 0.1.5-rc.1, 0.1.5-rc.2
```

即 **0.1.5 的 rc 线已发布**（rc.1 / rc.2）。本仓库当前基线仍是
`vendor/dsh-runtime/0.1.2-rc.1/manifest.json`（见 `vendor/dsh-desktop.pin`）。

### 结论：**不迁移，继续观察**——依赖解除不等于触发条件成立

> **先澄清一个我一度搞错的术语**：任务板的「V2→V3 迁移」**不是记忆格式**，
> 而是**会话 JSONL 的持久层格式迁移**（上游 PR #898）。依据是仓库既有的研究文档：
> `docs/research/09-audit-architecture.md:199` 称其为「会话持久层将做真格式迁移
> （V2→V3 JSONL + keyed `main` 槽位 + 编码变更可选独立新根）」，并明确标注
> **「这是 n+1 内最大的数据工程」**。因此本议题的实体是**数据工程**，
> 与本文档化的记忆写入策略**分属两件事**——把它们混在一起判断会得出错误结论。

依据 ADR-0006（月度观察窗 + **红线触发制**）与 ADR-0008（基座只 pin 不改）：

1. **红线未触发。** 基线升级要连带 35 个补丁全量重锚 + 品牌重放 + 30 bundles
   rc 化 + 打包链路适配 + 升级场景端到端验证（2.0.0 那次的实测代价）。
   ADR-0006 背景明写「追赶快车会反复消耗重锚成本」。
2. **观察窗未走完。** 0.1.5 目前只有 rc 线（rc.1→rc.2 已在迭代），stable 未出。
3. **与记忆系统写入策略无关**（本文第 1 节已定：策略由本仓库配置与插件决定，
   不随宿主小版本漂移）。

### 迁移若启动，真正要处理的是这四条已定位的风险

这**不是本轮的发现**，而是仓库既有审计的结论
（`docs/research/09-audit-architecture.md` 风险表）。此处汇总，以免下次重新论证：

| # | 风险 | 要害 |
| --- | --- | --- |
| 1 | `SESSION_FORMAT_VERSION=0` 但 **seed 形状演进** | **常量冻结 ≠ 内部 shape 冻结**；「本构建不认识的每个事件类型都会拒绝重建」（fail-closed）→ 升后写的会话，**旧构建拒绝打开** |
| 2 | 会话持久层真格式迁移（V2→V3 JSONL + keyed `main` 槽位 + 编码变更可选独立新根） | 不兼容回写、双根并存、旧根只读化——**需要决策而不只是执行** |
| 3 | **投影缓存双份**（259 zstd/225M + 259 json/144M） | 重建触发条件与失效语义**未成文**；「换 runtime 即整缓存作废重建」目前只是**隐式假设** |
| 4 | `dsh-my-quotes` 的 zstd 多帧解码与官方 persistence **同构耦合** | 上游改容器参数（编码配置/新根/文本模式）即需同步改解码器，**否则静默索引停更且无告警通道** |

**第 4 条直接落在本仓库的自研插件上**，是 Loop 3「能力闭环」与本议题的交汇点：
它属于「跑不通就该降级标注」的那一类能力。

### 触发迁移的条件（写下来，避免下次重新论证）

出现以下任一情形时重开本议题：

- **安全类**：上游披露影响本发行版的漏洞，且补丁无法在本基线上落地；
- **阻塞类**：某项必要能力只在 0.1.5+ 提供，且无本基线可用的替代路径；
- **破坏类**：上游变更使现有 35 个补丁中的某项**无法**在当前基线上维持。

### 迁移若启动时的验收手段（Loop 2 已备好）

`packaging/verify-patches-v2.sh`（35 锚点、**哈希无关的 glob 定位**）与门禁校验项
`patch-anchors` 已就位——重锚后跑门禁即可判定，不必再靠人工比对。
这正是 Loop 2 本轮补上的能力，就是为这个窗口准备的。
