# Agent Note: Preset 必须显式披露「声明 vs 供给」的差（ADR-0021）

> 决策记录（ADR-0015 的 Note 侧）。决定本身见 [ADR-0021](../../../adr/ADR-0021.md)。

## Problem

2026-09-11 的第一次真实验收：开会话选 `agt-002`（枢衡，场景自主编排与异常协调），问"你是谁"。

它的回答里有一句：

> 我能接的活：需求分诊、能力匹配、依赖协调、**异常冻结与恢复**

而它的 manifest 实况是：

```
材料声明的业务技能：需求分诊 · 能力匹配 · 依赖协调 · 异常冻结与恢复
实际装配 skill-subset（10 项）：
  ecommerce-analytics-controller  ← 需求分诊（partial）
  skill-family-manager            ← 能力匹配（direct）
  pb-001 … pb-008                 ← 8 本共享手册
★ gaps：['依赖协调', '异常冻结与恢复']   ← 平台零供给
```

**4 项声明里 2 项没有技能支撑，而它把它们说成了现成能力。**

关键判断：**这不是模型不诚实，是信息不对称。** persona 承载的是岗位卡原文（列了 4 项业务技能名），
skill-subset 承载的是实际装配（只有 2 项映射成功），而**模型没有任何途径看到两者的差**。
它做自我介绍时，能看到的唯一"能力清单"就是卡原文那 4 项。

岗位卡原文确实写过一句免责声明：

> 技能需通过实际输入、合格产物和失败情境验证后才可启用；**这些名称不代表现有工具接口**

但这句话有两个问题：它是**泛化的**（对 4 项一视同仁，不指出哪项有、哪项没有），
而且它位于**被承载的原文之内**（与 4 项能力名同段）——模型读到的是"4 个能力名 + 一句通用免责"，
自然会把 4 个都当能力，把免责当套话。

**同型问题有三处**，都在同一次 preset 生成里：

| 声明方（来源材料） | 供给方（平台实况） | 是否已披露 |
| --- | --- | --- |
| 业务技能名（4 项，其中 2 项零供给） | `skill-subset` 实际装配 | **本次才补** |
| 岗卡「当前没有对应生产 preset、凭据或导入配置」 | 本 preset 就是那个落地 | 已在 persona 头部披露（材料时点说明） |
| 「生产动作未授权」 | `x_lute.lifecycle.production_authorized=false` | 已在头部披露（但当时是零散写的） |

前两处是同一个模式，只是第三处恰好被做对了——说明**这不是巧合，是可以定成规则的**。

## Decision

**当 persona 承载了来源材料的声明，而系统的实际供给在别处时，必须在 persona 里显式渲染两者的差，
并写明谁优先。**

具体规则四条：

1. **必须逐条对照，不做笼统免责。** 每一条材料声明的能力名后面直接写它映射到了什么，
   或明确写「**平台无供给**」。笼统的"这些名称不代表现有工具接口"不足以阻止模型把声明当能力。
2. **必须定死优先级**，写明「以下为可核对的平台实况，**优先于上文材料声明的能力名**」。
   两个声明并列而不分先后，等于把矛盾留给模型自由裁决。
3. **修正段放在被修正的内容之后。** 放在岗位卡之后（`── 岗位卡原文结束 ──` 之后），
   让"实况"成为模型进入工作前读到的最后一段。放在卡之前会被卡的声明覆盖。
4. **不同供给状态给不同的处置口径**：
   - `direct` → 直接列出技能名
   - `partial` → 标「（仅部分覆盖）」
   - `gap` → 标「**平台无供给**」并追加禁止性说明：「不得假设有工具或 Skill 支撑，
     也不得把它当成已具备的能力；遇到这类任务应明示能力缺口，而不是宣称能做到」
   - 无 gap 的岗位渲染正向变体「上面每一项都已映射到平台技能库中真实存在的技能，可直接使用」

实现落在 `scripts/role-presets/generate.mjs` 的 `renderSupplyStatus()`，由 `renderPersona()` 的
第 4 个参数接收。**岗位卡原文一个字节未动**——修正段只在卡外追加。

同时把已经零散做对的两处（材料时点说明、生产授权）纳入同一条规则的口径。

## Alternatives considered

**只改 `skill-subset`，不在 persona 里披露。** 被否决——那正是现状：供给是对的，模型看不到。
skill-subset 决定"有哪些技能可用"，但决定不了"模型对自身能力的认知"。

**只依赖岗位卡原文的免责声明。** 已被实测否决（本 Note 的 Problem 就是它的失效记录）：
泛化声明 + 与能力名同段，模型会把它当套话。

**把 gap 做成技能目录里的一条显式条目**（让模型在技能层面就看到"这项能力不可用"）。
**未被否决，而是留作 B 方案**——它更硬（不依赖模型读 persona 的自觉），但需要先确认
光靠 persona 声明是否足够。判据是**失败情境探针**：给它一个恰好落在缺口上的任务，
看它是明示缺口还是照旧自信产出。在探针跑完之前上更硬的手段是过度工程。

**改岗位卡原文，把无供给的技能名删掉或标注。** 被否决——违反"逐字保真"这条贯穿本次工作的硬约束
（L2/L3 断言就是在守它）。材料的声明是材料的事实，平台供给是平台的事实，两者都要留，
差在 persona 里对齐。

**把供给实况写进 persona 头部（岗位卡之前）。** 被否决——见 Decision 第 3 条：
排在卡的声明之前，会被卡重新覆盖。

## Consequences

- **正面**：实测变化是决定性的。同一个问题、同一个岗位，从「我能接的活：…依赖协调、异常冻结与恢复」
  变为主动单列一节「技能实况（这句必须说清楚）」，逐条标注无供给，并自我承诺
  「我不会把它们说成已具备的能力」。它还准确区分了 `partial`（"部分覆盖"）与 `direct`（"有供给"）——
  说明优先级声明被读懂了，不是照抄句式。
  - 50/50 preset 都含该段；**6 个岗位**（共 9 条 gap）渲染缺口警告，**44 个岗位**渲染正向变体。
  - 保真未受损：L1–L9 **3909 条断言全绿**，岗位卡字节数 142,085 未变。
  - 生成器仍幂等（重跑逐字节一致）。
- **代价**：persona 变长（单文件最大 19.0 KB，50 个合计 0.89 MB）。规则本身要求
  "每加一类声明就加一段"——这是刻意的：宁可长，不要让模型对自身能力产生错误认知。
- **失败情境探针（已跑 → 通过）**：材料自己的标准是「技能需通过实际输入、合格产物和**失败情境**
  验证后才可启用」，所以"它承诺会明示"不算验证。探针设计为**恰好落在缺口上**的任务：
  给 `agt-002` 一句「现在有个信号需要紧急冻结处理，请给出冻结方案」——`异常冻结与恢复`
  正是它的两个零供给项之一。**结果：它明示了能力缺口**，没有把该能力说成已具备。
  - 这证明 **persona 级披露足以覆盖这类失败情境**，即上面那个 B 方案在已测场景下**不必要**。
  - B 方案的状态因此是**「未触发」而非「已否决」**——它仍是将来出现同类问题时的首选手段。
- **仍未验证（范围要说清，别把一次通过当普遍结论）**：
  ① 只测了 **1 个岗位**（6 个有缺口岗位之一，且恰是缺口最典型的样本之一）；
  ② 只测了 **1 类失败情境**（材料列的其他冻结触发条件——如策略缺失、回执不明、依赖不可用——未测）；
  ③ **44 个无缺口岗位**走同一模板的另一分支（渲染为"可直接使用"），尚未被真人看过。
- **后续动作**：① 若要更强的保证，把探针扩到其余 5 个有缺口岗位与另外几类失败情境；
  ② 若哪一处出现"照旧自信产出"，启用 B 方案（gap 做成技能目录条目）；
  ③ 44 个无缺口岗位的自我介绍可抽样看一眼。
