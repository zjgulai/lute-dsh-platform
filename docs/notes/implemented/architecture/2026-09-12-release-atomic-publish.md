# 发布产物的发布语义：为什么「重跑一次构建」曾经会无声抹掉一份已经交付给客户的产物

- 日期：2026-09-12
- 状态：implemented
- 决策记录：ADR-0057
- 相关：[2026-09-12-shipping-surface.md](2026-09-12-shipping-surface.md)（ADR-0056；本条的「机读判据守护」与它的「只减不增基线」是同一条方法论）

## Problem

起因是一次误判风险：有人发现 `packaging/release/2.2.0/` 里的 DMG 不见了。排查脚本时，`packaging/sign-and-dmg.sh` 第 35 行被读了出来：

```bash
rm -rf "$REL"; mkdir -p "$REL"
```

`$REL = release/<版本>`。也就是说，**这个脚本每次运行都会先清空整个版本目录再重制**。

### 先把事故本身查清：不是这一行干的

不能把「文件不见了」直接归因给读起来最刺眼的那行代码。现场证据说了另一件事：

- `release/2.2.0/` 目录的 mtime 是 23:08，但里面的 `manifest.json`、`SHA256SUMS`、`VERSION` 三个文件**都保留着 22:50 的原始 mtime**。若 `rm -rf "$REL"` 真的执行过，这三个文件不可能还带着旧时间戳。
- `~/Downloads/DSH-Desktop-LUTE-2.2.0-mac-arm64.dmg` 的扩展属性是 `com.apple.quarantine: 0082;6aa56c42;Feishu;` —— 由**飞书客户端**下载产生；它的大小 639,234,068 与 SHA256 `e74fb6d0…4ac86e` 与消失前那份**逐字节相同**。文件是被移走后又下载回来的，从未被销毁。

所以真实原因是飞书客户端的文件流转，与脚本无关。**这一条必须写准**，否则会留下一个错误的事故史，把后续维护者的注意力引到错误的防线上。

### 但风险是真的，而且比看上去更糟

把「不是它干的」说清楚之后，第 35 行的问题仍然成立，且性质比「重复劳动」严重得多：

**它把「毁掉上一份产物」放在「新的一份还没做出来之前」。** 毁掉之后，`hdiutil create` → 挂载 → `codesign --verify --deep --strict`（Setup.app 与载荷内 app 两道）→ 才能拿到一份可发布的产物；其中任何一步失败——`hdiutil` 出错、验签不过、磁盘写满、Ctrl-C——留下的都是「旧的没了、新的也没有」。而 `rm -rf` 之后，旧产物在**任何地方都没有留下字节**，找不回来。

这与 ADR-0002 立下的契约正面冲突。那条 ADR 说 `release/<版本>/` + `SHA256SUMS` 是二进制交付物「可校验、可回滚的下载渠道」，也是**唯一**的交付家（二进制不进 git）。一个交付家可以被一次手滑抹平、且无法找回，那么「可回滚」这句话是不成立的。

### 同一轮读脚本还读出两个同族缺陷

**其一：无主构建锁会永久挡住构建。** 锁机制靠目录存在性互斥（`[ -d "$LOCK" ]` → 退出 1），而锁只在 `trap ... EXIT` 里清理——一次 SIGKILL 就能留下无主锁。现场 `packaging/release/.build.lock/` 就是一个**空目录、无 pid、无任何构建进程**的残留，mtime 22:49。它会让下一次构建直接以「另一构建进行中（…存在），请串行执行」退出，而**操作者没有任何手段判断这个锁是真的还是残留的**。

**其二：报错路径上有一处 bash 3.2 陷阱。** 原脚本的错误分支写着 `echo "...dmg 不可发布（$DMG）"`——裸变量紧跟全角左括号。macOS 自带 bash 3.2.57 会把多字节字符的首字节吃进变量名，在 `set -u` 下直接以 `unbound variable` 崩掉（本机实测：`bash -c 'set -euo pipefail; a=FOO; echo "$a（bar）"'` → `bash: a\ufffd: unbound variable`，退出码 1）。后果很别扭：**在最需要把话说清楚的那条路径上，脚本自己先崩了，什么都不打印。** 本仓库此前已经踩过并修过同族的一处（提交 `afe641c`）。

## Decision

已在 ADR-0057 中固化，要点与实现位置：

1. **`release/<版本>/` 只有两种合法状态：不存在，或一份完整且已全部通过终验的产物集合。** 没有中间态。
2. **构建与终验在 `$REL` 之外的临时区完成**（`release/.staging.XXXXXX`）。期间版本目录一个字节不动。
3. **就位靠一次原子改名**：临时区里先摊平 dmg + `SHA256SUMS` + `VERSION` + `manifest.json`，再整目录 `mv` 就位。不存在「dmg 换了、SHA256SUMS 还没换」的窗口。
4. **同号重制默认拒绝**（退出码 1，先于一切重活执行——秒级失败，不浪费一次数分钟的构建），打印目录内容与现有产物 SHA256，给出「换版本号」或「`--force`」两条路。
5. **旧产物归档不删除**：`--force` 下改名到 `release/.archive/<版本>-<时间戳>/`。改名不复制、不占额外空间，旧字节保持可回溯。
6. **构建锁记 pid**：持有者已消失则打印说明后回收；持有者仍在则拒绝并报出 pid。判据从「目录是否存在」换成「进程是否真的还在」。
7. **发布语义由可执行断言守护**：`packaging/scripts/release-publish-guard-test.sh`，沙箱化（脚本与其依赖被复制进临时目录，`PKG_ROOT` 由 `dirname "$0"` 推出），因此**永不触碰仓库 `release/` 下的真实产物**。

顺带修掉的：`$REL` 就位目录原本由 `mkdir -p` 建为 0755，改由 `mktemp -d` 建会变成 0700——就位前显式 `chmod 755`，避免权限在重构里悄悄漂移；以及上面那处 bash 3.2 全角括号陷阱（含新写代码里同类的两处）。

## Alternatives considered

逐条与 ADR-0057 的「备选方案」对应，这里记取舍的真实理由：

- **只把 `rm -rf "$REL"` 换成 `rm -f "$DMG"`。** 看起来「不再清空目录」了，但**破坏时序一模一样**：仍是先毁旧、后制新。这条被否决得最干脆——它治的是症状的字面，不是症状的形状。
- **不删目录，构建完原地覆盖 DMG。** 得到的是「新 dmg + 旧 SHA256SUMS」这种不一致状态，而 `SHA256SUMS` 是本项目唯一的完整性锚；失败时留下的正是这种状态。原子性不是加分项，是这个目录存在的理由。
- **拒绝一切同版本重跑，不给 `--force`。** 迭代成本会转嫁给操作者，并催生「手工把目录删掉再跑」这种绕过——**那恰好就是本次要消灭的行为**。所以守卫的形态必须是「默认拒绝 + 显式表态 + 归档」，而不是「一律不许」。
- **`--force` 时删掉旧产物。** 与「必须能回答客户手上那版对应哪份源码」冲突；也让「同号异构」事后无法取证。归档的成本几乎为零（改名而已），没有理由选删除。
- **只做原子就位、不做同号守卫。** 同号异构仍然会静默发生。它和本次事故是邻居：一个抹掉旧字节，一个悄悄换掉旧字节。
- **改成只增的 `history/<构建号>/`。** 与「版本号 = tag = 打包版本」的一对一契约冲突，下游（安装卡、灰度 SOP、GitHub Release 附件）不知道该读哪个。
- **本轮一并修改 `build-pkg.sh` 与 `assemble.sh` 的同族缺陷。** 有意放弃。`build-pkg.sh` 在当前环境**无法取得真实验证**（`.pkg` 路径已无调用方，自 2.2.0 起不在交付面），而本仓库的验收纪律是不接受口头验收——**改一个自己验证不了的东西，是把风险从「已知」换成「未知」**。登记为后续动作，等有可验证场景再动。

还有一条**没做的决定**，明确留给用户：是否把 `release-publish-guard-test.sh` 接进 `pnpm run gate`。它已沙箱化、可安全自动化，代价是每次提交多一次 `hdiutil`（十余秒）。本轮不擅自增加门禁时长。

## Consequences

**已验证的证据**（`bash packaging/scripts/release-publish-guard-test.sh`，29 项断言全通过，退出码 0）：

| 组 | 断言 | 结果 |
| --- | --- | --- |
| G1 首次构建 | 临时区先建、dmg 就位、`shasum -c` 通过、目录权限 755、无 `.staging` 残留、锁已清理 | 7/7 |
| G2 同号重跑 | 退出码 1、给出拒绝说明、**产物字节未变** | 3/3 |
| G3 `--force` | 退出码 0、旧产物归档、**归档里正是重制前那份字节**、新产物 `SHA256SUMS` 复核通过 | 5/5 |
| G4 终验失败 | 退出码 1、目标目录**未出现**（无半成品）、临时区已清理、锁已清理 | 4/4 |
| G5 锁语义 | 无主锁被回收、活锁报出占用、退出码 1、**活锁未被误删** | 4/4 |
| G6 参数守卫 | 无参/`-h`/未知选项/多余参数退出码各自正确 | 4/4 |

**另外三条在真实产物上取得的证据**：

- 对已发布的 `2.2.0` 直接重跑（不带 `--force`）：退出码 1，产物 SHA256 前后都是 `e74fb6d0…4ac86e`（未被触碰），且现场那个无主锁被自动回收。
- 回收无主锁之前，先确认现场锁确实是残留：`release/.build.lock/` 零条目、无 pid、`pgrep` 无任何构建进程。**不是猜它是残留，是验证它是残留。**
- 测试全程结束后复核：`2.2.0` 仍为 `e74fb6d0…4ac86e`，其 `SHA256SUMS` 仍复核通过，`release/` 下无任何测试残留。

**正面**

- 构建失败、验签失败、磁盘写满、中途 Ctrl-C 都不再损坏已发布产物——**由结构保证，不由人的谨慎保证**。
- 同号异构从「无声发生」变成「必须显式 `--force` 表态」，且表态后旧字节可回溯。
- 无主锁不再永久挡住构建；活锁仍被正确拦截。
- 报错路径不再因 bash 3.2 陷阱而崩掉。

**负面 / 代价**

- 构建期峰值磁盘占用上升：同一版本重制时临时区与旧产物并存，本版约多占 610M。作为交换，写满磁盘从「灾难」降级为「安全的失败」——这正是不再加前置空间检查的理由。
- 同版本正常重跑要多打一个 `--force`，是有意保留的摩擦。
- `release/` 下多出隐藏目录 `.staging.*` 与 `.archive/`；整个 `release/` 已被 `packaging/.gitignore` 忽略，`release/*/` 的 glob 也不匹配它们。

**后续动作**

- **N1**：`build-pkg.sh` 的锁路径与 `sign-and-dmg.sh` **早已不互斥**（前者 `release/<版本>/.build.lock`，后者 `release/.build.lock`，两者注释却都声称共用锁）。因该脚本已无调用方，先按 ADR-0013 裁定「归档出工作树」还是「修好后保留」。
- **N2**：`assemble.sh:84` 仍是 `rm -rf "$STAGE"`。破坏半径较小（staging 是构建工作区、由脚本自己重建），但会连带删掉 `staging/<版本>/payload`——那是 dmg 的唯一重建源。建议同等治，需先确认 payload 的可重建性是否真如设计所设想。
- **N3**：是否把 `release-publish-guard-test.sh` 接进 `pnpm run gate`（见上，留待用户裁定）。
