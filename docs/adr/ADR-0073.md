# ADR-0073 · 出货面由白名单决定，不由构建机的目录状态决定；机器路径守卫必须能看见打包后的 tarball

- 状态：accepted（2026-09-13）
- 日期：2026-09-13
- 决策者：用户（「bobo-cto 是一个机器人助理智能体，不参与当前 LUTE Agentic System 项目的打包」+ 对本轮三个选项的批复）+ agent（本次取证、判定与落地）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-13-shipped-preset-scope-and-payload-guard.md)
- 相关：ADR-0056（机器路径只减不增的守卫）、ADR-0057 / ADR-0058（同号归档与找回）、ADR-0061（本机使用外部产品走 profile 本地装配）、ADR-0067（已发布产物不许被删）、ADR-0024（`lute-cordis` 是产品默认预设）、ADR-0072（同一批次：预设与技能面的另一处静默失效）

## 背景

### 缺陷一：出货边界等于「打包那台机器上碰巧有什么」

用户告知 `bobo-cto` 是本机自有的机器人助理智能体、不参与本项目打包。取证发现它**已经在出货面里**，
而且是从 2.3.0 起就在：

| 读数 | 结果 |
| --- | --- |
| `hdiutil attach release/2.3.3/DSH-Desktop-LUTE-2.3.3-mac-arm64.dmg` → `tar tzf skills-presets.tar.gz` | 含 `presets/bobo-cto/`（`agent.cordis.yml`、`manifest.json`、`preset.yml`、`skills/pb-cto-01..04`） |
| 出货 `completeness.json` 的 `presets` | 52 条 = `agt-001..050` + **`bobo-cto`** + `lute-cordis` |
| 装配期冻结指纹 `staging/.freeze-2.3.3.start` | 记着 `/Users/lute/.dsh/.agent-presets/bobo-cto/agent.cordis.yml` 的哈希 |
| 版本回看（各版 `payload/skills-presets.tar.gz`） | 2.2.0 只有 `lute-cordis`；**2.3.0 起多出 `bobo-cto`** |

成因是一个没有任何过滤的整目录拷贝（`packaging/assemble.sh` §0）：

```sh
cp -R "$DSH_HOME_DIR/.agent-presets/." "$SP/presets/"
```

`~/.dsh/.agent-presets` 是**开发机的运行时状态**：谁在这台机器上新建一个预设，它就会随下一版
出给客户——静默、无日志、无读数。2.2.0 装配时 `bobo-cto/` 还不存在（该目录创建于其后），
所以这不是「谁决定要发它」，而是**机器状态决定了出货面**。装配脚本自己早就写下过这个风险，
但当时只防了「外部产品挂载」，没防「多出一个 preset 目录」。

### 缺陷二：机器路径守卫对打包后的载荷是全盲的

同一版出货里，守卫的报告与事实相反：

| 守卫扫什么 | 读数 |
| --- | --- |
| app 内嵌 profile（`$BUNDLED`，装配时的真根） | `✓ 无新增（当前 37 条，基线 39 条）` |
| 把同一版出货的 `skills-presets.tar.gz` 解开再扫 | `✗ 出货树新增 103 个含构建机路径的文件`（`exit 1`）——100 个 `presets/agt-*/{agent.cordis.yml,manifest.json}`（材料根 `/Users/lute/project/AI组织变革`）+ `bobo-cto` + `lute-cordis` |

根因是两层：① payload 里的 tarball 是**二进制**，`grep` 一律跳过（守卫的扫描器 `grep -rlFI`）；
② 守卫只被喂了 `--root "$BUNDLED"`，而 tarball 尚未生成、也从未被列入扫描面。
另有 13 个随包技能（`skills/`，如 `dsh-desktop-diagnostics`、`simplify-codebase` 的文档与
`jtbd-analyzer` 的自测报告）写着构建机目录。**仪器全绿而面在漏**——这是 P-02 那一类第四次换入口复发。

## 决策

1. **出货预设面改白名单**（`packaging/scripts/select-presets.mjs` + `packaging/shipped-presets.json`）：
   岗位预设按 `pattern` 准入且数量必须等于 `expectPatternCount`；其余目录必须在配置里**显式登记并写明
   `why`**；**出现未登记目录即中止装配并点名**；登记了却在本机不存在、或数量不符，同样中止。
   现状登记一项：`lute-cordis`（ADR-0024：承载确定性压缩后端的产品默认预设，2.2.0 起随包）。
2. **出货副本的构建机路径改占位符**（`packaging/scripts/rewrite-build-paths.mjs`）：在 `select-skills`
   之后、打 tar 之前对 `$STAGE/.sp` 跑一遍，按一张**写了含义的映射表**最长前缀优先改写
   （`__LUTE_MATERIAL_ROOT__` / `__LUTE_REPO__` / `__DSH_HOME__` / `__DSH_APP_SUPPORT__` / `__BUILD_DESKTOP__`）。
   表里没覆盖到的形态**响亮失败**（新形态该由人决定，不由脚本猜）。**本机 `~/.dsh` 下的原件不动**：
   在这台机器上那些路径是有用的。
3. **守卫扩到打包后的载荷**（`scan-machine-paths.mjs --tarball <file>…`）：解包到临时目录后
   用同一把尺（`grep -rlFI`）扫描，命中记为 `<tarball 名>!<成员路径>`。`assemble.sh` 在 tar 生成后
   对 `skills-presets.tar.gz` 再跑一次守卫（`--quiet`，因为它只为新增即中止而存在）。
4. **三条判据各自配反向自测并进门禁**：`gate:shipped-presets-scope-selftest`、
   `gate:build-path-rewrite-selftest`、`gate:machine-path-tarball-selftest`。每条都含
   「恒真桩突变」与「沙箱副本（符号链接路径）」两类反向用例——判据必须能说「不」，且不能静默不干活。

## 备选方案

- **黑名单（只排除 `bobo-cto` 这个名字）。** 被否：下次换一个名字照样静默随包，等于把
  「开发机状态决定出货面」这个根因原样留着。
- **把 `bobo-cto` 从本机移走，不改装配。** 被否：本机确有在用；而且它治的是这一次的名字，
  不治「多出一个目录」这件事。移走本机资产是给流水线让路，方向反了。
- **保留整目录拷贝，只在装配后加一次人工审查。** 被否：这正是 P-08——用纪律守只有机制能守住的东西。
- **让改写器直接改 `~/.dsh/.agent-presets` 与 `~/.dsh/skills` 里的原件。** 被否：本机上这些路径
  有实际用途（材料就在这台机器上）；为了让客户看不到，先让自己也看不到，是拿可用性换整洁。
  分工应当是「本机保留事实、出货副本用占位符」。
- **守卫扫描全部四个 payload tarball。** 部分采纳：只对**未被覆盖**的那一个开扫描口，其余在
  `assemble.sh` 的注释里写明理由与读数——`profile.tar.gz` ≡ 已扫过的 `$BUNDLED`（同一份 §0 快照 +
  同一份离线 `node_modules`，构造保证）；`DSH Desktop.app.tar.gz` 除内嵌 profile 外实测 **0 命中**
  （`tar -xzO --exclude 'Contents/Resources/dsh-profile/*' | grep -c` = 0）；`aeis-portable.tar.gz`
  是第三方 python 运行时，其路径由 `reloc-aeis.sh` 在安装时重定位。整包解包（396M/169M）是纯成本。
- **把登记表做成「岗位也让脚本从材料现算」。** 被否：岗位集合的材料来源是仓库外的
  `AI组织变革` 材料根，装配机未必有；白名单是**出货意图**的记录，本就该是一份可评审的显式清单。

## 后果

- **正面**：
  - 「本机多出一个预设」这条路径被机制堵死：未登记即中止并点名（实测 `S2`），
    且判据在恒真桩突变下失效（`M1`）——它钉的是那个判据本身，不是顺带被别的检查拦住。
  - 出货面的构建机路径从 **103 个文件**降到 0（模型由 `R1` 与守卫共同保证；重切 2.3.3 后实测见 Note）。
  - 守卫的盲点被堵上：`--tarball` 使「打包后的载荷」也进入判据面，且 `T4` 钉住「tarball 不存在」
    不许被当成「没命中」。
- **负面 / 边界**：
  - 白名单要维护：将来要新增出货预设，必须去 `shipped-presets.json` 做一次**显式决定**并写明理由。
    这是有意买的代价——把「谁有资格出货」从机器状态里拿出来，交给一次表态。
  - 客户看到的材料出处变成占位符（`__LUTE_MATERIAL_ROOT__/05-agents/roles/AGT-001.md`）。
    比一个指向别人机器的绝对路径更诚实，但它不再是可直接点开的路径。
  - **本机原件与出货副本从此不再逐字节相同**（仅限这些占位符所在的行）。任何「拿本机预设与
    出货包逐字节比对」的做法，从此必须先把这一步算进差异里。
  - 守卫对 tarball 的扫描成本随包体增长；当前只挂 5.7M 的 `skills-presets.tar.gz`。
- **后续动作**：
  - 重切 2.3.3（同名归档，`--force`）：用户确认尚未外发。
  - 若将来 payload 增加新的 tarball（或改用新打包格式），在 `assemble.sh` 的那次调用里
    一并登记扫描面——「哪些二进制载荷需要开箱检查」本身要有清单。
  - `aeis-portable.tar.gz` 的 273 处命中（第三方 venv 的记账路径）当前在 `reloc-aeis.sh` 的语义内；
    若哪天要收紧，单独立项，不要顺手塞进这条。
