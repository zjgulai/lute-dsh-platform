# ADR-0001 · GitHub monorepo 管理：单仓库发布 DSH 二开平台

- 状态：accepted（原文未入库，本篇为证据重建）
- 日期：2026-09-06
- 决策者：用户（lute）
- 原文：从未提交到仓库；本篇依据仓库事实（`README.md`、`.github/pull_request_template.md`、`docs/research/`、ADR-0003/0004）重建，决策内容与日期沿用 `docs/adr/README.md` 索引登记值。

## 背景

二开产物最初散落在多个本地目录（技能集、各插件、打包脚本），客户交付需要一套可发布、可回溯的载体。发布渠道需要同时满足国内（codeup）与公开（GitHub）两个方向。

## 决策

**以单一 monorepo 管理全部二开产物，经 GitHub 仓库发布**：远端为 `origin`（`github.com/zjgulai/lute-dsh-platform`）与 `codeup`（阿里云）；main 分支保护、Conventional Commits、PR 模板化（`.github/pull_request_template.md`）。

> **2026-09-17 更正（QG-008）**：本行写下的「main 分支保护」在写下之后的很长一段时间里**并不存在**——实测 `GET /repos/{r}/rulesets` 返回 `[]`、`GET /branches/main/protection` 返回 404。这不是决策错，而是**把意图写成了事实**：一份还没被机制守住的声明，读起来和已生效的声明一模一样。
> 现在它由机制守着：声明在 `scripts/gates/ruleset-declaration.json`，只读审计 `node scripts/gates/audit-rulesets.mjs` 逐条比对 API 读数（ADR-0106），门禁项 `ruleset-audit` 在每次跑门禁时复核。同一段历史记在 `docs/pitfalls-playbook.md`。

## 备选方案

多仓库（技能集 / 插件 / 打包各自成库）：被否决——跨库版本对齐成本高，且客户交付需要单一版本号；发布时需多次跨库操作。

## 后果

- 正面：单版本号覆盖全部产物；交付与发布以一次 tag 完成。
- 负面/代价：仓库体积与目录治理压力集中到一处（该压力在 ADR-0011 的能力归组中正式处理）。
