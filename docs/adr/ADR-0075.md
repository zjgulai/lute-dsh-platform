# ADR-0075 · 发布前门禁只量「待发布」的对象：射程从 git 里的家推导，射程为空必须报「跳过」而不是「通过」

- 状态：accepted（2026-09-13）
- 日期：2026-09-13
- 决策者：agent（本次实测、定级与判据设计；用户指令「同意执行顺序」后落地）
- 决策记录：[Note](../notes/implemented/contract/2026-09-13-gate-scope-and-skip-state.md)
- 相关：ADR-0058（入库清单是「我们承诺过什么」的家）、ADR-0067（已发布产物不可删除）、
  ADR-0014（门禁是硬门槛）、ADR-0043（失败必须给出为它负责的读数）、ADR-0065（G1/G2 守卫）、
  ADR-0071（复发故障总账）

## 背景

`pnpm run gate:full` 的唯一红项是 `patch-anchors`：

```
fail contract patch-anchors
     - packaging/staging/2.2.0/app/DSH Desktop.app: FAIL G1 HMR 生产守卫 (found 0, want >=1)
     - packaging/staging/2.2.0/app/DSH Desktop.app: FAIL G2 console 转发 (found 0, want >=1)
     - packaging/staging/2.3.0/app/DSH Desktop.app: FAIL G1 HMR 生产守卫 (found 0, want >=1)
     - packaging/staging/2.3.0/app/DSH Desktop.app: FAIL G2 console 转发 (found 0, want >=1)
fail 40/41 项通过（mode=full）
```

红是**真的**：那两个 app 树确实没有 G1/G2。但把这条红当成「该打扫卫生了」是错的，理由是四条实测：

1. **锚点清单单调增长，历史产物逐版累积。** 两条各自正确的规则相乘，结果是任何一棵在
   「某条锚」出现之前装配的树都**永久**判红。而这条红与它本要拦的东西（本次装配把补丁弄丢了）
   在输出上**完全不可区分**——于是「清掉历史目录」成了让本项变绿的唯一手段。

2. **这条教训本仓库已经写过一次。** `packaging/verify-patches-v2.sh` 头部：

   > 把历史版本号（曾为 2.0.0）硬编码在默认值里，会随目录裁剪变成结构性红灯：
   > 表现为 35 条 MISSING，与「补丁真的漂移」在输出上不可区分。

   当时修的是**脚本默认值**；同一根因随后从**门禁扫描集**长回来。同一根因复发两次（P-11）。

3. **那棵绿的树也不可信。** `staging/2.3.1/app` 的守卫文件 mtime 是 `09-13 14:07:15`，而 2.3.1 的
   入库清单记的 build 是 `20260913-125353`（12:53:55）——该树在**发布之后**被就地改过（当时它是
   最新的树，守卫开发中顺手patch了它）。它的绿**不证明任何出厂字节**。扫描集里于是同时存在
   两种不可信：永久红的（历史）与假绿的（被改过的暂存树）。

4. **射程为空时，本项静默报绿。** `gate.mjs` 旧代码：`if (targets.length === 0) return { passed: true, violations: [] }`。
   更早一步，`main()` **根本不渲染 `note`**——`passed: true` 一律打成 `ok contract <名字>`，
   于是三处 check 注释里写的「环境不存在时跳过，不假绿也不假红」在**读数上完全同形**：
   模型里有这个区分，读数里没有，等于没有（P-02 的第二种形态）。

顺带记录一条同源的镜像教训（并发会话同日实测）：2.3.1 曾在「Spotlight 全盘查不到」的取证下被宣告
永久丢失，18:06 却从飞书落地目录找回了哈希逐位相同的副本。**搜索工具的沉默不是缺席的证据**；
本 ADR 修的是它的对偶：**射程为空的沉默不是合格的证据**。

## 决策

1. **给本项一个显式的射程判据**，落在 `scripts/gates/patch-anchor-scope.mjs`（纯函数 + 反向自测）：
   射程 = 本机 `/Applications` ∪ `packaging/staging/` 下**未打 tag** 的 app 树。
   判「已发布」的权威家是 **git tag**（ADR-0058：清单入库 → 打 tag，tag 才担保得住字节）；
   已有 tag 的版本，其字节由 `packaging/release/<版本>/` 的产物与仓库外归档负责（ADR-0067），
   不由发布前门禁度量。

2. **门禁读数分三态：`ok` / `skip` / `fail`，`note` 必须渲染。** `skip` 表示「本项**没量到任何东西**」，
   不计入通过数（摘要行写作 `ok 41/42 项通过（mode=full，跳过 N）`）。`theme-tokens` 与
   `worktable-fence` 的「环境不存在」路径接到同一状态上——它们早就声称会跳过，只是读数里看不出来。

3. **已发布版本的证据是产物，不是暂存树；并且不因此删除任何 staging 树。** 射程判据让历史树
   **自动退出**扫描，不需要谁来记得清理，也不需要删任何东西。删目录是这条路的结果，不是手段：
   2.3.1 找回之前，`staging/2.3.1/payload` 曾是本机唯一残存的字节痕迹，而「清掉陈旧 staging」
   这条压力正好指向它。

4. **判据的默认错误方向选「多量」而不是「放行」。** 取 tag 而不是「有无入库清单」正是为此：
   同号重制时旧清单仍在 `release/` 里，按清单判会把**重制出来的新树**静默排除——门禁对着一棵
   从未量过的树说 ok。读不到 tag（浅克隆 / git 不可用）时全部纳入。

## 备选方案

- **删掉 `staging/2.2.0`、`staging/2.3.0`（本次最初的建议）**：能让红消失，但（a）仓库里再没有
  任何地方记录「v2.2.0 / v2.3.0 出货时不含 G1/G2」；（b）它清空的正是门禁的输入，而空射程当时
  报绿——清理会让门禁看起来被修好，实际是被弄哑；（c）2.3.1 的暂存树在找回前是本机唯一痕迹。
  **否决：用打扫卫生修仪器**。
- **把已发布版本登记进 `scripts/gates/exemptions.json`**：豁免是「存量未达标」的家（只减不增），
  而这里的问题是**判据射程错了**，不是对象劣于标准。登记进去等于承认「已发布版本应当通过今天的
  锚点集」，那是把判据的缺陷写成对象的欠账。
- **让空射程继续静默绿**：即现状。空射程恰恰是「清理过之后」的必然状态，也是最需要说话的时点。
- **用「有无 `release/<版本>.sha256`」判已发布**：见决策 4，会把同号重制的新树静默放行。
- **只在注释与文档里写清楚射程**：已经写过一次（`verify-patches-v2.sh` 头部），第二次从门禁长回来。
  靠人记得不是工程解（ADR-0057 的教训）。

## 后果

- `patch-anchors` 的读数变成自解释的：

  ```
  ok   contract patch-anchors（扫描 本机 /Applications；待发布 staging：2.3.2 2.3.3；
       已发布（有 tag，由 ADR-0067 归档负责）不参与：2.2.0 2.3.0 2.3.1）
  ok   contract patch-anchors-scope-selftest
  ```

  「谁被量了、谁退出了、为什么」写在每一次读数里，不再需要读代码才知道。
- 门禁项 41 → 42（新增 `patch-anchors-scope-selftest`，7 个反向用例，含「无条件纳入」与
  「空射程恒置 false」两种恒真桩突变）。
- `packaging/staging/` 不再有「不删就会让门禁变红」的压力，历史树可以按取证价值留下。
- **遗留一**：`packaging/verify-patches-v2.sh` 的默认 `STAGE_VERSION=2.3.1` 仍然陈旧（当前是 2.3.3）——
  裸跑该脚本今天验的是**已发布**的那棵树。今日**故意不修**：它在出货载荷里，改动会与已装配的
  2.3.3 载荷不同源（`gate:staging-freshness` 会判红），须随下一版一起改。
- **遗留二**：v2.3.2 有入库清单、有已归档并锁定的产物，却**没有 tag**。按 ADR-0058 的口径
  （tag 才担保得住字节），它因此仍留在本项射程内——这不是缺陷，是口径如实。
- **遗留三**：无 tag 的环境（新克隆）会全量纳入扫描；因为那里没有 staging 树，实际无影响。
