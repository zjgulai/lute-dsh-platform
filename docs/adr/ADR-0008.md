# ADR-0008 · harness submodule 初始化但仅作只读参照系

- 状态：accepted
- 日期：2026-09-11
- 决策者：用户（lute）+ agent（grill-me 决策树 Q2）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-11-lute-refactor-three-phase.md)

## 背景

`vendor/dsh-desktop/.gitmodules` 声明了 `deepseek-harness` 子模块（`https://github.com/deepseek-ai/deepseek-harness.git`），但该目录为空，`vendor/dsh-desktop.pin` 记为 `harness-submodule: NOT-INITIALIZED`，运行时改取 `vendor/dsh-runtime/0.1.2-rc.1/*.tgz` 预打包产物。后果是：基座理解只能来自 tgz 产物与补丁锚点文字，35 个补丁的重锚需人工反查，每次上游窗口成本 3-5 人日（见 docs/research/10-debt-solution.md C4）。

## 决策

**初始化 `deepseek-harness` 子模块并 pin 到 `a66e4702047846cdaa10c66c9d3df3951f5ea70d`（runtime 0.1.2-rc.1），仅作为只读参照系：**

1. 子模块**不参与构建**——`assemble.sh` 与打包链继续使用 `vendor/dsh-runtime/0.1.2-rc.1/*.tgz`，交付行为零变化。
2. 子模块用于三件事：架构文档引用真实源码路径、补丁重锚时对照上游实现、升级评估时检索上游是否已修复问题。
3. `vendor/dsh-desktop.pin` 的 `harness-submodule` 字段由 `NOT-INITIALIZED` 改为已初始化，并纳入门禁校验（实际 sha 与 pin 不一致即拒绝构建）。

## 备选方案

- **A 维持 tgz 运行时、不初始化**：被否决——补丁锚点核对仍靠人工，痛点不解决。
- **C 初始化并改为源码构建**：被否决——会改变已跑通的交付链，与 ADR-0007「不改交付链」冲突；上游源码构建需 pnpm 全量安装与构建，交付路径显著变重。
- **D 只在文档中登记上游 sha、不落盘源码**：被否决——无法检索，等价于现状。

## 后果

- 正面：补丁重锚从人日级降到分钟级；架构文档可引用可打开的源码路径；升级评估可先在上游查证是否已修复。
- 负面/代价：磁盘占用增加（上游完整 checkout 量级为数千文件）；子模块会带来「pin 更新与桌面行为变更分离」的提交纪律要求（沿用壳层 fork 的既有规则）。
- 后续动作：门禁新增 pin 校验项（见 `.scratch/lute-refactor/spec.md` 门禁分层表）；子模块初始化与 pin 文件更新需同一次提交完成。
