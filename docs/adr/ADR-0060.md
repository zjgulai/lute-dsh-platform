# ADR-0060 · 模型准入判据补两关：tool_call 必须「回灌验证」且「多轮重复」——单轮产出 `tool_calls` 不足以判定能干活

- 状态：accepted
- 日期：2026-09-13
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/capability/2026-09-13-siliconflow-model-audit.md)
- 相关：ADR-0059（中转站接入以逐模型实测工具调用为准入判据——本条是它的**续补**：那轮的三关判据在第二个提供方上被证明不够）、ADR-0024（容量表以实测为准、文档值不可信）、ADR-0043（报失败必须给出为它负责的读数）、ADR-0009（一份事实只有一个家）

## 背景

ADR-0059 为「接入第三方模型提供方」立了判据：**逐模型实测工具调用**，且必须用 `tool_choice: "auto"`（用 `required` 会造假阴性），schema 是否声明 `tools` 不可作依据。

该判据在 PoYo 上工作良好，于是被原样拿到硅基流动（首方聚合站，72 个模型）上复用。结果发现**它不够**——存在两类模型能通过这一关、却仍然无法支撑 agent 主循环：

**① 单轮产出 `tool_calls` 不代表调用对象合规。** `Qwen/Qwen3.6-35B-A3B` 连续两轮都正确产出 `get_weather` 调用，按 ADR-0059 的判据应判「可用」。但把它返回的 `tool_calls[0]` 原样回灌进下一轮请求时，服务端 `400`：

```
0.ChatCompletionMessageFunctionToolCallParam.type
  Input should be 'function' [type=literal_error, input_value=None, input_type=NoneType]
```

即该模型的 `tool_call` **缺 `type:"function"` 字段**。合规样本对照：`deepseek-ai/DeepSeek-V4-Pro` 返回 `{"index":0,"id":"…","type":"function","function":{…}}`。

这条缺陷的严重性在于它落在 agent 循环的**第二步**：DSH 每执行完一次工具都要把 assistant 的 `tool_calls` 回灌给服务端，所以「缺 type」= 每次工具调用之后的那一轮必崩。而**单轮测试在结构上不可能发现它**——服务端只在接收 assistant 消息时才校验这个字段。

**② 间歇性失败会被少量轮次掩盖。** 对该模型追加 6 轮重复：**4 轮正常、2 轮完全不产 `tool_call`**（33% 静默失败）。它此前「两轮全过」纯属抽样运气。

**③ 附带结论：模型新旧、价格档位都不是质量信号。** 站内 `Pro/` 前缀 = 付费档、无前缀 = 免费档；实测付费档在同族里**没有一条胜出**（保留清单 9 条全为免费档，含旗舰 `DeepSeek-V4-Pro`）。且同族 `-Instruct` 版本可能整体弱于 `-Thinking` 版本：`Qwen/Qwen3-VL-{8B,30B-A3B,32B}-Instruct` 三个全部不产 `tool_calls`，而同尺寸 `-Thinking` 全部通过——与 ADR-0059 记录的「Claude 旗舰全线不可用」同型。

## 决策

1. **准入判据由三关升为四关，逐关实测，缺一不可：**
   ① 上游可达（`/v1/chat/completions` 非 4xx）→ ② 工具产出（`tool_choice:"auto"` 下产出 `tool_calls`，名字正确）→ ③ **形状合规（`tool_call` 带 `type:"function"`，且把工具结果回灌后仍 `200` 且正文非空）** → ④ **稳定性（重复 ≥3 轮全部通过）**。
   第 ③、④ 关为本次新增，适用于**所有**提供方，不分中转站还是首方。
2. **第 ③ 关的验证方式是「回灌」而不是「再问一次」。** 具体动作：取第一轮响应里的 `tool_calls[0]`，构造 `assistant(tool_calls=[tc])` + `tool(tool_call_id=…, content=…)` 两条消息，再发一次；要求 `200` 且 `choices[0].message.content` 非空（空正文同样不可用——`ByteDance-Seed/Seed-OSS-36B-Instruct` 即因此被剔除）。
3. **同分决胜用抽测，但不把抽测当门槛。** 三项轻量抽测（不该调工具时是否乱调 / 严格 JSON 输出 / ~1 万 token 海捞针）仅用于并列排序。实测 18 个候选里 15 个满分，**区分度有限**，因此不得以「抽测满分」宣称模型更强——本 ADR 明确不给出「谁更聪明」的结论。
4. **筛选目标是「每族一条当代最好的 + 每个不重叠角色一条」，不是「把所有能用的都留下」。** 硅基流动清单据此由 25 条收窄到 9 条：剔除的每一条都带可复现证据（HTTP 状态码或逐轮读数），可用的同族备选单独记入 Note 供替换，不与保留项并列。
5. **上下文窗口一律实测，且用零成本方法。** 发 ~130 万 token 的超长 prompt，从 `400` 报文读 `max_prompt_tokens (N)` / `maximum context length is N`。被拒请求不计费，故该维度可随时复测；未声明模型继续落到保守兜底值。

## 备选方案

- **沿用 ADR-0059 的三关判据。** 否决，且这正是本轮踩到的坑：三关会放行 `Qwen3.6-35B-A3B` 这类「测试全过、真跑必崩」的模型。教训是**判据必须在第二个场景上重验**，第一轮通过不等于判据充分。
- **用「多轮重复」替代「回灌验证」。** 否决：重复只能发现不稳定，发现不了形状违规——该模型在 6 轮里形状违规一次都没复现（6 轮全带 type），却在回灌时必崩。两者查的是不同维度，不能互相替代。
- **把回灌验证做成「让模型自己再调一次工具」。** 否决：那样测的是模型的第二次决策，不是服务端对 assistant 消息的校验；缺 `type` 的缺陷只在「客户端回传」这条路径上暴露。
- **保留全部通过四关的模型（72 个里 50 个）。** 否决：模型选择器是**人工选用面**，50 行里绝大多数是功能重叠的同族变体；清单的价值在于「每一行都值得选」，不在于「不漏掉任何可用项」。可用备选记入 Note 而非清单。
- **按文档值填上下文窗口。** 否决（沿用 ADR-0024）：实测 `moonshotai/Kimi-K2.7-Code` 是 `262140` 而非文档常写的 `262144`；且本方法零成本，没有理由退让。

## 后果

**正面**

- 判据补上了 agent 循环里最容易漏测的一步（回灌），从此对任何新提供方都能一次筛干净。第 ③ 关的构造方式可复制：**取上一步响应、原样构造成下一步请求**。
- 硅基流动清单 25 → 9，每一条剔除都有状态码或逐轮读数支撑；验收以「运行中的进程读到了」为准（动态 Host 包直读活着的 `llm` 注册表，`gjldCount=9` 与文件逐项一致，进程未重启）。
- 拿到两条可复用的**先验**：付费档不等于更强；同族 `-Instruct` 版本可能整体不产工具调用。两条都在两个独立提供方上重复出现。

**负面 / 待办**

- 四关判据的成本约为每模型 4~5 次带工具请求；对 72 个模型规模仍可行，但再大一个量级就需要先做静态预筛（如按 `sub_type` 剔除非对话模型）。
- 判据只覆盖**工具链路**，不覆盖代码/推理质量。9 条保留项之间「谁更聪明」**没有结论**，延迟数字只反映轻量请求。
- 第 ④ 关的「≥3 轮」是经验阈值：33% 的失败率在 3 轮里被漏掉的概率约 30%。对稳定性要求更高的场景应提高到 6 轮以上。
- 清单收窄到每族一条后**没有同族冗余**，上游抖动时无自动降级；备选名单已落档，但降级仍需人工。
