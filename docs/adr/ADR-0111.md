# ADR-0111 · 打包链版本凭据单一事实源化 + T-00 备份树迁出仓库

- 状态：accepted（2026-09-17）
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/packaging/2026-09-17-version-credentials-single-source-and-backup-relocation.md)
- 相关：ADR-0063（固定签名身份）、ADR-0066（向导版本消歧）、ADR-0075（patch-anchors 射程）、ADR-0080（判据唯一家）、ADR-0103（快照见证）

## 背景

2.0.10 基座（D 轨道）落定后，打包链在两处暴露出**把一代基线写成常量**的缺陷：

1. **版本戳四处硬编码 `2.0.5`**：`assemble.sh` 的 `CFBundleVersion` 戳、`build-setup-app.sh`
   的向导版本与其复核、`VERSION` 载荷凭据里的 `DSH_BASELINE`、`manifest.json` 的
   `dsd_baseline`。用 2.0.10 产物装配时它们会联合产出「2.0.5-lute.2.5.0」这种
   谎报基线的版本戳——Gatekeeper 层无感，但 `profile-channel-admission` 与
   `setup-wizard-state` 都按此戳记录凭据，2.0.10 世代的载荷将携带 2.0.5 的假凭据。
2. **install.sh 预写向导 skip 状态时硬编码 `desktopVersion: "2.0.5"` /
   `dshVersion: "0.1.2-rc.1"`**：这两个值会被首启的
   `profile-channel-admission.ts` 读作「这份 profile 是在哪个版本下 setup 的」证据。
   假凭据跟随客户机长期存在。

同时 `smoke-test.sh` 的完整性比对仍把 app 侧 node_modules 写死为
`app.asar.unpacked/`——T-06 收敛时漏掉的第 5 个消费面（§12 只处理了 4 个）。

另一件阻塞:`packaging/backup/pre-2.0.10-migration/`（T-00 备份，7.9G）放在仓库
工作树内，以 untracked 身份使 `repo-attest`（ADR-0103）快照对它做
`git hash-object` 全量读取——实测单次快照 174.8s，`repo-attest-selftest` 在
`runNodeTestFile` 的 120s 上限内必超时（退出码 124），gate:full 结构性卡死。

## 决策

1. **基线串的唯一事实源 = staged app 自己的 `CFBundleShortVersionString`**。
   `assemble.sh` 在暂存后读取并派生 `${DSH_BASELINE}-lute.${VERSION}` 写入
   `CFBundleVersion`，写后当场复核；读不出合法值（非 `数字.数字.…`）即中止。
   `build-setup-app.sh` 改为第三参数接 `<基线>`，不硬编码任何一代。
2. **新增 `DSH_RUNTIME` 载荷凭据**：VERSION 里新增一行，事实源 = staged app 的
   `@deepseek-ai/dsh/package.json`（运行时 bundle 在 app 侧 node_modules；live
   profile 侧没有该包——第一版写成 `$PROFILE/node_modules` 是路径臆断，实测取空
   后修正）。`manifest.json` 的 `dsd_baseline` 同步改为从 `$DSH_BASELINE` 注入。
3. **install.sh 预写向导状态改为消费载荷 VERSION 的 `DSH_BASELINE` / `DSH_RUNTIME`**；
   载荷缺这两个字段时**跳过整段预写**（宁可在首启多见一次可跳过的向导，不编造
   版本凭据）。老格式载荷（无 `DSH_RUNTIME` 行）自动落入此分支，行为不变差。
4. **smoke-test.sh 的 bundle 比对改走 `scripts/lib/app-resources.mjs` 布局探测**
   （与 assemble.sh/verify 同一判定家），探测失败落一条红而不是拿固定路径猜。
5. **T-00 备份树迁出工作树**（用户选定「迁出仓库树」）：移至
   `~/project/Magpie-Horch-backups/pre-2.0.10-migration/`，仓库内
   `packaging/backup/README.md` 记录去向与回滚引用；计划文档的 T-00a 引用同步改。
   不走 `.gitignore` 方案——那只是让判据看不见 7.9G，税还在每次克隆/tar 上。

## 备选方案

- 换一个新硬编码 `2.0.10`：拒绝——下次升级（2.0.11+）同一缺陷原样复发；本 ADR
  的目的就是把「哪一代基线」从常量变成读数。
- `DSH_RUNTIME` 硬编码 `0.1.5-rc.2`：拒绝，同上；且升级运行时而不升基座时两字段
  会失锁。
- 备份树 `.gitignore` 登记：拒绝（见决策 5）；调大 selftest 超时到 45min：拒绝，
  那 26 分钟级长测会把 T-10 排期拖垮，且税本身是无意义的 I/O。

## 后果

- 任一世代基座装配时版本戳自动对齐，无需人工跟改四处；`install.sh` 的向导凭据
  与载荷真实版本一致。2.0.5 世代的老载荷行为不变（缺字段→跳过预写）。
- `repo-attest` 快照恢复秒级（实测 174.8s → 0.5s），`repo-attest-selftest`
  17.5s 内 9/9；gate:full 解锁。
- 已知暂态（登记，不修判据）：`patch-anchors` 对本机 `/Applications`（2.0.5）
  跑 v3 锚 REPORT 2 红（PR-2/5 前缀差异 + P0-2v2 拆分文件缺失）——T-11 生产
  切换后自消，不给 10 天窗口状态建永久机制。
- 迁出期间 repo-attest 曾报一次 SIGTERM 路径红：after 快照撞上 `mv` 窗口，
  差异值与 `sha256('missing\0<path>\0UNKNOWN')` 精确吻合，迁出完成后重跑 9/9
  全绿——按 ADR-0103 的「transient」语义归档为并发窗口效应，非产品缺陷。
- 后续动作：`assemble.sh` 抬头注释里仍留一处「DSH Desktop 2.0.5」历史描述
  （只读文档面，不影响行为）。
