## 背景

用户要把「岗位 Preset」从组织清单变成交付物：一个 Preset 下挂多个 Agent 产品，一个产品由多个功能组成工作流；每个功能是「页面引导输入 → 确定性拼提示词 → 触发模型/工具 → 结果按预置 UI 模板填充 → 作为下一功能输入」。

本机取证（真实读数，不是推测）后确认这件事缺的是**声明**，不是机制：

- **产品没有家**：`/Users/lute/project/` 下没有任何一份文件说明某个目录是一个 Agent 产品、它有哪些功能、入口在哪。
- **产品没有判据**：新应用抽屉今天能列的两类东西都不是产品——50 个岗位是材料里的组织拓扑（`GET /api/dsh-role-matrix/list`），11 个容器是「有会话的目录」（`GET /api/worktable/workspaces`）。
- **提示词没有可审形态**：拼接逻辑尚不存在；一旦散进面板代码，它就是产品里唯一无法回放、无法审计的部分，而它恰恰决定模型看到什么。
- **结果没有契约**：模板填充若交给模型自由发挥，「预置 UI 模板」就不再是预置。
- **机制全都有先例**：跨插件开面板所需的客户端服务 API（基座自己以 `ctx.provide` 提供 `sessions` / `connection` / `theme` / `layout` / `uiRenderer` 等）；会话开工三连（工作台客户端 `vendor/dsh-worktable/01_content/lib/client.js` 正在用）；工作流运行时（官方 `dsh-workflow` + `dsh-tool-workflow` + `workflow-run` 界面）。

因此缺的是一份**声明契约**与一个**启动器消费规则**。

## 决策

1. **产品形态 = 一份声明 + 一个实现包。** 声明是项目目录里的 `product.json`，顶层恒为 `{ "schemaVersion": 1, "products": [ … ] }`（只有一种形状，不做单对象/数组双形状）；实现包、`prompts/`、`templates/`、`artifacts/` 都在同一个产品目录里。**每个产品归属 50 个岗位之一**（`preset` 字段必填——岗位是它的垂直基座与默认装配）。**产品代码留在各自项目**：本仓库（Magpie-Horch）只出规格、校验器与启动器，不吞并产品。
2. **技能分三层，产品技能打包进产品。** L0 全局技能（`~/.dsh/skills/`）→ L1 岗位专属技能（preset composition 用 `dsh-skill-subset` 声明子集）→ **L2 产品局部技能（产品目录内 `<产品>/skills/`，由产品插件在自身 fiber scope 注册）**；同名遮蔽近层胜远层。提示词骨架取技能正文，页面输入是它的变量；拼接是纯函数 `buildPrompt(skillBody, inputs)` 且有快照；缺变量必须抛。**模型只产出结构化字段，模板由确定性渲染**——不允许模型自由生成 UI。
3. **启动器只发现与开入口，不拥有事实**（延续 ADR-0028）：扫描**显式配置的允许根**下的 `product.json`，新增路由按 ADR-0030 逐插件打栅栏；发现结果必须报告来源（`scannedRoots` / `skipped` / `unreadable`），不静默。开入口走产品注册的客户端服务 `ctx.provide('<service>', entry)` / `ctx.get('<service>')`。
4. **点开一张卡 = 打开该产品的入口面板**（用户裁定），不是新建会话。新建会话的三连降为第 2 级回退（声明了但包未安装时），第 3 级（两者都无）卡片禁用并写明原因。
5. **产品跑在本机同一个 DSH 实例**。远程域名形态（如 `audits.lute-tlz-dddd.top`——同一套壳 + 一个自己的插件包）不在本期；它需要的是一份独立规格，不是这份的变体。
6. **抽屉结构合并成一个区块**：工作目录为主键，产品/Agent 是卡上的选项；没有 `product.json` 的目录显示「尚未产品化」而不是消失。

## 备选方案

- **集中一份产品登记表**：放弃。它是第二份事实，产品一改就漂移；且与 ADR-0028「启动器只拥有连接，不拥有事实」冲突。
- **点开 = 新建会话**：放弃作为默认动作。要的是「进产品」而不是「开聊天」；三连保留为回退。
- **提示词内联在 `product.json`**：放弃。长 Markdown 塞进 JSON 不可读不可复用，而技能库已经是这一层的家（加载契约、分发、preset 装配子集三样现成能力）。
- **模板由模型生成**：放弃。模板会失去「预置」含义，字段与版式随模型漂移且无法审计。
- **产品代码收进本 monorepo**：放弃。产品是各自项目的事；本仓库只出规格与校验器（校验器以独立命令形式对任意产品目录可跑）。
- **把流程写进 preset 的 composition**：放弃。本平台在同类问题上已付过代价——`file:` 依赖是安装时刻的硬链接快照，安装后新增文件不会自动进去，症状是「功能静默不生效 + 日志一句 warn」（`docs/architecture.md` §1 同步语义）。产品是代码，preset 是装配；preset 挂载产品，产品自己声明功能与工作流。

## 后果

### 正面

- **一个文件说清一个目录是什么**：卡片可以做到「点开必能用」，且判据取自产品自己的目录，不取自人工登记。
- **提示词与模板第一次成为可回放、可门禁的证据**：四件证据（输入 / 提示词 / 回执 / 产物）让「AI 可视化工作流」有审计面，而不是只有好看的按钮。
- **产品可增删而不动基座**：新应用不需要预先知道有哪些产品，也不需要改代码就能多出一张卡。

### 负面 / 未决

- **多了一次约定的写入**：每个产品要有人写 `product.json`；M1 的试点会把约定的粗糙处压出来。**已压出四处**（骨架单数→多技能组合、功能级 `kind`→步骤级 `steps[]`、回执字段集不足、两档 `status` 不够用），见 [ADR-0034](ADR-0034.md) 与其 Note。
- **技能三层要求纪律**：产品技能不得图省事落进 `~/.dsh/skills/`（那样「这个技能属于哪个产品」就只能靠名字猜）；岗位专属技能与全局技能同名时靠 preset 子集的遮蔽语义取胜，这条语义由既有机制保证，但**产品层是新加的**，M1 必须在真会话里验证 L2 确实只在该产品挂载处可见。**M1 已把「L2 不落全局目录」做成机检**；「L2 只在该产品挂载处可见」仍需 M2 在真会话里证伪。
- **扫描根是新的安全面**：必须与第一期 worktable 同等对待（回环栅栏 + 允许根 + 负例探针），默认空 = 不扫。**M2 范围，尚未实现。**
- **M1 试点已落地**：`KOL-Hunter`（`/Users/lute/project/KOL-Hunter`）；归属岗位 `agt-033 结伴 · 达人与联盟合作`（确认依据：该岗位 `dsh-skill-subset` 的 16 个技能里已含 `p2s-kol-creator-matching`，与产品本职逐字重合）；首个功能 `select-candidates` 已端到端跑通并留下产物、快照、四件证据与 14 项自检。
- **规格已被 M1 压过一轮**：实现偏差已回写规格 v2 §11（而不是各说各话）；M2–M4 的可验收命令仍在规格里。
