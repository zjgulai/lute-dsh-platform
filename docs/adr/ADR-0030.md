# ADR-0030 · 在 `/api` 下注册 exact 路由的插件，绕开了平台自己的来源栅栏——因此必须逐个插件打栅栏

- 状态：accepted
- 日期：2026-09-12
- 决策者：agent（取证后提出；两侧判据均已实测，见 Note）
- 决策记录：[Note](../notes/implemented/contract/2026-09-12-worktable-trust-fence.md)

## 背景

融合上游第三方插件 `dsh-worktable`（v0.3.3，sha `2f4f6c8`）时逐条读它的 `apply()`：
它注册 8 条 HTTP 路由 + 1 条 WebSocket 升级路由，**一条都不校验来源**，
且 `file` / `site` / `write` / `mkdir` / `fs` / `git` 的客户端可控路径**不做根约束**。
`write` 是任意文件写入（`writeFile` 会创建），`file` 是按扩展名回 `text/html` 的任意文件读取，
`term` 是 `node-pty` 交互式 shell。

直觉上这不该是问题——DSH 自己在 `/api` 上有一条总闸。逐字读应用内代码取证：

```js
// dsh-client-connection/lib/index.js:707
const route = { kind: "prefix", path: API_PATH /* "/api" */, handler: async (req, res) => {
  const rejection = connection.requestRejection(req)   // isTrustedApiRequest → 403；browserAuth → 401
  ...
```

```js
// dsh-host-webserver/lib/index.js:322
match(pathname) {
  const exact = this.exact.get(pathname);
  if (exact !== void 0) return exact;        // ← exact 表先命中，前缀永远轮不到
  let best
  for (const [prefix, route] of this.prefixes) { ... }
}
```

**两边合起来是一个反直觉的结论**：平台栅栏挂在 `/api` 这条**前缀**上，
而 `match()` 先查 **exact** 表。所以任何插件只要把路由注册成 `kind: "exact"`、
路径形如 `/api/<plugin>/...`，它的请求就**压过**平台那条前缀——**绕开 DSH 自己的
来源栅栏（Host 回环 / `sec-fetch-site` / `Origin` 同源）与浏览器会话认证**。

升级表更彻底：

```js
this.upgrades = new Map()            // 独立表，按精确路径匹配
registerUpgrade(route) { this.upgrades.set(route.path, route) }
```

平台侧**没有任何**升级路由判据，而浏览器对 WebSocket **不施加同源策略**——
任意网页都能开 `ws://127.0.0.1:<port>/api/worktable/term` 拿到一个交互式 shell。

也就是说：**「平台已经有栅栏了」这条假设对本类插件不成立**，
而「本机插件所以安全」同样不成立——回环监听 ≠ 可信（DNS rebinding 绕 Host 判据）。

## 决策

**对每个在本平台安装的第三方插件，逐插件打来源信任栅栏，且在插件的 `apply()` 入口
包住整个 `webServer` 对象。**

具体到 `dsh-worktable`：`dsh-patches/worktable-fence/` 往
`vendor/dsh-worktable/01_content/lib/index.js` 最前面注入一段独立 ESM，并把
`const webServer = ctx.webServer;` 改成 `const webServer = __wtFence(ctx.webServer, ctx);`。

包住**整个对象**而不是逐条路由加守卫，是为了 **fail-closed**：
`apply()` 里所有 `register` / `registerUpgrade` 自动过栅栏，**上游将来新增的路由也默认被覆盖**。

两道防线：

1. **请求级**：socket 回环（127/8、`::1`、`::ffff:127/8`）+ Host 回环 +
   `sec-fetch-site ≠ cross-site` + `Origin` 与 Host 同源。HTTP 允许 Origin **缺失**（curl 等
   非浏览器客户端）；**WebSocket 要求 Origin 必须存在**——浏览器必然发送它，
   而对 WS 而言它是唯一的跨源防线。显式 `Origin: null`（沙箱 iframe / `file://`）一律拒绝。
2. **允许根**：客户端可控路径解析后必须落在家目录 / 临时目录 / DSH 家目录之内。
   校验前对**最深的已存在祖先**做 `realpath`（目标可能还不存在，`/write` 会创建文件），
   因此 macOS 的 `/tmp → /private/tmp` 不会误判，`~/../../etc/passwd` 归一后即越界。

## 备选方案

- **A. 直接改 worktable 源码并提交进本仓库。** 否决：上游第三方，源码进本仓库违 ADR-0010/0012
  的归属契约，且上游发版无法合并。
- **B. 不装 worktable，自建等价能力。** 否决：重写成本远超收益，且「应用抽屉」是它的核心
  差异化，重复造轮子违 ADR-0009。
- **C. 把栅栏做在 DSH webserver 层（全局）。** **技术上最优，本轮不采纳**：改基座违 ADR-0008
  「基座只 pin 不改」。这是本决策的**已知次优**——正确形态是上游自己加栅栏，
  或平台层统一栅栏（需要先与上游/基座达成一致）。本栅栏因此明确登记为**临时收敛手段**。
- **D. 只信赖平台那条 `/api` 前缀。** 否决：`match()` 的 exact 优先使它对本类插件**无效**，
  这是本 ADR 要记录的核心事实。**取证的实测**见下。

## 后果

**得到**

- 9 条入口全部过栅栏；且因为是包住对象而非逐条加守卫，**上游新增路由默认被覆盖**（fail-closed）。
- 实测（`pnpm run accept:worktable-fence`，31 条探针）：栅栏在位时 16 条负向全部 403/拒升级；
  把**未打栅栏的上游原文**喂给同一套探针，16 条负向**全部转红**——`/etc/passwd` 读到 200、
  越根写入成功、跨源与无 Origin 的 WebSocket **升级成功（101）**。
- 阶段 C 用平台 `/api` 前缀的**行为替身**在场做对照：`/api/worktable/health` 回 **200**
  而非平台的 401（exact 压过前缀），而插件没注册的 `/api/other` 仍回 401。
  **这条栅栏是唯一防线，不是纵深里的第二层**——「有没有它都一样」被实测排除。

**代价**

- 栅栏是**补丁**不是上游行为，上游每次发版需重锚。`apply.mjs` 的 pin 守卫与 `--check`
  模式让这件事**响亮失败**而不是静默失效；`vendor/dsh-worktable.pin` 未 bump 前不得升级。
- 补丁会让 `lib/index.js.map` 失效（行号位移）——只影响 devtools 定位，运行时无关。
- 注入块与被注入 bundle **同处一个模块作用域**，顶层标识符撞名会让 `var`/`function`
  静默互相覆盖（栅栏被顶掉）。已加机器判据（门禁的撞名检查 + 其自检用例）。

**后续动作**

- 上游若自行加栅栏，或基座提供平台级栅栏（备选 C），本补丁应整体撤除。
- 本判据（`worktable-fence` 门禁 + `accept:worktable-fence` 探针）是**这一类插件**的模板：
  下一个在本平台安装、且在 `/api` 下注册 exact/upgrade 路由的第三方插件，按同一形状收敛。
