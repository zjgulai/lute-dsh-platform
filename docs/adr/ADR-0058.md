# ADR-0058 · 发布清单入库：清单是脚本的产出而非 SOP 的人工步骤，且必须先于 tag 落库

- 状态：accepted
- 日期：2026-09-13
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/architecture/2026-09-13-release-manifest.md)
- 相关：ADR-0002（DMG 发布走 Releases 附件 + `release/` 哈希清单；本 ADR 第一次真正实现它）、ADR-0009（一份事实只有一个家）、ADR-0057（发布语义：原子就位 + 同号守卫；本 ADR 的清单写在就位之后）、ADR-0056（靠人记得不是工程解，机读判据才是）、ADR-0014（门禁硬门槛）

## 背景

ADR-0002 记的实现是「产物落在 `packaging/release/<版本>/`，附 `SHA256SUMS`，`release/` 目录本身不入库」；而 `docs/release-process.md` 从 2026-09-06 起写的是另一件事：

> 计算 `shasum -a 256 <dmg>` → 写入 `release/<version>.sha256` 清单（**入库**）。

同一件事有两个说法，且**入库的那一支从未执行过**：全仓没有任何 `.sha256` 文件，仓库根 `release/` 自初始提交 `3b437af` 起只有一个 README。哈希的**值**确实存在过，但散在 7 处——完整值只在 `packaging/CHANGELOG.md`，其余（根 `CHANGELOG.md`、ADR-0057、Note、`PLAN.md`）都是截断成 `e74fb6d0…` 的散文；而唯一机读的那份 `SHA256SUMS` 被 `packaging/.gitignore` 忽略。七个家，没有一家能跑 `shasum -c`。

真正让这件事从「文档不一致」升级为「契约破损」的是 2.2.0 的取证：

- 客户手上那版 DMG 的实际分发通道是飞书（恢复回来的那份带 `com.apple.quarantine: …;Feishu;`），字节走出仓库后，仓库侧没有任何东西能认领它；GitHub Releases 里也**没有** v2.2.0（最新是 v2.0.0），而 `README.md` 正告诉客户「从 Releases 下载」。
- 更硬的一条：**2.2.0 的载荷含未提交源码**。`profile.tar.gz` 内的 `vendor/packages/surfaces/dsh-newapp-local/src/client/launcher.ts` 有 377 行，而 tag v2.2.0（`afe641c`）里是 337 行；`probeChannels` 探针与 `agentPresets` 双载体回退**既不在 tag 也不在 HEAD**，却出现在载荷的 4 个文件里（vendored 源码、vendored `lib/client.js` 及其 map、`node_modules` 下的同名产物）。那 40 行从未被提交。

也就是说 ADR-0057 第 4 条自己写下的契约——**版本号 = git tag = 打包版本**，理由是「同号不同字节一旦流出去，客户手上那版对应哪份源码就无法回答」——**已经破了**，破在正在交付的那一版上。

## 决策

1. **仓库根 `release/<version>.sha256` 是清单唯一入库的家。** 实现 SOP 的原意，不订正它。上与 `packaging/release/` 分工明确：`packaging/release/` 是**产物的家**（几百 MB 二进制，被 `packaging/.gitignore` 忽略，不进 git），仓库根 `release/` 是**清单的家**（几百字节，必须进 git）。
2. **清单由 `packaging/sign-and-dmg.sh` 生成，不是人工步骤。** SOP 之所以十天一次没执行，是因为它把这件事写成了「算哈希 → 写文件 → 提交」——三步都得靠人记得。现在哈希由脚本算，人只剩「提交」一个动作。
3. **清单必须带源凭据**：`version` / `dmg` / `build` / `source_commit` / `source_dirty` / `profile_snapshot`。只有哈希是不够的——哈希能证明「字节没变」，证明不了「对应哪份源码」，而后者正是 2.2.0 出事的地方。
4. **`source_commit` 由 `assemble.sh` 在装配时刻记录**，不在制 DMG 时取。源是**装配**那一刻被读走的（§0 快照）；制 dmg 时再取 HEAD 会记下一个更晚的提交，那是记错，比不记更糟。
5. **`source_dirty` 的判据是保守的**：整个仓库有任何未提交改动（含未跟踪文件）即判 `1`。宁可误报，不可漏报——2.2.0 出事时，没有任何字段说出「这版载荷含未入库源码」。dirty 时脚本**记录不撒谎并当场告警，但不中止构建**（见后续动作 N1）。
6. **时序固定为：构建 → 提交清单 → 打 tag。** tag 必须指向含清单的那个提交，否则 tag 担保的是源码、不是客户手上的字节。
7. **哈希与注释同住一个文件。** macOS `shasum` 会跳过 `#` 开头的行（6.02 实测 `exit 0`），因此清单仍是 `shasum -a 256 -c` 可直接消费的格式，不必为源凭据另开一个文件（那会让同一件事有两个家）。
8. **失败方向是「产物完好、清单缺失」。** 清单写在原子就位**之后**：宁可放弃两者一起原子就位（它们分属两个父目录，本来也无法用一次改名同时落位），也不允许出现「清单描述了一份并不存在的产物」。
9. **2.2.0 的清单是事后补录，如实标注 `source_reconstructible=no`。** 不猜、不补：哈希可校验（与产物内 `SHA256SUMS` 逐字节一致），源凭据标注为不可回溯。

## 备选方案

- **乙：订正 SOP，承认清单与二进制同居且不入库，删掉根 `release/`。** 否决。它会把这个状态**固定下来**：哈希继续散在散文里、无一家可校验，且客户手上的字节永远无法被仓库认领。附带一个具体代价也已查实——删根 `release/` 必须同时删 `.gitignore:73` 的 `!release/**`，否则 `checkGitignoreWhitelist`（`scripts/gates/checks.mjs:41-56`）会把 `release/**` 剥成 `release` 再查磁盘存在性，目录没了即判「幽灵条目」，门禁直接红。
- **只入库哈希、不带源凭据。** 否决。那样得到的是一份「能证明字节是我们发的」却答不出「从哪个提交来」的记录——而 2.2.0 正是后者出了事。
- **清单与产物一起原子就位。** 做不到：两者分属不同父目录，无法用一次 rename 同时落位。按第 8 条选定失败方向。
- **由 `sign-and-dmg.sh` 取 `HEAD` 当 `source_commit`。** 否决：会记下比装配更晚的提交，属于把错误答案写进凭据（见决策 4）。
- **纯哈希文件 + 另一个 provenance 文件。** 否决：两份文件描述同一件事，违反 ADR-0009；且注释行实测能被 `shasum -c` 容忍，没有拆的理由。
- **dirty 时中止构建。** 本轮不做。把它升级为硬失败属于门禁的职责（N1），现在就让构建在既有工作流里变红会打乱发布节奏；本轮先保证「记录不撒谎 + 当场告警」。
- **把清单写进 `packaging/release/`。** 否决：那目录被忽略，等于没入库。

## 后果

**正面**

- 客户手上的字节可被仓库认领：清单与 DMG 同目录时 `shasum -a 256 -c <version>.sha256` 即可验证。
- tag 第一次同时担保**源码与字节**（时序见决策 6）。
- 「装配时工作树是否干净」第一次有字段说出来，而不是等人事后翻载荷。
- 清单生成从「人的一步」变成流水线的产出，与 ADR-0056 同一条方法论。

**负面 / 代价**

- 每次发布多一次提交（清单必须先于 tag 入库）——有意保留的摩擦。
- `source_dirty` 判据保守，会因与出货无关的工作区改动误报为 `1`。误报方向上是安全的（只会让人多看一眼），但会让该字段在长期高频开发时较常为 `1`。
- 仓库根 `release/` 从「一个 README」变成「每版一个文件」，需要对它做一次 `.gitignore` 白名单外的确认（已由现存的 `!release/**` 覆盖，实测门禁通过）。

**后续动作**

- **N1**：把「载荷源码保真」做成门禁——载荷内嵌了完整 `vendor/` 源码树，因此可机读比对「payload 里的 vendor 树 vs tag 的树」；这才是**能**抓到 2.2.0 那件事的判据（哈希抓不到）。同期把 `source_dirty=1` 升级为硬失败。
- **N2**：2.2.0 的处置仍未决。按本 ADR 决策 6 与 ADR-0057 第 4 条的同号规则，不应重打 2.2.0；剩余选择是补发 2.2.1（从干净提交装配）或维持「不可回溯」标注。留给用户裁定。
- **N3**：GitHub Releases 缺 v2.2.0（最新是 v2.0.0），而 `README.md` 指向 Releases 下载——该渠道对当前版本是空的。
- **N4**：哈希的散文副本（根 `CHANGELOG.md`、`packaging/CHANGELOG.md`、`PLAN.md` 的截断值）本轮**未动**：它们是已发布版本的史料，改写属于独立的编辑决定。清单成为机读的唯一家之后，这些位置宜改为指向清单而非复述数值。
