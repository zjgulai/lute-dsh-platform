# ADR-0034 · 功能的提示词骨架 = 多技能组合（岗位方法 + 产品契约）；功能内部下沉为 `steps[]`

- 状态：accepted
- 日期：2026-09-12
- 决策者：用户（M1 试点定为 KOL-Hunter + 岗位归属）+ agent（试点压出的偏差）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-12-native-agent-product-multiskill-skeleton.md)
- 修订：[ADR-0033](ADR-0033.md) 决策 2 的「提示词骨架取技能正文」一句——取的是**多条**技能的组合，不是一条

## 背景

[ADR-0033](ADR-0033.md) 裁定「一个功能的提示词骨架是一个**技能**，而不是 `product.json` 里的内联字符串」。规格 v1 据此把字段写成单数 `features[].skill`，并把功能的 `kind` 定为 `"model" | "deterministic"` 二选一。

M1 用真实项目（`/Users/lute/project/KOL-Hunter`，功能 `select-candidates`，归属岗位 `agt-033 结伴 · 达人与联盟合作`）把这条压了一遍，压出两处表达不了实际情况的地方：

1. **骨架不是一条技能。** 达人方法论在岗位技能里——`agt-033` 的 `dsh-skill-subset` 已声明 `p2s-kol-creator-matching`（六维匹配 / ROI 折算），实体在 `~/.dsh/skills/` 下。但「本产品输出哪些字段、六维权重各取多少、分级阈值是多少、超预算怎么处理」是**产品自己的事**。写进岗位技能，等于让产品改自己的口径必须去动岗位；写进 `product.json`，等于把长 Markdown 塞进 JSON（ADR-0033 已否决）。
2. **功能内部的 `kind` 二选一表达不了。** `select-candidates` 天然是两段：一段纯算术（归一化 → 六维加权 → 预算硬约束 → 排序 → 折减 ROI），一段判断题（写理由、下结论、指出池子缺什么）。标成 `model` 会让「`deterministic` 不得调模型」这条约束失效；标成 `deterministic` 则是说谎。

## 决策

1. **`features[].skill`（单数）→ `features[].skills[]`（有序数组，带角色）。** 每条技能声明 `{ id, layer, role }`，`role` 至少两档：
   - `method` —— L1 岗位专属技能，管「**怎么想**」：方法论、算法口径、业务约束；
   - `contract` —— L2 产品局部技能，管「**产出什么形状**」：字段、权重取值、分级阈值、边界。
   拼装要求两层同时在场，缺任一层直接抛。
   **分工的理由是可评审性**：方法归岗位、形状归产品，两者的评审人不同；写进同一条技能会让一次产品的口径微调必须走岗位技能的评审。
2. **口径（权重、阈值、折减公式）的唯一事实之家 = L2 技能正文的表格**，由工具**从技能正文读**（`pipeline/skills.mjs` 的 `readWeightsFromSkill` / `readGradesFromSkill`），不硬编码在代码里。配套自检项断言「工具实现的维度集合 == 技能权重表的维度集合」「折减公式在技能正文里逐字存在」。
3. **功能级 `kind` 下沉为步骤级 `steps[]`。** 每个步骤各自声明 `kind: "deterministic" | "model"`。`deterministic` 步骤不得调模型这条约束由功能级移到步骤级，语义不变、覆盖面变准。
4. **由此产生两条机检契约**（分工写死在声明里之后，「数字归工具、判断归模型」从倡议变成契约）：
   - 模型回写进产物的六维分 / 总分 / 预估 ROI / 预算契合，必须与工具读数**逐字相等**；
   - **分级只能降不能升**——阈值判出的分级是算术结果，模型可降级并写明理由，不得升级。
5. **`products[].status` 增补 `statusReason`。** 两档枚举回答不了 M1 落地时的真实状态（功能已跑通、入口面板尚未打包安装）。理由必须是机读字段，不是文档里的散文。
6. **`kind` 为 `model` 的功能，其模型步不由产品脚本直接调用模型。** M1 取「脚本拼装提示词 → 外部模型产出 → `--advise` 并入」；产品最终形态里这一步应由产品插件在会话内触发，凭证与模型路由归基座。落点须在 M2 前定。

## 备选方案

- **一条功能只挂一条技能**（v1）：放弃。见背景第 1 条。
- **口径硬编码在打分代码里、技能只写散文说明**：放弃。同一份口径会有两个家，改一处忘另一处正是本平台已付过代价的漂移模式。代价是技能正文的权重表被约束成可解析的表格格式——这个代价值得。
- **把产品契约也写成 L1 岗位技能**：放弃。产品换口径要动岗位技能，且多个产品会争抢同一批岗位技能名。
- **保留功能级 `kind`，用 `steps[]` 只做说明性描述**：放弃。那样两条新契约（数字逐字相等、只降不升）就没有声明依据，只能靠人记。
- **把 `statusReason` 写成文档链接**：放弃。卡片要当场说实话；让用户点进仓库翻文档才知道 draft 卡在哪，等于没说。

## 后果

### 正面

- **方法与形状可以各自演进**：岗位换方法论不动产品，产品换字段不动岗位。
- **口径只有一个家且有守卫**：改口径只改技能表格；只改一处而另一处没跟上，自检红。
- **「数字归工具」从倡议变成可机检的契约**：两条负例探针实测均为 exit 1（改写 `totalScore`、把 `exclude` 升到 `test`）。
- **分工写进声明，就能被门禁读**：M1 的 14 项自检里 6 项是真机检，M4 直接搬进门禁即可，不需另起一套。

### 负面 / 未决

- **产品必须明确声明它依赖哪条 L1**，声明错了自检会红，但「该不该依赖这条」仍是人的判断，机器判不了。
- **技能正文被约束成可解析格式**：权重表、阈值表、折减公式都得写成人能读、机器也能读的形状；纯散文写不出这种技能。
- **模型步落点未定**（决策 6）：当前靠脚本外挂，凭证与模型路由都不在基座内，这是 M2 前必须收口的临时形态。
- **`--advise` 并入路径不是最终形态**：它证明了契约能守，但没证明「会话内一键跑通」。M2 要补。
