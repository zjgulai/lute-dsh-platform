# ADR-0020 · 岗位小队 = 单 preset 的人格 + 技能并集，不做多 preset 挂载

- 状态：accepted
- 日期：2026-09-11
- 决策者：用户（lute）+ agent（DSH 语义取证 + 材料实测后提出）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-11-role-squad-contract.md)

## 背景

需求是「未来通过同时添加多个 Preset 的方式来组成小队办公」。这句话在 DSH 里落不下地：

1. **一个会话挂一个 preset**——`agentPresets.mount()` 只在会话创建的 `setup()` 里被调用，
   且会话跑过一轮后 host 拒绝更换（该会话历史是在原组合下产生的）。
2. **子 Agent 只能 bind**——`composeFrom()` 的原文注释是 "It is a bind, not a mount"，
   并拒绝已 join 的 context。所以「每个子 Agent 配一个岗位 preset」在语义上被封死。
3. **standing mount 按 preset id 单飞**，同一 preset 的多个会话共享同一个组合实例。

材料侧 `ADR-0003`（D-020）早已定下相反的形态：一张工单一个 Case Agent、一个主岗位人格、
其他岗位**贡献按需 Skills**，并明确取消 LLM 多 Agent 路由与岗位 Agent 互聊。

两侧对照，"小队 = 一个人格 + 一份技能并集"是**收敛解而非妥协**：
`dsh-skill-subset` 本就吃 skills 数组，小队即一个 preset，其技能白名单是若干岗位技能集的并集，
无需任何新运行时机制。

实测另暴露两个必须先修的问题：**①** 首版生成器把 `can_be_primary` 硬编码为 `true`（50/50），
而材料中只有 **12 个**岗位有主岗位资格、**38 个只能贡献**——读这份契约的编队生成器会无声地
选出一个永远当不了队长的岗位当队长；**②** "全流程贡献岗位并集"的天真做法经实测为
**47–104 项技能**（FLOW-02 达 104），而单岗位只有 2–13 项（均值 7.6）。

## 决策

1. **小队 = 一个 preset**：编排人格 + N 个岗位的技能并集 + 成员职责引用。不是多 preset 挂载，
   也不是岗位 Agent 互聊。
2. **契约落在 `manifest.json` 的 `x_lute.squad`**（LUTE 自有格式，官方 roster 不读，
   扩展它不违反任何 schema）；`preset.yml` 严格只保留官方三字段。
3. **`can_be_primary` 必须由材料算出**（`primary_eligible_flow_ids` 非空），不得是常量。
4. **新增 `lead_rules`**：逐条取自各流程 `primary_role_selector` 中 targets 为本岗位的规则，
   附 `selector_status` 与 `zero_or_multiple_match_disposition`，使岗位对"何时能当队长"自足。
5. **生成器硬约束：零匹配或多匹配一律 WAIT，绝不 fallback 到贡献岗位当队长。**
   材料对全部 8 条流程定的都是 `WAIT`；其中 FLOW-01 / 05 / 07 的队长取决于尚未编译的范围条件。
6. **成员集合不自动推导**：材料把 flow-scenario 绑定标为未验证候选，且流级
   `required_skill_contract_refs` 为空、`skill_contract_mapping_status = not_instantiated`。
7. **技能并集必须有预算**：47–104 项不可直接装配，成员数应按并集预算反向裁剪。
8. **本轮只落契约与闸门**：不实现生成器、不改挂载机制、不碰 `agents` / `subagents` 宿主平面。

## 备选方案

**同时挂载多个 preset。** 被 DSH 语义否决：一个会话一个 preset，且跑过一轮后拒绝更换。

**子 Agent 各带一个岗位 preset。** 被 `composeFrom` 的 bind 语义否决：那是继承父方已组合的
实例，不是给子方挂新组合。

**用 `dsh-agent-team-gui` 的 team 承载小队。** 被否决——其 member 各自携带 model / role /
fallback / token limit / tool policy，是"多模型并行分工"模型；把岗位塞进 member 等于重新引入
材料明确取消的多 Agent 路由。两者形态相似、语义相反。

**小队 = 全流程贡献岗位的技能并集。** 被实测数字否决（47–104 项），目录税过高，
且与材料「按需 Skill 装配」原则相悖。

**在 preset 目录加 `squads/` 子目录登记小队。** 被否决——官方 roster 只扫一层，
子目录不进 roster，且会与 `manifest.json` 形成第二份事实源（ADR-0009）。

**删掉 `can_be_primary`、让生成器每次回查 `collaboration-graph.json`。** 被否决——
岗位 preset 将无法自证编队资格，且把"谁是队长"散落到生成器里。留字段但算准它。

## 后果

- **正面**：小队形态与材料架构同构且无需新机制；`manifest.json` 成为可机器装配的单一事实源；
  新增的 L9 断言把"契约与材料漂移"从静默变成红灯；修掉了一个会静默产出错误编队的 bug。
- **负面/代价**：FLOW-01 / 05 / 07 的队长依赖未编译的 predicate，目前无法自动编队；
  成员集合仍依赖人工指定；技能并集预算阈值尚未定。
- **后续动作**（四条齐备后才实现生成器）：① 编译 3 条流程的 selector predicate；
  ② 实例化流级 `required_skill_contract_refs`；③ 定技能并集预算阈值（起点建议 ≤40）；
  ④ 在此之前小队只能由人显式给出成员名单。
