# ADR-0116 · 预设行的 config 对着插件自己的 schema 判；工具不得把上游的键名钉成字面量

- 状态：accepted（2026-09-17）
- 决策者：用户（lute）+ 2.0.10 升级轮
- 决策记录：[Note](../notes/implemented/contract/2026-09-17-preset-config-schema-mirror-and-structural-anchor.md)
- 相关：ADR-0008（基座只 pin 不改）、ADR-0009（一份事实只有一个家）、ADR-0014（门禁硬门槛 + 豁免只减不增）、ADR-0056（出货面守卫）、ADR-0067（已发布版本归档，不复判）、ADR-0091（三无 preset 的人格层同源判据）

## 背景

上游 2.0.10 把 `@deepseek-ai/dsh-persona` 的配置键从 `text` 改成**必填**的 `prefix`。实测：

```
Config({ text: '…' })   → ✗ $.prefix missing required value
Config({ prefix: '…' }) → ✓ 接受
```

后果不是「人格没生效」，而是**整棵 preset 树载入失败**——日志以 10MB/2min 洪泛，用户看到的只是
「输入会话，大模型没反应」。而这次改名**同时打穿了三个消费面**，形状是同一个：**上游改了一条事实，
我们的产物与工具里还钉着旧值，且没有任何判据会因此变红**。

- **产物面**：2.5.0 待发布出货载荷里 `presets/agt-*/agent.cordis.yml` 仍是 `text: |-`（52 行违法）。
  live 根修好了，不等于要发出去的东西修好了。
- **工具面（同步器）**：`sync-fullstack-persona.mjs` 把键名钉进锚点正则，键名一改锚点永久失配，
  人格层判据整条**空转**——它红得正确，但要人工来消，且这次事故正是「改了产物、忘了工具」。
- **工具面（生成器）**：`gen_bmg_preset.mjs` / `gen_preset.mjs` 仍写 `text: >-`，重跑会把已修好的
  预设再写坏。

一个关键负结果：**键名无法从 schema 推导**——`Config.dict` 把四个键全标成 `required:true`，
没有区分度，所以「自动发现哪个键是人格正文」不可实现；schema 能判的只有**内容是否合法**。

## 决策

1. **产物面建一面会自己变红的镜子**：新判据 `gate:preset-config-schema` 按**插件自己的 `Config`**
   判每一行 config。三层判据：① `Config(obj)` 调用一次（与宿主 loader 同 schema、同调用点 ⇒ 同判罚）；
   ② **键集判据**（row 键集 ⊆ `Config.dict` 键集）——因为 schemastery **不拒未知键**，只调一次 schema
   会漏掉「旧键还在、新键有默认值」；③ 取不到 schema / 解析不了 → 归 `unverifiable`，**单独计数、
   绝不并进「已核实」**。
2. **四态分母必须守恒**：`discovered = ok + failed + unverifiable + notApplicable`。射程 = live 根 +
   **待发布出货载荷**（已打 tag 的版本按 ADR-0067 排除，避免对冻结产物长期判红）。接线到
   `scripts/gate.mjs` 与 `packaging/assemble.sh`（**在 `tar` 之前**判出货副本）。
3. **工具面认结构、不认键名**：`sync-fullstack-persona.mjs` 的锚点改为
   `- id: persona` → `  name: '<pkg>'` → `  config:` → 恰好**一个**字面块标量键；键名任意、写回原样
   保留；0 个或 ≥2 个都响亮失败（猜错键会把人格写进 `suffix`，两边都不报错，只有行为变了）。
4. **一条事实一个家**：键名的家只有插件自己的 `Config`。配置镜按它开罚单；同步器只负责读写正文；
   两个 legacy 生成器改用 `prefix`。任何文件都不得再手抄一份键名表——手抄的表就是下一个会过期的旧值。

## 备选方案

- **把正则里的 `text` 换成 `prefix`**：换个新字面量继续钉，下次改名同样复发（且本次事故正是这么来的）。
- **从插件 schema 推导正文键**：实测不可行（`Config.dict` 四键全 `required:true`，无区分度）。
- **让同步器容忍 `text|prefix` 两种键名**：读侧可应急，但容忍集合本身是第二份会过期的事实；写侧
  一旦两个键同时存在就必须猜，猜错即写进错键。
- **只在 `assemble.sh` 里判**：出货前才红，开发期看不见。
- **给 2.5.0 的 52 条开豁免**：它红的就是「即将发出去的字节是坏的」，豁免等于把它发出去。

## 后果

- 键名一改，产物面有配置镜红、工具面同步器不再空转；`pnpm run gate` 84/88 → 85/88，
  `agent-fullstack` 由红转绿（`persona 同源=是 4224 字符`）。
- **门禁当前是红的，且是设计内的红**：`staging/2.5.0` 出货载荷 52 行违法，只能由 **r8 重切**清除，
  不许豁免；r8 验收后**退役 `staging/2.5.0`**，否则该判据永久红。
- **未核实面必须一直显式**（`dsh-plan-mode`×105、`dsh-skill-subset`×103 未导出 `Config`；`!!js`×5）：
  「读不到」不是「都合格」。
- 键集判据只适用于我们生成器的 YAML 形态；非 package 行与无 config 行归 `notApplicable`，不是「通过」。
- `verify-lossless.mjs` 仍读侧容忍两种键名，未与「键名一个家」收口；两个 legacy 生成器的落点
  （`brand-marketing-growth` / `overseas-*`）已不在 live 预设根，是否退役未决。
- 更一般的一条：**凡是「产物形态」的判据，都应当对着产物的权威（插件 schema / 运行时解析器）判，
  而不是对着我们手写的字面量判**；凡是工具需要知道「上游的某个名字」时，先问这份事实的家在哪里。
