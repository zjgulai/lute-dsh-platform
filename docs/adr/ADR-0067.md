# ADR-0067 · 已发布的产物不允许被删除：仓库外归档 + `uchg` 锁定 + 门禁核对 + 找回命令

- 状态：accepted（2026-09-13）
- 日期：2026-09-13
- 决策者：用户（明确要求「不允许删除发布的版本和历史发布的版本」）+ agent（机制与判据设计）
- 决策记录：[Note](../notes/implemented/contract/2026-09-13-release-artifacts-immutable.md)
- 相关：ADR-0057（产物要么缺席要么完整）、ADR-0058（入库清单：清单是「我们承诺过什么」的家）、ADR-0056（机器路径只减不增）、ADR-0014（门禁是硬门槛，豁免只减不增）、ADR-0063/0065/0066（同一批发布面修复）

## 背景

已发布过的 DMG **两次**从 `packaging/release/<版本>/` 里消失，每次都只剩
`manifest.json` / `SHA256SUMS` / `VERSION`：

| 版本 | 现状 | 取证 |
| --- | --- | --- |
| 2.2.0 之前某次（2026-09-12） | 产物消失 | 当时结论是「不是 `sign-and-dmg.sh` 所为」（三个伴随文件保留原始 mtime），但**没查出是谁** |
| 2.3.1（2026-09-13 发现） | 产物消失 | Spotlight 全盘查不到该 dmg；`release/.archive/` 无；本机**无 APFS 本地快照**（`tmutil listlocalsnapshots /` 为空）→ 不可回滚 |

已排除的怀疑对象：仓库里没有任何脚本会删产物（`grep` 过 `git clean` / `rm -rf release` / `rm *.dmg`，
唯一命中的是发布守卫自测删它自己的沙箱）；`~/.zsh_history` 无相关记录；cron 与 `~/Library/LaunchAgents`
里的 LUTE 代理都不做清理。

真正的问题不是「谁删的」，而是**这件事发生时没人说话**：`release/<版本>.sha256` 已经进了 git，
它就是我们「承诺过这串字节」的书面记录（ADR-0058），而承诺与字节分家后，系统里没有任何一处会报错——
直到某个客户拿着清单来核对。这与本批修复的另一条同源（失败必须给出为它负责的读数，ADR-0043）。

用户裁决：**不允许删除发布的版本和历史发布的版本**。

## 决策

1. **发布即归档到仓库外**：`sign-and-dmg.sh` 在发布成功（原子就位 + 入库清单）之后，把该版本目录
   （dmg + SHA256SUMS + VERSION + manifest.json）复制到
   `$HOME/Library/Application Support/LUTE/releases/<版本>/`（可用 `LUTE_RELEASES_ARCHIVE` 覆盖），
   **回读校验**归档副本的 sha256 必须与已发布那份逐字节相同，否则本次发布判失败。
   归档在构建树之外：`git clean -xdf`、`rm -rf packaging/release`、重新克隆都碰不到它。
2. **两处副本加 `uchg` 锁定**（用户不可变标志）：删除/改名/覆盖一律 `Operation not permitted`。
   唯一合法的解锁点是 `sign-and-dmg.sh` §5 重制同一版本号时的归档改名；其他任何删除都必须先
   显式 `chflags -R nouchg`——**把误删变成「必须表过态才可能发生」**。锁不上即判发布失败：
   不允许「以为锁了其实没锁」。
3. **判据唯一实现 + 进门禁**：`packaging/scripts/release-verify.sh` 对照 `release/*.sha256` 逐个核对
   产物是否存在、哈希是否一致、归档是否一致、是否已锁定；`scripts/gate.mjs` 的
   `release-artifacts-intact` 每次 `pnpm run gate` 都跑它。判定语义：
   - 版本目录整体不存在 → SKIP（本机从未发布过该版本：新克隆/新机器，不假红）
   - **版本目录在、dmg 不在 → 红灯**（这正是 2.3.1 的形态）
   - dmg 在、哈希不符 → 红灯
   - 未登记目录（早于 ADR-0058 清单机制的版本，如 2.0.1）→ 只报告并补锁，不判红
4. **找回是命令，不是手工**：`packaging/scripts/release-restore.sh <版本> [--from <dmg 路径>]`。
   从归档或**任何外部副本**（客户手上那份、聊天软件里那份）恢复，先与 git 清单对哈希，
   **对不上即拒收**——这条同时就是「客户手上那串字节是不是我们发的」的判定器。恢复后自动加锁。
5. **丢失要宣告，不许沉默**：`release/<版本>.lost` 记录「该版本产物已确认不可找回」的日期、取证与
   找回办法。它是**事实记录，不是豁免**：门禁把「早已宣告丢失的那一个」与「刚刚又丢了一个」区分开，
   后者必须红灯；每次跑门禁都会把宣告念出来。
6. **重申禁止同号重制**（ADR-0057）：用同一版本号重做出的是另一串字节，不是那一版。产物丢了要找回。

## 备选方案

- **只在 SOP 里再写一句「请注意不要删」**：已经写过两次，两次都没拦住——把纪律寄托在记忆上，
  是本仓库反复否决的做法（ADR-0057「靠人记得不是工程解」）。
- **把 DMG 纳入 git**：每版 600 MB，仓库会被撑爆；且 LFS 需要一个说得出「谁有权删」的家。
- **只做归档、不做仓库内副本**：构建侧看不到产物、门禁无从对照，等于把核对推给人。
- **只上锁不做归档**：`chflags` 挡得住 `rm`，挡不住「解锁后删」「磁盘清理工具」「整个目录被搬走」；
  两份不同物理位置的副本才谈得上「找得回」。
- **把归档放云端（GitHub Releases / 对象存储）**：需要网络与凭据，且引入「谁有权删远端对象」的新问题；
  作为**后续项**（发布动作里已有上传 Releases 的步骤），不作为本地不可变性的替代。

## 后果

- 磁盘占用翻倍：每个已发布版本约 600 MB（本机现为 5 个版本）。这是用户明确要求的代价。
- 已补做历史版本：2.0.1（早于清单机制，无哈希可核，归档时留下 `ARCHIVED-SHA256`）、2.2.0、2.3.0、2.3.2
  均已归档并锁定。
- **2.3.1 永久丢失**（本机无副本、无快照），已按第 5 条宣告；任何外部副本可经 `release-restore.sh`
  核验收回。已发出的 2.3.1 dmg 因此成为「唯一存世副本」。
- `pnpm run gate` 增加约 4 秒（三份 610 MB 产物的全量哈希）。核查代价随版本数线性增长，将来版本变多时
  再评估是否把哈希挪进 `--mode full`。
- 重制路径（`sign-and-dmg.sh --force`）已处理解锁与归档改名；`uchg` 不会挡住合法重制。
- 这条纪律只覆盖**本机**：产物一旦离开本机（飞书直传、GitHub Releases 附件），它的存续取决于远端的
  保留策略——所以「分发」与「留档」必须分开做，本地归档不是备份策略的替代。
