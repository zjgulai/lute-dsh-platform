# ADR-0057 · 发布产物的发布语义：构建在临时区完成、原子改名就位；同号重制须显式 `--force` 且旧产物归档不删除

- 状态：accepted
- 日期：2026-09-12
- 决策者：用户（lute）+ agent（事故复盘后要求「这个问题要解决，不能再这样发生」）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-12-release-atomic-publish.md)
- 相关：ADR-0002（DMG 发布：`release/<版本>/` + SHA256SUMS 校验清单，本 ADR 补上它从未写明的**重制语义**）、ADR-0009（一份事实只有一个家）、ADR-0014（门禁硬门槛 + 豁免只减不增）、ADR-0056（出货面守卫：把「靠人记得」换成「机读、只减不增」）

## 背景

`packaging/sign-and-dmg.sh` 第 35 行曾是：

```bash
rm -rf "$REL"; mkdir -p "$REL"
```

它每次运行都先清空整个版本目录再重制。后果不是「重复劳动」，而是**破坏性的时序**：毁掉上一份产物这件事发生在**新的一份还没做出来之前**。此后任一步失败（`hdiutil` 出错、验签不过、磁盘写满、Ctrl-C），得到的是「旧的没了、新的也没有」——而目录里可能正躺着已经交付给客户的字节。

2026-09-12 的实测取证澄清了两件事，都必须记准：

1. **当天那次「DMG 从 `release/2.2.0/` 消失」不是这一行干的。** 现场证据：`manifest.json` / `SHA256SUMS` / `VERSION` 三个文件都保留了 22:50 的原始 mtime——若 `rm -rf` 执行过，它们会随目录一起消失或被子进程重建。真正的原因是飞书客户端把文件移走后又下载回 `~/Downloads`（那份的 `com.apple.quarantine` 记录着 agent=Feishu，且与原产物逐字节相同，SHA256 `e74fb6d0…4ac86e`）。**结论：不要把这行当成事故原因**，它只是一条独立的、真实存在的风险。
2. **风险本身是真的。** 只要有人出于任何理由重跑一次该脚本（补一个补丁、换一个图标、重新出一次包），上一份已交付的产物就会无声消失，且**不可找回**——因为 `rm -rf` 之后没有任何地方留过它的字节。这与 ADR-0002 建立的「`release/` + SHA256SUMS 是唯一可校验、可回滚的交付家」直接冲突：家可以被一次手滑抹平。

同时暴露出两个同族缺陷：

- **无主构建锁会永久挡住后续构建。** 锁是 `release/.build.lock` 空目录，靠存在性互斥；一次 SIGKILL 就能留下无主锁。2026-09-12 现场就躺着一个（空目录、无 pid、无构建进程），它会让下一次构建直接以「另一构建进行中」退出——**用户无从判断该锁是真的还是残留的**。
- **报错路径上有一处 bash 3.2 陷阱。** 原脚本 `echo "...（$DMG）"` 里裸变量紧跟全角括号：bash 3.2（macOS 自带 3.2.57）会把多字节字符的首字节吃进变量名，`set -u` 下直接以 `unbound variable` 崩掉。也就是说**「该报的错」报不出来**。（同族教训本仓库已记录过一次：提交 `afe641c`「bash 3.2 下 `$VAR（` 会把全角括号吃进变量名——三处一起修」。）

## 决策

1. **`release/<版本>/` 只有两种合法状态：不存在，或一份完整且已全部通过终验的产物集合。** 不存在「构建到一半」的中间态。这一条是契约本身，其余四条都是它的实现手段。
2. **构建与全部终验在 `$REL` 之外的临时区完成**（`release/.staging.XXXXXX`），期间版本目录一个字节都不动。构建成功与否都不影响已发布产物。
3. **就位靠一次原子改名**（`mv`，同卷内的 rename）：先在临时区把 dmg + `SHA256SUMS` + `VERSION` + `manifest.json` 摊平成完整集合，再整目录改名就位。读者要么看到旧的完整集合，要么看到新的完整集合，不存在「dmg 换了但 SHA256SUMS 还没换」的窗口。
4. **同号重制必须显式表态。** 版本目录已有内容时默认**拒绝**（退出码 1，先于一切重活执行），并打印目录内容与现有产物 SHA256，给出两条路：换版本号（推荐），或加 `--force`。理由是本仓库的核心契约「**版本号 = git tag = 打包版本**」——同号不同字节一旦流出去，「客户手上那版对应哪份源码」就无法回答。
5. **旧产物归档而非删除。** `--force` 下把旧目录**改名**到 `release/.archive/<版本>-<时间戳>/`，永不删除。归档是改名，不复制、不占额外空间，且旧字节保持可回溯。
6. **构建锁记 pid，无主锁自动回收；活锁仍必须挡住。** 锁内写入持有者 pid；pid 已不存在（或锁内无 pid 记录，即旧版脚本遗留）时打印一行说明后回收；pid 仍在则拒绝并报出持有者。判据是「**进程是否真的还在**」，不是「目录是否存在」。
7. **发布语义必须有可执行断言守护。** 新增 `packaging/scripts/release-publish-guard-test.sh`：把待测脚本连同依赖复制进临时目录，`PKG_ROOT` 由 `dirname "$0"` 推出，因此测试**永不触碰仓库里 `release/` 下的真实产物**；用合成签名载荷跑完「首次就位 / 同号拒绝 / `--force` 归档 / 终验失败不留半成品 / 无主锁回收 / 活锁拦截 / 参数守卫」共 29 项断言。理由是 ADR-0056 已经立过的同一条：**靠人记得不是工程解，机读判据才是。**

## 备选方案

- **只把 `rm -rf "$REL"` 换成 `rm -f "$DMG"`（只删同名产物，保留元数据）。** 表面上「不再清空目录」，但**破坏时序一点没变**：仍然先毁旧、后制新。放弃。
- **不删目录，构建完原地覆盖 DMG。** 失去了原子性——读者能看到「新 dmg + 旧 SHA256SUMS」的不一致状态，且失败时留下的正是这种状态。而 `SHA256SUMS` 恰恰是本项目唯一的完整性锚。放弃。
- **拒绝一切同版本重跑，不提供 `--force`。** 会把迭代成本转嫁给操作者，并催生「手工去把目录删掉」这种绕过行为——**那恰好是本次要消灭的东西**。放弃；改为「默认拒绝 + `--force` 显式表态 + 归档」。
- **`--force` 时直接删掉旧产物。** 与「必须能回答客户手上那版对应哪份源码」冲突，也让「同号异构」在事后无法取证。放弃。
- **只做原子就位，不做同号守卫。** 静默的同号异构仍然会发生——它和本次事故是邻居风险：一个抹掉旧字节，一个悄悄换掉旧字节。放弃。
- **把版本目录改成只增的 `history/<构建号>/`（每次构建一个新目录）。** 与「版本号 = tag = 打包版本」的一对一契约冲突，下游（安装卡、灰度 SOP、Release 附件）也不知道该读哪一个。放弃。
- **本轮一并修改 `packaging/scripts/build-pkg.sh` 与 `packaging/assemble.sh` 的同族缺陷**（见「后果·后续动作」）。放弃于本轮：`build-pkg.sh` 已无调用方，其 `.pkg` 构建路径**无法在当前环境下取得真实验证**，而本仓库的验收纪律是「不接受口头验收」——**改一个我验证不了的东西，是把风险从「已知」换成「未知」**。登记为后续动作，等有可验证的场景再动。

## 后果

**正面**

- 构建失败、验签失败、磁盘写满、中途 Ctrl-C，**都不再损坏已发布的产物**——这是本次要解决的问题，现在由结构保证，不由人的谨慎保证。
- 「同号不同字节」从「无声发生」变成「必须显式 `--force` 表态」，且表态后旧字节仍可回溯到 `release/.archive/`。
- 读者永远看不到半成品：目录要么缺席，要么完整。
- 无主锁不再永久挡住构建；活锁仍被正确拦截（两者都有断言）。
- 报错路径不再因 bash 3.2 全角括号陷阱而崩掉（原脚本继承来的缺陷一并修掉）。

**负面 / 代价**

- **构建期峰值磁盘占用上升**：临时区与旧产物并存，同一版本重制时约多占一份 dmg（本版 610M）。作为交换，写满磁盘从「灾难」降级为「安全的失败」——这正是不再做前置空间检查的理由。
- **同版本正常重跑要多打一个 `--force`。** 这是有意的摩擦：它把「我在覆盖一个已经流出去的东西」这件事摆到操作者眼前。
- `release/` 下多了两个隐藏目录 `.staging.*`（构建期）与 `.archive/`（归档）。整个 `release/` 已被 `packaging/.gitignore` 忽略，不进版本库；`release/*/` 的 glob 也不会匹配它们。
- 测试引入 `codesign` 与 `hdiutil` 依赖（macOS 限定，与本仓库其余打包工具一致）。

**后续动作**

- **N1：`build-pkg.sh` 的锁与 sign-and-dmg.sh 早已不互斥。** `sign-and-dmg.sh` 用 `release/.build.lock`，`build-pkg.sh` 仍用 `release/<版本>/.build.lock`，两者注释都写着「dmg/pkg 共用 release 目录，串行执行防互删」，实际检查的却是两个不同路径——**声称的互斥是失效的**。该脚本当前无调用方（`.pkg` 自 2.2.0 起已不在交付面），故按 ADR-0013 的资产处置口径应先裁定「归档出工作树」还是「修好后保留」，而非直接改。
- **N2：`assemble.sh:84` 仍是 `rm -rf "$STAGE"`**（`STAGE = staging/<版本>`）。破坏半径小于本 ADR 处理的对象——staging 是构建工作区而非交付家，且它由脚本自己重新生成；但它会连带删掉 `staging/<版本>/payload`，而那正是 dmg 的唯一重建源。建议同等治（临时区 + 原子改名），需先确认 payload 的「可重建性」是否真如设计所设想。
- **N3（可选）：把 `release-publish-guard-test.sh` 接进 `pnpm run gate`。** 它已沙箱化、不碰真实产物，代价约十余秒。本轮未接，因为它会给每次提交增加一次 `hdiutil` 调用；是否值得由用户在「门禁时长」与「回归保护」之间裁定。
