# ADR-0059 · 中转站接入以「逐模型实测工具调用」为准入判据：PoYo 拆两条路由，且在拿到 key 前不写进任何默认位

- 状态：accepted（2026-09-13 修订：判据与路由清单已按实测更正，见「决策」1、2 与文末「修订记录」）
- 日期：2026-09-13
- 决策者：用户（lute）+ agent
- 决策记录：[Note](../notes/implemented/capability/2026-09-13-poyo-relay-route-intake.md)
- 相关：ADR-0009（一份事实只有一个家；本条的模型清单以站方机读 catalog 为唯一来源）、ADR-0014（门禁硬门槛）、ADR-0024（容量表以实测为准、文档值不可信——本条把同一条方法论推到「工具能力」这一维）、ADR-0043（报失败必须给出为它负责的读数）、ADR-0056（靠人记得不是工程解）

## 背景

用户持有 `poyo.ai`（中转站）的 API key，问能否加进「设置 → 模型」，并要求给出接入建议。

排查发现三件互相独立、混在一起看就会做错决定的事：

1. **该站有三个互不相同的 API 面**：异步任务面（`/api/generate/submit`，图像/视频/音乐/TTS/3D，`200` 只代表任务已创建）、OpenAI 兼容对话面（`/v1/chat/completions`、`/v1/responses`）、以及 Anthropic 原生面（`/v1/messages`）。只有对话面才与「设置 → 模型」相关。
2. **该站没有模型列表端点**：`GET /v1/models` 实测 `404`（`POST /v1/chat/completions`、`/v1/responses`、`/v1/messages` 无 key 均 `401`，证明三条面存在）。因此设置页的「获取可用模型」按钮**必然失败**，模型 ID 只能手填或从站方机器可读 catalog 拷。
3. ~~**该站 29 个对话模型里，只有 3 个声明了工具能力**~~ —— ❌ **本条推断已被实测推翻，属假阴性**。schema 里没有 `tools` 字段**不等于**服务端不支持工具调用：实测 11 个对话模型能稳定产出合法 `function_call`，其中 `kimi-k3` / `deepseek-*` / `gemini-*` / `gpt-5` / `grok-4.6` 的 schema 里都没有工具字段。真正不可用的是**另一批**——全部 Claude Opus / Sonnet 系（含 `claude-opus-5`）接受 `tools` 却永不产出 `tool_calls`。详见 Note 的「修订：实测结论」。

第 3 条当时被当作决定性的：DSH 的 agent 主循环靠 `bash` / `read` / `write` / 技能这些工具调用运转，落在没有工具的模型上就是「能聊天、不能干活」。**这条因果仍然成立**——但在拿到 key 实测后，第 3 条的**事实部分**被证伪，且方向与直觉相反（见「决策」1）。

## 决策

1. **「工具调用」升为对话类中转站的准入判据——但判据必须是实测读数，不是 schema 声明。** 一个对话模型能否进 DSH，只能靠**真发一次带 `tools` 的请求、检查响应里是否出现 `tool_calls` / `function_call`** 来判定；站方 catalog 是否声明 `tools` **不可作为依据**（本站实测二者无关，且方向不可预测）。同时：测工具能力**必须用 `tool_choice: "auto"`**，用 `required` 会制造假阴性（`claude-fable-5-1` 在 `required` 下报 `Server exception`、在 `auto` 下两轮全对）。判据链修正为：**逐模型实测工具调用（`auto`）→ 协议匹配 → 上游可达性 → 容量 → 凭据 → 入站 IP → 模型级白名单**。
2. **PoYo 拆成两条路由，而不是一条。** `poyo`（`api: openai-completions`，11 个实测工具稳定的对话模型）与 `poyo-responses`（`api: openai-responses`，3 个 gpt-5-6 变体）。拆开的理由有两层：**协议**不同（那 3 个只声明 `openai-responses`，连 `openai-chat` 都没有），**实测能力**也不同——同一模型在两条路由上的工具行为可以不一致（`deepseek-flash`、`grok-4.6` 在 chat 正常、在 responses 返回参数非 JSON 的 `function_call`），故路由不能按模型族批量迁移。两条路由的模型清单**只收录实测工具稳定者**。
3. **两条路由共用同一个凭据引用** `POYO_API_KEY`，由设置页写入凭据服务；`settings.yaml` 里只留引用名，密钥值永不落盘到配置文件。
4. **pi-ai 的自动探测在该站是错的，必须显式纠偏。** `detectCompat` 只对 deepseek/zai/moonshot/together/nvidia/cerebras 等做特判，`api.poyo.ai` 落默认值；默认值与该站 schema 有 5 处不一致（`maxTokensField` 默认发 `max_completion_tokens` 而该站只声明 `max_tokens`；`stream_options`、`store`、`reasoning_effort`、`developer` role 都会被发而该站 chat 面均未声明）。这 5 项在路由的 `compat` 段显式关断/纠偏，不允许依赖「默认大概没问题」。
5. **不要把 PoYo 写进 `agent-default-model`，也不给它读图位。** 本轮只登记路由，不动默认模型与 `vision-router`；工具能力在拿到真 key 实测通过之前，一律不进任何默认位。
6. **改动的生效判据是「装载点接受」，不是「文件写对了」。** 用真实 settings 节跑一遍 `llm-pi-ai` 的 schema 与 `apply()`（在 `process.resourcesPath` 下加载真实插件），确认它把 5 条路由全部 materialize；只有到这里才算接线成功。

## 备选方案

- **甲：不接对话面，只把 PoYo 当媒体生成后端。** 保留为**主用法**而非替代项——异步任务面本来就不吃工具调用，绕开了本 ADR 的全部约束。但它不回答用户的原问题（「能不能加进设置页」），故不作为唯一结论。
- **只建一条 `poyo` 路由，先跑无工具对话。** ~~已实现，但不足以支撑 agent 用法；留下它就是留下一个「看着能用、实际干不了活」的默认位。~~ 已实现且**实际有工具**（实测通过）；但两条路由仍要并存，因为 `gpt-5-6-*` 三个只支持 `openai-responses` 协议，走不了 chat 面。
- **把 `claude-*` 走 Anthropic 面（`api: anthropic-messages`）以绕开工具缺口。** 本轮不采纳。~~站方为这 12 个 claude 模型提供的唯一 schema 里没有工具字段~~ —— 该理由已作废（schema 与工具能力无关）。**修正后的理由更强**：实测这 12 个 claude 模型**根本不产出 `tool_calls`**，无论走哪条协议面都解决不了；换协议不能给模型补上它没有的能力。若将来要试，应先用 `auto` 模式在 Anthropic 面实测一次，而不是从协议声明推断。
- **把 `defaultContextWindow` 按模型族估高。** 否决：估高会直接 400，估低只让压缩早触发。两个方向的代价不对称，取保守下界 131072。
- **把 29 个模型全量登记。** 否决，但依据已更正：不是「26 个无工具」，而是**实测只有 14 个具备工具能力**（11 个 chat + 3 个 responses），其余 15 个要么不产 `tool_calls`、要么上游 500/402。选择器里不该出现不能干活的行。

## 后果

**正面**

- 用户的问题有了可执行答案：设置页确实能加，步骤与坑写在同一份 Note 里。**并已跑通端到端**：21/29 模型可用，14 个工具调用实测通过。
- 一条可复用的准入判据（**逐模型实测工具调用，`auto` 模式**）从此对任何中转站生效。这条判据的**对立面同样可复用**：读 schema 声明推断工具能力是错的，本轮为此付出了返工代价——先按「只有 3 个声明工具」收窄了模型清单，实测后发现该收窄既漏掉了 11 个真能用的、又留下了 5 个不能用的。
- 「pi-ai 自动探测对自建路由可能是错的」这件事第一次有具体证据（5 处不一致逐条对上 schema），后续接任何新中转站都能照这个清单先核一遍。
- 配置的验收有真实读数：真实 schema + 真实 `apply()` 全部 materialize，不是「文件看着对」。
- **一个新的、可复用的事实：中转站有两个独立准入维度**（入站 IP 白名单、模型级放行），二者错误码可区分，且都排在凭据校验之后。「退回去只当媒体后端」不是绕开它们的方法。

**负面 / 代价**

- `defaultContextWindow: 131072` 是保守值而非实测值——该站不对外给出上下文窗口数字，故按 ADR-0024 的口径，这个字段**明确标注为未实测**。
- 两条路由共用一个凭据引用，意味着 key 只有一个家；这是有意的（ADR-0009），代价是不能给两条路由配不同额度。
- ~~`openai-responses` 面的 SSE 事件协议未经验证~~ —— ✅ **已解**：三个 responses 模型流式路径实测返回完整的 `response.created` → `response.completed` 序列，非流式下 `output[].type == "function_call"` 携带合法 `arguments` JSON，工具调用参数可正常恢复。
- **上游稳定性成为新的主要保留意见**：本轮实测到 4 个模型 `500 Server exception` + `gpt-5.4` 的 `402 insufficient_quota`（**PoYo 自己的上游 OpenAI 账号欠费，用户余额充足也修不了**）。站方自述稳定性略低于官方，对「一断就整轮重来」的 agent 主循环是真实风险，故 PoYo 仍不写进默认位——**理由从「工具未验证」改为「上游稳定性未达标」**。
- **同一模型在不同路由上的工具行为可以不同**（`deepseek-flash`、`grok-4.6` 在 chat 正常、在 responses 参数非 JSON）。这使「按模型族批量迁移路由」的做法不可靠，每迁一次都要重测。

**后续动作**

- **N1**：~~对 `poyo-responses` 做一次流式 function call 端到端实测~~ —— ✅ **已完成并通过**。通过后**仍未上默认位**（见「负面 / 代价」末条）。
- **N2**：把本 ADR 的准入判据（**逐模型实测工具调用 → 协议 → 上游可达性 → 容量 → 凭据 → 入站 IP → 模型级白名单**）落成可执行的核验脚本，避免下次接站重新手查一遍。本轮脚本暂存 `/tmp/poyo_probe/`，尚未收进仓库。
- **N3**：媒体生成面（异步任务）本轮未接，若要用需另开一条决策记录——它走的是任务提交与轮询，不是对话协议，不该塞进 `llm-pi-ai`。

## 修订记录

- **2026-09-13（同日修订）**：本 ADR 的原始版本把「schema 声明了 `tools`」当作准入判据，并据此把 PoYo 的模型面收窄为「3 个有工具 + 26 个只能聊天」。拿到可用 key 后逐模型实测，该前提被证伪，故修订三处：**(a)** 准入判据从「读声明」改为「逐模型实测工具调用」；**(b)** 路由模型清单改为实测放行的 11 + 3；**(c)** 不写进默认位的**理由**从「工具未验证」改为「上游稳定性未达标」。原始推断过程保留在 Note 的正文里并就地标注撤销——那次失误的教训（**读契约下结论 ≠ 实测**）比结论本身更值得留档，与 ADR-0024 同一条方法论。
