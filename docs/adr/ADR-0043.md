# ADR-0043 · 门禁报失败必须给出「为它负责的读数」：输出按流分流保留，退出码不得折算

- 状态：accepted
- 日期：2026-09-12
- 决策者：agent（一次无法定性的门禁红灯暴露取证缺陷后提出）
- 决策记录：[Note](../notes/implemented/contract/2026-09-12-script-evidence-by-stream.md)

## 背景

`scripts-runnable` 在 `gate:full` 报过一次失败：

```
fail contract scripts-runnable
     - packages/surfaces/dsh-skill-center-local: test 脚本运行失败（退出码 1）
       — }); ⏎ /* assert on the output */ ⏎ This ensures that you're testing the behavior
         the user would see in the browser. Learn more at https://reactjs.org/link/wrap-tests-with-act
```

**这三行是 React 的 `act()` 警告，不是失败原因。** 报告说了「退出码 1」，却没有任何一条读数
为它负责——读的人无从知道哪个测试挂了。随后 13 次复现尝试（隔离 `gate:full` 一次、直连
连跑 10 次、12 个 burner 压 10 核一次）全部通过，源文件 mtime 也早于该次门禁两小时，
**根因至今未定**。

但「它为什么无法被定性」是可以定性的。实测同一个包：

```
stdout =  784 字节   ← 含 vitest 全部汇总（Test Files / Tests / 失败用例名）
stderr = 5821 字节   ← 全是 act() 警告
```

而旧实现的取证方式是：

```js
const output = `${error.stdout ?? ''}${error.stderr ?? ''}`.slice(-SCRIPT_OUTPUT_TAIL)  // 4000
// checkScriptsRunnable 再取最后 3 行非空
```

stdout 全在前、stderr 全在后，拼成一个 blob 再按**位置**截尾。stderr 有 5821 字节 >
4000，于是截尾窗口被 stderr 独占，784 字节的汇总**在任何一次运行中都不可能出现在报告里**
——无论那一次是绿色还是红色。这不是偶发，是证据通道对该包**结构性失效**。

同一函数里还有第二处，形态相同但更彻底：

```js
if (error.killed) return { code: 124, ... }              // 文档声明「超时按 124 记」
return { code: typeof error.status === 'number' ? error.status : 1, ... }   // 兜底折算成 1
```

Node v26 实测，`execFileSync` 超时时 `error.killed` 是 `undefined`：

```
killed = undefined   signal = SIGTERM   status = null   code = ETIMEDOUT   (node v26.0.0)
```

于是超时**从不进入 124 分支**，一律掉进 `?? 1` 被报成「退出码 1」——文档声明的契约
与运行时行为不一致，且超时与真正的测试失败在报告里长得一模一样。

两处的共同点：**报告里的那个数字不是读数，是折算出来的。** 这与 ADR-0040 同族——那里的
`退出码 0 + 无输出` 也是「看起来有读数、其实没有信息」。

## 决策

1. **输出按流分流保留，不拼接。** `runScript` 返回 `{ code, stdout, stderr, note? }`，
   两个流各自截尾到 `SCRIPT_OUTPUT_TAIL`。调用方按流取证，谁的体量大都不再挤掉另一个。
2. **取证时每个流各自标注、各自限额。** 违规消息形如
   `stdout: … ⏎ stderr: … ⏎ <note>`。警告仍在报告里，但不再顶掉汇总。
   按**正则过滤**的调用方（`patch-anchors`）仍扫两个流——位移只在按位置截尾时发生。
3. **退出码必须来自真实读数，不得折算。** 没有 `status` 时返回 `code: null` 并附
   `note` 说明原因（信号名 / 输出超限 / 超时），报告为「脚本未给出退出码」。
4. **超时判定两个字段都查**：`error.killed === true || error.code === 'ETIMEDOUT'`，
   兼容不同 Node 版本的错误形状。
5. **显式设 `maxBuffer`（16 MiB）。** 默认 1 MiB 对测试运行器太紧，且超限本身没有
   `status`——不设就会与决策 3 一起把「输出超限」读成「测试失败」。
6. **该逻辑独立成 `scripts/lib/run-script.mjs`。** 它的正确性只能被真实子进程证伪，
   而 `gate.mjs` 是带顶层副作用的脚本、import 即执行整轮门禁，测不了。

## 备选方案

- **只把 `SCRIPT_OUTPUT_TAIL` 调大。** 治不了本：两个流体量差一个数量级时，位置截尾
  总是让大的那个赢，只是把阈值往后推。
- **按「哪个流更长」选一个报。** 正是旧实现失败的原因——体量与信息量无关，5821 字节的
  重复警告信息量为零，784 字节的汇总才是判据。
- **合并两流但按行去重后再截尾。** 去重对「700 行一模一样的警告」有效，但对「700 行
  各不相同的警告」无效，鲁棒性依赖噪声恰好重复，不能作为契约。
- **把 `error.killed` 换成只看 `error.code === 'ETIMEDOUT'`。** 会把其他 Node 版本上
  合法置位 `killed` 的路径丢掉；两半都查成本为零。

## 后果

- 门禁报失败时，报告里必定包含「失败发生在哪」的读数；警告不再具备淹没汇总的能力。
- 超时、被信号杀、输出超限、真正的非零退出，四者在报告里**互相可区分**。
- `scripts-runnable` 的既有判据不变（仍按退出码是否非零），改的只是取证方式；
  127 空转分支与豁免逻辑不受影响。
- `test:gate` 的 glob 增加 `scripts/lib/*.test.mjs`，新助手层从此纳入自检范围。
- 本次那次 `dsh-skill-center-local` 红灯**仍然未定性**——本 ADR 修的是「下次能定性」，
  不是「这次已解释」。不得据此把它记成已解决。
