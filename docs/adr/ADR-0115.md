# ADR-0115 · 浅色主题取真中性骨架；官方被消费的 alias 必须全量接管，字面兜底上收

- 状态：accepted（2026-09-17）
- 决策者：用户（lute）+ 浅色主题色彩审计轮
- 决策记录：[Note](../notes/implemented/surface/2026-09-17-light-theme-neutral-palette-contract.md)
- 相关：ADR-0009（一份事实只有一个家）、ADR-0014（门禁硬门槛 + 只减不增豁免）、ADR-0019（官方 UI 改写锚必须运行时解析）、ADR-0029（主题 Token 判据两侧共同证伪）、ADR-0104（Codex 视觉语法与默认风格）、ADR-0110（视觉多源收口）

## 背景

深色主题整改收尾后，浅色主题被报「充斥着很多种蓝色和蓝色的涂层」。审计（只读，2026-09-17）实测到的
不是一处写错的色值，而是**品牌皮肤只覆盖了不到一半的可见 token**：

- 官方浅色块声明 **90** 个自定义属性，但其中只有 **79 个是 `--dsw-alias-*`**（另 11 个是
  `--dsw-specific-*`）；官方前端**真实消费 44 个 alias**（把 `--dsw-specific-menu` 也算上是 45），
  `dsh-theme-local` **只接管 19 个**。未接管的 25 个里，`--dsw-alias-link` = `#4176e6`（DeepSeek 蓝）
  被消费 6 处（markdown 链接、fileMention、sourceLink、fetchUrl），而 `--dsw-alias-brand-primary`
  在皮肤里是品牌绿 `#347A2F`——同屏两种「品牌色」。附带事实：`#4176e6` 在**皮肤浅色底 `#F6F7F4`** 上
  对比度 **3.94:1**——原记的「4.24:1」是它对**纯白**的值，两个底色被混用了，真实缺陷更重。
- 官方「中性」自带两套：`--dsw-static-neutral-*`（真中性）与 `--dsw-static-neutral-bluish-*`（蓝味），
  而浅色 alias **默认全部走 bluish**。加上皮肤层的绿味，浅色 `L≥0.88` 的近白色值实测 **29 个不同值**
  （其中 3 个是纯白——`#fff` / `#ffffff` / `#ffffff2e` 三种写法并存，属命名不一致而非色值不一致）。
- 硬编码 hex **335** 处（口径：hex 出现数 − token 定义数；审计当时 315，差 20 由同期并发写入的
  theme-local 新组件解释——把 26 个未跟踪文件排除后回到 319），**18 个 token** 带多重字面兜底、
  合计 **88** 种变体（`--dsw-alias-border-l1` 有 **10** 种、`label-primary` 与 `label-secondary`
  各 **8** 种）。色相直方图：**210–239° 有 90 个不同色值**（审计当时 88），品牌绿所在的 90–149° 仅 33 个。
- 浅色 `layer-1/2/3` 由 `color-mix` 派生后 **layer-1 最亮、layer-2/3 更暗**，与深色
  `base < surface < layer-2 < layer-3` 单调递增的层级语法相反。**已在真实 Chrome 里逐条求值确认**
  （相对亮度：浅色 base 0.9265 → layer-1 1.0000 → layer-2 0.9753 → layer-3 0.9911，非单调；
  深色 0.0098 → 0.0167 → 0.0267 → 0.0349，单调）。
- 深色有 **18** 条 `body[data-ds-dark-theme]:not([data-dsh-skin])` 专用整改层（全在
  `skill-panel.module.css`），**浅色对应形态 0 条**；非 node_modules 的 CSS 里 `data-ds-dark-theme`
  共提及 24 处。

参照系（一手取证）：`/Applications/ChatGPT.app`（bundle id `com.openai.codex`）的
`webview/assets/app-30b4fba457b3.css` 实测 **中性色阶 24 级全部零色相**（`#fff` → `#0d0d0d`），
7 个彩色仅作语义槽位；其 `gray-100 #ededed` 与 DSH 官方 `--dsw-static-neutral-150 #ededed` 同值。
即：**专业感来自中性彻底去彩度 + 彩色限于语义，而不是来自选了什么颜色**。官方有真中性尺却不用它。

本次判断的射程是「**皮肤没有接管全部被消费的 token**」这一类缺陷，它同时解释蓝色残留、冷暖冲突
与包间方言。上游自身也有一次未收口的 token 改名（`--dsw-alias-brand-primary-new-colorprimary-new-color`），
说明这类缺陷会复发。

落仓探针在审计之外还带回一条**新发现**：皮肤里所有「向白提亮」的派生式都写成
`mix("#FFFFFF", n, base)`（即 `color-mix(in oklch, #FFFFFF n%, base)`），而**白在 OKLCH 里色相是
`none`**——Chrome 把 `none` 带进结果（计算值形如 `oklch(0.299442 0.00884613 none)`），上色时把缺失
色相当 0，于是派生层的冷暖方向**翻转**，与基色无关。真实引擎实测：

| 表达式 | 渲染结果 | 与基色方向 |
|---|---|---|
| 基色 `#202420` | `rgb(32, 36, 32)` | 冷（R<G） |
| `color-mix(in oklch, #FFFFFF 6%, #202420)` | `rgb(50, 44, 45)` | **暖（R>G）← 翻转** |
| `color-mix(in srgb, #FFFFFF 6%, #202420)` | `rgb(45, 49, 45)` | 冷（R<G）= 基色 |

浅深两态的 layer-2/3 全部中招，与 `in srgb` 对照的通道差 **1–7 级**（浅色侧 1 级，属量化噪声；
深色侧 5–7 级）。**这条不改变本轮决策**——真中性调色板令色相无定义，会顺带消掉它；但它说明
「派生式在哪个色彩空间插值」本身是一个需要判据的维度，将来若启用带彩度的预设，必须为此单独定判据。

## 决策

**1. 浅色取真中性骨架，品牌绿只作强调。**
`theme-tokens.ts` 已是「6 色 palette + `color-mix` 派生」结构，只要 palette 本身零色相，全部派生
自动成为真中性。codex 预设浅色六值改为 `lightBackground #F7F7F7`、`lightForeground #0D0D0D`、
`lightInlineCode #F3F3F3`、`lightSidebar #F9F9F9`，`lightSurface` 保持 `#FFFFFF`，
`lightAccent` 保持品牌绿 `#347A2F`。

**深色在同一批（B1）同步去彩度**——深浅必须是同一套灰阶的两种曝光，只改浅色等于把不一致从
「浅色内部」搬到「深浅之间」。深色六值改为 `darkBackground #171A17 → #131313`、
`darkSurface #202420 → #1C1C1C`、`darkSidebar #191C1A → #161616`、
`darkInlineCode #292D29 → #212121`、`darkForeground #F1F4F0 → #EDEDED`，
`darkAccent` 保持品牌绿深色变体 `#58B848`。取值即 Codex 灰阶 dark 侧
（`gray-50 #131313` / `gray-75 #161616` / `gray-150 #1c1c1c` / `gray-200 #212121` / `gray-900 #ededed`）。
去彩度后深色层级 `base #131313 < sidebar #161616 < surface #1C1C1C < layer-2 ≈ #272727
< layer-3 ≈ #303030` 仍单调递增，`color-mix` 派生式不需要改。

**2. 官方前端消费的 44 个 alias 全量接管（新增 25 个）。**
原记的「45 个 / 新增 26 个」把 `--dsw-specific-menu` 算了进去——它是 `--dsw-specific-*` 而非 alias，
正是把「90 个声明」当成「90 个 alias」时被一起数进来的那一个。按语义归族的细分（品牌/链接、状态色、
markdown 面、按钮控件、文字遮罩）需在实现时按 25 个重新归，本 ADR 不预填。
`button-primary-fill` 与 `--dsw-specific-menu` 由既有别名自动跟随，不单独接管。官方前端**不消费**的
35 个 alias（以及 10 个 `--dsw-specific-*`）不接管：不为看不见的东西定语义，也让「接管面」保持在一个
客观判据上。

**3. 字面兜底上收，surface 不再自带色值（两态一起做）。**
surface CSS 只写 `var(--token)`；「皮肤未加载时的保底值」由构建时从 `presets.ts` 的 codex 预设
生成一份静态默认样式表，单一事实源仍留在 `presets.ts`（ADR-0009）。`skill-panel` 现有的深色专用
覆盖层改造为两态对称的语义层。**深色同样要收口**：深色下实测仍有 14 个蓝味字面量
（`team-hub/admin-ui/styles.css` 的 `#181a1b`/`#202124`/`#3c4043`、
`studio.css` 的 `#18181b`/`#27272a`/`#303034`），只收浅色等于重演本次故障的不对称。

**4. 浅色层级方向修正。**
`layer-1/2/3` 改为从 `surface` 向 `base` 派生，保证 `base < layer-1 < layer-2 < layer-3`
单调递增（`layer-3 = surface = #FFFFFF`），与深色同向。浅色的层级色差实际由 `base ↔ layer-1`
一级承担，layer 之间靠阴影与边框——这是浅色系统的物理约束，不假装三层各有明显色阶。

**5. 新增门禁 `theme-alias-coverage`。**
判据：从产物 CSS 提取「被 `var()` 消费的 light alias 集合」，必须 ⊆ theme-local 接管集合。
数据源在运行时从产物提取，**不硬编码清单**。与既有 `theme-tokens` 分工为「官方消费 vs 本仓接管」
对「引用 vs 定义」。存量 26 个登记进 `scripts/gates/exemptions.json`，只减不增（ADR-0014）。
配套：`scripts/acceptance/theme-palette-audit.mjs` **已落仓**（五组取证 + 真实引擎求值，带 16 条仪器
自检与 `--break <split|blue|scan>` 突变验证），本 ADR 的全部数字都由它产出、可逐条复跑；
`scripts/acceptance/theme-engine-crosscheck.mjs` **已落仓**（跨引擎对照，见「后果」第一条）；
`docs/pitfalls-playbook.md` 补一条根因「皮肤只覆盖了一半的可见 token」。
**本条的门禁本体 / exemption 登记 / pitfalls 条目三件本轮未做**，阻塞原因已验并写在
[Note](../notes/implemented/surface/2026-09-17-light-theme-neutral-palette-contract.md) 的
「执行顺序约束」末尾：门禁的判据取自 B1 的接管集合，先写只能把当前缺陷状态冻成 exemption 基线。

## 备选方案

- **保留绿味中性画布，只清蓝味**：否决。绿味中性在浅色下极难维持一致，一个色值没跟上就显脏；
  而取证已证明「没跟上」是常态。真中性把「未跟上」的代价从偏色降到无色相，更鲁棒。
- **接管全部 90 个 alias**：否决。另外 45 个官方不消费，其中 `label-primary-bluish`、`brand-text`
  一类语义本身与品牌冲突，为它们定映射是无意义劳动，且会让接管面失去客观判据。
- **只接管蓝色/冲突的 26 个**：否决。滚动条、`markdown-code-block` 等非蓝但同样不统一的 token
  会留下，下次还要再开一轮。
- **全量替换为 token 并删除所有兜底**：否决。「skin 未加载」会退化成官方蓝味而非优雅降级；
  上收优于删除。
- **浅色三层各给明显色阶**：否决（物理不可行）。`layer-1` 若为纯白，上面的层无法更白。
- **只改浅色、深色不动**：否决。那只是把不一致从「浅色内部」搬到「深浅之间」。

## 后果

- 浅色的蓝味可从结构上归零（palette 零色相 ⇒ 派生零色相）；`--dsw-alias-link` 改指品牌绿后
  链接与品牌统一，在**皮肤浅色底 `#F6F7F4`** 上对比度 **3.94:1 → 4.92:1**（纯白底上是
  4.23:1 → 5.29:1），**修掉一个既有 AA 缺陷**，且缺陷比原记的更重。
- 上游再发生 token 新增/改名而下游未跟进时，由 `theme-alias-coverage` 拦住，不再依赖用户肉眼发现。
- **本 ADR 只记录决策，实现未开始；B0 已完成**（本件 + Note + 落仓的审计探针 + ADR 索引登记）。
  批次：B0 留痕 → B1 皮肤层与 44 个 alias 接管 → B2 兜底上收 → B3 门禁与变异测试 →
  B4 实况验收（浅/深截图、对比度、键盘、reduced-motion）。
- **B1 被序列化在 `docs/plans/2026-09-17-appearance-revamp.md` 的 P1 之后**（用户 2026-09-17 确认）：
  该计划的 contrast 字段把当前 palette 的派生结果逐字冻结进了 `theme-tokens.test.ts` 的 golden 断言，
  而 palette 是更底层的字面量——先改会让对方正在写的对比度缩放基线一起漂移。等对方落地、测试转绿后
  再改 palette，并按新值重新冻结 golden。约束与解除条件写在
  [Note](../notes/implemented/surface/2026-09-17-light-theme-neutral-palette-contract.md) 的「执行顺序约束」。
- **尾债已清（且已跨引擎复核）**：`color-mix(in oklch, …)` 的实际输出已完成真实引擎逐条复核
  （探针 §6/§7），并已用**产品同版 Electron 的 Chromium** 复算——两条尾债是不同的两个问题：
  「在真实引擎里求过值」与「在**产品那个**引擎里求过值」。实测探针跑 Chrome `153.0.8010.48`，
  产品 Electron 43.3.0 自带 Chromium `150.0.7871.212`（差三个大版本），20 条表达式
  **逐字节相同**，含 `oklch(… none)` 的计算值序列化。对照脚本
  `scripts/acceptance/theme-engine-crosscheck.mjs` 已落仓、可复跑；它另把「vendor 的 Electron
  与应用包的 Electron Framework 同版」写成前置断言，版本分叉时响亮失败，而不是给出一个
  看起来可迁移的假象。
- **未决尾债**：无实况浅色截图（browser bridge 未连接、43120 需配对凭证），B1 前必须先取证，
  否则改的是「我以为的浅色」。**不能用产物级渲染冒充它**：探针 §6 已在真实 Chromium 里逐条求出
  派生色的 sRGB 输出，但那是**调色板**的实况，不是**界面**的实况，两者不能互相顶替。
  `theme-tokens-live.mjs` 不模拟 theme-local 的运行时注入，属探针射程之外。
- **取实况的路径已收窄为一条**（2026-09-18）：`dsh web` 打印的带 token URL **不可走**——那等于把凭据
  贴进会话，违反 AGENTS.md 与 ADR-0008 的凭据红线（本 ADR 初稿曾把它列为候选，此处撤回）。
  只剩 **browser bridge**：用户在**自己已登录的浏览器**里接上 bridge，由本会话直接读实况 DOM 与
  计算色。它比截图硬——截图只能量像素，bridge 能给出「哪个 token 渲染成什么」，而 B1 需要的正是后者。
  实测 2026-09-18 00:2x 仍 `no browser extension is connected to the bridge`（会话内两次探测），
  **B1 因此仍未开工**；`43120` 直连返回 `http=401`。
- **需用户确认的视觉变化**：markdown 链接由蓝变绿影响每一段正文，须在 B1 截图后确认。
  深色同步去彩度会扩大改动面，上一轮刚验收的深色证据需重跑。
