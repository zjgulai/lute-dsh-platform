# ADR-0051 · `parses=False` 拆成「源码写坏」与「判据未定终点」两类，逐卡带行号

- 状态：accepted
- 日期：2026-09-12
- 决策者：用户（同意把「20 张源码写坏的卡」列为下一入口）+ agent（剖析与取证）
- 决策记录：[Note](../notes/implemented/capability/2026-09-12-paper2skills-parse-defects.md)
- 订正：[ADR-0049](ADR-0049.md) 收尾时那句「余下 20 张是源码本身写坏（全角标点）」

## 背景

ADR-0049 / ADR-0050 收尾时都留了同一个数：**20 张已恢复但 `ast.parse` 不过**。
上一版 README 把归因写成「源码本身写坏（全角 `（`、`：`）」，并按这个归因提了下一入口：
「失败集中在全角标点，很像一次批量的中文化替换误伤了代码」。

本轮实测把这个归因**推翻成两条**，且两条要修的地方完全不同。

### 一、那 20 张不是一类，是两类

`parses` 只回答「这段能不能跑」，不回答「这段是不是实现」。用一把与 oracle 无关的
结构尺子就能分开：**被选中的围栏之后还剩几个围栏边界**。

- `after <= 1`（只剩收栏）→ 正文终点**唯一确定**，取到多少就是多少；解析失败只能来自源码本身。
- `after > 1` → 终点不唯一，恢复区可能一路吃到卡正文。

实测 20 张里 `after <= 1` 的**恰好是那 5 张 oracle**，`after > 1` 的**恰好是那 15 张 unverified**，
零例外。再补一把独立尺子（恢复区末行是不是散文行）：20 张里 **18 张末行是散文**
（`## ④ 技能关联`、`**组合效果**：`、`<CAMEL_TASK_DONE>` 之类），全部落在 `after > 1` 那侧。

结论：

| 分类 | 张数 | 含义 | 取到的正文是不是实现 |
| --- | ---: | --- | --- |
| `UNLABELED` | **5** | 卡里源码写坏；终点唯一 | 是，但跑不起来 |
| `WINDOW_TRUNCATED` | **15** | 无 oracle 时终点不唯一，吞了卡正文 | **不是** |

### 二、5 张源码缺陷各不相同，一份「批量替换」解释不了

逐卡定位（`defect_line` / `defect_detail` 字段里就是这行字）：

| 卡 | 行 | 病 |
| --- | ---: | --- |
| `Skill-CodeXEmbed-Code-Semantic-Embedding` | 208 | 第 204 行 `"code": """` 开串，串体里 docstring 又写三引号 —— Python 的串**不嵌套**，外层在内层**开引号**处被提前收尾 |
| `Skill-Model-Performance-Monitor` | 62 | `health_` 后跟控制字符 `U+0001` |
| `Skill-RFM-Segment-Campaign-Dispatcher` | 170 | 第 168 行开 `(`、第 170 行用 `}` 收，括号种类不匹配 |
| `Skill-Real-Time-Competitive-Repricing` | 58 | 三引号开串到末尾仍未收尾 |
| `Skill-TimeCMA-LLM-Forecasting` | 1 | `from paper2skills-code.03-时间序列…` 连字符不在标识符字符集里，逐字抄了文件系统路径当模块名 |

五种形态，五种成因，没有共同来源。

### 三、「全角标点误伤代码」这条假设不成立

全角 `（` 出现在 **1,110 张**卡的恢复区里（9,768 次），其中 **1,091 张正常 `ast.parse`** ——
它们全在字符串与注释里，合法。全角 `：` 同理（1,037 张 / 1,018 张能过）。
`U+0001` 在全语料只出现 2 处，另一处 `Skill-New-Product-Opportunity-Mining` **能 parse**。
含连字符模块名的 import 在 **5,355 条 import 里只有 1 条**。

所以：**既没有批量污染，也没有批量可修**。上一版 README 那句归因是本轮推翻的。

### 四、「卡里实现 ≠ 仓里的实现文件」——顺手钉死

拿仓内真源码当外部真值（vault 仓 git 历史 `paper2skills-code/**/*.py`，**1,288 个**，
比工作区那 199 个多一个数量级）逐卡做行签名覆盖率：

- 20 张里的 **1 张**（`Skill-Model-Performance-Monitor`，0.989）确实来自真源文件；
- 其余 **19 张**卡内实现**不在真源码树里**（最高覆盖率 ≤0.10，多数 0.03–0.07）。

即「卡里那段」与「仓里那个文件」是两套东西。这一条让「去仓里取完整实现」这条路彻底断掉，
也让上一段「源码写坏」的判定有了独立参照：坏的是**卡里那段**，仓里那份是好的。

## 决策

1. `data/code-recovery.json` 里 `parses=false` 的卡**必须带** `defect`（封闭词表两支）、
   `defect_line`、`defect_detail`；`parses=true` 与 `unrecovered` 的卡**不许带**。
2. 判据实现在 `scripts/build-source-code.py` 的 `defect_of()`：先找可精确指认的源码缺陷
   （控制字符 → 嵌套三引号 → 非法模块名 → 括号不匹配 → 三引号未收尾），找不到再看
   `after <= 1` 与否，据此分两支。
3. `stats.defects` 记这份分解；`--check` 把 `parses` / `defect` / `defect_line` /
   `defect_detail` 一并纳入逐卡对账，改了判据不重跑就红。
4. `test/source-code.spec.mjs` 逐张点名锁住 5 张的**行号与原因文案**，并锁住 15 张必须
   落在 `unverified` 侧；`--selftest` 扩到 36 条断言，覆盖每一支判据。

## 备选方案

- **把那 15 张的正文按语法截到最后一个完整语句，当实现交付。**
  这是编造边界。实测 `longest_parseable` 在 5 张 oracle 上的输出就是反例：
  它给出的「最长可 parse 前缀」分别是 199 / 61 / 164 / 56 / 0 行，
  与残缺位置毫无关系（199 行是测试块的起点，不是缺陷点）。放弃。
- **给 `unverified` 那张降级路径加 `ast.parse` 门槛，让它自己认输。**
  ADR-0050 已经实测否掉：`## ④ 技能关联`、`### 前置技能` 都是合法 Python **注释**，
  15 张因此把整段正文当成了实现。语法尺子在无 oracle 时不够用。
- **只写文档说明，不改索引字段。**
  那就还是「每轮重新发现 20 这个数」。文档会漂、字段不会：`--check` 与 81 条单测都盯着它。
- **把 5 张源码缺陷就地修好（改标点、删控制字符、换 import 写法）。**
  修的是**语料**而不是本包；本包只读 vault 的 git 历史，改工作区既不入交付也会与
  `sha256` 口径打架。已实测可行的那一条（`from time_cma_llm_2025.model import …` 能 parse）
  记在这里备查，**不在本包落地**。

## 后果

- README 里那句归因已就地订正；`parses=False` 从「一个数」变成「一份可审计的分解」。
- 15 张 `WINDOW_TRUNCATED` 的恢复区**内容不可信**这一事实被记进索引。
  它们此前也只是 `unverified`（卡面无节选、无 oracle 可校验），本次是把「不可信」说清，
  **不是新增一层降级**，也没有任何卡因此改变分层。落盘张数 1,317、行数 259,365、
  可解析 1,297 全部不变，`sha256` 逐卡不变。
- 本包对 vault 仍是只读。**5 张缺陷留在语料侧**，属于语料自身的债。
