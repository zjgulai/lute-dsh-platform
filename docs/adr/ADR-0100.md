# ADR-0100 · 请求体读取收成有界契约：两处 HTTP 面各自实现、上限由实测天花板推导

- 状态：accepted（2026-09-16）
- 决策记录：[2026-09-16-bounded-request-bodies](../notes/implemented/capability/2026-09-16-bounded-request-bodies.md)
- 关联：[ADR-0009](ADR-0009.md)（一份事实一个家）、[ADR-0015](ADR-0015.md)（决策留痕）

## 背景

`dsh-wanzh-hulian` 与 `dsh-team-hub` 都在插件/服务自有的 HTTP 面上读请求体，两处**都没有上限**：

- wanzh 的 `readBody`：`req.on("data", c => chunks.push(c))` 收到多少攒多少；
- team-hub 的 `collect`：`for await (const chunk of req) chunks.push(chunk)` 同理。

宿主**不会**替它们兜底：`DesktopWebServer.register`（`app.asar.unpacked/lib/webserver.js`）
只做浏览器访问许可判定，对请求体零限制（2026-09-16 读实现确认）。因此这是真实漏洞而非纵深防御：
一条 loopback 连接即可推高宿主进程 RSS，team-hub 场景下一条已登录的局域网连接即可吃满网关内存。

仓库里已有共享实现 `shared/host/http.ts`（`readBoundedJson` / `readBoundedBody`，默认 64 KiB），
但它**不能被这两个包复用**：它是 TypeScript 源码，只对「有 `src/` 且有构建步」的包生效；
wanzh 是无构建步的纯 JS 包（`main` 直接指 `lib/index.js`），team-hub 直接跑 `src/*.mjs`。

## 决策

1. **上限、deadline 与错误语义收成一份契约**，两个包各自实现同一份：
   `Content-Length` 声明超限或累计实际字节超限 → `BODY_TOO_LARGE` / 413；
   超 deadline → `BODY_TIMEOUT` / 408；连接中断 → `BODY_ABORTED` / 400；
   非法 JSON → `BODY_PARSE_ERROR` / 400。任何错误**不回显原始 body**。
2. **只信实际字节**：`Content-Length` 仅用作「提前拒绝」的加速，绝不作放行依据。
   三个真实对抗形态被明确覆盖：无 `Content-Length` 的分块传输、每个 chunk 都合法但累计超限、
   body 传一半断开。声明偏小、实际超发**不列入**——HTTP/1.1 下不可表达（见备选方案）。
3. **上限按「面」分档，不按端点逐个拍**。wanzh 全部 7 条读 body 的路由都是小型设置形态，
   统一 64 KiB；team-hub 分两档——网关**透传面**（代理与 `/api/*` RPC）32 MiB、
   网关**自有面**（登录/改密表单 8 KiB、admin 控制台 64 KiB）。
4. **透传上限由实测天花板推导**：Desktop profile 实际挂载 `dsh-file-upload`
   （`~/.dsh/profiles/desktop/package.json`），其自身上限 `MAX_JSON_BYTES = 18 MiB`，
   取 32 MiB 留 ~1.8× 余量。低于它会打断真实业务。
5. **`try` 块内返回 promise 必须 `await`**（`return await f()`，不是 `return f()`）。
   后半句不是风格问题：`return promise` 下拒绝不会被本函数的 `catch` 接住，
   症状是「请求进了处理器、却永远没有响应」加上一个未处理拒绝。

## 备选方案

- **复用 `shared/host/http.ts`**：被结构否决（见背景）。若强行复用，需要给 wanzh 引入构建步、
  或把共享源改成 `.js` 并重排 `scripts/gates/sync-shared.mjs` 的消费面——那是跨模块架构改动，
  不是本卡（估算 S）的范围。代价被显式接受：两份实现，由两侧同一组测试用例守着。
- **给 team-hub 只加「不透传」的保守上限（如 1 MiB）**：会打断文件上传等真实业务，
  属于「为了安全打断产品」。拒绝。
- **代理面改为流式转发（不缓冲）**：技术上更优，能彻底消除缓冲峰值。但需要改
  `fetch(..., {duplex: 'half'})` 的语义与中途失败的收尾路径，超出本卡范围，登记为后续项。
- **补一条「声明 10 字节却发 500 字节」的用例**：2026-09-16 实测**不可表达**——
  Node 的解析器把 `Content-Length` 当帧边界，多出的字节会被当成下一个管线请求，
  拿到的是解析层 400。写这样的用例只会得到一条永远通不过或永远空转的判据，故不写，
  并在测试文件里留下注释说明原因，避免后来者重新加一条假用例。

## 后果

- 两处 HTTP 面的内存占用不再由请求体大小决定；超限请求不进入业务 handler、不写配置。
- wanzh 的 7 个调用点与 team-hub 的 6 个调用点全部改走有界读取；team-hub 的
  `createRequestHandler` 从 `startServer()` 中提出，成为可测的缝（`startServer()` 不返回
  server 句柄，测试起它会让进程挂住）。
- 未覆盖：跨进程并发下的总内存上限（每连接独立限额，未做全局配额）；代理面的流式转发。
- 相关残余风险与既有缺陷的复发证据见决策记录与 [P-24](../pitfalls-playbook.md#p-24--files-清单漏掉运行时被-import-的文件而缺失被门禁当-note-跳过)。
