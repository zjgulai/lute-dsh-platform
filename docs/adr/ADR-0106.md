# ADR-0106 · 保护面由机制守着：声明 + 只读 API 审计 + 离线反向自测，且「权限不足」不得读成「未配置所以通过」

- 状态：accepted（2026-09-17）
- 决策记录：[2026-09-17-branch-and-tag-protection](../notes/implemented/contract/2026-09-17-branch-and-tag-protection.md)
- 关联：[ADR-0102](ADR-0102.md)（分母由被检查对象的完整集合推出）、[ADR-0105](ADR-0105.md)（CI 的判据面）、[ADR-0094](ADR-0094.md)（三态读数）、[ADR-0001](ADR-0001.md)（本 ADR 更正了它的一处失实声明）、[ADR-0058](ADR-0058.md)（tag 与字节可回溯）

## 背景

QG-008 的目标是「`main` 和发布 tag 不能绕过已建立的检查」。开工时的实测事实：

```
$ gh api repos/zjgulai/lute-dsh-platform/rulesets
[]                                   ← 一条 ruleset 都没有
$ gh api repos/zjgulai/lute-dsh-platform/branches/main/protection
{"message":"Branch not protected", "status": 404}
```

同时，两处文档**声称**保护已经存在：

- `docs/adr/ADR-0001.md`：「main 分支保护、Conventional Commits、PR 模板化…」
- `docs/release-process.md`：「提交（Conventional Commits）→ PR（main 分支保护）→ 合并。」

这就是本仓库总账里的「把意图写成事实」：一份还没被机制守住的声明，读起来与已生效的声明**一模一样**。
卡面把它写成了 TODO 的一条：「建立只读 API audit，文档不再声称不存在的保护」。

## 决策

### 1. 声明是唯一事实之家

`scripts/gates/ruleset-declaration.json` 声明应当存在的保护：`main` 的 `deletion` / `non_fast_forward` /
`pull_request` / `required_status_checks`，以及 `v*` tag 的 `deletion` / `non_fast_forward` / `update`。
审计只说「现状是否等于声明」，不解释规则应当是什么；**多出来的规则与 bypass actor 同样算违规**。

### 2. 比对逐字相等，且「读数拿不到」是第三种结果

只读审计 `scripts/gates/audit-rulesets.mjs` 的退出码就是契约：

| 码 | 含义 |
|---|---|
| 0 | 与声明全等 |
| 1 | 拿得到读数，但与声明不符 |
| 2 | **拿不到读数**（未认证 / 权限不足 / 网络故障 / API 形状变了） |

2 与 1 必须分开，这是卡面负例的直接要求：「API 权限不足…权限不足不得解释成『未配置所以通过』」。
合并成一个非零码，会让人以为「已经比对过、只是不一致」——而实际上什么都没比。

### 3. 两级端点读取，不是多此一举

`GET /repos/{r}/rulesets`（列表）**刻意只返回摘要**，不带 `conditions` 也不带 `rules`。
拿列表去比对，逐条规则永远是「不存在」——实施中第一版就是这样报出
「API 里没有任何 ruleset 覆盖这个 ref」，而**此刻保护已经生效**。判据读错端点，会把
「保护在」判成「保护不在」，与它该防的方向正好相反。所以审计先列后详，逐条 GET detail。

### 4. 应用由声明推导，且默认 dry-run

`scripts/gates/apply-rulesets.mjs` 把声明转成 API payload。手写第二份 payload 等于同一条事实有两个家，
而分家的那一刻「审计通过」就是谎话（审计比的是声明，生效的是 payload）。默认 dry-run；
`--apply` 才写远端，且同名 ruleset 已存在时**拒绝**而不是覆盖（覆盖会让「现在生效的到底是什么」
需要靠时间戳推断）。

### 5. 离线反向自测的基线是**真实 API 读数**

`scripts/gates/fixtures/rulesets-live.json` 是从真实仓库采下来的 payload（只裁剪为审计读取的字段并排序）。
如果基线是手写的「理想响应」，整套变异只是在验证我和我自己一致。

### 6. 人审计不了的东西，就不要写进文档

ADR-0001 的更正以**引用块**形式写在原句下面，不改写历史决策——它记的是当时的意图；
新增的部分说明「那句话曾长期不成立，现在由机制守着」。

## 备选方案

| 方案 | 取舍 |
|---|---|
| 只在 GitHub UI 里点几下配置 | **否**。UI 里的状态没有任何本地判据能复核，且下一次误点没人知道——这正是本卡要消灭的形状 |
| 手写一份 ruleset payload 存档 | **否**。同一条事实两个家，迟早分家（ADR-0009） |
| 用 legacy branch protection API | **否**。「管理员 bypass/break-glass」与 tag 规则表达不了，且 ruleset 是 GitHub 的现行机制 |
| 审计与配置合并成一个命令 | **否**。能改又能验的模块最后总会变成「先改再验」的自我确认 |
| 权限不足时判「跳过」 | **否**。跳过会被读成「不需要保护」；正确做法是判红为**无读数**并说清是哪一种失败 |
| `required_approving_review_count: 1` | **否**。单人仓库要求 review 等于自我审批，是**名义保护**——比没有保护更糟，因为它看起来像保护 |

## 后果

正面：

- main 与 `v*` tag 现在真的不可绕过，且**由 API 自己证实**（见下）。
- 「文档声称不存在的保护」被修掉：ADR-0001 的更正写明了那段历史，`release-process.md` 指向审计命令。
- 15 条反向自测（8 条事故变异 + 权限不足 + 列表端点形状 + 声明形状 + fixture 真实性），
  基线取自真实 API 读数。
- 门禁新增两项：`ruleset-declaration-selftest`（quick，离线）与 `ruleset-audit`（L2 只读，
  拿不到读数时报**类型化 skip** 而不是判红——本机与 CI 都可能没有 `gh`）。

负面与已知边界：

- **`ruleset-audit` 需要网络与 `gh` 凭证**：在 GitHub Actions 里默认没有 `gh` 认证，因此它在 CI 上是
  skip（带 `api-unavailable` 类型）；真实读数目前只在开发机上取。要让它在 CI 里生效需要
  `GH_TOKEN`——那是独立决策，本轮未做。
- 声明里的 `required_approving_review_count` 取 0：这是**有意的**，理由见备选方案表；
  但它意味着「PR 必须存在」不等于「有人看过」。
- `bypass_actors` 为空数组是**声明**而不是遗漏；将来若要放行，必须改声明并留决策记录。
- GitHub 的 ruleset bypass **不留审计事件**，所以「break-glass 留下审计记录」这条自动验收项
  在本机制下只能靠流程（改声明 + PR 说明），不能靠 GitHub。
- **误阻塞风险已实际存在**：`gate (full)` 目前在有依赖/嵌套仓的项上判红（`pin-consistency` 在干净检出上
  必然失败，因为 `vendor/dsh-desktop/` 被白名单式 `.gitignore` 排除、也没有 `.gitmodules`）。这意味着
  **在那些项修好之前，任何 PR 都无法合并**。这是有意为之的诚实状态，但它是本 ADR 最需要盯的一条。
