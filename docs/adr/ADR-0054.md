# ADR-0054 · 改动生效的判据是**装载点的字节**：门禁从「副本有没有这个文件」升到「字节一不一样」

- 状态：accepted
- 日期：2026-09-12
- 决策者：agent（用户验收报障「胶囊没消失」触发诊断；用户批准修复范围）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-12-loadpoint-bytes-drift.md)
- 相关：ADR-0009（一份事实只有一个家）、ADR-0014（门禁硬门槛 + 只减不增的豁免）、ADR-0018（构建产物 `lib/types` 的入库边界）、ADR-0053（上一轮：能力事实读它的家）

## 背景

用户对上一轮交付（ADR-0053）的验收退回两条，其中第一条是「出海技能 / AI全栈技能 并没有从对话框上方消除」。

诊断结论：**仓库里改对了，应用跑的是旧字节。**

`dsh-overseas-skills/lib/client.js` 在仓库里已经不再注册 `conversation.input.dock`（R1 已完成，该包测试全绿），但 DSH 真实装载点

```
~/.dsh/profiles/desktop/node_modules/dsh-overseas-skills/lib/client.js
```

仍是带 `OverseasPaletteStack` 的旧版（66,796B vs 仓库 52,671B）。三个原因叠在一起，缺一个都不会发生：

1. **硬链接会被编辑打断**：profile 里的 `file:` 依赖是**硬链接实体副本**而非符号链接。编辑工具用 tmp+mv 落盘会换掉 inode，仓库那一份从此与装载点分了家，此后每次构建都只写进仓库。
2. **测试读仓库**：该包的契约测试断言的是仓库文件，因此全绿。
3. **门禁只断言文件存在**：`profile-files-sync` 检查的是 `files` 清单条目在装载点在不在——副本旧但它**在**，于是也全绿。

结果是「门禁全绿 + 功能没生效」可以同时成立，而唯一的证据在用户的屏幕上。

顺带查出两处同族缺陷：

- `profile-metadata-sync` 盯的是 `<profile>/vendor/`。而 `vendor/` **不是装载点**——它只是「内嵌 profile 拷贝物化」的判别标记（harness 全仓仅一处引用，`existsSync(join(profileDir, 'vendor'))`）。真正的解析锚点是 profile 根 `package.json`（`resolveOverlayPackage` 的 `profilePackageUrl`）。这条校验一直在看一份没人执行的东西，却自称「live profile 副本」。
- `scripts/sync-profile.mjs` 同样只写 `vendor/`，所以「同步一下就好了」这句话在那天是错的：照它做，用户屏幕不会有任何变化。

## 决策

**把「改动生效」的判据钉在装载点的字节上，并且只钉可执行的产物面。**

1. 新增门禁项 `profile-bundle-sync`：对**仓库受管**且已在装载点安装的每个 `file:` 依赖，逐个比较断言面文件的字节，不一致即失败。
2. 断言面（`loadPointFiles`，规则一处定义、门禁与同步脚本共用）＝
   - **`lib/` 顶层的 `*.js|mjs|cjs`**——直接**读源码目录**而非读 `files` 清单：有的包用 `lib/**` 通配声明，按清单取会一个都取不到，恰好漏掉最该盯的那个文件；
   - `files` 清单里声明的**文件**条目（`manifest/*.json`、`cordis.patch.yml`…）。
3. 明确排除：`lib/types/**`（TS 类型产物，装载点不执行）、`*.d.ts` / `*.map` / `*.tsbuildinfo`、`.md` 文档、通配条目、声明的**目录**条目，以及 `package.json`——后者是 pnpm 在装载点**重写**的（剥掉 `devDependencies` / `scripts`），拿它跟仓库比必然不等，属于把噪声写进判据。
4. `scripts/sync-profile.mjs` 增加 `--loadpoint`：把修复落到真实装载点（tmp+mv 原子替换），与门禁共用同一份断言面定义。
5. 作用域限定为**本仓库受管的包**：另一个项目自己的 `file:` 依赖漂移不在本仓库门禁里判——否则本仓库要为别人的状态变红，然后被加豁免。

## 备选方案

- **断言整个包目录逐字节一致。** 更彻底，但会把 `lib/types/**` 与别的包的 TypeScript 源码一起拉进来。实测：本机立刻多出 3 条与运行时无关的红（deepresearch 的类型产物、KOL-Hunter 的模板）。门禁为噪声变红的下场是它被整体忽略——这正是本 ADR 要修的病，不能在这里复发。
- **只断言 `files` 清单声明的条目。** 漏掉 `lib/client.js` 这类用通配声明的包；而且清单是「交付形态」的声明，不是「装载点执行什么」的事实。
- **让 `vendor/` 继续承担校验，另加一句注释说它不是装载点。** 不解决任何问题：用户的症状就是「照门禁做了，屏幕没变」。
- **不建门禁，只把这次的两个文件同步过去。** 下一次有人用编辑工具改任何一个 `lib/*.js`，同样的坑原样复现——而这正是 2026-09-11 那次 `dsh-preset-lint-local/lib/lint-preset.mjs` 丢失事件留下的教训，本次是第二次踩。

## 后果

**正面**

- 「门禁全绿但功能没生效」这一类失效模式有了结构性的哨兵：只要仓库产物的字节没进装载点，门禁就红，且给出可执行的修复命令。
- 修复方向从「凭记忆 cp」变成 `node scripts/sync-profile.mjs --apply --loadpoint`，与门禁共用同一份断言面，不会分叉。
- 顺带暴露一个反直觉的好消息：`tsdown` 是**就地写** `lib/client.js`，硬链接在构建后仍然存活，所以 `lib/*.js` 的常规构建路径不需要手动同步。真正打断硬链接的是**编辑工具**。这解释了为什么这个坑只在「手改 bundle / 手改附带源文件」时出现，也让门禁的告警面收窄。
- 本机当场抓到第二条真实漂移：同一包的 `manifest/role-assignments.json` 停在 172,674B（仓库 197,708B）——它是 `lib/role-map.js` 的构建输入，装载点旧一份意味着任何直接读它的消费者会拿到过期的归位表。

**负面**

- 门禁多了一条与「本机是否装了 profile」相关的判据；未安装时按「未安装即跳过」处理（与 `profile-metadata-sync`、`profile-files-sync` 同语义），因此它在 CI 上恒真——**它守的是开发机的真相，不是 CI 的真相**。这是刻意的：失效模式只发生在开发机。
- 装载点内容比较是逐文件读全量字节，包多时有一点 IO 成本（本机实测 115 个文件量级，可忽略）。

**后续**

- `vendor/` 那两条（`profile-metadata-sync` 与 `sync-profile.mjs` 的默认模式）语义仍是「内嵌副本」，本轮**不动**其行为；但它的措辞不得再自称 live profile 装载点。已在代码注释里写明两者的区别。
- 已知未覆盖：`dsh-kol-hunter-local`（源码在另一个项目 `/Users/lute/project/KOL-Hunter`）的 `lib/client.template.js` 同样漂移（仓库 11,714B vs 装载点 10,383B）。按本 ADR 第 5 条不在本仓库门禁内，应由那个项目自己的流程处理。
