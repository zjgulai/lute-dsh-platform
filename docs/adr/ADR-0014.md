# ADR-0014 · 门禁全量硬门槛 + 只减不增的临时豁免（N5=A2）

- 状态：accepted
- 日期：2026-09-11
- 决策者：用户（lute）+ agent（grill-me 决策树 N5，用户选择 A 项并经 A2 收口）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-11-lute-refactor-three-phase.md)

## 背景

用户要求门禁最终为**全量硬门槛**：每个包都必须能被机器证明（typecheck + test）。但实测存量与之冲突——20 个插件中 11 个无 `test` 脚本、12 个无 `typecheck`，其中 `dsh-deepresearch-local`（46 个 `@deepseek-ai` 依赖）、`dsh-browser-local`（19 个）、`dsh-agent-team-gui-local`（44 个）属上游 typed 包范围，补齐成本显著高于 11 个小包（按 1-3 天/包估算合计 12-20 人日）。若一期即全量硬门槛，会立刻全红、任何改动都无法提交（死锁）。

## 决策

**终态为全量硬门槛；过渡期以「只减不增的豁免文件」收口，而非关闭规则：**

1. 门禁自一期第一天即为**硬阻塞**（硬门槛校验项见 `.scratch/lute-refactor/spec.md` 门禁分层表）。
2. 存量未达标的包登记进 `scripts/gates/exemptions.json`，每条必须含 `package` / `reason` / `owner` / `deadline` 四字段。
3. 门禁校验豁免文件本身：**禁止新增条目**（条目集合只减不增）、**禁止延长已登记期限**、**期限到期即拒绝**。
4. 三期结束时豁免文件必须为空；门禁对非空豁免文件返回非零（终态自证）。
5. 本次改动的包不受豁免保护——变更包级 typecheck 与 test 立即生效。

## 备选方案

- **A1 先补齐、后开门**：门禁文件先提交但默认不阻塞，12 个包补齐后统一切换。被否决——补齐期可能长达 3 周，期间防线为空。
- **A3 拆包分级**（契约级先行硬门槛、重型包三期收口）：被否决——分级本身会长期充当新的豁免理由，「为什么这个包可以例外」无法收敛。
- **C 只建软门禁**（全部报告不阻塞）：被否决——等价于没建防线，与用户选择的全量硬门槛相悖。

## 后果

- 正面：防线从一期第一天生效；债务以**可机器审计、带期限、带 owner、只减不增**的形式存在，而不是散落在各包里的隐性例外（上游 `verify-package-readme-limitations` 的 allowlist 手法同理，区别在于本仓库的条目自带失效期与冻结规则）。
- 负面/代价：每个豁免包都是显式承认的债务；若到期未补齐，门禁将阻塞整个仓库（这是刻意设计——债务到期即成为最高优先级）。
- 后续动作：一期落地门禁骨架与豁免文件；三期逐包补齐并删除条目，最后验证「非空豁免即失败」的终态。
