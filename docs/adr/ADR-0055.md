# ADR-0055 · 依赖层的可复现判据：清单与锁文件逐条对齐、依赖不得指向机器路径、宿主类型来自内建运行时 tgz、产物未入库则 build 先于 test

- 状态：accepted
- 日期：2026-09-12
- 决策者：agent（用户批准「依赖可复现」为本轮范围）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-12-dependency-reproducibility.md)
- 相关：ADR-0008（基座 pin）、ADR-0014（门禁硬门槛 + 只减不增的豁免）、ADR-0016（依赖符号链接与目录可迁移性）、ADR-0017（**包的类型检查必须指向内建运行时的类型**，本 ADR 第 4 条执行的就是它）、ADR-0018（构建产物入库边界）、ADR-0054（上一轮：改动生效的判据是装载点的字节）

## 背景

2026-09-12 的干净检出验收（ADR-0044 收尾）暴露出一个比「某个包红」更大的结论：**主仓的绿有一部分是本机那份 node_modules 给的。**

同一棵检出 `c1f9572`，两套依赖口径给出两个结论：

- 按本机那套依赖（`typescript` 5.7.3 等）→ quick 15/15、full 19/19 全绿；
- 按仓库里**已提交的清单**全新解析 → 18/19，9 个包红。

这不是九个病，是三个。逐个量过之后：

**一、锁文件契约：24 个受管包里 7 个是坏的。**

| 形状 | 包 | 实证 |
| --- | --- | --- |
| 没有锁文件 | `dsh-loopx-plugin`（22 devDeps）、`dsh-overseas-skills`（4）、`dsh-role-matrix-local`（16） | 目录里只有 `node_modules/`，无 `pnpm-lock.yaml` |
| 清单改过、锁文件没重生成 | `dsh-skill-subset`、`dsh-auto-compact-local` | `ERR_PNPM_OUTDATED_LOCKFILE`：`typescript` 锁 ^5.6.3 / 清单 5.6.3；3 条 peerDependencies 不在锁里 |
| 锁文件格式与仓库口径不一致 | `dsh-team-hub` | 只有 `package-lock.json`（npm v3），pnpm 报 `ERR_PNPM_NO_LOCKFILE` |
| 两者都有 | `dsh-browser-local` | `@types/node` ^22.20.0 vs ^22.20.2；`typescript` ^6.0.3 vs 5.6.3 |

**二、钉与消费方配置互相矛盾，且被本机依赖掩盖。**

`dsh-browser-local` 的 `typescript` 在三个地方是三个数字：清单 `5.6.3`、锁文件 `^6.0.3`→6.0.3、`node_modules` 里 `5.7.3`。而它的 `tsconfig.json` 要 `"target": "ES2024"` 与 `"rewriteRelativeImportExtensions": true`——两者都要 ≥ 5.7。按已提交清单装出来的树，这个包 typecheck 直接红：

```
tsconfig.json(3,15): error TS6046: Argument for '--target' option must be: … 'es2023', 'esnext'.
tsconfig.json(18,5): error TS5023: Unknown compiler option 'rewriteRelativeImportExtensions'.
src/server.ts(264,26): error TS2802: … needs '--target' of 'es2015' or higher.
```

同一包的第二个病：11 条 devDependency 写的是 `/Applications/DSH Desktop.app/…` 这台机器上的绝对路径，24 个包里只有它这么写。pnpm 把该目标记成**相对形式**，而相对前缀取决于安装深度——上一轮换深度重装时它从 `../../../../../Applications/…` 变成 `../../../../../../…`，锁文件因此不可能跨目录移植。

**三、`pnpm install` 本身在两处失败，且产物入库状态与门禁步骤顺序不自洽。**

- `dsh-role-matrix-local` 与 `dsh-skill-center-local` 的 `pnpm-workspace.yaml` 里留着 pnpm 交互式审批写下的占位串 `esbuild: set this to true or false`，导致 `pnpm install` 退出码 **1**（`ERR_PNPM_IGNORED_BUILDS`）。对照：把同一行写成 `true` 的 `dsh-algo-skills-local` / `dsh-newapp-local` 退出码 0。
- 9 个包有 `build` 脚本，其中 5 个（`root-brand` / `agent-team-gui` / `algo-skills` / `newapp` / `role-matrix`）的 `lib/` **没有入库**，而门禁的步骤顺序写死为 `typecheck → test → build`。干净检出里 `lib/` 不存在，`test` 看到的是「文件不存在」。实测（把 `lib/` 移开再跑真实 vitest）：role-matrix 10 失败、algo-skills 8、newapp 6、root-brand 4，四个包全红；`skill-center` 与 `agent-team-gui` 全绿。

## 决策

**把依赖层的可复现写成一个可以离线、确定地判定的契约，并让它进主门禁。**

1. **新增门禁项 `deps-reproducible`**（`scripts/gates/dependency-reproducibility.mjs`），判四条：
   - 清单声明了依赖就必须有 `pnpm-lock.yaml`；
   - 逐条 specifier 与锁文件 importer `.` 记的**完全相等**（清单 → 锁文件正向包含，与 pnpm 的 `ERR_PNPM_OUTDATED_LOCKFILE` 同向）；
   - 依赖 spec 不得是机器绝对路径（`/…`、`~/…`、`C:\…`），锁文件里的 `file:` / `link:` 目标**解析后不得逃出仓库根**；
   - 同一个名字不得在 `dependencies` / `devDependencies` / `optionalDependencies` 里重复声明。

   「逃出仓库根」而不是「出现 `../`」：ADR-0017 指定的内建运行时 tgz 走的就是
   `version: file:../../../vendor/dsh-desktop/vendor/dsh-runtime/<版本>/….tgz`——它出得了包目录，
   但仍在仓库内，跟仓库一起搬。判成「有 `../` 就违规」会把 ADR-0017 的正确做法一起禁掉。

   判据**不 shell 出 pnpm、不联网**：只解析已提交的文本。理由有两条——`file:` 与注册表混合的树离线跑不出结论；而 `pnpm install --frozen-lockfile` 实测在同一棵树上给过不一致的结论（`dsh-preset-lint-local` 首轮 FAIL、次轮与随后连跑三次 OK，锁文件全程 git 干净），一个会漂的判据不能当门禁。

2. **重复声明单列一条违规。** 同一个名字写在两个字段里时 pnpm 只让优先级最高的那一侧生效（实测：`dsh-browser-local` 的 `@deepseek-ai/schemastery` 写在 `dependencies(^3.18.1)` 与 `devDependencies(3.18.2)` 两处，锁文件只记 `^3.18.1`；`dsh-deepresearch-local` 的 `dsh-storage-sqlite` / `dsh-web-fetch-http` 同形）。另一侧不会报错、也不生效，是写给下一个读的人看的谎。

3. **peerDependencies 只在「该名字没有在本地声明过」时才要求锁文件记录它**——这是 pnpm 的实际行为：`dsh-browser-local` 的 7 条 `*` peer 因为都已在 devDependencies 里出现而被放行，`dsh-auto-compact-local` 的 3 条则被要求进锁文件。

4. **依赖一律可在仓库内解析，禁止机器绝对路径。按 ADR-0017 分两类落地**：
   - `@deepseek-ai/dsh-*`（DSH API 类型）→ **内建运行时 tgz**：`file:../../../vendor/dsh-desktop/vendor/dsh-runtime/0.1.2-rc.1/deepseek-ai-<name>-0.1.2-rc.1.tgz`。browser-local 需要 11 个宿主包，其中 9 个在运行时包里，逐一对齐到 `0.1.2-rc.1`。
   - `@deepseek-ai/cordis` 与 `@deepseek-ai/schemastery` → **注册表精确钉**（`4.0.2` / `schemastery` 已在 `dependencies` 的 `^3.18.1`）。运行时 tgz 里**没有**这两个（`ls …/0.1.2-rc.1/ | grep cordis` 只有 cordis 的插件，没有 cordis 本体），它们本来就是宿主的第三方依赖。

   这一条是**执行** ADR-0017 的决策 1，不是新决策：那份 ADR 一天前已经写明「从 `vendor/dsh-desktop/vendor/dsh-runtime/0.1.2-rc.1/*.tgz` 安装对应依赖，**不依赖 `/Applications/DSH Desktop.app` 的路径**」，但直到本轮，24 个包里没有任何一个真的这么写过。

5. **`typescript` 的钉必须满足消费它的 `tsconfig.json`。** `dsh-browser-local` 从 `5.6.3` 改为 `~5.7.3`，与同样要 `ES2024` + `rewriteRelativeImportExtensions` 的 `dsh-agent-team-gui-local` 对齐。

6. **统一包管理器口径为 pnpm。** `dsh-team-hub` 的 `package-lock.json` 换成 `pnpm-lock.yaml`（24 个包里其余 20 个都是 pnpm）。

7. **`allowBuilds` 必须写确定的布尔值。** 占位串两处改成 `true`（与同类包一致）；`dsh-loopx-plugin` 新增 `pnpm-workspace.yaml`，对 5 个带构建脚本的传递依赖显式写 `false`（`@deepseek-ai/dsh-subprocess-local`、`@google/genai`、`koffi`、`node-pty`、`protobufjs`），让 `pnpm install` 退出 0 而不是把决定悬空。

8. **full 模式的逐包脚本顺序改成判据驱动**（`packageScriptOrder`）：
   - 有 `build` 且产物根目录**未入库** → `typecheck → build → test`（干净检出里产物不存在，必须先造出来）；
   - 否则 → 保持 `typecheck → test → build`（已提交的产物就是被测对象，先构建会用新字节盖掉它，从而掩盖「src 改了、lib 没重编」的漂移）。

   产物根目录由 `main` / `exports` 推导（本仓 9 个带 build 的包 `main` 全是 `lib/index.js`），不写死目录名。

9. **宿主类型一律来自内建运行时 tgz；类型图有传递依赖时按闭包声明**（第二轮补，执行 ADR-0017）。
   24 个包里有 5 个的 `@deepseek-ai/*` 是**手做的机器本地符号链接**（指向 `/Applications/DSH Desktop.app/…` 或仓库根那份 gitignore 的 `.dsh-types/`），其中 7 条对应的包在清单里根本没声明——`pnpm install` 不会造出它们，所以干净检出必红。两类落地方式：

   - **只 import 直接依赖的包** → 逐条 `file:` tgz：`dsh-overseas-tools` 1 条、`dsh-wanzh-hulian` 2 条、`dsh-theme-local` 5 条、`dsh-deepresearch-local` 24 条（含它原先从注册表 `^0.1.5-rc.1` 拉的整条 npm 发布线——ADR-0017 明确否决过的路，且与随应用交付的运行时不是同一份字节）。
   - **宿主类型图会互相 import 的包** → 按**闭包**声明：`dsh-agent-team-gui-local` 的 client 半从 6 个入口包出发，`lib/types/**/*.d.ts` 里的 `@deepseek-ai/*` 引用闭包是 **54 个**；并入这些包 `dependencies`/`peerDependencies` 中在运行时存在者，实得 **72 个**，逐条 `file:` tgz。

   为什么少一个都不行：`dsh-client-ui-slots` 的 `SessionStandardProps` 是**空接口**，`sessionId` / `useSessions` 由 `dsh-client-ui-session` 的 `declare module` 合并进来。该包不在树里时，`skipLibCheck` 会把未解析的 import 静默变成 `any`，报错落到源码上（`TS2339`），看不出病根。

10. **判据不是「`tsc` 绿」，是「没有解析失败」。** `skipLibCheck` 让不完整的类型图照样能绿，所以验收看的是 `tsc --traceResolution` 输出里有没有 `@deepseek-ai/*` 解析失败：实测 agent-team 的 client program **0 条**。

11. **上游声明的缺口写进入库的模块增强，不靠生成目录。** `scripts/gates/dsh-types.mjs` 的 `augmentDeclarations()` 在生成目录 `.dsh-types/` 里补三条上游缺失声明（运行时真有、`.d.ts` 里没有）：`Session.events`、`SessionHeader.seedLength`、`JsonValue` 重导出。走 tgz 直装的包看不到那份生成物，因此同样三条以**入库**形式表达：`packages/surfaces/dsh-agent-team-gui-local/types/upstream-declaration-gaps.d.ts`，由 tsconfig 的 `files` 纳入。两处是同一份事实的两个消费面，上游修复后一起删。

    其中 `SessionHeader` 一条必须经 tsconfig `paths` 映射到**声明它的那个文件**（`lib/types/types.d.ts`）：主入口只是 `import type` 进来使用、并未重导出，而模块增强只能并进声明它的模块；增强块内的声明还必须显式 `export`，否则不并。

## 备选方案

- **用 `pnpm install --frozen-lockfile` 当门禁判据。** 最贴近事实，但要联网，且实测会漂（见上）。离线解析已提交文本 + 用 `--frozen-lockfile` 做人工复核，是能同时拿到「确定」与「贴近事实」的组合。
- **无条件改成 `typecheck → build → test`。** 简单，但会掩盖已入库产物的漂移：`dsh-browser-local` / `dsh-deepresearch-local` / `dsh-theme-local` 的 `lib/` 是**已提交的交付物**，先构建就无法发现「src 与提交的 bundle 不一致」。
- **机械判据用「测试是否 import `lib/`」。** 更贴题，但要静态分析每个测试的解析路径才能判定，而且很容易写错——实测 5 个包里有 3 个既 import `src/` 又执行 `lib/`（走的是 `import '../lib/client.js'` 副作用导入与 `readFileSync('lib/client.js')` 这类 grep 抓不到的形态）。按「产物入没入库」判，机械、可离线、且不会漏。
- **把 `dsh-browser-local` 的绝对路径依赖原样留着、只补锁文件。** 补出来的锁文件照样带 `../../../../../Applications/…`，换深度即失效——修的是症状，病是清单里那 11 条路径。
- **把机器路径这条写进 `scripts/gates/exemptions.json` 开局豁免。** 该文件只减不增、到期即拒绝（ADR-0014），且这条路径能当场修干净：11 条依赖对应的版本全在库里，实测换完之后 `tsc` 零错误、111 个测试全过、`lib/` 构建正常。
- **只用注册表版本区间（`0.1.2-rc.1`），不接内建运行时 tgz。** 实测同样能全绿，也满足 ADR-0017 的立意（自包含、与交付运行时同版本、不碰 `/Applications`），但它是 ADR-0017 明确没选的那条路：注册表那份是**另行发布**的产物，与随应用交付的 tgz 不保证字节相同，而且要联网。那条 ADR 一天前已经选好了，本轮没有理由另起一套。
- **把判据写成「锁文件里出现 `../` 即违规」。** 简单，但会禁掉 ADR-0017 指定的 `file:../../../vendor/…tgz`——一条规则如果会拦住仓库自己的既定做法，那它是错的。改成按包目录解析、只判「有没有逃出仓库根」。
- **顺手把 `dsh-deepresearch-local` 的 `^0.1.1-rc.2` 一起升到 `^0.1.5-rc.1`。** 不做：本轮只清掉「不生效的那一侧声明」，保持 pnpm 实际生效的解析结果不变。动版本是另一件事，需要它自己的验证。（第二轮已作废：那条 `^0.1.5-rc.1` 整条换成内建运行时 tgz，见决策 9。）
- **沿用 `.dsh-types` 的符号链接供给（第二轮）。** 它其实是被低估的机制：`.dsh-types/node_modules/@deepseek-ai/` 是**完整的扁平 251 个包**，包内 symlink 的 realpath 落在那棵树里，于是任何传递 import 都能解析——旧树能绿正是靠它。放弃的理由有两条：那份供给是 gitignore 的生成物，`pnpm install` 不会造它（`scripts/dsh-types.mjs --apply` 才会，而它没有被写进任何上手步骤）；且一旦**同名包以实体目录**装进 `node_modules`，realpath 就不再落在供给树里，解析回落 —— 干净检出里 5 个包红，正是这套机制被实体目录挡住的结果。tgz 直装把「类型从哪来」变成清单里可读的一行。
- **只装直接依赖，传递的交给 `skipLibCheck`（第二轮）。** 这就是 agent-team 的 `sessionId` 报错背后的真实状态：类型图缺件被静默转成 `any`，绿与不绿都不说明类型检查真的跑过。ADR-0017 的立意正是「类型检查要有真实语义」。
- **给 agent-team 加一条 `paths` 回落到 `.dsh-types`（第二轮实测不可行）。** `paths` 的替换是**字面路径**、不走 package `exports`：`@deepseek-ai/dsh-client-ui-session/client` 会去找 `.dsh-types/…/dsh-client-ui-session/client` 这个不存在的目录（真路径是 `lib/types/client`），子路径导入一律落空。放弃。
- **把两条 `TS2322`/`TS7006` 用 `as any` 或放宽 tsconfig 压掉（第二轮）。** 那两条是**真实类型错误首次被看见**：`dsh-overseas-tools` 的 `renderExa` 返回 `{type: string}` 没收窄成 `ContentBlock`；`dsh-wanzh-hulian` 的 19 个工具共用 `additionalProperties: true` 的输出 schema，被推成 `Record<string, JsonValue>`，而「可能缺席的可选字段」在 TS 里归一成 `?: undefined`，`undefined` 不是 `JsonValue`。修在类型上（显式 `@returns`、闭合五键 schema），不是压掉。

## 后续（下一轮的两个候选，本轮已量过但没落）

- **把「源码 import 的宿主包必须声明」做成门禁第 5 条。** 本轮的病（`node_modules` 里手做符号链接、清单里没声明）现行门禁只在**干净检出**里才暴露，本机树上完全看不见。离线可判的版本：扫 `src/` 与 `lib/` 里 `@deepseek-ai/*` 的 import，凡不在 `dependencies`/`devDependencies`/`peerDependencies`/`optionalDependencies` 里、且不等于包自身名字的，报违规。实测全仓命中 **1 个包**：`dsh-file-upload-local` → `@deepseek-ai/dsh-client-ui-primitives`（改成 tgz 声明即可）。两个已知噪声必须先处理：`dsh-deepresearch-local` 的 `@deepseek-ai/dsh-deepresearch/remote` 是**自引用**（用包自身名字，须排除）；`dsh-browser-local` 的 10 条全在 `tests/` 里（含已移除的 `dsh-host-apiproxy`），所以规则要么只判 `src`/`lib`，要么先处理那批测试。
- **`.dsh-types` 与 ADR-0017 的关系需要在文档里收口。** 它现在只服务少数仍以 symlink 取类型的包（`skill-center` / `role-matrix` / `algo-skills` / `newapp` 的 tsconfig 里提到它），而 `scripts/dsh-types.mjs --apply` 没有被写进任何上手步骤；本轮 5 个包已不再依赖它。

## 后果

**正面**

- 依赖层的坏锁文件从「7 个包、只有干净检出才发现」变成一条离线门禁的退出码。「把这两个文件倒回 `c1f9572`，新规则报 25 条违规、覆盖全部 7 个包；当前状态报 0 条」——这是可以直接复跑的对照。
- `dsh-browser-local` 从「照清单装出来 typecheck 红」变成 `pnpm install --frozen-lockfile` → `tsc` 零错误 → 111 测试全过 → 构建成功，且锁文件里 9 个 `file:` 目标全部落在仓库内、0 条机器路径。
- 24/24 个包的 `pnpm install --frozen-lockfile --lockfile-only` 退出 0（修复前 16 OK / 3 FAIL / 4 装不上）。
- 干净检出（`git worktree add --detach 8f8cbdd` + 逐包 `pnpm install --frozen-lockfile`）里 `gate:full` 从「多包红」收到 **19/20**，唯一红的 `scripts-runnable` 是 5 个包的另一层问题（见「后续」），且 `adr-index`、`deps-reproducible` 全绿。
- **第二轮补齐后，接受标准达成**：干净检出（`git worktree @ 84aba6d` + 本轮 5 包改动）逐包 `pnpm install --frozen-lockfile` **24/24 退出 0**、`gate` quick **16/16**、`gate:full` **20/20**。5 个包的类型来源全部落在仓库内的内建运行时 tgz，0 条机器路径、0 条手做符号链接；`dsh-agent-team-gui-local` 的 client program 在 `--traceResolution` 下 `@deepseek-ai/*` 解析失败 **0 条**。
