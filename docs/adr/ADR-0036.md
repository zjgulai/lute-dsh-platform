# ADR-0036 · 产品包由岗位 preset 的行挂载，且故意不声明 `dsh.bundle`——把「局部技能」变成结构上不可搞错的事

- 状态：accepted
- 日期：2026-09-12
- 决策者：用户（「产品技能要单独打包到对应的产品中作为局部技能」）+ agent（按 `dsh-skill` 的 scope 契约取证后落形态）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-12-product-package-preset-mount.md)
- **决策 3 已被 [ADR-0037](ADR-0037.md) 取代**：产品包改为挂两层（岗位行注册技能与工具、profile 行带 `role: entry` 只开入口），不再靠「不声明 `dsh.bundle`」硬失败来防泄漏。决策 1/2/4/5/6 仍然有效。
- 承接：[ADR-0033](ADR-0033.md)（产品形态）、[ADR-0034](ADR-0034.md)（功能骨架分层）

## 背景

ADR-0034 定了三层技能与「L2 产品局部技能」，但只写到「由产品插件在自身 fiber scope 注册」，没有说清**那个 scope 是什么、由谁决定、怎么才会搞错**。M2a 要把它做实，取证后得到三条硬事实：

1. **分层是挂载位置决定的，不是插件自己实现的。** `@deepseek-ai/dsh-skill` 的契约是「宿主 + 按 scope 分层」：宿主行与 repository 插件落入**全局层**，**由 agent preset 常驻组合挂载的插件落入该 preset 的层**；读取时合并，最近层直接赢得重名。
2. **同一个包可以同时挂两层，而且不会报错。** 本机先例 `dsh-skill-subset`：它既在 profile 的 `dsh.profile.bundles` 里（patch 在宿主层插一行），又被 50 个 preset 按名引用（preset 层各插一行）。两处都真在跑。
3. **50 个岗位组合是生成物。** `scripts/role-presets/generate.mjs` 每次运行重写全部 `~/.dsh/.agent-presets/agt-*/agent.cordis.yml`；手改生成物会在下一次生成时消失。

把这三条叠起来，误用路径是：**把产品包也加进 profile 的 `bundles`** → 它的 patch 在宿主层再插一行 → 产品技能被注册进全局层 → 每个会话都能看到 → **没有任何报错**。

## 决策

1. **产品目录本身就是那个包。** `product.json`、`skills/`、`pipeline/`、`run.mjs`、`lib/index.js` 同住产品根，`skills/<kebab>/SKILL.md` 是唯一副本：提示词管线读它，插件注册也读它。不复制、不生成副本，因此不存在「两份技能」的漂移面。
2. **挂载点写进生成器，不写生成物。** 产品行由 `scripts/role-presets/generate.mjs` 的 `PRODUCT_MOUNTS` 声明并渲染；`agt-033` 因此多出 `- id: product-kol-hunter / name: 'dsh-kol-hunter-local'`。
3. **产品包故意不声明 `dsh.bundle`，也不提供 `cordis.patch.yml`。** 它不是遗漏，是纠错设计：缺这两个东西会让「把它加进 profile bundles」在启动期**硬失败**（`profile bundle "…" declares no dsh.bundle`），响而不哑；反之若声明了，误用会静默把局部技能变成全局技能。平台插件 skill §1.5 对这类包给的就是这条路——按名由 preset 行引用，不要写进 bundles。
4. **归属与装配是两个事实，各自有家，且必须一致。** `product.json` 的 `preset` = **产品说它属于谁**（产品自己的家）；`PRODUCT_MOUNTS` = **岗位说它挂谁**（岗位组合的家）。产品自检有一项读生成的 `agent.cordis.yml` 断言「该岗位的组合里确实挂了这个包」，不一致即红。
5. **frontmatter 解析只有一份实现。** 插件复用 `pipeline/skills.mjs` 的 `parseFrontmatter`，只把失败策略从「抛」换成「warn 后跳过」——构建期要严格，运行期缺一条技能不该把整个组合拖垮。**策略可以不同，解析器不能有两套。**
6. **安装用 `link:`，不用 `file:`。** `file:` 是安装时刻的硬链接快照（本平台已付过代价，见 `docs/architecture.md` §1）；`link:` 是活软链，产品目录一改即生效。

## 备选方案

- **把产品包加进 profile 的 `dsh.profile.bundles`**：放弃。patch 会在宿主层再插一行，产品技能注册进全局层且无任何报错——静默失败比响亮失败坏得多。
- **挂在 profile 层，用 `config` 区分「这是产品包」**：放弃。靠约定把全局行降级，等于让每个产品都赌自己没写错配置。
- **手改 `~/.dsh/.agent-presets/agt-033/agent.cordis.yml`**：放弃。生成器每次重写全部 50 个岗位，手改会被冲掉且不留痕。
- **把产品代码收进 Magpie-Horch 当受管包**：放弃。与 ADR-0033「本仓库不吞并产品代码」冲突；产品住在自己的项目里，本仓库只出规格、校验器与启动器，外加一行装配声明。
- **插件自带一套 frontmatter 解析**：放弃。同一个 `SKILL.md` 两个消费者两套解析，必然漂移；自检里那条「插件注册的正文与管线读到的逐字节相同」就是为了钉死它。
- **打包时把 `skills/` 复制进包内**：放弃。既然产品根就是包根，复制只会凭空造出第二个家。

## 后果

### 正面

- **「局部」变成结构属性而非约定**：挂载层决定可见范围，误挂会硬失败。
- **一个文件两个消费者不会各读各的**：管线与插件逐字节一致，有自检项守着。
- **产品可自证挂载**：`node run.mjs --check` 直接读生成出来的岗位组合，断言挂载点存在、且没进 profile bundles。
- **新增产品只动一行装配声明**：`PRODUCT_MOUNTS` 加一条，重跑生成器，产品目录本身零改动。

### 负面 / 未决

- **产品包绕开了本仓库的门禁**：它不在仓库里，`luteOrigin`/`luteOwner`/`lutePublish` 与 `package-identity` 都管不到它。代偿是产品自带 18 项自检，但这是两种治理，不是一种。
- **挂载层只到 preset 粒度**：同一个岗位挂多个产品时，它们的 L2 技能在该岗位层合并（注册表同层重名先到先得并告警）。「只在这一个产品处可见」目前做不到，除非将来有比 preset 更细的常驻挂载点。
- **`PRODUCT_MOUNTS` 的路径是绝对的**：profile 用 `link:/Users/lute/project/KOL-Hunter`，换机器要改。**未运行**：只在本机验过。
- **运行时作用域尚未在真会话里证伪**：本轮完成的是形态、静态自检与插件单测；「在 agt-033 会话里能加载该技能、在别的会话里加载不到」需要重启 Harness 之后才能实测。**未运行，不宣称。**

**后续动作**：重启后做两个会话的对照探针（agt-033 会话内 `skills` 目录含 `kol-hunter-candidate-screen`，`lute-cordis` 会话不含）；随后 M2b 收口模型步与入口面板。
