# ADR-0016 · 嵌套仓库治理：受管目录不得含未声明的独立仓库

- 状态：accepted
- 日期：2026-09-11
- 决策者：用户（lute）+ agent（对抗性审计实测后提出）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-11-lute-refactor-three-phase.md)

## 背景

一期把「包身份三元组」写入全部受管包时，`dsh-team-hub` 与 `dsh-task-board-local` 的元数据无法进入父仓库提交。实测根因：这两个目录各自带一个 `.git` 目录，是**独立的嵌套仓库**，而不是父仓库的子模块。

- `dsh-team-hub`：远端 `github.com/zhoujianbin/dsh-team-hub`，52 个跟踪文件，处于 detached HEAD（提交 `24eb47e`）
- `dsh-task-board-local`：远端 `github.com/etony668/dsh-task-board`，17 个跟踪文件，位于 `main`（提交 `4e7f97c`）

`git ls-files --stage | grep '^160000'` 为空——父仓库**完全不记录**它们，既没有 gitlink 也没有 `.gitmodules` 条目。后果是父仓库的 200 次提交与这两个包无关，它们的 79 + 17 个文件对父仓库不可见；更严重的是两者当时分别有 16 个与 6 个文件的**未提交改动**（`dsh-team-hub` 的 `src/` 有 541 行二开源码尚未入库，且处于 detached HEAD），一旦有人清理工作树就会永久丢失。`git add` 对它们静默失败（退出码 0、无任何输出），这也是这些文件长期没有被纳入治理的原因。

## 决策

**受管目录不得包含未在 `.gitmodules` 中声明的独立仓库；此约束由门禁 `nested-repos` 强制。**

处理顺序（先保内容、再改形态、后立规则）：

1. **先保内容**：在各自仓库内提交当时的未提交改动（`dsh-team-hub` 的 Desktop 成员策略层二开；`dsh-task-board-local` 的 client inject 适配与元数据），使工作树干净、改动进入可达历史。
2. **归档历史**：用 `git bundle create --all` 把两个仓库的完整历史导出为 bundle，存至工作树之外的 `~/project/_archive/Magpie-Horch-20260911/nested-repo-bundles/`，并**实测可克隆恢复**后再继续。
3. **改形态**：移除两个嵌套 `.git`，将它们折叠为 monorepo 内的普通目录，与其余 18 个受管包形态一致；包身份沿用既有分配（`dsh-team-hub` 为 `self`，`dsh-task-board-local` 为 `internalized` + 上游 `@etony668`）。
4. **立规则**：新增门禁 `nested-repos`——受管目录下存在 `.git` 而未在 `.gitmodules` 声明即失败；`.gitmodules` 声明的子模块（如只读参照系的 `vendor/dsh-desktop`）不算违规。

## 备选方案

**注册为正式子模块。** 与壳层 fork 对 `deepseek-harness` 的做法一致，保留独立历史与远端。被否决的理由是内容风险：两者工作树当时都不干净，`git submodule add` 需要把目录移开或重新克隆，会直接丢掉那 22 个文件的改动；而且这两个包已被二开到与上游分叉的程度（来源注册在 `luteOrigin` / `luteOwner` 中），子模块的「跟随上游」语义与「本地二开层」现实不符。

**保持现状（嵌套仓库继续存在）。** 被否决——内容会持续失管，父仓库的门禁读不到这些文件，且 `git add` 静默失败使问题难以察觉。

**移出仓库、只留 pin 元数据（像 npm 外部层那样）。** 被否决——它们是平台运行时的一部分（`dsh-team-hub` 是成员协作网关，有 72 项测试；`dsh-task-board-local` 是会话任务看板），移出会让门禁与本地开发都失去覆盖。

## 后果

- 正面：父仓库首次完整拥有这两个包的内容——`git status` 能看见、门禁能校验、提交能覆盖；`tracked+ignored` 与 `nested repo` 两类静默失管状态都由门禁守住，不会再复发。
- 负面/代价：两个包失去独立历史与远端（折叠后不再能 `git push` 到各自上游），历史仅保留在 bundle 归档与提交信息中；未来若要向上游回馈改动，需从 bundle 恢复再操作。这一代价是刻意的：本地二开层已与上游分叉，双轨维护的成本高于收益。
- 后续动作：ADR-0010 的三分治理中，两者的来源已登记；若不希望长期持有分叉，可在二期评估「上游已修复则退役」路径（`dsh-task-board-local` 的 client inject 修复属上游可回馈项）。
