# ADR-0011 · 能力五组归位 + 生成式目录墙（不引入 pnpm workspace）

- 状态：accepted
- 日期：2026-09-11
- 决策者：用户（lute）+ agent（grill-me 决策树 N2）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-11-lute-refactor-three-phase.md)

## 背景

20 个插件当前平铺在仓库根目录，无分组、无组地图。上游 DeepSeek Harness 的对应机制是 `packages/<group>/<pkg>/`（64 个能力组）+ 每组一个 README 作为权威包地图 + 由源码生成的 `docs/{tool,config,persistence}-catalog.md`。但上游是 140 包规模，且为此引入了 pnpm workspace、双 tsconfig 聚合（`tsconfig.host.json` / `tsconfig.client.json`）、Project Reference 约束门禁等一整套机制。

## 决策

**目录按能力归为 5 组，但不引入 workspace 与子包 typecheck 分裂；用生成式目录墙替代人工索引：**

| 组 | 归属 | 代表插件 |
| --- | --- | --- |
| `capabilities/` | 对外业务能力 | overseas-skills、overseas-tools、wanzh-hulian、deepresearch、browser、memory |
| `surfaces/` | 用户可见界面 | agent-team-gui、skill-center、task-board、my-quotes |
| `platform/` | 平台基础与呈现 | theme、root-brand、ui-polish、file-upload、rename-conversations、auto-compact |
| `contract/` | 契约与校验 | skill-subset、preset-lint |
| `infra/` | 工程与交付 | team-hub、patches、scripts、packaging |

每组一份 README 声明其拥有的能力与包清单（组地图）。新增 `scripts/gen-catalog.mjs` 从各组 `package.json` 生成 `docs/catalog/`（能力清单、工具清单、slot 占用、skill 计数、profile 清单），门禁校验「生成物与再生成结果一致」，手改即拒绝。

## 备选方案

- **A 保持现状**：被否决——会继续长成 30 个同级目录，且没有「能力归谁拥有」的答案。
- **B 归组 + 引入 pnpm workspace 与双 tsconfig 聚合**：被否决——上游为 140 包规模设计的机制，对 20 个业务插件带来同等的拓扑复杂度（依赖方向约束、Project Reference 维护、双 face 编译）而不带来对应收益。
- **D 归组 + 保留人工索引**：被否决——人工索引正是 `docs/README.md` 今天与真相脱节的原因。

## 后果

- 正面：目录漂移被消除；「某能力归谁拥有」有 3 分钟内的答案；文档索引由生成器保证与代码一致。
- 负面/代价：迁移会改变 `file:` 依赖路径与硬链接 inode（需重装重链，见架构红线「编辑工具会打破 file: 硬链接」）；生成器成为新的事实源，需同步纳入门禁维护。
- 后续动作：二期执行归组与生成器落地；迁移脚本必须走 tmp+mv 原子替换，不得用 `cat >` 直接覆盖硬链接。
