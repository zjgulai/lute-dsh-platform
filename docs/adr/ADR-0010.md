# ADR-0010 · 包平面三分治理：自研层 / npm 外部层 / 处置候选层

- 状态：accepted
- 日期：2026-09-11
- 决策者：用户（lute）+ agent（grill-me 决策树 N1）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-11-lute-refactor-three-phase.md)

## 背景

仓库内 20 个 `dsh-*` 目录的**治理性质并不相同**，但当前被同等对待：部分是本仓库从零写的自研代码；部分是从上游 npm 包内部化而来（`dsh-deepresearch-local` 源自 `@deepseek-ai/dsh-deepresearch`、`dsh-browser-local` 源自 `@yuxianglin/dsh-bridge-browser`、`dsh-memory-local` 源自 `@furongjun1999/dsh-memory`、`dsh-task-board-local` 源自 `@etony668/dsh-task-board`、`dsh-auto-compact-local` 已改名为 `@deepseek-ai/dsh-auto-compact`）。另一方面，本机 live profile（`~/.dsh/profiles/desktop`）另有 12 个**直接来自 npm、仓库内无源码**的插件（`dsh-pocket`、`dsh-better-sidebar`、`@xmanrui/dsh-im`、`@liustack/modlens`、`@liustack/modsearch`、`@zseven-w/dsh-noema`、`dsh-vision-router`、`dsh-context`、`dshmarket`、`@changfenhuang/dsh-genui`、`@tt-a1i/archify-dsh`、`@dhicoc/dsh-reverse-skill` 等），它们与仓库内代码混在同一个 bundles 列表里，边界不清。

## 决策

**按治理性质把包平面分为三层，只有第一层纳入仓库门禁：**

1. **自研层（self）**：本仓库拥有源码与演进权，纳入版本管理、纳入门禁、按 ADR-0011 能力归组、按 ADR-0012 补身份元数据。约 19 个包。
2. **npm 外部层（npm-pinned）**：仓库内无源码，只在 `docs/catalog/profile-manifest.md` 登记名称、版本、来源与 pin 依据，不进仓库、不纳入门禁。约 12 个包 + 2 个基座 bundle。
3. **处置候选层（to-dispose）**：`_attic/`、`.gitignore` 白名单幽灵路径、32.9MB 之类的大体量游离资产，按 ADR-0013 分级处置。

内部化而来的包（含上游来源的）归入自研层，但必须在身份元数据中标注 `internalized` 与原上游包名，以保留「上游已修复则可退役」的判断依据。

## 备选方案

- **A 全部内部化**：把 npm 外部层也 vendor 进仓库。被否决——仓库体积成倍增长，且失去上游更新能力（与 ADR-0006 的月度跟进策略冲突）。
- **B 全部外部化**：自研插件也发布 npm 再安装。被否决——与客户离线 pkg 交付链（ADR-0002、ADR-0004）冲突，且引入发布与版本仲裁成本。
- **D 不区分、同等对待**：被否决——正是「门禁不知该对什么负责」的根因。

## 后果

- 正面：仓库里「能改的东西」与「装上来的东西」边界首次清晰；门禁只对能改的东西负责，避免对无源码依赖误报。
- 负面/代价：需要维护 `profile-manifest` 与 live profile 的一致性（外部层版本漂移不会自动被门禁发现，需按 ADR-0006 观察窗人工复查）。
- 后续动作：一期在自研层包上写入身份三元组（`luteOrigin` / `luteOwner` / `lutePublish`）；二期产出 `profile-manifest` 生成物。
