# ADR-0018 · 构建产物 `lib/types/` 的入库边界与 build 可执行性

- 状态：accepted（2026-09-11）
- 决策记录：[Note](../notes/implemented/architecture/2026-09-11-lute-refactor-three-phase.md)

## 背景

`lib/types/` 是包对外**声明的类型接口**（`exports` 与 `files` 都指向它），而它同时是构建产物。二者的边界此前从未定过，于是同一件事在仓库里出现了三种做法：

| 包 | 是否入库 `lib/types/` | 有无源码 | `lutePublish` |
| --- | --- | --- | --- |
| `dsh-browser-local` | 入库（48 文件） | 有 `src/` | false |
| `dsh-deepresearch-local` | 入库（80 文件） | 有 `src/` | false |
| `dsh-loopx-plugin` | 入库（15 文件） | **无源码**（纯预构建产物） | **true** |
| `dsh-agent-team-gui-local` | 不入库 | 有 `src/` | false |
| `dsh-skill-center-local` | 不入库 | 有 `src/` | false |

三种做法都各自成立，所以问题不是「谁做错了」，而是**没有任何规则**，且入库的那两个包已经在漂移。

实测到的漂移（`tsc -b --force` 后 `git status` 可见，三次复现一致）：

- `dsh-deepresearch-local/lib/types/index.d.ts`：入库版本缺 `Service` 导入，且多一个 `[x: number]: () => Promise<void>` 索引签名——已与 `src/index.ts` 不一致。
- `dsh-deepresearch-local/lib/types/client/index.js`：入库版本不含 `src` 里新增的注释。

门禁今天看不到这件事：`index-drift` 管 `docs/` 生成物，`catalog-fresh` 管 `docs/catalog/packages.md`，没有任何校验项覆盖 `lib/types/`。因此「改了 `src` 却忘了重建产物」会一路静默到消费方拿到过期类型。

## 决策

**一、入库边界按「有无源码」划分，不按包身份划分。**

- **有 `src/` 的包**：`lib/types/` 入库。理由不是「应该入库」，而是交付链的现实约束——受管包以 `file:` 依赖被 profile 安装，pnpm 按 `files` 打包，构建不会在安装时自动跑。产物不入库，`file:` 安装就会缺类型。
- **无源码的纯预构建包（`dsh-loopx-plugin`）**：`lib/types/` 是**作者手写内容**，不是产物，必须入库。它的 `lib/` 是唯一真源。
- 因此 `dsh-agent-team-gui-local` / `dsh-skill-center-local` 不入库也**不算违规**——它们由打包流水线统一产出。本 ADR 只要求「有 `src/` 且入库」的包保持产物新鲜。

**二、`build` 必须被门禁真实执行。**

`scripts-runnable`（ADR-0014）原先只验证 `typecheck` 与 `test`，`build` 从未被跑过——脚本存在但能不能跑通无人校验。本 ADR 把 `build` 纳入该校验项。动机：「产物是否新鲜」这个问题必须先有「产物能被生成」才谈得上，而后者此前没有任何校验覆盖。

**三、产物新鲜度校验（`types-fresh`）：本轮实现后主动撤回，原因是它无法非空转地成立。**

原计划新增 `types-fresh`：重新构建并把输出与入库内容比对。实现并实测后发现它做不到诚实判定，已完整撤回（连同其纯函数与测试，未留在仓库里）：

- `dsh-browser-local` 的 `build`（`tsc -b && tsdown`）**退出码 0，且不改动 `lib/types/index.d.ts`**（md5 与 mtime 前后一致）。即它的 build 并不是该产物的权威生成者，因此「构建后比对」在该包上恒为空转。
- `dsh-deepresearch-local` 的 build 因自身 5 个类型错误退出码 1，无法生成产物，新鲜度无从判定。

一个恒真的校验项比没有校验项更糟：它给的是假信心。因此宁可撤回，也不留下一个永远显示「ok」的校验项。撤回理由与复现方式记在本文件，避免后人重走一遍。

**四、本轮**不**为 `lib/types/` 新增入库清单，也不改 `.gitignore`。** 边界由「有无 `src/` + 是否入库」推导，不额外维护列表。

## 备选方案

**全部移出跟踪（一律不入库）。** 最干净，但会打断 `file:` 交付链：profile 安装时按 `files` 打包，不入库又不在安装时构建，装出来的包就没有 `lib/types/`，消费方类型解析失败。要修就得给每个包加 `prepare` 脚本并在安装时跑构建——那是把交付链的复杂度换成「安装时构建」这一新的失败面，收益不抵。

**全部入库，包含无源码的包。** 与现状一致，但等于承认「产物可以漂移」，正是本次要解决的问题。

**改为把 `lib/types/` 指向 `.dsh-types` 统一供给（ADR-0017 的延伸）。** 方向正确但解决的是另一个问题：ADR-0017 管「类型从哪来」，本 ADR 管「入库的产物是否与源码一致」。两者叠加才完整。

**用「构建后 git diff 为空」代替独立校验项。** 需要门禁改工作树（构建会写 `lib/`），而门禁的契约是只读报告。**此方案已实现并实测，随后撤回**——见「决策」第三节：`dsh-browser-local` 的 build 不改动其 `lib/types`，比对恒为空转；`dsh-deepresearch-local` 的 build 又跑不通。撤回而非保留，理由是恒真的校验项提供假信心。

**为每个包声明 `typegen` 脚本再校验新鲜度。** 这是让 `types-fresh` 真正成立的唯一路径——需要一个「权威生成该包类型产物」的命令，而不是复用可能并不产出这些文件的 `build`。本轮不引入：它要先逐个确认每个包的产物由什么生成，属独立工作量，故连同 `types-fresh` 一起推迟。

## 后果

**正面。** 「有源码的包，产物入库」从三种习惯变成一条规则，边界由 `src/` 与 `files` 推导而非人工维护；`build` 首次纳入门禁校验，结束了「脚本存在但从未被跑过」的状态。

**负面。** 入库产物的**新鲜度**仍无机器校验——本 ADR 只解决了「怎么放」，没解决「是否过期」。这是明确的未竟项，不是遗漏：已记入 `dsh-deepresearch-local` 豁免条目的 todo，并在决策第三节写清复现方式，避免后人重复尝试同一方案。

**后续动作。**

1. **推迟项**：为每个「有 `src/` 且入库 `lib/types/`」的包确认权威生成命令（不是复用 `build`），确认后再引入按包声明的 `typegen` 与 `types-fresh`。
2. 修复 `dsh-deepresearch-local` 的既有漂移与 5 个类型错误；其 `build` 恢复可跑通后，`scripts-runnable` 会立即对它生效。
3. `dsh-loopx-plugin` 不参与任何产物校验——它无源码，`lib/types/` 是作者手写内容。该理由写在校验逻辑里，不靠约定。
